## 可执行的产品契约

1. 显式请求的身份、覆盖、单位、列与排序优先；其次才是公开且适用的已注册指标/产品默认。SQL写法和参考展示习惯没有高于请求的地位。用户明确改单位时同步转换计算、精度、别名，不在评分器里乘100补救。
2. 每指标先定义事实集合和完整身份，再定义分组与显示。订单身份是`order_id`；明细是`(order_id,order_item_id)`；评价是`(review_id,order_id)`；档案`customer_id`与自然人`customer_unique_id`不能互换。自然人键用于归并身份，不授权反向扫描同一人全部档案借用州、默认地址等属性。
3. 默认TopN为最多N行，候选不足不补行；排名按最终展示精度，先主指标，再完整身份元组升序且NULL最后。身份只在主指标相等时裁决，不能压过主指标。明确含并列/前N档时另按RANK/DENSE_RANK契约，不能偷偷用LIMIT截断。明确主指标却未明确并列时遵循公开默认；多指标且不能唯一判断按谁排时必须澄清，不能从Gold倒推默认。
4. 普通完整列表保留未知指标，若存在获授权的展示排序则NULL最后；寻数值最值的实体只在数值已知候选中选择。未知值过滤只能用于当前寻优指标，不能导致同请求其他计数的总体被缩小。金额/均值无事实与0不同，缺数据不自动补0。
5. 时间窗口先固定事件来源、锚点和半开区间，再分周/月；最近N自然日含D，范围为`[D-(N-1),D+1)`。周为周一起始，首尾不足整周不删周也不把窗外金额带进来。连续历与仅事实周期是两个请求契约，不能靠当前结果8行或14行选择答案。
6. 默认地址不是“下单时真实使用的收货地址”。现有表没有订单地址快照，也不保证每档案唯一默认地址。关系分析可允许订单跨不同默认州组重复；唯一订单地理归属则必须有另行定义的数据质量规则。禁止任意取地址ID最大的一条冒充当前唯一地址。

## 评分必须补齐的边界

评分应读取付费前冻结的逐题`orderPolicy`，不从候选SQL、Gold字符串里的ORDER/LIMIT组合猜契约。元数据是测评侧契约，不能注入生产请求作为逐题答案提示。它需要区分：无序完整多重集、按时间升序、显式完整列表排序、严格TopN、明确含并列。每题列数、单位、NULL、值精度、重复行多重性与原有数值容差仍严格，不能做横纵表互转、显示列增删、百分数自动换算或集合去重。

无序比较只允许行排列变化；有序无LIMIT也必须拒绝倒序。完整列表主排序键相同的行可在该并列块内换序；严格TopN默认完整身份决定名单，不能以“同分都合理”替换边界成员。隐藏排序键例如T4-012的评价条数无需额外输出，但评分可依据冻结参考所对应的身份和顺序；不能按输出均分代替排序条数。

`verification.json`列出了每个split现有启发式的漏检/误约束ID。正式包含T5-001的显式销售额降序，以及各时间列表；开发包含T2-005、T2-010的显式数量排序和时间列表。只改5个LIMIT后宣称评分契约已完备，会保留错误放行。若本轮不实现元数据评分，必须明确这项未决并阻止以“排序契约一致”通过A出口；不能将旧比较器的松漏当作新正式验收规则。

按主实施者新增要求，`scoring-policy-proposal.json`已逐题提供200条、按`dev/formal:id`标识的三个模式：`UNORDERED_MULTISET`保留完整多重集，`ORDERED_ALL_ROWS`检验完整集和请求排序，`LEGACY_TOP_N`保留已有严格TopN比较及其边界。列索引从0开始；有序完整列表只按公开请求键排序，同键块内部可排列，不发明次级键。25题旧默认漏排序、5题旧默认多加排序的差异都显式列出。新外部控制器必须对p9和候选使用同一份冻结评分，而不能信任旧JAR忽略未知元数据后的默认grade。本审计不负责生产或控制器实现；接入及免费反例验证完成之前，V4仍为`NOT_EVALUATION_ADMITTED`。A审查只能核对本地契约，不能宣称D流程已运行。

## 技术与设计导读

以T5-018为例：输入先明确“仅有默认地址的订单”这个覆盖，再沿`orders.customer_id → customers.customer_id → shipping_addresses.customer_id`找到关联档案和默认地址，按`(地址州,登记州)`分组，用`COUNT(DISTINCT order_id)`计订单，最后按订单数与两个州键稳定取20组。一个订单O对应RJ/MG两个默认州时会在两组各出现一次；组内DISTINCT消除同州重复，却绝不消除跨州关系。输出只是关系组合与订单数，不能拿它算全订单唯一地理占比。审计JSON用`suite+id`、源题面/SQL SHA和`issueIds`追踪来源，参考答案和反例不会与候选输出混合。

技术抓手是显式请求契约、事实身份、分组多重性、逐题排序元数据和反例；没有新增检索打分、衰减或Top-K。排名的数学次序是“主指标优先，完全相等时才比较身份元组”，不是给ID加一笔权重；因此较差主指标不会因ID较小挤掉较好对象。展示精度决定默认并列，用户明确原始精度时覆盖；含并列排名只把业务指标放进排名窗口，身份用于最终展示。空锚点、未知分母、无默认地址和多默认州各有明确兜底，不借现库无异常偷省定义。

这批建议消除5题隐形Top100/行序约束、4题NULL展示偏差、4题候选或时间/地址范围欠明，以及开发1题显式值域偏差；不保证模型准确率上涨。替代方案“全局忽略排序”会放过明确倒序，“全部补完整日历/全部LEFT JOIN”会违背已明确的有限范围，“任取最新地址”会凭空创造业务身份。面试追问“为什么DISTINCT还会跨组重复？”——它只在每个分组内部按订单键去重，关系本来就可能一对多；“修参考为什么不是刷分？”——V3历史不动、V4逐条Errata先登记、统一新参考同期对照、保留89%与难度分层，并用反例增加错误放行检查，而非看到候选答案后改Gold。

用户无需启动外部服务来完成本审计。后续必须核对三条：数据沿哪个事实关联键流转、调用账目中0与未知的区别、失误究竟是请求/参考/评分还是模型生成层。真正冻结V4前还需独立检查实际新文件与评分实现，并对新参考执行只读SQL校验；原Gold200可执行不能代替新参考校验。
