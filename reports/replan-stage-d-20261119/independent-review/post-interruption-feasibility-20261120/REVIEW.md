# 中断后可行性独立复核：预算算式成立，真实接入尚未成立

复核范围是源码、既有独立中断审计的元数据、父任务的预算草稿和本机合成实验。本次没有运行供应商调用、读取真实 Key、重放中断批次、调用生产 monitor 的 observe/validate/verify/audited_rounds，也没有读取旧 68 题答案或 SQL、unseen/holdout。新增文件仅在本独立目录。冻结 C1 和历史证据不改。

**裁决：预算 v2 的 60/60 算式与独立计算一致；本机最终 8 场景、9 个断言支持“同一次已发请求可以继续读取迟到 usage”的概念；另一个真实 Java 合成场景 16/16 支持保留原约 15 秒超时及候选 UNKNOWN。三者都不构成工程接入通过，更不授权再次付费评测。** 传输阶段隔离、持久化监控、整轮时间、高峰边界和资源上限尚未通过工程集成验收。¥10 方案不能被描述成够用保证。阶段 D 没有完成。

## 1. 请求怎么流转，以及为什么中断

以一条“最近一个月各城市订单金额”为例，`LlmSqlGenerator.invoke` 先持久化候选 `CostQuota` 的 PENDING，再调用 `RequestBudget.startModelCall`，然后进入 `model.call`。Python 公共发送门按题号、尝试次数、提示词指纹生成唯一 permit，并在传输前持久化。一个请求最多两次模型调用，后一次只能是带反馈的修正。不存在名为 `BudgetedModelCall` 的类；用这个名字解释当前实现会误导读者。

若完整响应及可信 usage 在截止前到达，候选 lease 结算已知成本，公共层也按同一 permit 记账。若 15 秒到而 usage 没拿到，业务返回超时，候选 UNKNOWN 保留每次 ¥0.10 占款；当前代理也用这个绝对截止关闭读取。本次中断审计已经确认的新 4 次 UNKNOWN 均是 0 字节上游正文、非完整响应，不能据此断定实际消耗为零，也不能猜一个平均成本结算。

本次执行真实 HTTP 答案是 76/100：71 SUCCESS、4 REQUEST_TIMEOUT、1 RESOURCE_LIMITED，24 题未问。新 76 次应用调用和公共 permit 对应 72 次已知、4 次未知；已知成本 ¥0.13064558，已知 token 234,218。累计已知 139 次、¥0.29376746。候选保留 7 个 UNKNOWN，承诺金额 ¥0.99376746，仅余 ¥0.00623254，无法再预留 ¥0.10；公共保留 6 个 UNKNOWN，承诺金额 ¥0.89376746。两个层次的占款不得相加当作供应商账单。未知 token 和金额仍是 null。

## 2. 技术抓手和身份凭据

候选层用 `holdId → {requestId, callNumber, promptSha256, status}` 记录 PENDING/UNKNOWN 的来源；monitor 的 `bindings` 把候选 hold 接到公共 permit token，`permitFences` 保留原始题号和 request fence。公共层每个 permit 只有一次最终 completion，原始响应另存字节文件并绑定 SHA-256 和长度。迟到回调必须回到原 permit，不能归到下一题，不能先在 15 秒写一个空 completion 再于 120 秒覆盖。

`CostQuota.Lease.close()` 将未结算调用标成 UNKNOWN，并令 lease settled；没有 UNKNOWN 自动释放路径。monitor `_transition` 要求历史已观察 UNKNOWN 的每个身份和内容原样存在。它不会因公共层迟到拿到完整 usage 而自动删除候选占款。源码允许公共 KNOWN 与候选 UNKNOWN 并存，但这只是静态兼容性判断，没有跑真实 monitor 交易和下一题并发集成。若已有 UNKNOWN 被移除、身份改写、事件重写或快照不一致，现有机制停机。

`SendGate.after` 的真实结算门槛比 POC 严格：完整原始响应，五个 usage 字段必须是非负整数，`prompt+completion=total`，`hit+miss=prompt`，prompt/total 正数；再查输入估计、8192 输出上限、¥0.10 预留和服务端工具等边界。POC 的历史 check-2 只检查 usage 是字典；最终 check-3 已补五整数/等式和矛盾 usage 拒绝场景，但没有执行真实 `SendGate.after` 估计/费用/持久化结算，不是生产 KNOWN 结算测试。

F JAR 包含 CostQuota，B JAR 没有，所以候选预算只约束未来 F 调用，公共预算约束 B+F。独立校验六份 Java 文件与冻结提交 `e114648a963bf109a38ad232628f1df70915a6d4` 的 Git 原始字节一致；两个冻结 JAR 的 SHA 也一致。当前源码、JAR 和父草稿的绑定见 `source-and-draft-review.json`。

## 3. 数字和数学边界

预算敏感性独立计算共 180 个场景：6 种层/调用量、¥5/¥10 两种额度、已知每调用成本 ¥0.002/0.005/0.010、未知数 0/10/20/40/全未知。它们是假设场景，不能当作预测或真实调用报价。父草稿 v2 的 60 个场景逐个匹配；v1 把未来 B 的预算也算到 F，是保守高估，保留历史不能改称精确结果。

设现有承诺为 C0、未来 N 次调用，其中 u 次未知，未知每次预留 q=0.10，已知每次成本 c，且 0≤c<q。最终承诺 `F=C0+(N-u)c+uq`。只要有一次已知调用，最坏排列的准入峰值 `W=F+q-c`，因为必须先预留 q，收到 usage 后才缩为 c；全未知时 W=F。最优排列在 u=0 时也是 W，u>0 时可将未知放最后，峰值为 F。不能只拿最终金额与额度比较。

例如公共层未来 1804 次、全部已知、每次 ¥0.005：最终 ¥9.91376746，但最后一次预留峰值 ¥10.00876746，¥10 会在完成前停下；该假设下最多准入 1802 次。即使每题只调用一次，902 次、每次 ¥0.010 的峰值也为 ¥10.00376746，最多 901 次。候选层看似通过的 UNKNOWN 数不能独立证明公共层也通过；F 的 UNKNOWN 必须是公共层全部 UNKNOWN 的子集。

假设重新完整走 DEV100+target2+formal600+unseen200，未来 902 题、最多 1804 调用；F 502 题/1004 调用，B 400 题/800 调用。加上历史 144 题/146 应用调用，累计 1046 题/1950 调用，超过当前 970 题上限 76 题、1940 调用上限 10 次，也超过最初全局 1002 题上限 44 题。当前公共 ledger 的 76 次若继续计数，未来 cap 需 1880；历史旧 70 次应用调用仍不能被清零。该路线目前只是计算假设，旧路线已封存。

全未知配置包络为公共 ¥181.29376746、候选 ¥101.39376746，整数 ¥182 只是该假设的配置包络，不是推荐额度、付费申请或供应商硬账单上限。调高额度必须新登记并生成派生迁移，保留 budgetId、pricingIdentity、预留、已知 139/¥0.29376746 和全部旧 hold；Java 加载还要求配置额度与账本额度相等。不能修改原始账本，不能借改额度清除 UNKNOWN。本次没有实现迁移。

## 4. 本机实验证明什么、没证明什么

父任务最终 `loopback-check-3` 为 8 场景/9 断言，4212.920 ms；这是父任务已执行结果，本独立复核只读校验其当前脚本 SHA、原始结果 SHA、场景和元数据，没有另跑网络实验。脚本仅接受 literal `http://127.0.0.1`、固定 synthetic key、最多 1 秒缩尺 grace；供应商调用和真实 Key 读取均为 0。历史 check-1/check-2 均保留：check-1 有预期断连异常，check-2 记录该断连，check-3 再补 usage 分类。本独立核验曾捕获 check-2 的源 SHA 不再匹配当前脚本，随后改绑定新 check-3，绝未覆盖旧结果或把旧结果归到新源码。

在 250 ms 答案窗和 550 ms 合成响应下，旧代理收不到 usage，延长读取的新合成代理能在同一次 POST 收到 228 字节完整回复。客户已断线仍可收集；等着不走的客户会被抑制迟到 SQL；及时回复仍交付；超收集窗保持未知；缺 usage 保持未知；过期 permit 是 0 POST；各场景至多一次 POST 和一次 after 回调。

这些数只证明机制，不证明真实供应商能在 120 秒内给出完整 usage，也不保证 completeAccounting 会变成零未知。正式门槛要求所有六个正式轮次 `unknownUsageCalls==0`，只扩预算不会消除这个独立阻断。

另只读核对真实冻结 C1 JAR 的合成探针 `real-java-probe/check-4`：1 个场景、16/16 生产者断言；HTTP 504，外部 15104.216 ms，Java 内部 15001 ms，MODEL 14902 ms；1 个本机 POST、1 次 after。原 PENDING 的 requestId/callNumber/prompt SHA 和 holdId 最终原样保持 UNKNOWN，knownCalls/cost 均为 0；迟到合成 usage 为输入 10、输出 5、总 15，原 HTTP 不含 SQL。独立复核核对 HTTP/原体 SHA、permit token、快照身份及 launcher/依赖归档字节与当前源一致，没有重跑 Java 或网络。该探针的供应商/真实凭据为 0，但只采用 +1 秒 grace，不是实际 +105 秒测试；768 个真实批次原件未变是生产者断言，本次不再次读取真实批次。该单场景补上真实 Java 15 秒与 hold 保留证据，不能取代后续 monitor/TLS/资源/高峰/发送阻塞验收。

真实接入有六项阻断：

1. **发送阶段隔离。** POC 将 inherited socket 的统一 deadline 改为 accounting deadline。`_check_send_open` 只在发送前检查原截止，connect/TLS/sendall 内部阻塞仍可能用延长 timeout。生产必须把 connect/write 与 read 截止真正拆开，只允许原 15 秒内已经发出的同一连接继续读，不能延长握手或写入，不能重连重发。
2. **业务响应时间。** waiting-client 的 504 在 553.744 ms 才返回，超过 250 ms 答案窗。它证明 SQL 被抑制，没有证明 HTTP 按时返回。必须另行实测冻结 Java 原始 15 秒响应、状态、modelCalls、错误、时延和 SQL 执行路径；迟到 SQL 永不进入评分和执行，答案证据不可变。本项只说明该缩尺 POC 的证据边界，不否定另行归档的真实 Java 探针。
3. **真实监控和归属。** 必须验证迟到 AFTER 与下一题、下一次 BEFORE 并发时仍落原 permit fence、A/B 快照和不可变原始事件；未知候选占款保留，重复 callback/写失败停机。POC 的普通列表回调没有验证这些。
4. **可信 usage。** 必须经过上文真实五字段校验、完整响应/重复键拒绝、价格和估计边界；缺失、矛盾、截断、重复键、超窗不能用平均值或零补齐。
5. **整轮时间和高峰。** 当前 1620 秒只在每题开始前检查，末尾 drain(120) 在该检查外，1620+120 的名义外沿至少达到 1740 秒，尚未计收尾。必须冻结并实际检查包括收集、持久化、shutdown 的整轮绝对上限，并证明最迟收集截止不跨用户禁止的高峰边界。现有 SEND_GUARD=120 和剩余请求时间的算术需要重新核验，不能靠口头保证。
6. **资源与生命周期。** collector 必须有并发数、原始响应字节、连接、线程和回调上限，最终 drain 有界、所有已接收线程可收束、异常/崩溃保留 UNKNOWN。后续题可以继续运行不等于允许无限挂起读取。新观察协议需要新登记冻结和完整免费集成验证，之后任何付费仍另需授权。

## 5. 设计权衡与面试答辩

直接把 15 秒调为 120 秒会改变业务 SLA 和模型/纠错可用时间，污染候选效果比较；本方案必须保持业务时间不变，只改变采集完整账务证据的观察窗口。用平均已知成本填补 UNKNOWN 会制造精确幻觉并违规释放占款；继续保留候选 UNKNOWN 的代价是资金仍会被占满，即使公共 completeAccounting 改善也不能保证 F 续跑。

追问一：“公共层已知、应用层还未知，是否记了两次费用？”回答要点：两层是独立准入视角，不相加当账单；permit token 与 hold 绑定用于追踪同一次调用。业务返回的 UNKNOWN 是当时的观测事实，公共层之后拿到完整原始 usage 可记录事实，但候选历史 UNKNOWN 的释放需要另行审计迁移协议，当前机制不允许自动释放。

追问二：“延长读取为什么不算偷偷延长模型预算？”回答要点：只有连接/写入仍以原 15 秒截止、业务 HTTP 与 SQL 执行证据保持原时间和结果、没有重发或迟到 SQL 进入业务，才能这样解释。本 POC 恰好还没证明前两条，不能据此宣称 SLA 完全不变。收集窗口、整轮耗时、峰时保护和未知率必须作为独立数据公开。

用户当前无需启动外部服务或提供 Key。下一步只能先补齐免费工程验证，不能重放旧批次或启动新付费轮次。若日后提出新登记，必须让用户核对三件事：同一请求如何跨两个账本追踪、已知/未知 token 和成本分别是多少、错误停在发送/业务/usage/配额哪一层。不得发布这次未完成 DEV100 的准确率或 P95。
