# 请求总预算：实现、工程验证与设计导读

本专项对应改进方案阶段3，只处理请求总时间、模型调用次数、真实取消和账目。未修改评测题目、Gold、Prompt、澄清、检索权重及业务语义。工程测试通过不代表准确率或P95验收通过；真实对照按另行冻结的协议执行。

## 已验证的数字

- Java全量 **436/436**，失败/错误/跳过均0；其中新增预算测试 **14/14**。依赖未变化。
- 真实PostgreSQL：400ms请求预算下执行5秒`pg_sleep`，接口在1500ms断言上限内返回；服务端查询被取消，后续`SELECT 1`成功。预算专测日志中SQL约438ms结束。只断客户端连接曾不能立即停止服务器睡眠查询，现已先`Statement.cancel()`再`Connection.abort()`。
- 本地真实HTTP持续滴流：1200ms预算，接口在2200ms断言上限内返回，连接实际断开，HTTP请求数1，无SDK隐藏重试。
- 16个工作线程占满后，第17次请求拒绝，实际模型调用0；没有无界等待队列。
- 取消池2个线程、64个排队位置；70个阻塞清理任务中4个被拒绝并显式记录，调用方不等待清理。
- 本轮工程测试真实模型调用 **0**、供应商费用 **¥0**。准确率、真实模型Token、三轮P95尚待对照，不能由上述测试推算。

详细日志在本地`reports/request-budget-tests.log`与`reports/request-budget-full-tests.log`，不会把临时日志作为历史归档证据覆盖提交。

## 请求例子与数据流

以“2018年订单数”为例：Controller进入编排器，建立一个`requestId`和单调时钟截止点；会话改写、澄清、检索、模型、SQL校验、EXPLAIN、执行、结果检查及会话结束持久化共享该截止点。默认总预算15000ms，全链路最多2次模型调用，发起纠错时剩余时间至少2000ms；改写也消耗这2次中的一次。

模型网络调用之前先占用调用次数并记`IN_FLIGHT`，不是成功后才计数。若第1次返回10输入+5输出Token、第2次纠错超时，则响应仍记2次调用、15个已知Token、1次未知用量。已执行成功的首答可保留，`budget.termination=DEADLINE_EXCEEDED`明确说明提前停止；首答成功只表示执行成功，是否业务正确仍由请求之后的离线Gold比较决定。没有成功首答则返回`REQUEST_TIMEOUT`（HTTP504）。次数耗尽或工作池满返回`RESOURCE_LIMITED`（HTTP503）。

`timings.totalMs`包括等待失败纠错的时间，不能退回首答耗时；旧分阶段timings描述选中答案，完整请求阶段分解看`budget.stageMs`。同一阶段多次进入的时间累加，不是各次重试的独立计时；各次模型耗时仍由调用记录保存。

## 核心组件与身份追踪

- `RequestBudget`：`System.nanoTime`截止点、调用计数、取消钩子、首答checkpoint、分阶段计时及Snapshot。嵌套纠错入口复用当前对象，不重置时钟。ThreadLocal上下文显式绑定到工作线程，退出时移除，不能跨请求串账。
- `RequestBudgetRunner`：调用方按剩余纳秒等待Future。16个守护工作线程配`SynchronousQueue`，请求不能排队；不响应中断的后台任务继续占住原线程位，防止“前台超时，后台无限增长”。嵌套调用不再提交线程池。
- `BudgetHttpRequestFactory`：共享JDK HttpClient；单次读超时取配置与剩余预算的较小值，预算到期中断并关闭活动响应体，覆盖持续滴流。鉴权仍在每条请求，不保存在共享HttpClient。
- `BudgetJdbcGuard`：query timeout取数据库配置和剩余预算的较小值，向上取整到驱动秒粒度；总预算补足亚秒截止。取消时先cancel后abort。statement关闭与取消共用资源锁、`active`标记，防止钩子误杀已归还连接池并被下一请求借用的连接。
- `EvaluationTrace`：先记调用再完成替换，停止时新增`REQUEST_STOP`并封存选答和尝试记录；晚到后台结果不能改变评分证据。
- `LlmCallLog`：JSONL用`requestId + callNumber`关联晚到回复，`LATE_`标记与`usageKnown`区分。缺失usage或只有0Token时保守视为未知，不能冒充免费。日志开关关闭仍累计预算用量。

本机制不涉及检索排序或Top-K，不新增任何权重。`remaining >= 2000ms`只是重试准入条件，不是预计模型会在2秒内答完的预测；最大调用次数与截止时间必须同时满足。超时首答保留按成功状态选择，不使用Gold，也不根据离线评分挑答案。

## 边界与设计权衡

15秒是资源上限，与“三轮平均P95低于8秒”是两项条件。不能把超时改成8秒、删掉超时样本来制造P95达标。Java线程调度、GC和操作系统都可能带来截止附近偏差，本实现不是硬实时系统；按实际墙钟报告偏差。

只设每次HTTP/SQL超时，会让改写、首答、纠错的上限相加。只调用`Future.cancel(true)`只能发中断，无法证明socket和数据库已停止。因此组合总截止点、真实资源钩子与有界工作池。没有采用无限虚拟线程吞掉卡住驱动，因为超时后台任务仍会持有连接和外部资源。

取消池也有容量上限：无法保证恶劣驱动一定及时取消。饱和时`budget.cancellationRejected`明确报告未提交的清理任务；已接受任务也可能仍在排队，字段为0不等于已完成清理。拒绝时不改为调用方执行，避免接口又被卡住；HTTP/SQL自身超时仍作为后备。数据库cancel本身若卡住，后续abort也会被延迟，最终依赖驱动/网络超时；16个工作位限制本应用增长，不是数据库全局资源配额。

客户端取消不能证明供应商停止生成或计费。未知费用仅报告已知下界；晚到JSONL单列对账，不回写原响应、不偷偷改历史评分。进程退出前未收到usage、供应商始终不返回usage或日志写入失败时，最终账单仍可能无法从应用重建。SDK内部自动重试被设为1次，新旧历史结果不能直接据此做预算因果比较，off/on必须使用同一份新代码。

会话、缓存、日志持久化等外部I/O也在有界工作线程内，但没有对每种第三方驱动都提供强制取消钩子。迟到副作用不具备事务撤回保证；本项目仍为只读问数、单用户演示边界，不能宣称分布式事务或硬实时隔离。

## 面试答辩与验收路径

1. **“超时返回就等于取消了吗？”** 不等于。解释等待线程、执行线程、网络socket和服务器SQL是不同层；给出滴流HTTP、`pg_stat_activity`取消检查与工作池容量数字，承认驱动不响应时的后备上限。
2. **“纠错没结束，为什么返回成功？”** 返回的是已校验且执行成功的首答，停止原因独立暴露。费用含所有已发起调用，未知usage单列；离线评分发生在选答之后，Gold不参与生产决策。

验收顺序：`mvn test` → 固定同一提交全量Gold200/200 → 同一旧eval100题off/on交替三轮 → 核对题目/Gold/结果/首答Prompt指纹、逐调用账目与最终选答 → 汇总P95、准确率、费用、超时、未知/晚到用量。独立审核仍需未参与调参的外部来源；AI可做内部题意/SQL/结果复核，不能将自身复核升级为独立盲测。

用户核对重点：问题在哪一步耗时、每次已知和未知费用分别是多少、停止是MODEL/EXECUTION还是资源容量问题。本专项无需用户额外配置外部服务；当前本地数据库已可用。
