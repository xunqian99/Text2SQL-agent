## 技术与设计导读

**请求怎么走。** 用户问“每个仓库库存总量和平均库存是多少”：先过歧义检查，检索仓库/库存及相关列；既有上下文组装器生成DDL、主键、业务口径与系统规则；`PromptTemplate`约束未要求名称时输出`warehouse_id`，模型本轮实际按该字段分组输出`SUM(quantity)`和`AVG(quantity)`。SQL再过只读校验、数据库执行和严格结果比较。T4-027原Gold输出名称，所以即使模型遵守统一产品默认仍计错。若输入只写“销售额”，在调用模型前先澄清是否含运费；不靠模型猜。

**技术抓手与凭据。** 核心为`PromptTemplate`、已有`HybridSchemaProvider`、`MetricRegistry`、`EvalRunner`、`RequestBudget`与`DeepSeekOffPeakPolicy`。完整主键来自真实schema，不是按`*_id`猜测；枚举采用已有局部上下文来源记录。冻结用Git提交与文件SHA，真实调用用Prompt SHA和`requestId:callNumber`关联。p19没有新增运行时过滤来源标签或AST语义证明器：“过滤有依据”目前是提示约束，并非程序能证明每个WHERE合法；T3-008正是边界反例。

**数学与防线。** 本批未改directHits/expandedTables、检索权重、衰减或Top-K，不存在新的保送算法。每题系统消息增加144字符，不改变同题其他组件；历史p18对照还叠加此前输入修复，不能声称单变量。保留完整主键防止部分键去重；名称不保证唯一，名称关联必须保留事实。提示约束不能保证模型遵守，T2-030仍输出名称就是反证。无匹配名称、复合键、零事实、NULL和并列都不能靠“多加JOIN”统一解决；只读校验能防写操作，不能证明统计语义正确。

**收益与量化结论。** 工程回归1,047+102项通过，输入与运行身份核对完整，减少了未经说明的产品默认；但开发准确率由78%降为70%，P95仍约15秒。本批没有证明性能或准确率提升。97次调用的已知费用下界和10次未知用量必须一起说，不能只报两毛钱就宣布低成本。

**设计取舍与面试追问。** 没选“单表输出ID、多表输出名称”或按难度分流，因为它把题库写法偷渡进生产；也没选自动重写生成SQL的WHERE/SELECT，因为缺少请求契约证明时会删掉用户明确需要的信息。“为什么单测全过还降分？”——单测约束确定性机制，模型遵从、业务契约、网络耗时和冻结参考一致性是不同门槛，本次真实筛选负责暴露后三者。“为什么不关澄清、把超时放宽？”——这会改变产品安全取舍与比较口径；本次17项执行后不匹配已经说明单靠延长时间也解决不了全部问题。
