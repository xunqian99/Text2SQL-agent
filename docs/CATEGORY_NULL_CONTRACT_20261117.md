## 技术与设计导读

### 1. 请求与数据流

输入“每个商品类目的订单数量是多少？”：

1. 认证、速率、请求预算后进入原Schema检索与列裁剪。
2. 现有`MetricRegistry`从同一份`schema/metrics.yml`加载24条指标和新增1条`dimensionPolicies`，没有新增知识源或网络服务。
3. 问题命中“商品类目/类目/品类”等别名，且**裁剪后的实际上下文**同时存在`products`表与`product_category_name`列，才将`DIMENSION_POLICY product_category_nulls_v1`附加到口径文本。
4. 默认规则告诉模型在按该列分组时附加`products.product_category_name IS NOT NULL`；同时注入明确的用户覆盖规则。输入若为“请包含类目缺失的订单，保留NULL分组”，应不附加这一过滤。
5. 模型生成后仍经过原AST、EXPLAIN与只读执行。业务层不偷偷补WHERE，也不删结果中的NULL行。最终按冻结只读参考结果独立比较。

“一共有多少个商品？”没有命中类目规则，维度政策不注入，不能把类目未知的商品从总商品数里删掉。涉及类目但并非分组的问题可能收到规则文本，因此文本明确限定为“仅在该字段作为分组维度时生效”；这不是自然语言意图的硬分类器。

### 2. 组件、来源与边界

- `DimensionPolicy`：记录名称、表、列、别名、默认过滤与边界说明。业务规则与SQL执行分离，不负责修改模型输出。
- `MetricRegistry.appendDimensionPolicies`：检查问题别名与实际表/列，保留原指标文本，追加带唯一名称的规则；不会把已被裁掉的列重新塞进文本。
- `HybridSchemaProvider`：在表选择与列裁剪之后注入；全Schema回退路径也检查政策。`FullSchemaProvider`使用同一政策；关闭semantic时两条路径都不注入。
- `MetricRegistry.definitionSha256`：继续标识同一份启动资源快照。新增政策也进入既有缓存键和调用观测指纹，避免旧SQL缓存跨口径复用。需要重启加载新定义。
- `PromptTemplate`系统正文与版本不变。本轮改变的是业务定义输入，SHA-256可追踪；不是阶段3加速候选，不恢复延迟筛选。

规则不参与表评分、Top-K或桥接，不强制召回依赖表，也不提高products的排序。原`directHits`/`expandedTables`和扩展衰减设计不变，已由200题前后身份对比验证；不能为了注入政策把伴生表升级成核心命中。若列被裁掉，宁可不注入，避免引用上下文不存在的列；本轮也不声称解决所有漏表/漏列。

数据库反例用只读VALUES CTE，不修改业务库。Java独立oracle先按商品找到类目，再用每类目的订单ID集合去重，与使用生产默认过滤的SQL结果比较：

- 同一订单含同类目两个商品，类目订单数只能计1；样例books有2个不同订单，不能误计3件商品。
- 同一订单跨books/toys，可以分别进入两个类目；类目订单数之和不等于全站去重订单数。
- NULL类目在默认分组中消失，明确保留时样例NULL组为2笔订单；空字符串组和文字“未知”组分别保留，不能混成NULL。
- 全部类目为NULL、没有明细、没有商品均分别验证；默认排除不是把未知值改成0，也不是凭空补出没有订单的类目。

英文类目翻译缺失不等于原始类目为NULL；明确保留未知时，不能先用INNER JOIN翻译表把它们丢掉。政策文本写出这一边界，但不是完备SQL语义验证器。模型仍可能违反业务定义；AST安全检查也不会证明业务口径正确。需要真实结果对照，失败必须保留。

真实保留NULL场景生成了LEFT JOIN products，而只读参考使用INNER JOIN；当前库明细找不到商品的数量为0，两者本轮结果相同。这是数据覆盖边界，不能从一次等价结果推断孤儿数据下也正确。反例中的缺失商品按“仅匹配到商品的明细”计算；孤儿商品是否并入未知组需要另一个业务定义，尚未宣称支持。

### 4. 取舍与面试追问

没有在所有SQL后拼`IS NOT NULL`：会误删总量、改变LEFT JOIN语义，也无法尊重用户明确要求保留未知。没有在响应里删除NULL行：这是静默改结果，会掩盖原SQL的口径错误。没有把规则塞进全局系统消息：只在实际字段存在且问题涉及类目时加入业务上下文，便于范围审查和资源指纹追踪。

使用现有业务注册表中的独立维度条目，而非伪造“类目订单数”指标匹配整句题目；它可以服务类目订单数、类目商品额等多个统计任务，但没有扩成通用BI建模平台。缺点是软约束依赖模型遵守，不能承诺100%语义正确；本轮选择公开证据与后续对照，而不是自动修SQL来隐藏错误。

**问：为什么多一个NULL行也算错？** 因为项目已明确分组默认值，包含NULL会改变分组全集。规则公布之前题干确有隐含口径，不能把所有差异都怪模型；公开约定之后仍要验证模型是否遵守。

**问：如何证明不是对评测题硬编码？** 生产不读取题ID/Gold；规则按业务字段与别名注入，缺表/缺列不注入，用户可显式覆盖。新增跨类目、重复商品、空字符串和未知值反例，并检查200题的检索不变。但这仍是已知问题驱动的修复，不是独立盲测或泛化证明。
