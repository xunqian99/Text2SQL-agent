## 2. 根因与改动

### 2.1 同分种子在截断前缺少决胜规则

`LexicalSchemaRetriever` 会先找直接命中的表，再从最高分的 3 张表扩展关系。原来种子只按分数排序：同分时保留上游插入顺序，而词典内的 `Map.copyOf` 不保证遍历顺序。**Top-K 的最终排序稳定，不代表它前面的种子截断也稳定。** 一旦第 3、4 名同分，选谁扩展会改变后续分数与表名单。

现在种子按「分数降序 → 表名」排序后再截断；合并同一个别名的多表归属时按表名排列；最大匹配词按「长度降序 → 词文本」排序。这里固定的是原来未定义的平局选择，未调整评分公式和扩展预算。

### 2.2 不可变集合不等于有序集合

`SchemaCatalog.tablesByName()` 改用不可修改的 `LinkedHashMap` 保留数据库元数据顺序。`RetrievalResult` 对分数、证据和扩展表保序复制，证据里的列表也做防御性复制，避免后续修改原列表污染快照。

数据身份没有被混为一个集合：

- `directHits`：检索器内部记录自然语言/标识符直接命中。
- `expandedTables`：记录关系扩展或连通性修复补入的表。
- `evidence`：保留各表的命中或扩展原因。
- `tableNames`：保留实际排名与截断后的表名单。
- `coreTargets`：生产 Provider 从证据中排除扩展表，再补入实体取值与适用指标依赖；传给 Join 规划器。

本次保留这些身份判断，规划器不再把目标集合的遍历顺序当作业务优先级，而是恢复检索排名，未排名目标最后按名称排序。

### 2.3 等价 Join 路径也必须有确定的决胜顺序

`JoinGraph` 在去重后按「强度降序 → 无向列级规范键」输出边，保证邻接表顺序稳定。数据库外键查询也补齐目标表、目标列的排序键。

`JoinPathPlanner` 的多源 Dijkstra 优先队列改为「距离 → 检索排名 → 表名」。尝试目标及候选根时采用固定的检索优先顺序；同覆盖率、同总代价时保留最先出现的候选，这个先后现在有明确依据。

最终生成树生长仍优先比较边强度和新表相关度。完全相同时，先比较新表名，再选择更相关的已连接父表，最后才比较列级规范键。回归测试保住了原有的事实表根和外键主干偏好，没有用列名字母序覆盖相关度。

### 2.4 枚举提示需要排到具体物理取值

`ValueRetriever` 原来只排「别名长度 → 别名」，同一个别名出现在多表、多列时仍会继承词典 Map 顺序。现在补齐「表 → 列 → 物理值」决胜键。原有目标表过滤、物理条件和去重规则保持不变。

## 3. 权重、边界与不能承诺的事

本次没有修改现有权重：一跳扩展仍取 `源表实际分数 × 0.4 × 边强度`，同一目标多条路径取最大值，不累加邻居数量；直接命中的表不会被扩展分数覆盖。当前验收配置只有 1 跳，外键强度 1.0，约定关系强度 0.5。

最终 Top-8 排序仍是「分数降序 → 同分直接命中优先 → 表名」。**0.4 衰减只是降低扩展分数，并不保证所有直接命中都高于所有扩展项。** 比如高分种子 10 的外键邻居可以得到 4 分，仍可能超过得分 1 的弱直接命中；二级比较器只保护同分情况。本次没有把这种评分策略改成直接命中硬保送。

桥接仍最多补 2 张表，所以 Top-8 不是最终总表数的绝对上限；Provider 还可能补入指标依赖。Join 最短路代价仍为强边 1、弱边 2，属于加权偏好，不是“任意条数外键永远优于一条约定关系”的硬规则。沿用的图模型也会把存在外键的同一表对上的约定关联提升为强边，强度标记不能被当成每个列对都有数据库约束的证明。

Join 规划仍是 Steiner 树的启发式近似，不保证全局最优或全目标连通。原有全量回退、桥接预算、空计划回退与 SQL 校验继续生效；确定性不能证明选表正确、连接语义正确，或不会给出部分计划。本阶段没有扩展 Provider 的目标表白名单规则。

这次固定平局后，最终表名单、Join 路径和模型输入可能改变：相对修复前进程 1，本轮进程 1 有 **8/100** 道提示词发生变化。因此此前 92% / 91% / 93% 不能直接充当这份新代码的准确率结果，需要后续重新跑真实模型对照。

## 4. 提示词指纹如何落地

`PromptFingerprint.messagesSha256` 对有序消息计算 SHA-256，包含角色、原始文本、assistant 工具调用和工具响应。采用结构化 JSON 编码，避免简单拼接导致 `ab+c` 和 `a+bc` 无法区分；不删除空白、不重排消息。

首答、纠错、多轮消息和工具调用入口都在发送前计算指纹，完成调用后把 `promptHashVersion` 与 `promptSha256` 写入调用 JSONL。截断或 SQL 提取失败的调用也带指纹。`include-content=false` 时不保存正文，指纹仍保留；`observability.enabled=false` 则仍不写调用日志。供应商请求直接失败、未形成调用账目的分支，本阶段没有新增日志事件。

边界：

- 指纹覆盖本项目的文本与工具消息，不是整个 HTTP 请求；模型名、温度、输出预算、工具定义需结合配置另行比较。
- 本项目链路不发送图片或音频；指纹工具没有声称支持这些内容。
- 指纹只新增到 JSONL，没有变更数据库日志表和 REST 响应结构。
- 指纹相同只能帮助确认输入一致，不能承诺模型输出一致。

## 6. 技术与设计导读

### 6.1 一个具体请求怎么流

输入“每个大区的订单数量” → `LexicalSchemaRetriever` 保留命中证据并按固定顺序取扩展种子 → `HybridSchemaProvider` 组装表列、指标、取值和示例 → `JoinPathPlanner` 按权重与相关度确定连接提示 → `PromptTemplate` 组装系统/用户消息 → `PromptFingerprint` 得到 64 位十六进制指纹 → 正常服务继续调用模型，离线探针到此停止。

日志最终新增的是 `promptHashVersion=text-tool-messages-v1` 与 `promptSha256=<64位摘要>`。错误定位时先看分段摘要：表清单/分数变了，查检索；表清单没变而 DDL 变了，查列剪枝/Join；只有取值提示变了，查枚举；分段都一致而最终摘要变了，再查消息组装。

### 6.2 为什么不用更省事的替代方案

- 不把所有表统一按名称排序：那会抹掉检索相关度。名称只用于已经比较完业务优先级的平局。
- 不把 `Map.copyOf` 全部机械替换成 `LinkedHashMap`：保序只能保留已有顺序，无法消除上游无序；种子截断、图算法优先队列与枚举输出必须各自有决胜规则。
- 不记录完整提示词来证明一致：默认记录指纹与分段摘要已能比较差异，无需把所有问题和 SQL 正文落盘。
- 不通过修改 Gold 或手工固定某几题的答案消除变化：本次规则适用于任意同分种子、等代价路径和同名枚举。

### 6.3 面试追问

**问：你最终的 Top-K 已经稳定排序，为什么还会漂移？** 因为种子有独立的 Top-3 截断；它在最终 Top-K 之前决定扩展哪张表。必须在每个会影响成员选择的边界上定义完整决胜顺序，不能只修最后一层。

**问：400 次比较全一致，是否就能保证准确率稳定？** 不能。它只验证这份数据、Schema 和配置下的输入构造；模型服务仍可能有不确定性。还要结合提示词指纹与实际配置，多轮统计执行准确率、修复题、回退题和延迟。

### 6.4 用户需要核对什么

当前数据库可用，不需要额外配置。重点核对：请求流到哪里才调用模型；本轮为什么没有模型费用；看到准确率变化时，先确认输入指纹和配置是否一致，再归因到检索、字段、Join 或业务口径。

后续另开一个阶段修复“负增长率触发非负金额检查”，再开展真实模型的独立多轮对照。本阶段到此结束。
