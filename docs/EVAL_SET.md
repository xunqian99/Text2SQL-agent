# 评估集说明

这份文档回答三个问题：评估集是什么、为什么这么设计、你需要亲自确认什么。

## 1. 评估集是什么，为什么必须有

Text2SQL 系统「感觉上变好了」是没有意义的。评估集的作用是给系统装一把尺子：
固定 200 个问题，每个问题都有人工审核过的标准 SQL，每次改动系统后重跑一遍，
用**执行准确率**（生成的 SQL 跑出来的结果，和标准 SQL 跑出来的结果是否一致）衡量好坏。

为什么用执行准确率而不是比对 SQL 字符串：同一个问题有无数种正确写法。
「每个州有多少订单」可以写成 join，也可以写成子查询；列顺序、别名、大小写都可以不同。
字符串匹配会把这些正确答案全判成错，严重低估真实水平。业务真正关心的是
「跑出来的数字对不对」，所以比结果集。

## 2. 200 条怎么分层

| 层 | 文件 | 条数 | 考察什么 | 对应 ROADMAP 阶段 |
|---|---|---|---|---|
| T1 单表基础 | `T1_single_table_basic.yaml` | 40 | 过滤、排序、去重、NULL 判断 | 阶段 1 |
| T2 单表聚合 | `T2_single_table_agg.yaml` | 40 | COUNT/SUM/AVG、GROUP BY、HAVING | 阶段 1 |
| T3 时间窗口 | `T3_time_window.yaml` | 30 | 同比环比、近 N 天、自然周月季 | 阶段 2 |
| T4 多表 join | `T4_multi_join.yaml` | 45 | 2–3 表关联、内外连接 | 阶段 3 |
| T5 深层 join | `T5_multi_join_deep.yaml` | 20 | 4 表以上、自连接、桥接表 | 阶段 3 |
| T6 业务语义 | `T6_business_semantics.yaml` | 25 | GMV、复购率、留存、客单价等口径 | 阶段 4 |

分层本身就是面试材料：它能直接回答「你的准确率是怎么测的」。
T1 跑不动说明工程有问题，T6 跑不动说明语义层没做——**分层让失败可以归因**。

## 3. 一条评估记录长什么样

```yaml
- id: T6-003
  difficulty: business_semantics
  tags: [口径, 复购率]
  question: 复购率是多少？（下单 2 次及以上的用户占全部下单用户的比例）
  gold_sql: |
    WITH per_user AS (...) SELECT ...;
  notes: 【需确认】复购率分母假设为「有过有效订单的全部用户」...
```

字段含义：

| 字段 | 作用 |
|---|---|
| `id` | 唯一编号，失败归因时用来定位 |
| `question` | 用户实际会问的中文问题 |
| `gold_sql` | 人工审核过的标准 SQL，是「标准答案」 |
| `notes` | 口径假设说明。**标【需确认】的必须由你确认** |
| `tags` / `difficulty` | 用于分组统计，看哪一类能力弱 |

标准答案的结果集不写在 YAML 里，单独存在 `data/eval/gold_results.json`。
原因是有的题目结果集有几十行，塞进 YAML 会变成一堆转义符，人工审核口径时没法看。
而「标准 SQL 必须人工审核」是硬要求，可读性不能牺牲。

## 4. 执行准确率怎么算（含三个坑）

规则：把模型生成的 SQL 和 `gold_sql` 各跑一次，比较结果集。

规范化处理（`scripts/eval_lib.py`）：

1. **浮点精度**：都四舍五入到 4 位小数，避免 `1.0` 和 `1.0000001` 被判成不同
2. **NULL 表示**：psql 默认把 NULL 输出成空串，会和「空字符串」混淆，所以用 `@@NULL@@` 哨兵显式标记
3. **行顺序**：只有 `ORDER BY` 和 `LIMIT` 同时出现时顺序才算数；否则按多重集比较，排序不影响判定

还有一个容易忽略的点：数字不能格式化成科学计数法（`610` 不能变成 `6.1E+2`），
否则同一个数字两种写法会造成假失败。

## 5. 评估集质量自检

写完评估集必须先自检，否则后面测出来的准确率是假的。

```bash
python scripts/validate_eval_set.py      # 校验：可执行 + 无退化题
python scripts/refresh_gold_results.py   # 重新生成标准答案快照
python scripts/format_eval_yaml.py       # 重新排版（仅在格式被破坏时用）
```

校验会检查两类致命问题：

- **SQL 跑不通**：标准 SQL 自己都执行失败，这条题就是废的
- **退化题**：答案恒为 0/NULL 或返回空结果。这种题无论模型怎么答都测不出差异

设计过程中确实踩到过这两种问题，都已修掉，细节见第 7 节。

## 6. 评估集管理原则（来自 ROADMAP 5.5）

- 评估集**不能用来调 prompt**。调 prompt 用开发集，评估集只在阶段验收时跑
- 每次跑评估都要记录快照：代码版本、prompt 版本、模型版本、时间戳
- 标准 SQL 要人工审核，宁可少而准，不要多而错
- 发现标准 SQL 有误时，修正后要重跑历史版本，保证可比性

## 7. 你需要亲自做的事

这是本文档最重要的一节。AI 能写 SQL，但**业务口径必须由你拍板**，
否则面试官问「为什么 GMV 排除取消单」时你答不上来。

T6 层 25 条全部标了【需确认】，因为它们都涉及口径选择。最需要你确认的几条：

| 条目 | 需要你决定的问题 |
|---|---|
| T6-001 | GMV 含不含运费？含不含已取消订单？ |
| T6-002 | 客单价的分母是「订单数」还是「人数」？分子含不含运费？ |
| T6-003 | 复购率的分母是「全部下单用户」还是「注册满 N 天的用户」？ |
| T6-005 | 会员渗透率是「订单渗透」还是「人数渗透」？ |
| T6-006 | 准时率的分母含不含未送达订单？ |
| T6-008 | 动销率的分母是「全部商品」还是「有库存的商品」？ |

这些没有标准答案，取决于业务定义。你的任务不是算对，而是**能说清你选了哪个口径、为什么**。
面试官想听的是这个。

## 8. 设计过程中修掉的真实问题（面试可以讲）

这部分是加分项：它证明评估集是认真做出来的，不是随便生成的。

**问题一：退化题。** 最初有一批题答案恒为 0，比如「有多少商品从没被卖出过」。
原因是合成数据是按真实订单反推生成的，所有商品都至少被卖过一次。
这类题无论模型怎么答都测不出差异，已全部替换。

**问题二：标签数据生成 bug。** `user_tag_map` 的生成 SQL 用了 `CROSS JOIN LATERAL`，
但子查询里没有引用外层表，PostgreSQL 把它当成不相关子查询只求值一次，
导致 96096 个会员全部拿到同一个标签，所有标签类题目答案都退化。
修复方式是让标签按真实行为推导（高价值、流失风险、价格敏感等）。

**问题三：快照数据无差异。** `member_snapshot.level_id` 直接复制了当前等级，
导致「当前等级 vs 快照等级」这类对比题答案恒为 0。
修复方式是让快照等级产生约 15% 的合理漂移。

**问题四：时间窗口太短。** 「最后 7 天销售额」返回空——
因为数据集最后 7 天只有 8 笔订单且全是已取消，没有商品明细。
窗口改成 90 天才有区分度。

这四个问题的共同点是：**SQL 本身没错，是数据没有区分度**。
如果不做自检直接拿它们测准确率，会得到虚高的数字，面试时一追问就露馅。
