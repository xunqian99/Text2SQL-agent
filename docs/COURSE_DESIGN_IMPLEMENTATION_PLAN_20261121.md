# Text2SQL Agent 课程设计实施计划

状态：**P0、P1、P2 已完成；P3 尚未开始**。

本计划的目标是把现有 Text2SQL Agent 变成一套能现场演示、能解释数据流、能展示失败原因和成本的课程设计作品。重点放在可解释工作台和离线评测面板，不继续堆叠未经评测的提示词规则，也不新增付费模型评测。

## 1. 当前基础与问题

项目已经具备以下后端能力：

- Spring Boot REST 入口 `POST /api/ask`；
- Schema 检索、指标口径注入、外键路径规划和多轮会话；
- SQL AST 只读校验、执行计划代价检查、只读账号和超时控制；
- HTTP 响应已经包含 SQL、结果行、列名、实际检索表、Schema 字符数、模型 Token/费用、分段耗时、会话 ID 和费用预算快照；
- `src/main/resources/static/index.html` 已有问数页面、表格视图、图表视图和会话入口。

当前缺口是：页面没有把 SQL、检索依据、校验过程、Token/费用和失败阶段完整展示出来；离线评测报告也没有形成老师可以直接查看的结果面板。因此现有系统看起来像“能问数的页面”，还不像一套可解释、可评估的 Agent 工程。

现有评测数字必须按版本区分：固定候选三轮正式结果为 `256/300（85.33%）`，后续候选正式结果为 `234/300（78.00%）`。这些数字都低于原门槛，不能包装成稳定生产准确率。课程设计应展示真实结果和失败归因，不等待新的付费评测来补齐展示层。

## 2. 总目标与非目标

### 2.1 总目标

完成一套“可解释问数工作台”：用户输入问题后，页面同时展示最终结果和生成链路证据，使一次请求能够回答：

1. 问题经过了哪些步骤；
2. 使用了哪些表、列和业务指标；
3. SQL 为什么被接受或拒绝；
4. 模型花了多少 Token、耗时和费用；
5. 失败属于检索、生成、校验、执行、超时还是结果不匹配。

### 2.2 明确不做

- 不新增 MySQL、Oracle 等方言；
- 不做模型微调；
- 不做写库、修改业务数据或自然语言生成 INSERT/UPDATE/DELETE；
- 不做多租户和复杂后台权限系统；
- 不把历史 96% 单轮结果写成当前稳定准确率；
- 不因为做课程展示而重新调用 DeepSeek；
- 不改变原题、Gold、评分器和已有评测门槛。

## 3. 分阶段实施顺序

一次只实施一个阶段。前一阶段的代码、测试和数字验收通过后，才进入下一阶段。

### 阶段 P0：问数结果可解释化

这是第一阶段，也是课程设计最应该先完成的阶段。

页面在现有问数结果下增加一个可折叠的“执行证据”区域，至少包含：

- 用户问题和会话 ID；
- 最终 SQL，以及是否发生问题改写；
- 实际检索到的表和 Schema 字符数；
- `directHits`、`expandedTables`、`metricDependencies`、`safetyBridges` 四类来源；
- AST/只读校验状态、违反规则列表和执行状态；
- 检索、生成、校验、执行、总耗时；
- 输入 Token、输出 Token、总 Token、模型费用和预算状态；
- 成功结果、澄清状态、超时状态和失败消息。

优先复用现有 `AskResponse` 字段。如果某项证据尚未进入 HTTP DTO，只补一个只读 `TraceView` 字段，不修改模型调用顺序和评分逻辑。

P0 的验收数字：

| 指标 | 验收值 |
|---|---:|
| 成功、澄清、校验拒绝、执行失败、超时五类响应均能展示 | 5/5 |
| 证据字段完整展示 | 100% |
| 新增页面逻辑触发的模型调用 | 0 |
| 原有 Java 回归测试 | 全部通过 |
| 原 Gold200 自检 | 200/200 |
| 后端新增模型等待 | 0 ms |

P0 不承诺准确率提升。它解决的是“系统做了什么无法说明”的课程设计缺口。

### 阶段 P1：离线评测面板

实施结果见 [P1 阶段报告](COURSE_DESIGN_P1_EVALUATION_20261121.md)。

P1 读取已有 JSON/JSONL 评测报告，生成只读汇总，不启动模型。页面展示：

- 题数、正确数、准确率、SQL 成功率；
- P50/P95、超时数、澄清数、UNKNOWN 用量数；
- 已知 Token、已知费用下界、预算预留；
- 结果不匹配、超时、澄清、校验拒绝等失败分类；
- 不同候选版本之间的对比。

面板必须保留测量版本、题集身份和报告文件 SHA，避免把不同版本的数字拼成一个“最好成绩”。

P1 的验收数字：

- 面板汇总与原始报告逐项一致，准确率误差为 0；
- 至少展示两个真实历史版本：`85.33%` 和 `78.00%`；
- 至少覆盖 4 类失败原因；
- 读取报告过程模型调用为 0、业务库写操作为 0。

### 阶段 P2：失败归因与请求回放

实施结果见 [P2 阶段报告](COURSE_DESIGN_P2_REPLAY_20261121.md)。

把请求终态统一成可解释分类：

```text
RETRIEVAL      表或列召回不足
GENERATION     没有得到可用 SQL
VALIDATION     AST、只读或代价护栏拒绝
EXECUTION      数据库执行失败
TIMEOUT        模型或数据库超时
CLARIFICATION  问题口径不足
RESULT_MISMATCH 执行成功但结果与 Gold 不一致
```

回放功能只读取已保存的请求证据和 Gold，不重发模型请求。页面必须明确标注“离线回放”，避免把回放结果误当成新的供应商评测。

## 4. 一次请求的数据流

以“2018 年每月 GMV”为例：

```mermaid
flowchart LR
    Q[中文问题] --> A[AskController]
    A --> R[Schema 检索与口径匹配]
    R --> C[SchemaContext]
    C --> P[PromptTemplate]
    P --> G[模型生成 SQL]
    G --> V[AST 与只读校验]
    V --> E[EXPLAIN 代价检查]
    E --> D[只读数据库执行]
    D --> S[结果比较与会话收尾]
    S --> T[TraceView 与页面]
```

检索阶段必须继续保留来源身份：`directHits` 记录问题/别名/枚举直接命中的表；`expandedTables` 记录关系图扩展表，扩展分数按 `source × edge × 0.4` 衰减，Top-K 仍为 8，安全桥接最多 2 张；指标依赖和安全桥接分别记录，不能压平成一个“相关表”集合。

极端情况必须 fail-closed：模型超时显示超时并保留 UNKNOWN 用量；SQL 被 AST 或 EXPLAIN 拒绝时显示拒绝原因，不执行数据库；问题需要澄清时显示口径选项，不伪造 SQL；来源凭据缺失时显示“来源不可追踪”，不能假装解释完成。

## 5. 技术选型

| 层 | 方案 | 原因 |
|---|---|---|
| 接口 | Spring Boot REST，复用 `/api/ask` | 不改变核心生成链路 |
| 页面 | 现有静态 HTML/CSS/JavaScript | 用户熟悉 Java，不引入新的前端工程负担 |
| 证据模型 | `TraceView`/只读 DTO | 隔离内部 `AgentResponse`，保持接口稳定 |
| 评测读取 | Jackson 读取 JSON/JSONL | 不启动模型，不改业务库 |
| 结果展示 | 表格、折叠面板、简单 ECharts | 直观展示结果和指标 |
| 追踪身份 | requestId、prompt SHA、题目 ID、报告 SHA | 证明结果来自哪个版本 |

不新增业务写库。若需要保存页面操作，只保存本地审计 JSONL；原业务 PostgreSQL 继续使用只读账号。

## 7. 设计取舍与答辩准备

**为什么先做可解释工作台，不先继续调准确率？**

因为当前准确率在不同冻结版本间为 78.00% 和 85.33%，继续用单轮结果包装收益会破坏可信度。工作台先把真实数据流和失败证据固定下来，后续任何模型改动都能比较。

**为什么不把四类来源合并成一个相关表集合？**

直接命中、图扩展、指标依赖和安全桥接的身份不同。扩展表有 0.4 衰减和 Top-K 截断，指标依赖与安全桥接不参与同一 lexical 排序。合并后无法解释表为什么进入上下文，也无法判断扩展表是否挤掉直接命中。

**如何区分模型错和本地系统错？**

用 requestId 和 callNumber 绑定模型证据，用 prompt SHA 固定输入，用阶段耗时和终态分类区分：没有 SQL 是生成/超时问题，SQL 被拒绝是校验问题，SQL 执行成功但结果不一致才进入结果比较归因。

**为什么不做全量后台管理和多租户？**

它们不能增强 Text2SQL 核心闭环，却会引入权限、数据隔离和运维复杂度。课程设计先证明单用户只读问数链路完整。

## 8. 实施规则与用户配合

第一阶段只做 P0。P0 通过后再决定是否进入 P1，不因页面细节同时改提示词、检索和评分器。

本计划当前不需要 DeepSeek Key、Docker 重启或付费评测。用户只需要确认课程老师是否要求登录、数据库 ER 图或演示视频；若没有额外要求，默认按单用户、只读、本机演示实现。
