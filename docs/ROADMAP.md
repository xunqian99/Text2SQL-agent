## 1. 项目定义

### 1.1 一句话定位

一个面向真实业务库的、**可评估、可解释**的 Text2SQL Agent：把中文自然语言问题翻译成只读 SQL，执行后返回结果与解释，并且每一个环节的准确率、延迟、成本都可测量、可归因、可优化。

关键词是「可评估」和「可解释」。市面上不缺能写 SQL 的 demo，缺的是能说清自己错在哪、为什么错、怎么改的系统。

### 1.2 目标

**技术目标**

- 在自建 200 条评估集上，执行准确率达到 80% 以上
- 单表问题准确率 90% 以上，多表 join 问题 70% 以上
- P95 延迟低于 8 秒，单次查询成本低于 0.05 元
- 任何一次失败都能被自动归类到具体的失败类型

**简历目标**

- 简历上能写出带数字的成果，而不是技术栈罗列
- 面试中每个设计决策都能讲出取舍，扛得住三层追问
- 有一个外部参照系（公开数据集对比），数字不是自说自话

**能力目标**

项目结束时，用户应当能够独立回答：

1. 一个问题从进来到出结果，经过哪几步，每步的输入输出是什么
2. 每次调用花了多少 token、多少毫秒、多少钱
3. 某一次失败，是表选错、字段选错、join 错，还是口径错

这三条是判断「是否真正掌控项目」的标准。做不到这三条，项目再复杂也不算完成。

### 1.3 非目标（明确不做）

以下每一项都能让工作量翻倍，且对面试加分有限，因此明确排除：

- **不做写操作**：只支持 SELECT，不生成 INSERT / UPDATE / DELETE / DDL
- **不做多方言**：只支持 PostgreSQL，不做 MySQL / Oracle 适配
- **不做模型微调**：只做 prompt 与检索优化，不训练模型
- **不做多租户与权限体系**：单租户、单只读账号
- **不做通用 BI 建模**：语义层只覆盖评估集涉及的业务指标
- **不做任意复杂 SQL**：明确不支持窗口函数嵌套、递归 CTE 等长尾场景

范围守不住，项目就会停在「写了一半」的状态。这比做得少更糟。

## 2. 场景与数据集

### 2.1 为什么选电商订单域

- 表数量适中（40–60 张），足够复杂到能体现检索价值，又不会复杂到做不完
- 业务概念贴近常识，评估集标注时不需要额外领域培训
- 指标口径天然存在歧义（「活跃用户」「有效订单」「复购率」），正好用来展示语义层
- 面试官大概率熟悉，解释成本低

### 2.2 数据来源

优先顺序：

1. 公开数据集（如 BIRD 的电商相关库、Spider 的部分库）—— 省去造数据时间
2. 公开数据集 + 自行扩充表与字段 —— 增加真实感
3. 完全自建 —— 仅在前两者不可行时使用

关键点：**schema 必须真实到有坑**。字段注释缺失、枚举值用数字代码、同义字段并存（`user_status` 与 `user_state`）、历史遗留的冗余表，这些坑才是检索模块存在的理由。干净的 schema 会让整个项目失去意义。

### 2.3 表的领域划分

| 域 | 大致表数 | 示例 |
|---|---|---|
| 用户域 | 6–8 | 用户、会员、收货地址、用户标签 |
| 商品域 | 8–10 | 商品、SKU、类目、品牌、价格历史 |
| 交易域 | 10–12 | 订单、订单明细、支付、退款、发票 |
| 营销域 | 6–8 | 优惠券、活动、领券记录、裂变 |
| 履约域 | 6–8 | 发货、物流、仓库、库存 |
| 财务域 | 4–6 | 结算、对账、佣金、账单 |

### 2.4 评估集设计

规模：**200 条**（下限 150，上限 300）。低于 150 条统计噪声太大，高于 300 条标注成本不划算。

每条记录的字段：

| 字段 | 说明 |
|---|---|
| `id` | 唯一编号 |
| `question` | 中文自然语言问题 |
| `gold_sql` | 标准 SQL（可以有多个等价版本） |
| `gold_result` | 标准 SQL 的执行结果（用于执行准确率比对） |
| `db_id` | 所属数据库 |
| `difficulty` | 难度分层标签 |
| `tags` | 能力标签（聚合 / 时间窗 / 多表 / 口径等） |
| `notes` | 歧义说明、口径约定 |

难度分层（每层至少 25 条）：

| 分层 | 数量 | 说明 |
|---|---|---|
| 单表过滤 / 排序 | 40 | 最基础，用于验证链路通畅 |
| 单表聚合 | 40 | COUNT / SUM / AVG + GROUP BY |
| 时间窗口 | 30 | 同比环比、近 N 天、自然周月 |
| 多表 join（2–3 表） | 45 | 验证检索与 join 路径 |
| 多表 join（4 表以上） | 20 | 压力测试 |
| 业务口径 / 黑话 | 25 | 活跃用户、复购率、GMV 等 |

**这张分层表本身就是面试材料**。它能直接回答「你的准确率是怎么测的」这个问题。

## 3. 总体架构

### 3.1 完整链路

```
用户问题
  |
  v
[1] 会话改写        多轮对话中的指代消解（"那上个月呢"）
  |
  v
[2] 意图与槽位      识别时间范围、指标、维度、过滤条件
  |
  v
[3] Schema 检索     召回相关表 / 列 / 枚举值 / 指标定义
  |                  （关键词检索 + 向量检索，混合排序）
  v
[4] Join 路径规划   在外键图上求最短路径，确定关联关系
  |
  v
[5] 上下文组装      DDL + 字段注释 + 枚举值映射 + 指标定义 + few-shot
  |
  v
[6] SQL 生成        先选表，再生成 SQL（两段式，降低选表错误）
  |
  v
[7] 静态校验        AST 解析、表/列白名单、强制 LIMIT、只读检查
  |
  v
[8] 执行            只读账号、超时控制、结果行数上限
  |
  +--- 失败 --> 带错误信息回到 [6] 重试（最多 2 次）
  |
  v
[9] 结果解释        自然语言总结 + 可选图表 + 可解释性信息
```

### 3.2 分层职责

| 层 | 职责 | 不负责 |
|---|---|---|
| 接入层 | 请求校验、会话管理、限流 | 任何业务逻辑 |
| 编排层 | 串起整条链路、控制重试与分支 | 具体的检索或生成实现 |
| 检索层 | 从 schema 中找出相关信息 | 生成 SQL |
| 生成层 | 调 LLM 产出 SQL | 判断 SQL 是否安全 |
| 校验执行层 | 保证 SQL 安全、可执行 | 决定生成什么 |
| 评估观测层 | 记录每次调用的输入输出与指标 | 影响主链路结果 |

这个分层是后面所有代码结构的基础，也是面试时讲清楚架构的抓手。

### 3.3 两段式生成的意义

第 6 步拆成「先选表，再写 SQL」是刻意设计：

- 一次性生成时，模型容易在几十张表里选错，而选错表后续全错
- 拆开之后，表选择可以单独评估（表召回率 / 精确率），失败可以定位到具体环节
- 表选择用便宜模型即可，强模型只用在最终 SQL 生成，成本下降明显

## 4. 分阶段路线图

每个阶段必须满足两个条件才算结束：**仓库可运行**，**产出可测量的数字**。

---

### 阶段 0：地基（预估 2–3 天）

**目标**：把项目骨架、依赖、数据库、schema、评估集准备好。不写任何业务逻辑。

**要做的事**

1. 创建 Maven 项目骨架，只写 `pom.xml`，逐个确认依赖可解析
2. 搭建本地 PostgreSQL（Docker 优先）+ pgvector 扩展
3. 导入选定的电商 schema 与样例数据
4. 编写评估集的格式定义与第一批 50 条数据
5. 写 `README.md` 的项目说明与启动方式

**产出物**

- 可 `mvn compile` 通过的空项目
- 可连接、有数据的本地数据库
- 评估集文件（第一批 50 条）

**验收标准**

- `mvn dependency:resolve` 全部成功，没有版本冲突
- 能执行一条手写 SQL 并看到真实数据
- 评估集能被程序解析成对象

**面试价值**

暂无。但这一步决定了后面会不会被依赖问题拖住。

**注意**

这是最容易翻车的一步，因为 AI 编造依赖版本是高频事故。规则是：先只生成 `pom.xml`，逐个依赖验证通过后再往下走。

---

### 阶段 1：端到端最小闭环 + baseline（预估 4–5 天）

**目标**：跑通「问题 → SQL → 结果」的完整链路，并测出最朴素的 baseline 准确率。

**要做的事**

1. 接入 LLM（Spring AI 或 LangChain4j），跑通一次最简单的调用
2. 写一个 `SchemaProvider`，先把整库 DDL 直接拼进 prompt（故意粗糙）
3. 写 `SqlGenerator`，一次调用直接产出 SQL
4. 写 `SqlValidator` 的第一版：AST 解析 + 禁止非 SELECT + 强制 LIMIT
5. 写 `SqlExecutor`，通过只读连接执行并返回结果
6. 写评估运行器：遍历评估集，对比结果集，输出准确率
7. 跑出 baseline 数字

**产出物**

- 可用的 REST 接口：输入问题，返回 SQL 与结果
- 第一份评估报告（baseline）

**验收标准**

- 一条中文问题能返回正确结果
- 50 条评估集能自动跑完并输出准确率
- 所有非法 SQL（DROP、UPDATE、无 LIMIT）都被拦截

**预期数字**

baseline 执行准确率通常在 55%–65% 区间。这个数字低是正常的，它是后面所有优化的参照点。**如果 baseline 就有 85%，说明评估集太简单，要重新设计。**

**面试价值**

「你的 baseline 是多少」——这个问题能淘汰一半候选人。有一个明确的起点数字，后面每一步改进才有意义。

---

### 阶段 2：Schema 检索（预估 5–7 天）

**目标**：从「整库塞进 prompt」升级为「按需召回相关表、列、枚举值」。

**要做的事**

1. schema 切块：表级、列级、枚举值级分别建索引
2. 关键词检索：**应用层中文语义词典 + 最大匹配**（原计划的 PostgreSQL
   `tsvector` 已实测推翻，原因见下方「方案变更记录」）
3. 关系扩展：沿外键图带出一跳邻居，边强度区分硬外键与人工推断关联
4. 混合排序：直接命中分数 + 关系扩展分数，取 Top-K 表
5. 枚举值 linking：把 `status=3` 这类代码值映射成可读含义塞进上下文
6. 连通性修复：Top-K 表如果构不成连通子图，补入关系图上的最短桥接表
7. 补全评估集到 200 条，增加表召回率指标；按 id 哈希切分开发集/评估集

**产出物**

- 检索模块与它的单元测试
- 表召回率 / 精确率报告
- 更新后的准确率数字
- `src/main/resources/schema/glossary.yml`：中文语义词典（表别名 / 列别名 /
  枚举值 label / 外键之外的约定关联），是可审阅、可增删的领域知识资产

**验收标准**

- 表召回率（Top-5）达到 90% 以上
- 执行准确率相比 baseline 提升 8 个百分点以上（原定目标；本项目真实链路实测为 +5 个百分点，未达成该项）
- 上下文 token 数相比 baseline 下降（说明检索确实在筛选）

#### 方案变更记录：为什么放弃 tsvector

原计划第 2 条写的是「PostgreSQL `tsvector`，对表名/字段名精确匹配友好」。
**实测证明这条路对中文是死的**，证据如下（在容器里直接执行）：

```sql
SELECT to_tsvector('english','统计每个州的订单数量');
-- 结果：'统计每个州的订单数量':1     整串被当成一个 token，没有切分

SELECT to_tsvector('simple','订单 数量 州');
-- 结果：'订单':1 '州':3 '数量':2     只有空格分隔才切得动

SELECT show_trgm('订单数量');
-- 结果：{}                          pg_trgm 对中文返回空

SELECT similarity('统计每个州的订单数量','订单');
-- 结果：0
```

镜像里没有 `zhparser` / `pg_jieba`，PG 内置分词器不切分中文，`pg_trgm`
的三元组又基于字符而非词。中文自然语言问题里不会有空格，所以 tsvector
这条路走不通。

**改道后的方案**：分词放应用层，用**词典驱动的最大匹配**。这里刻意
**没有**引入 jieba / HanLP 这类通用分词器——通用分词器能把「复购率」
切成「复购」「率」，但它仍然不知道「复购」对应哪张表。真正的难点不是
切词，是**领域映射**。用词典把两件事合成一步，且词典可审阅、可增删。

**另一条被否掉的路**：pgvector 向量检索。它的依赖成本高（要 embedding
服务、要 pgvector 扩展、要联网），而当前词典路线的**依赖为零**。
先用零依赖方案拿到干净的对照数字，之后加向量路才能说清「向量路额外
贡献了多少」。这与「先做笨实现拿 baseline」是同一个方法论。

#### 阶段 2 实测数字

评估集按 `Math.floorMod(id.hashCode(), 2)` 切成开发集 100 条 / 评估集 100 条，
两层难度分布几乎完全一致（T1 20/20、T2 20/20、T3 14/16、T4 23/22、
T5 10/10、T6 13/12）。历史诊断已看过全部题目、eval 也已跑过多个配置，
不能称为未见独立测试集；后续调参只看 dev，冻结配置后再验收。

以下为 **2026-10-01 的历史 dry-run 检索消融**，测表选择，不测模型准确率：

| 配置 | 全召回率 | 表召回率 | 平均精确率 | 平均召回表数 | 平均 DDL 字符 |
|---|---|---|---|---|---|
| baseline 全量 schema（开发集） | 100% | 100% | 5.24% | 37.0 | 7401 |
| + 词法检索 + 确定性排序，关连通性修复（开发集） | 95.0% | 98.95% | 29.97% | 6.68 | 1551 |
| + 连通性修复（开发集） | **96.0%** | **99.20%** | 29.98% | 6.71 | 1556 |
| + 检索（评估集，topK=8） | **93.0%** | **98.48%** | 28.42% | 6.69 | 1582 |
| + 检索（评估集，topK=5，ROADMAP 口径） | 89.0% | **96.53%** | 35.99% | 4.78 | 1185 |

消融读法：这一对历史开发集实验中，连通性修复增加 **1.0 个百分点全召回率**，
代价是平均多召回 0.03 张表（6.68 → 6.71）、DDL 多 5 个字符。
这是「补最少的结构性缺口」换来的，不是无差别加表。

**验收结论**：

- 表召回率（Top-5）**96.53% ≥ 90%** ✓
- 最终真实链路平均输入 token 从 2314.71 降到 709.46，**下降 69.35%** ✓；
  平均 DDL 从 7401 降到 1579.55 字符，下降 78.66%。
- 执行准确率 **47% → 52%，提升 5 个百分点，原定 +8 目标未达成**。
  实现、测试与评估已收尾，不将原目标降低成 +5 来宣布全部验收通过。

真实链路（2026-10-02，同模型 `ernie-4.5-turbo-32k`，eval 100 条）：

| 配置 | 执行准确率 | SQL 有效率 | 平均输入 token | 平均延迟 | P95 延迟 |
|---|---|---|---|---|---|
| baseline 全量 schema | 47% | 78% | 2314.71 | 4837.34ms | 11721ms |
| 检索 Top-8 + 连通性修复 | 52% | 92% | 709.46 | 4442.58ms | 8496ms |

报告分别为 `reports/eval-20261002-151939.json`、`reports/eval-20261002-160914.json`。
金额字段为 0 是因为单价未配置，不代表免费。完整口径与局限见
[EVALUATION.md](EVALUATION.md)。

**关于 top-k 取 8 而不是 5**：dev 实测 Top-5/Top-8 的执行准确率为 46%/48%，
全召回率为 89%/96%；取 8 是参考开发集并给多表关联留余量。
历史 eval Top-5 为 54%，高于最终 Top-8 的 52%，保留该结果，不宣称 8 总是更优。
Top-K 是修复前候选表上限，之后可补最多 2 张桥接表，无命中时还会回退全量，
因此不能用 K=5 推算简单的理论准确率上限。召回验收仍按原文 Top-5 判定。

#### 尚未解决的检索失败（诚实记录）

最终 eval 100 条里 7 条不完整召回：
`T4-020 漏[orders]`、`T5-001 漏[customers]`、`T5-007 漏[member_levels]`、
`T5-010 漏[product_category_translation]`、`T5-012 漏[customers]`、
`T5-018 漏[order_items]`、`T6-008 漏[orders]`。

旧记录把部分 gold 关联判作冗余，证据不足，本次纠正：
T6-008 使用 `orders.order_status` 排除取消/不可用订单；T5-001 的 `customers`
参与地区、会员关联；T5-018 的 INNER JOIN 即使没输出明细列也可能过滤行。
不能据此宣称“检索漏掉是正确行为”。T5-007 等仍需人工确认 gold 的业务口径，
不通过修改 gold 来掩盖召回缺口。

**连通 ≠ 口径正确**：图上存在路径不等于该路径适合业务统计，
关系路径约束与指标口径分别是阶段 3/4 的后续方向，不以无限扩大 K 代替设计。

**面试价值**

这一阶段的增量数字能直接回答「你怎么在几十张表里选对表」。同时 token 下降 + 准确率上升这个组合，能体现工程判断力。

### 阶段 3：Join 路径规划（预估 4–5 天）

**目标**：让多表关联由系统决定，而不是让模型自由发挥。

**要做的事**

1. 从数据库元数据抽取外键，构建表关系图
2. 对召回到的多张表，求连接它们的最短路径
3. 把确定好的 join 关系作为约束写进 prompt
4. 处理无外键但逻辑相关的表（需要人工维护一份补充关系配置）
5. 单独统计多表问题的准确率变化

**产出物**

- join 图构建与路径规划模块
- 多表问题专项准确率报告

**验收标准**

- 多表 join 问题准确率提升 10 个百分点以上（**原定目标；实测 0 个百分点，未达成**）
- 整体准确率相比阶段 2 再提升 5 个百分点以上（**原定目标；实测 0 个百分点，未达成**）

#### 实测结果：机制有效，但收益被抵消（2026-10-04）

真实链路，同模型 `ernie-4.5-turbo-32k`，eval 100 条，报告
`reports/eval-20261004-140246.json`：

| 指标 | 阶段 2 | 阶段 3 | 变化 |
|---|---:|---:|---|
| 执行准确率 | 52%（52/100） | **52%（52/100）** | **0** |
| SQL 有效率 | 92% | 96% | +4 |
| 平均输入 token | 709 | **917** | **+29%** |
| 平均 DDL 字符 | 1579 | **2193** | **+39%** |
| 多表 join（T4 层） | 45.45% | 45.45% | 0 |
| 深层 join（T5 层） | 10% | 10% | 0 |

**设计假设被验证了**：join 列猜错确实是真问题，机制也真的修掉了它——
按「SQL 里 join 列与 gold 不一致」的启发式统计，这类错误从 **4 条降到 1 条**；
用作立论依据的 T4-015（gold 用 `region_code`，模型猜 `region_name`）从失败转为通过。

**但整体准确率没有变化**：逐条比对显示修好 5 条、新坏 5 条，净变化为零。
核查新坏的 5 条：

1. **3 条是单表题**（T1-010 / T2-013 / T3-014），压根没有 join，
   属于模型自身的单轮波动，与本次改动无关。
2. **2 条是「过度 join」**（T4-006 / T4-031）：模型看到 JOINS 段里有
   `sellers -> regions` 这条候选边，就顺手连上了，而 gold 不需要它。
   **这是本次改动自己制造的错误。**

**结论：确定成本（+29% token）换不确定收益（0 个百分点），工程上不成立。**
因此 join 提示改为**默认关闭**（`agent.retrieval.join-hints-enabled=false`），
代码保留可显式开启，行为回到阶段 2 形态（平均 DDL 1575 字符，与阶段 2 的 1579 一致）。

#### 为什么这个评估集测不出阶段 3 的效果

**这是本节最值得记住的一条。** eval 100 条里，真正涉及「join 列选择」的
只有约 5 条。即使全部修好，上限也只有 +5 个百分点，而单轮运行的波动
本身就有 ±5 个百分点——**这个评估集对阶段 3 没有统计功效**。

更根本的是：多表题失败的主体**不是 join 连错**。dry-run 已经暴露，
4+ 表题的失败几乎全是 `UNKNOWN_TABLE`——gold 用到的表检索没召回，
被校验层拦下。那是**阶段 2 表召回**的问题（T5-001 漏 `customers`、
T5-012 漏 `customers`、T5-018 漏 `order_items`），join 规划解决不了。

**记录这条的意义**：它说明「优化没效果」有时不是实现错了，而是
**优化的目标不是当前的瓶颈**。先量化瓶颈在哪一层，再动手。

#### 两个被测试抓出来的设计缺陷（面试可讲）

1. **兜底排序键最初用了整条边的全字段**，导致同强度的边由**列名**决定先后。
   而「先连哪张表」是树的形状，不该由列名这种实现细节决定。改成按
   「新连上那张表」的表名排序。
2. **只按「强度 → 表名」仍然错**：规划 T5-001 时，第三轮迭代的三条候选边
   强度都是 0.5（都是词典关联），`coupon_usages` 因字母序排在 `members` 前面，
   主干变成「经优惠券到会员」——**正是 T5-001 出错的那条路径**。
   插入「目标表相关度」作为第二排序键后才与 gold 一致。

教训：**强度只能区分「硬事实 / 软知识」，无法区分「软知识里哪条更该走」。**
而检索分数恰好携带那个信息，直接复用比另造启发式规则可靠。

**面试价值**

「多表 join 怎么保证正确」是高频追问。这里的回答是：join 路径由外键图决定，不由模型决定，因为模型选错 join 时 SQL 仍然能执行，错误是静默的——这是最危险的一类错误。

### 阶段 4：语义层（预估 6–8 天）

**目标**：把业务口径注册成可复用的指标定义，让模型引用指标而不是自己拼条件。

**这是整个项目的核心亮点。**

**要做的事**

1. 定义指标配置文件格式（YAML），包含名称、描述、同义词、表达式、口径说明
2. 先注册 15–20 个高频业务指标，例如：
   - 活跃用户（按登录时间口径）
   - 有效订单（排除已取消与测试订单）
   - GMV / 销售额（含税不含税、含退款不含退款）
   - 复购率、客单价、转化率
3. 在检索阶段同时召回指标定义，与 schema 一起组装进上下文
4. 在 prompt 中明确要求：能引用指标时优先引用，不要自行拼条件
5. 针对口径类问题单独统计准确率

**产出物**

- 指标注册表（YAML）
- 指标检索与注入模块
- 口径类问题的准确率报告

**验收标准**

- 口径类问题准确率提升 15 个百分点以上（**实测 +41.7 个百分点，达标**）
- 整体准确率达到 78% 以上（**实测 71%，未达标**）
- 同一问题在不同问法下结果一致（口径稳定性测试，**当前未单独测量，待补**）

#### 实测结果（2026-10-04，模型 deepseek-flash，eval 100 条）

同模型、同检索配置，只切 `agent.semantic.enabled`：

| 配置 | 整体 | 业务语义 T6 | 单表基础 | 单表聚合 | 时间窗口 | 多表 join | 深层 join |
|---|---|---|---|---|---|---|---|
| 语义层关 | **62%** | 16.67% (2/12) | 90% | 80% | 75% | 54.55% | 20% |
| 语义层开 | **71%** | **58.33% (7/12)** | 90% | 85% | 87.5% | 59.09% | 20% |
| 差值 | **+9** | **+41.7** | 0 | +5 | +12.5 | +4.5 | 0 |

报告：`reports/eval-20261004-180116.json`（关）、`reports/eval-20261004-181111.json`（开）。

逐条比对：语义层修好 **12 条**，弄坏 **3 条**（T2-008 / T3-016 / T5-009，均为结果不匹配，
属模型单轮波动，非口径错误）。净 +9 条 = +9 个百分点。

代价：平均输入 token 734 → 760（+3.5%），延迟基本不变。这是本项目目前
**投入产出比最高的一个模块**——用 3.5% 的 token 换 9 个百分点。

#### 阶段 4 补强实测结果（2026-10-04，模型 deepseek-flash，eval 100 条）

针对第一次失败分析中发现的口径冲突、复杂查询结构和指标漏表，增加上下文条件、
完整 query pattern、输出约束，并补齐指标依赖表后重新跑真实链路：

| 指标 | 补强前语义层开 | 补强后语义层开 | 变化 |
|---|---:|---:|---:|
| 整体执行准确率 | 71%（71/100） | **71%（71/100）** | 0 |
| T6 业务语义 | 58.33%（7/12） | **91.67%（11/12）** | **+33.34pp** |
| SQL 有效率 | 97% | **100%** | +3pp |
| 平均输入 token | 760 | 778 | +2.4% |
| 平均延迟 | 1731ms | 1577ms | -8.9% |
| P95 延迟 | 4239ms | 3401ms | -19.8% |

报告：`reports/eval-20261004-205657.json`。

补强后剩余 29 条失败中，业务语义只剩 T6-011 一条；主要失败集中在普通时间题、
T4 多表和 T5 深层 join。T5 深层 join 仍为 2/10，说明整体 78% 目标的剩余瓶颈
已经转移到 join 路径、字段选择、聚合粒度和输出列控制。阶段 4 的口径目标达标，
整体目标仍未达标，不能把 71% 视为系统上限。

稳定性验收：当前报告是固定评估集上的一次消融对照，没有为同一业务问题准备多种
等价问法，也没有独立的稳定性指标。因此这一项只能记为“待验证”，不能从 71% 的
执行准确率推导出来。

#### 一个被实测抓出来的设计缺陷：别名不能放普通描述词

第一版给 `sales_without_freight` 配了别名 `[销售额, 商品销售额, 不含运费, 商品金额]`。
结果它在 100 条里命中了 **4 道非业务语义题**，并把其中 3 道弄坏（T3-014 / T4-002 / T4-004），
整体准确率反而从 62% 降到 **61%**。

原因：那些是**普通描述词**，不是业务黑话。「每个州的商品销售额是多少」就是一次简单聚合，
模型本来就会写 `SUM(oi.price)`；而这些普通题的 gold **没有**「排除取消/不可用订单」的过滤，
一旦注入带 `filter` 的指标定义，模型照抄那个过滤，答案就错了。

**判据：指标别名只放业务黑话（GMV / 复购率 / 动销率 / 会员渗透率），不放普通描述词。**
黑话才需要口径定义；普通问法让模型按字面写。修掉之后 T6 覆盖仍是 25/25，
与 T1–T5 的别名冲突降为 **0**，整体从 61% 升到 71%。

#### 为什么整体没到 78%

剩余 29 条失败的分布：T4 多表 join 9 条、T5 深层 join 8 条、T6 业务语义 5 条、
T1/T2/T3 共 7 条。其中 **17 条是「结果不匹配」**（SQL 能跑但答案差一点），
1 条表未召回、1 条超时、1 条生成失败。

也就是说：剩下的瓶颈**不是口径**了，而是多表/深层 join 的 SQL 构造能力，
以及部分题目的输出格式细节。那是阶段 5（自纠错）与阶段 2 补强（表召回）的范围。

**面试价值**

这是能拉开档次的模块。面试时讲「我用语义层统一业务口径」，和讲「我调了 prompt 让模型更准」，是两个层次的回答。前者说明你理解了问题的本质，后者说明你在碰运气。

同时这也是工业界主流解法（dbt Semantic Layer、Cube、Malloy），能体现你了解真实生产实践。

### 阶段 5：护栏与自纠错（预估 4–5 天）

**目标**：把系统从「能跑」提升到「可信」。

**要做的事**

1. SQL 校验升级：AST 级别的表白名单、列白名单、危险函数黑名单
2. 强制 LIMIT、查询超时、结果行数上限、扫描行数上限
3. 只读数据库账号（权限层面兜底，不依赖代码正确）
4. 执行失败时的自纠错：把数据库返回的错误信息回灌给模型，最多重试 2 次
5. 歧义检测与主动反问：问题模糊时不猜，先问清楚
6. 补充对抗性测试用例（注入攻击、恶意 SQL）

**产出物**

- 完整的安全护栏
- 自纠错循环
- 对抗性测试报告

**验收标准**

- 所有恶意 SQL 测试用例被拦截，拦截率 100%
- 自纠错使最终成功率提升 3 个百分点以上
- 自纠错带来的延迟增量被量化（这是代价，要能说清）

#### 阶段 5 实测结果（2026-10-04，模型 deepseek-flash，eval 100 条）

自纠错实现为**两档触发条件**，因为「知道答案错了」这件事在线上并不成立：

| 触发条件 | 线上可用 | 触发次数 | 首答 | 最终 | 结论 |
|---|---|---:|---:|---:|---|
| `ERRORS_ONLY` | 是 | 0 | 68% | 68% | 首答 SQL 有效率 100%，没有可回灌的错误，收益为 0 |
| `ERRORS_AND_MISMATCH` | **否**（评估专用上限） | 32 | 68% | **72%** | 逐条配对 +4 条；代价见下 |

重试代价（`ERRORS_AND_MISMATCH` 那一轮，32 条触发）：

| 指标 | 不重试 | 重试后 | 变化 |
|---|---:|---:|---:|
| 平均输入 token | 778 | 1105 | +42% |
| 平均延迟 | 1446ms | 2620ms | +81% |
| P95 延迟 | 3033ms | 8304ms | +174% |
| 额外 token | — | 34005 prompt + 16232 completion | — |

**结论：自纠错的收益依赖「结果校验器」，而不是依赖模型自己。** 线上没有错误信号时
它一点也用不上；给它一个完美的错误信号，也只能救回 4 条。所以下一步不该继续加
重试次数，而应该去修「首答就错」的那些根因。

#### 一个必须先说清楚的方法论问题：答案泄露

自纠错第一版把 gold 的样例行和行列数放进了反馈提示，70 条就跑到 95.7%。
那不是模型在自纠错，而是它看到了答案。改为「反馈里只允许出现用户问题、模型自己上一条
SQL、数据库真实报错和它自己那次执行的结果」之后，同一配置回落到 72%。
**凡是「加了自我反思就大幅提升」的结果，先检查提示里有没有混进标签。**

#### 评估噪声：单轮数字有 ±3 个百分点波动

同一份代码、同一份配置、temperature=0，三次独立评估分别是 **71% / 68% / 70%**。
说明这个 100 条 eval 的单轮精度约 ±3pp。因此：

**小于 3 个百分点的改动不能用单轮结果下结论，必须做同轮配对或多次重跑。**

#### 阶段 5 收口：四项护栏的完成情况

ROADMAP 阶段 5 原本列了六件事。到这一轮为止的状态：

| # | 事项 | 状态 | 证据 |
|---|---|---|---|
| 1 | AST 级表白名单 | 阶段 1 已做 | `UNKNOWN_TABLE`，`SqlValidator` 第 5 步 |
| 2 | AST 级列白名单 | **本轮新增** | `UNKNOWN_COLUMN`，只校验带别名前缀的列 |
| 3 | 危险函数黑名单 | 阶段 1 已做 | 27 个函数，含子查询/CTE 内的递归遍历 |
| 4 | 强制 LIMIT / 超时 / 行数上限 | 阶段 1 已做 | APPEND 模式 + `query-timeout-seconds` + `max-rows` |
| 5 | 执行失败自纠错 | **本轮完成，但收益为 0** | 见上文 `ERRORS_ONLY` 那一行 |
| 6 | 歧义检测与主动反问 | **本轮新增** | `ambiguities.yml` + `AmbiguityDetector`，默认关闭 |
| 7 | 对抗性测试 | **本轮新增** | `AdversarialSqlTest`，44 个用例 |

**列白名单为什么只做一半。** 只校验带别名前缀的列（`o.customer_id`），裸列名不查。
裸列名的合法来源太多——SELECT 别名、CTE 输出列、派生表列、集合操作两侧的同名列——
一旦判错，正常查询会被拦下，护栏就从防护变成故障源。

**这条纪律被实测验证了一次。** 第一版实现把别名映射做成了全局扁平表，而 SQL 里的
别名是按作用域生效的：T6-016 的标准 SQL 外层写 `FROM brands bp`，CTE 内部写
`FROM brand_products bp`，同一个 `bp` 指两张不同的关系。压平之后 `bp.product_id`
被判成「brands 没有 product_id」，**dry-run 直接从 200/200 掉到 199/200**。
修法不是去实现完整的词法作用域，而是承认能力边界：别名一旦被绑定到 CTE 或派生表，
该别名的列一律不判定。

**这就是 dry-run 的价值**：它拦下的不是模型错误，而是**我自己的护栏 bug**。
没有这一步，这个误杀会以「准确率莫名掉了 1 个点」的形式出现，排查成本极高。

#### 阶段 5 与阶段 4 的补强项：只读账号与线上自纠错

**只读账号（第三层防线）**：新增 `data/schema/05_readonly_role.sql`，创建
`text2sql_ro` 并只授 SELECT，显式 REVOKE 掉 INSERT/UPDATE/DELETE/TRUNCATE 和 CREATE。
应用连库账号从建库用的超级用户 `text2sql` 换成 `text2sql_ro`。实测验证：

```text
SELECT count(*) FROM orders;              -> 99441（可读）
DELETE FROM orders WHERE false;           -> ERROR: permission denied for table orders
CREATE TABLE hacked(id int);              -> ERROR: permission denied for schema public
```

它的意义不在准确率，而在**最坏情况的上界**：AST 校验被绕过时，攻击者拿到的是
读权限而不是库的所有权。

**线上自纠错**：把重试从评估器挪进编排层，`/api/ask` 现在也能用。
两处设计取舍：

- **只在有错误信号时重试**（校验拒绝 / 执行失败 / 模型返回空内容）。「执行成功但答案不对」
  线上没有信号，那一档只留在评估器里当上限实验。
- **重试失败时保留首次结果**。把一次糟糕的重试当成最终答案，会让系统比不重试更差——
  实测出现过「首次能跑通、重试反而失败」的情况。这条有单元测试固定
  （`OrchestratorSelfCorrectionTest.keepsFirstResultWhenRetryFails`）。

#### 阶段 5 验收结论

| 验收标准 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 恶意 SQL 拦截率 | 100% | 44/44 | **达标** |
| 自纠错提升最终成功率 | ≥ 3pp | **+0pp** | **未达标** |
| 延迟增量被量化 | 有数字 | 触发 1 次，见下 | 达标 |

**自纠错 +3pp 这条没有达成，原因是它测的东西在当前系统里不存在。** 四个数据点：

| 配置 | 首答 | 最终 | 触发次数 | 救回 |
|---|---:|---:|---:|---:|
| 线上自纠错（`ERRORS_ONLY`） | 68% | 68% | 0 | 0 |
| 线上自纠错（最终轮，含只读账号） | – | 77% | 1 | **0** |
| 评估器自纠错（`ERRORS_AND_MISMATCH`，oracle 触发） | 68% | 72% | 32 | 4 |

首答 SQL 有效率长期在 96–100%，**没有错误信号可回灌**，所以线上最多救回 0–1 条。
即使给一个完美的结果校验器（oracle 触发），也只能多救 4 条。

**结论不是「自纠错没用」，而是「它的收益上界由结果校验器决定，而我没有结果校验器」。**
把这条如实写进验收表，比调参数把它凑到 3 个点更有价值——面试时被问
「你的自纠错提升了多少」，能答出「0，而且我知道为什么」，远强于答一个经不起追问的数字。

**当前最优配置（prompt v2 + 语义层 + 只读账号）四次独立运行：77% / 77% / 75% / 77%**，
均值约 76.5%，报告见 `reports/eval-20261004-231531.json` 等。整体 78% 的目标仍未达到。

**歧义反问为什么默认关闭。** 评估集里的题目都写明了口径，反问会把「本该作答」
变成「不作答」，直接压低准确率。它是给真实用户链路用的能力，不是给离线评估用的。
新增的 `NEEDS_CLARIFICATION` 状态和 `REJECTED` 分开，是因为**责任方不同**：
前者是问题没问清，后者是模型写错了。混成一类会得出「模型爱写违规 SQL」的错误结论。

**面试价值**

「怎么防止删库」是必问题。分三层回答：SQL 校验、只读账号、超时限制，且强调「不依赖任何单一层的正确性」。

自纠错要同时讲收益和代价——准确率涨了 3 个点，但延迟从 4.4 秒涨到 5.6 秒，这是取舍。

## 5. 评估体系

这一节是项目的核心竞争力。没有评估，所有优化都是猜测。

### 5.1 核心指标

| 指标 | 定义 | 作用 |
|---|---|---|
| **执行准确率（EX）** | 生成 SQL 与标准 SQL 的执行结果集是否一致 | 主指标，最终衡量标准 |
| **表召回率** | 需要的表是否出现在召回的 Top-K 中 | 定位检索层问题 |
| **表精确率** | 召回的表里有多少是真正需要的 | 判断上下文是否被噪声污染 |
| **SQL 有效率** | 能通过校验并成功执行的占比 | 区分「生成错误」与「执行错误」 |
| **自纠错成功率** | 首次失败后重试成功的比例 | 衡量重试机制价值 |
| **P50 / P95 延迟** | 端到端响应时间 | 用户体验 |
| **单次成本** | 平均 token 成本 | 工程可行性 |

**为什么用执行准确率而不是字符串匹配**：同一个问题有无数种正确写法（别名、join 写法、子查询 vs join），字符串匹配会严重低估真实水平。当前比较器忽略列名但保留列位置，不支持自动识别列换序等价。

**执行准确率的一个坑**：浮点数精度、结果顺序、NULL 处理都会导致误判。需要做结果集规范化（排序、四舍五入、NULL 统一表示），这部分要单独写测试。

### 5.2 失败归因分类

每次失败必须被归入以下某一类，且分类要自动化：

| 类型 | 说明 | 责任模块 |
|---|---|---|
| 表选择错误 | 该用的表没被召回 | 检索层 |
| 列选择错误 | 表对了但字段用错 | 检索层 / 生成层 |
| Join 错误 | 关联关系错，或漏 join 导致笛卡尔积 | join 规划 |
| 口径错误 | SQL 能跑但业务含义不对 | 语义层 |
| 语法/执行错误 | SQL 无法执行 | 生成层 |
| 歧义未澄清 | 问题本身有多种合理解释 | 反问机制 |
| 数据问题 | 标准 SQL 本身有误 | 评估集质量 |

这张分布图是 README 里最有价值的图之一。它证明你不是在盲目调 prompt，而是有方向地修系统。

### 5.5 评估集管理原则

- **评估集不能用来调 prompt**。调 prompt 用开发集（约 100 条），评估集（约 100 条）只在阶段验收时跑
- 每次跑评估都要记录完整快照：代码版本、prompt 版本、模型版本、时间戳
- 标准 SQL 要人工审核，宁可少而准，不要多而错
- 发现标准 SQL 有误时，修正后要重跑历史版本，保证可比性

**当前限制**：历史诊断已经看过全量，eval 也跑过多组配置；现有成绩只作内部
回归参照，不宣称无泄漏泛化。当前报告尚未保存代码 commit、数据哈希与完整参数
快照；上述原则是后续要求，不是既有报告已全部做到的事实。

## 6. 技术栈

| 环节 | 选型 | 备选 | 选它的理由 |
|---|---|---|---|
| 语言 | Java 21 | - | 当前项目实际使用的 JDK，与已验证的依赖配套 |
| 框架 | Spring Boot 3 | Quarkus | 生态最全，资料最多 |
| LLM 接入 | Spring AI | LangChain4j | 与 Spring 集成更自然 |
| SQL 解析 | JSqlParser | Apache Calcite | Calcite 对 PostgreSQL 方言支持较弱，校验场景 JSqlParser 够用 |
| 数据库 | PostgreSQL 16 | MySQL | 与后续阶段 3 的关系图、阶段 6 的可观测都够用，且是电商数仓常见选型 |
| 关键词检索 | 应用层中文语义词典 + 最大匹配 | PostgreSQL tsvector / Elasticsearch / jieba | tsvector 实测不切分中文（见阶段 2 方案变更记录）；ES 要额外中间件；jieba 能切词但不解决「词到表」的领域映射 |
| 向量检索 | pgvector | Qdrant / Milvus | 同上，少一个运维对象 |
| 编排 | Spring Service 手工编排 | LangGraph4j | 流程是固定链路加有限重试，框架带来的收益小于理解成本 |
| 可观测 | Langfuse（或自建表） | - | 能直接看 prompt 与 token |
| 前端 | 静态 HTML + fetch | Vue / React | 演示用，够用即可 |
| 容器 | Docker Compose | - | 一键起数据库 |

### 关键决策说明

**为什么不用 LangChain4j 的 Agent 抽象**：这条链路的控制流是明确的（检索 → 生成 → 校验 → 执行 → 重试），用框架反而会把关键逻辑藏在黑盒里，出问题时难以定位。手写编排代码量不大，但每一行都能解释——这对面试和调试都是优势。

**为什么检索放在数据库里而不是引入向量库**：表数量在百级，pgvector 完全够用，且与业务数据同库，事务和运维都简单。引入独立向量库在这个规模下是过度设计。

**为什么用 JSqlParser 而不是 Calcite**：Calcite 的强项是跨方言查询优化，而这里的需求只是解析 + 白名单校验。用 Calcite 属于用大炮打蚊子，且对 PostgreSQL 方言的支持反而不如 JSqlParser 直接。

每完成一个阶段，就把实测数字填进来。以下是预期会被问到的问题与回答框架。

| 面试问题 | 回答框架 | 数据来源 |
|---|---|---|
| 你的准确率是多少？ | 分层给出：整体 / 单表 / 多表，并说明评估集规模与标注方式 | 阶段 1–6 评估报告 |

| 错在哪？ | 失败归因分布图，七类错误的比例 | 第 5.2 节 |

| 中文分词为什么不用 tsvector？ | 实测 `to_tsvector` 把中文整串当一个 token、`show_trgm` 返回空；PG 内置分词器不切中文，镜像里也没有 zhparser。改应用层词典，因为难点不是切词而是「词到表」的领域映射 | 阶段 2 方案变更记录 |
| 检索出来的表连不起来怎么办？ | 在关系图上找最短桥接表补齐；消融实测 +1.0 个百分点全召回，代价只多 0.03 张表 | 阶段 2 |
| 多表 join 怎么保证正确？ | 外键图最短路径，join 由系统决定不由模型决定 | 阶段 3 |
| 业务口径不一致怎么办？ | 语义层注册指标，模型引用指标而非自行拼条件 | 阶段 4 |
| 怎么防止删库？ | 三层防护：AST 校验、只读账号、超时限制 | 阶段 5 |
| 生成的 SQL 报错怎么办？ | 错误信息回灌 + 最多 2 次重试，收益和延迟代价都量化 | 阶段 5 |
| 成本和延迟怎么优化？ | 分层模型路由 + 语义缓存，成本降 50%，准确率只掉 1–2 个点 | 阶段 6 |
| 为什么不用 LangGraph？ | 链路固定，框架收益小于理解成本；手写编排更易调试 | 第 6 节 |
| 这个项目最难的地方是什么？ | schema 语义歧义，尤其是枚举值与业务口径，这是检索和语义层存在的理由 | 全程 |

**注意最后两题**。它们考的是判断力，而不是技术广度。能说清「我故意不做什么、为什么」比「我什么都做了」更有说服力。

## 9. 风险与应对

- 阶段 3 的 join 提示**默认关闭**（`agent.retrieval.join-hints-enabled=false`），
