## 一、 系统整体架构与端到端核心数据流

### 1. 为什么选择确定性流水线（Pipeline），而不是完全动态的 ReAct Agent？
- **工业界教训**：完全动态的 ReAct 智能体把连表、选表、语法生成的全部决策都交给大模型自由发散。面对 37 张表的数仓，模型极易产生“幻觉连表”、“死循环调用工具”，且单次生成耗时通常在 30 秒以上，Token 消耗不可控。
- **架构抉择**：采用**“确定性规则/图算法前置守门 + 大模型核心翻译 + 物理沙箱后置兜底”**的混合流水线。
  - **检索与连表由图算法（BFS / Steiner Tree）保证 100% 拓扑闭环**；
  - **大模型只负责理解自然语言并映射到确定的 Schema 节点**；
  - **安全与代价由 AST 和 EXPLAIN 做绝对物理防御**。

### 2. 端到端 7 步核心数据流转
1. **歧义澄清与多轮改写**：`AmbiguityDetector` 检查是否有口径分歧；`QuestionRewriter` 进行指代消解与 Schema 0ms 复用；
2. **Schema 词法召回与连通性修复**：`LexicalSchemaRetriever` 提取候选表，并用多源 BFS 自动补齐缺失中枢桥接表；
3. **语义缓存拦截**：`SemanticCache` 基于归一化问题 + 配置指纹，命中则 0ms 纳秒级直接复用历史 SQL；
4. **全局最优连表拓扑规划**：`JoinPathPlanner` 基于多源 Dijkstra 斯坦纳树算法，生成总权值最小的连表树；
5. **列剪枝与 Prompt 组装**：`ColumnPruner` 将非核心列剥离，利用 U 型注意力曲线拼装高保真 Prompt；
6. **大模型推理生成**：受控调用大模型，支持 BYOK 自带密钥模式与大小模型级联路由；
7. **AST 语法审查与 EXPLAIN 代价拦截**：`SqlValidator` 审查写操作与系统表函数；`QueryPlanAnalyzer` 在物理执行前 1ms 扼杀全表笛卡尔积；
8. **只读事务安全执行**：`SqlExecutor` 设置 10 秒超时与只读事务，返回规整化数据集。

### 3. 全链路延迟分布（Latency Breakdown）
- **大模型生成（Generation）**：占总耗时 **89%~90%**（11 秒以上）；
- **Java 内部计算（检索、BFS、斯坦纳树、AST 校验）**：**< 20 毫秒（占总耗时不足 1%）**；
- **只读数仓查询（Execution）**：约 20~50 毫秒。
- **面试要点**：优化系统响应的核心矛盾在大模型身上，必须通过**二级语义缓存削峰**与**大小模型级联分流**来突破。

## 二、 Schema 检索、列剪枝与连通性修复（图遍历第一道防线）

### 1. 为什么不能直接把全量 DDL 喂给大模型？
- 37 张表全量 DDL 超过 8000 个 Token，不仅 Prefill 耗时长达 3~5 秒、成本暴增，更致命的是**触发大模型注意力稀释（Lost in the Middle）**，大模型极易在无关列中产生幻觉。

### 2. 连通性修复（`repairConnectivity`）怎么连？
- **业务痛点**：用户问“*各大区的商品销售额*”，词法命中了 `regions` 和 `orders`，但没提中枢表 `customers`。两张表在图上是不连通的孤岛。
- **算法三部曲**：
  1. **连通分量染色**：在已选表子图上跑 BFS，将彼此连通的表划入同一个圈子。第一个圈子编号为 **0 号分量（0号岛屿）**，孤立表为 1 号岛屿；
  2. **多源 BFS 波前推进**：把 0 号岛屿里的**所有表同时压入队列 `frontier` 作为起点**，向全图外键网络做波浪式扩散。**第一次撞到 1 号岛屿的节点时，在数学上绝对是两岛之间的“最少跳数（Hop Count）最短桥梁”**！
  3. **路径回溯与身份标记**：沿 `parent` 指针反向回溯，提取缺失的中间表（如 `customers`），标记 `score = 0.0`，证据为 `“连通性修复：补桥接表”`。

### 3. 多路径如何裁决？
- **第一级（跳数最少）**：多源 BFS 天然保证优先命中补表最少的路径（补 1 张表绝对优于补 2 张表）；
- **第二级（边权优先）**：斯坦纳树规划中物理外键（1.0）优于业务软关联（2.0）；
- **第三级（预算熔断）**：默认最多允许补 2 张表（`bridgeRepairMaxTables`），超限整条放弃，绝不无限扩张。

### 4. 极端边界：多个孤岛与彻底无法连接的表
- **多个孤岛（如 A、B、C 互不相连）**：外层 `while` 循环进行**滚雪球式迭代合并**。第一轮连通 A 和 B 并把它们合成一个大岛，**下一轮立刻重新染色，将合体大岛作为统一的 0 号分量**继续寻找 C，直到全连通；
- **物理绝缘孤儿表（无任何外键连通）**：多源 BFS 搜遍全图后队列跑空，`frontier.isEmpty()` 触发 `target == null` 判定，方法立刻返回空列表，**外层命中 `if (bridge.isEmpty()) break` 瞬间优雅退出**，耗时 < 0.5ms，绝无死循环风险。

## 三、 外键拓扑与斯坦纳树规划（图算法第二道防线）

### 1. 连通性修复 vs 斯坦纳树：根本区别是什么？
| 维度 | 连通性修复 (`repairConnectivity`) | 斯坦纳树规划 (`JoinPathPlanner`) |
| :--- | :--- | :--- |
| **流水线阶段** | 检索召回层（第一阶段） | 组装规划层（第三阶段） |
| **核心职责** | **选点（拉人入伙）**：把缺失的中间表拉进候选名单 | **选边（排兵布阵）**：规划出总权重最小、无环路的具体连接树 |
| **数学模型** | **无权图**（只看有无拓扑连接） | **带权图**（物理外键=1.0，业务字典软关联=2.0） |
| **算法实现** | **无权多源 BFS** | **带权多源 Dijkstra + 换根多起点重启（Multi-start Restart）** |

### 2. 为什么贪心连表算法会死锁？
- 传统的局部贪心算法（如 Kruskal）只看局部当前最短边，在 4 表以上环形图（如 orders - customers - sellers - payments）中极易选出包含死锁环路或多余伪支路的次优解；
- 斯坦纳树算法引入**换根重启（Candidate Roots Restart）**：分别以每一个核心业务表作为树根（大本营）跑一遍多源 Dijkstra，全局比较所有生成树的总边权，挑出代价绝对最小的一棵树。

### 3. 量化战果
- 3 表关联准确率达到 **100%**；
- 4 表及以上复杂深层查询（T5 难度层）准确率从初始基线的 **50% 暴增至 90.91%**。

## 四、 提示词工程与 Few-shot 动态注入机制

### 1. U 型注意力分布曲线（U-shaped Attention Curve）与首尾效应
- 大模型对超长上下文两端的敏感度极高，对中间部分容易产生注意力涣散（Lost in the Middle）；
- **布局编排**：
  - **头部（首因效应）**：系统角色定位、核心方言规则（PostgreSQL 时间函数）、强制规范；
  - **中部（低注意力区）**：容错率较高的表结构 DDL、辅助元数据；
  - **尾部（近因效应）**：**Few-shot 示例、动态外键清单、用户当前问题原文**，确保大模型带着最新鲜的连表与语法范式生成 SQL。

### 2. Few-shot 示例的 Jaccard 相似度重叠保送（`ExampleSelector`）
- **三级偏序比较器**：
  $$\text{共同表数量降序 (Overlap DESC)} \to \text{Jaccard 相似度降序 (Jaccard DESC)} \to \text{示例 ID 字典序 (ID ASC)}$$
- **为什么一级排序必须是 `overlap` 而不是纯 Jaccard？**
  - **防挤压设计（劣币驱逐良币）**：单表简单查询因分母极小导致 Jaccard 虚高（如 1/1 = 1.0）。如果只看 Jaccard，单表查询会把涵盖当前问题 3 张核心关联表、但带有 1 张辅助表的工业级多表 JOIN 示例全部挤死！
  - Few-shot 对 Text2SQL 最核心的价值是**教大模型怎么写表之间的 `JOIN ... ON`**，共同表越多，连表示范价值呈指数级上升；Jaccard 仅作为二级去噪（在重叠表相同时，惩罚无关杂表）。
- **两阶段两轮筛选（Two-Pass Selection）**：
  - 第一轮：严格筛选 `overlap > 0` 的示例进行保送（Top-3）；
  - 第二轮：若命中生僻表导致名额不足，自动降级补充通用高质量语法示例兜底。

### 3. 测试集防泄漏铁律（`Leakage Guard`）
- **自指作弊漏洞**：在 Benchmark 评测中，如果被测题目与 Few-shot 库中的题目文本一致，大模型会直接一字不差抄答案，评测分数虚高但上线即崩。
- **留一隔离防线（Leave-One-Out）**：
  ```java
  if (ex.question().strip().equalsIgnoreCase(normQ)) continue;
  ```
  严格剔除完全一致的题目，强迫模型参考邻近结构进行逻辑泛化，保证评估分数的绝对真实性。

### 4. 六大难度阶梯与错因映射
| 难度阶梯 | 代表题型 | 关键技术算子 | 大模型典型致命错误 |
| :--- | :--- | :--- | :--- |
| **T1 单表基础** | 简单明细过滤排序 | `WHERE`, `DISTINCT`, `LIMIT` | 字段名臆造、字符串大小写敏感 |
| **T2 单表聚合** | 分组统计指标 | `GROUP BY`, `HAVING`, `COUNT` | `WHERE`/`HAVING` 混淆、漏加 DISTINCT |
| **T3 时间窗口** | 同比环比、按月切片 | `DATE_TRUNC`, `LAG() OVER()` | 混用 MySQL `DATE_FORMAT`、除零崩溃 |
| **T4 多表 JOIN** | 2~3 表外键关联 | `INNER JOIN`, `LEFT JOIN` | 业务主键与外键连错、内连接漏行 |
| **T5 深层拓扑** | 4 表以上长链桥接 | 斯坦纳树全局规划 | 跨表臆造不存在的外键直连、笛卡尔积 |
| **T6 业务语义** | GMV、复购率、客单价 | 集中式指标字典（Glossary） | 自作主张把取消单算入成交、主键粒度搞错 |

## 五、 安全护栏、AST 遍历与执行代价防御

### 1. 为什么正则表达式防御是“防君子不防小人”？
- 正则匹配 `contains("DROP")` 会被注释穿透（`/* DROP */` 被误杀，`DROP/**/TABLE` 绕过正则），且完全无法感知语义嵌套。

### 2. 为什么选用 JSqlParser（击败 Calcite / ANTLR / Druid）？
- **零 Schema 强依赖**：仅 1.5MB 纯语法解析，不需要像 Apache Calcite 一样把全库元数据搬进内存；
- **AST 原位变异与无损反序列化**：通过 `plainSelect.setLimit(limit)` 改写后，直接调用 `select.toString()` 即可还原为标准合规 SQL（ANTLR 无法简单反序列化）；
- **Visitor 作用域识别**：`TablesNamesFinder` 原生自动排除 CTE（`WITH ...`）和子查询别名，精准只提取物理底表。

### 3. JSqlParser 深度绞杀的两大高危漏洞
- **H2 漏洞（数据修改 CTE 藏毒）**：攻击者利用 `WITH d AS (DELETE FROM orders ...) SELECT * FROM d`。顶层 100% 是 `Select`，真正的写操作藏在 `WithItem` 中。系统通过 AST 递归遍历 `WithItem.getStatement()` 彻底阻断非查询操作；
- **H4 漏洞（FROM 表函数提权）**：攻击者利用 `SELECT * FROM pg_ls_dir('/etc')` 列举目录或 `dblink` 跨库 SSRF。普通表达式 Visitor 扫不到 FROM 子句，系统挂载专用的 `FromItemVisitorAdapter`，对所有 `TableFunction` 节点实施**结构级一刀切禁绝**。

### 4. 生产级四重纵深防御体系（Defense-in-Depth）
1. **第 1 道：应用层 AST 哨兵 + YAML 常见黑名单**：在 JVM 内存 0ms 拦截已知 27 个高危函数（如 `pg_sleep`），保护数据库连接池不被无脑探测占满；
2. **第 2 道：JDBC 驱动物理装甲**：`connection.setReadOnly(true)`（内核级只读事务）、`statement.setQueryTimeout(10s)`（CancelPacket 物理强杀中断）、`statement.setMaxRows(201)`（探针防 OOM）；
3. **第 3 道：数据库引擎 RBAC 最小权限白名单（终极免人肉防线）**：账号默认 `REVOKE ALL ON ALL FUNCTIONS`，仅开白授权业务所需的聚合与日期函数。**哪怕 YAML 漏配了 1000 个流氓函数，内核层一律报 `Permission Denied` 击毙，无需人工维护黑名单**；
4. **第 4 道：只读副本与网络 Egress 物理沙箱**：直连只读从库，网络层禁止外网出站，彻底封死反弹 Shell 与 SSRF。

### 5. EXPLAIN (FORMAT JSON) CBO 预执行代价防御（`QueryPlanAnalyzer`）
- **解决核心痛点**：大模型生成 `SELECT * FROM orders, customers;` 语法 100% 合法，但在数据库里会产生 **100,000 $\times$ 100,000 = 100 亿行的全表无约束笛卡尔积**！
- **为什么只能用 `EXPLAIN`，严禁 `EXPLAIN ANALYZE`？**
  `EXPLAIN` 仅调用数据库代价优化器（CBO）看施工图纸，**耗时 < 1ms，根本不执行物理查数**；而 `EXPLAIN ANALYZE` 会真的引爆炸药去跑 100 亿行，当场把数仓打瘫痪。
- **严密防误杀条件**：
  只有当节点为 `Nested Loop`，且**既无自身 Join Filter、也无子节点 Index Cond（不是走索引的循环）、也不是 1 行标量子查询广播，且预估行数 > 1000 行时**，才铁证如山地定性为笛卡尔积并拦截！

## 六、 多并发机制、SQL 语义二级缓存与高可用

### 1. 为什么缓存 SQL 而绝不缓存查询结果集？
- **数据鲜活性（Data Freshness）是严肃数仓问数的底线**。如果缓存结果集，数仓数据更新后用户查到的是半小时前的陈旧脏数据且无任何告警；
- **缓存 SQL 复用的是大模型 2 秒的推理计算量，数据每次现查**。用数仓几十毫秒的只读代价换取 100% 鲜活真实数据，同时节省 99% 的大模型耗时与 100% 的 Token 成本。

### 2. 文本归一化（`SemanticCache.normalize`）的三处容错与两道红线
- **三处容错区（自动抹平杂质）**：
  1. 英文字母大小写（`GMV` = `gmv`）；
  2. 任意位置的空白字符、Tab、回车换行（全部折叠抹除）；
  3. **句末语气标点（利用 `+$` 尾部锚定正则 `[。？?!！，,；;：:、]+$` 剥离末尾连续标点）**。
- **两道绝对红线（触碰则 100% 判定未命中）**：
  1. **句中的字词、语序及句中逗号必须 100% 一致**！中文语序调换极易产生“主客反转”（“北京到上海” vs “上海到北京”、“客户最多的省份” vs “省份最多的客户”），坚决不用裸向量做模糊匹配，宁可重算也绝不答错；
  2. **系统配置指纹（`configSignature`）必须一模一样**：Prompt 模板、模型版本、检索 Top-K 参数被哈希进 Key 中，配置一改旧缓存自动作废，杜绝幽灵缓存。

### 3. L1 内存 + L2 数据库二级架构与细粒度并发锁
- **L1 采用进程内有界 LRU（`LinkedHashMap`）**：纳秒级读取，严格限定最大条目数防 OOM；
- **L2 采用 PostgreSQL 表持久化**：解决多实例不共享与容器重启冷启动击穿；
- **细粒度锁优化**：查 L1 内存时加纳秒级轻量锁；**查 L2 数据库的网络往返必须在锁外执行**，杜绝慢 I/O 阻塞全局并发。

### 4. 用户自带密钥（BYOK）防 OOM 内存泄露
- 针对前端传入的 `X-Api-Key` 动态客户端，采用带有容量上限的 `LinkedHashMap(accessOrder=true)`，重写 `removeEldestEntry(size > 32)`，**将外部输入决定的内存占用严格锁死在 32 个实例以内**，彻底封死攻击者伪造海量 Key 撑爆 JVM 堆内存的 DoS 漏洞。

## 七、 基准评测体系、消融实验台账与数据治理自证

### 1. 为什么评测体系只认“执行准确率”（Execution Accuracy）？
- **SQL 字符串匹配不可用**：别名不同、Join 换位、大小写不同都会被无情误杀（误杀率 > 40%）；
- **大模型当裁判不可用**：成本高昂、存在自身幻觉且不可复现；
- **执行准确率是唯一客观金标准**：生成 SQL 与标注 SQL 在物理沙箱真实执行，通过 `ResultNormalizer` 抹平浮点四舍五入（保留4位小数）、NULL 规整、无约束 ORDER BY 自动行排序对齐后进行多重集比对。

### 2. 同模型全链路消融实验台账（62% $\to$ 96% 的 34 个百分点拆解）
在底层基座模型（`deepseek-chat`）完全不变的前提下：
1. **零样本检索基线（62.00%）**：纯 Top-8 DDL 裸跑，多表题大面积死锁；

## 八、 智能体工具编排（Function Calling）与数仓探查沙箱

### 1. 为什么需要数仓探查工具？
- 静态 DDL 是黑盒：看不见枚举值（`status` 是 `delivered` 还是数字 `1`）、看不见缩写（圣保罗是 `SP` 还是 `Sao Paulo`）。

### 2. 五大只读探针定义与物理沙箱隔离
- **`INSPECT_TABLE`**：看表结构 + 前 5 行真实样例；
- **`INSPECT_COLUMN`**：查指定列的真实高频枚举值分布；
- **`SAMPLE_QUERY`**：试跑只读小查询（硬编码 `LIMIT 5`，3 秒超时强杀）；
- **`CHECK_JOIN`**：检查两表在给定条件下能否匹配出数据；
- **`EXPLAIN_QUERY`**：查看执行计划预估代价。
- **安全沙箱**：连接强制 `setReadOnly(true)`，规范表名从 Catalog 提取重构防注入，工具抛错作为 `Observation` 回传给模型而不是让应用崩溃。

### 3. 防死循环熔断与 DeepSeek 思考模式避坑
- **轮次熔断**：单次请求最多允许 2 轮工具交互，超限强制收口定稿 SQL，杜绝 Token 盗刷；
- **DeepSeek DSML 泄露防线**：最后一轮如果把 tools 物理拔掉，DeepSeek 思考模式会把工具意图打印为内部标签 `<｜｜DSML｜｜ calls>...` 导致语法校验崩掉；系统在最后一轮依然挂载工具，但注入一次性定稿提示词，兼顾协议兼容与确定性收口。
