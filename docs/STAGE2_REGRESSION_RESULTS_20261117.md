## 技术与设计导读

**请求与数据流。** “复购率是多少（下单2次及以上用户占全部下单用户）”先通过已有分母证据判断，再经检索与指标匹配，单个METRIC repeat_rate携带PERCENT/2进入提示，模型生成先按customer_unique_id汇总订单、再计算100×复购人数/下单人数的SQL，经过AST/EXPLAIN和只读执行输出3.04。用户明确要求小数时应输出0.0304。真实专项两种均通过，但不能证明其他指标或其他问题都遵守规则。

**技术、身份与优先级。** Metric.OutputUnit/outputScale、metrics.yml与PromptTemplate规则12/17实现输入契约；用户显式单位优先于当前指标默认，指标默认优先于未注册通用比例默认。单位挂在具体Metric上，不扩散到同一结果其他金额/人数列。原指标定义SHA进入配置与调用观测，promptSha256追踪真实发送输入。EntityPolicy区分customer_id连接键和customer_unique_id真人身份。它们是生成约束，不是SQL血缘证明器或响应后处理。检索directHits/expandedTables、0.4关系衰减、Top-K及最多2张桥接不变，冻结前200题检索上下文一致。

**收益与损失。** 原T3-002形状和T6-003单位已由真实专项证明修复；同时三轮均值86.33%不达标，说明全局默认规则的收益与代价必须同时交付。问题不只在模型慢：26次已执行答案不匹配需要处理语义边界，不能等延迟优化自然解决。

**边界防线。** PERCENT为原比值×100，DECIMAL_RATIO为原比值；不能看到0.03就自动乘100，因为0.03%本身可能正确。零分母返回NULL，增长率可负或超过100；不静默转置返回结果，不从Gold反馈给生产纠错。Top10边界并列和绝对变化/增长率等仍需显式契约。新规则不能凭关键词覆盖已经明确的请求或指标身份；本轮稳定失分是继续收窄适用边界的证据。

**替代方案与面试。** 不用放宽评分、删超时题、单轮择优或后处理把结果“修对”；这些会隐藏接口和口径问题。面试问“专项全过为什么仍不交付？”——先修目标题只证明局部行为，300次回归暴露净退步4.67pp，必须按预注册门槛否决。问“为什么不把所有客户统一去重？”——存储行、自然人、评价记录和订单是不同事实对象，业务词义与默认结果契约必须一致，不能用同一个去重规则覆盖所有计数。
