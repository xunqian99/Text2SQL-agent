## 技术与设计导读：一个请求怎么走

输入：`容量最大的仓库是哪一个？`。

1. 原澄清和检索链路取得仓库Schema；首次生成示例为 `SELECT warehouse_id FROM warehouses ORDER BY capacity DESC LIMIT 1`。
2. 原AST只读校验允许该SQL，数据库也能执行。启用结果检查时，新 `ExtremumProjectionChecker` 用当前问题、已校验词典和真实Schema绑定“仓库/容量”到 `warehouses.capacity`。**返回属性值来自产品实体寻优默认，不冒称用户显式要求了一列。**
3. 检查最外层SELECT。`ORDER BY capacity`只用于排序，不等于结果中返回容量；因此产生 `MISSING_EXTREMUM_ATTRIBUTE`，反馈保留产品契约版本、词典用语和真实字段来源。
4. 沿用既有自纠错机制，预算允许时最多再调用一次。示例修复为 `SELECT warehouse_id, capacity AS volume FROM warehouses ORDER BY capacity DESC LIMIT 1`；别名volume不会影响字段来源判定。
5. 第二次必须确认属性原值已进入输出且通过原有检查，才能替换首次。仅将warehouse_id改名capacity仍是遗漏；`capacity*0`等未支持表达式是UNKNOWN，不能当作修复，保留首答并累计两次费用。当前响应沿用原SUCCESS与“纠错失败保留首答”策略，**没有新增“语义正确”状态，也不承诺已知漏列一定被修好**。

HTTP验收覆盖成功补列、假别名仍漏列、复杂表达式无法确认、CTE补列、显式只要编号、首次已完整六条路径。两条保留首答的路径仍返回缺列，正是用来证明不会把无法确认的第二次答案冒充修复，而不是证明业务答案正确。

## 用什么实现，来源如何保留

- `ExtremumProjectionChecker.Requirement`：保存policy、tableAlias、columnAlias和真实 `Field(table,column)`。词典只负责语义映射，真实Schema还需证明列存在且为受支持数值类型；词典文本不能自己创造一个字段。
- `Decision`：明确区分NOT_APPLICABLE、PRESENT、MISSING、UNKNOWN。PRESENT只证明本项原属性出现在投影里，不证明排序、过滤、实体身份、Join或整条SQL正确。UNKNOWN既不判错，也不变成通过证明。
- JSqlParser 5.4：沿用已解析验证过的依赖，无新库。追踪直接列经过表别名、非递归CTE、CTE列重命名、派生表和普通星号后的来源；WHERE、ORDER BY、GROUP BY中的列不进入外层投影凭据。常量即使别名为capacity也没有目标字段来源。
- `ResultChecker.checkCorrection`：首答已证实遗漏后，纠错必须得到PRESENT，不能把UNKNOWN当修复。其余原有金额、比例、空结果等检查保持执行。
- `Text2SqlOrchestrator`：缓存命中同样接受启用的结果检查；可疑缓存回退生成，已知可疑的最终SQL不再写入缓存。缓存标识增加检查器开关和版本，`EvalRunner.effectiveConfig`记录 `resultCheckerPolicyVersion`。这是检查策略版本，系统Prompt仍为p19，不能伪装同运行版本重跑。
- 当前有效问题用于结果契约；带 `SessionContextSummary` 的文本继续供生成与纠错使用。历史摘要的“合计”等词不能凭拼接抹掉当前明确请求。本批不把摘要当新用户指令，也未实现全局输出偏好继承；复合/长期偏好仍需明确重述。

本批未更改Schema检索权重、directHits/expandedTables身份、0.4关系扩展衰减、Top-K、桥接上限2或任何题号分支。候选绑定必须唯一，**不按检索分数或词典遍历顺序挑一个答案**；多个字段同样满足时直接不适用。没有新的评分或防挤压权重；不能拿检索置信度替代语义证据。

## 边界与代价

当前只接受已声明的单句语法，例如“容量最大的仓库是哪一个”“哪个仓库容量最大”“仓库容量最大的是哪一个”，可带有限的查询前缀和标点；500字符以上直接不适用。数值属性及实体名称来自原词典，不在运行时代码写死warehouse、capacity或题号；会员积分等字段可以通过相同机制适用。

用户显式只输出某列、否定、复合指标、平均/合计/增长率、TopN、比较候选及语法未覆盖的表达不补隐含要求，避免误把“容量最大的仓库里哪个会员……”的排名属性转移给会员结果。该识别是保守有限语法，**不是通用中文语义解析**，召回低是明确代价；原题实测只有1/200适用。

非直接表达式（包括ROUND、CAST、CASE）、标量子查询、集合运算、递归CTE、NATURAL/USING关联、未知表、歧义列名或无法展开的别名列表均保守UNKNOWN。SQL超过20,000字符或追踪深度超过12也放弃判断。没有证明算术等价、NULL语义、排序正确或实体标识完整；别名正确并不足以过关，出现函数也不自动判错。引用同名列或CTE遮蔽时来源必须能唯一追踪，不能只搜索SQL字符串。

检查在首答执行之后，所以无法节省首次调用；命中后可能多花一次模型调用与数据库执行。仍受15秒请求预算、最多2次调用、重试剩余时间及原DeepSeek逐次时段门禁限制。UNKNOWN的首次结果不触发新纠错，已知遗漏但无法修复的结果不缓存。**无法根据本次免费验证声称延迟或成本下降**；新一次真实评测须计入新增纠错Token及未知用量。

这里只覆盖启用了ResultChecker的普通生成/纠错/缓存链路；旧基线关闭检查时不改变行为，不声称独立工具循环已有同等输出契约。SQL安全仍由独立只读校验和只读账号负责，语义检查放弃判定不表示安全层也放行不安全SQL。

## 为什么这样做与面试追问

没有按结果列名寻找capacity，因为 `warehouse_id AS capacity`就能骗过；没有在全部SQL文本中搜索capacity，因为它可能只在排序、过滤或内层计算出现。没有直接改写SQL加列，未知聚合或分组下强加列可能改变结果甚至执行失败。选择有限来源追踪加有界纠错，换来可解释信号，代价是覆盖窄、部分正确复杂表达式无法被确认修复。

**追问：为什么UNKNOWN的首答不纠错，纠错答案UNKNOWN却不采用？** 首答UNKNOWN没有足够证据判错，不能无端花钱；但首答已确定MISSING后，第二次必须提供修复证据才能替换。证据门槛与“是否已经确认有缺陷”相关，不能用“没再报错”偷换“已修好”。

**追问：这不就是只修一题的过拟合吗？** 若只报告T1-028变过就是过拟合叙事。本实现读取已有词典和真实字段、采用同一实体寻优契约，没有题号/Gold分流；58项边界及7项编排测试验证机制。仍只覆盖原集1/200，也没有新模型准确率，所以必须公开范围，后续独立题或盲测才能判断泛化，不能据此宣传整体修复。
