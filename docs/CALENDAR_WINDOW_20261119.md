## 1. 核心机制与具体请求

请求：“最近30天内有登录记录的会员有多少人？”

1. 现有检索选择会员事实与`last_login_date`。`SchemaCatalog`读取真实库范围并缓存；`DatabaseSchemaReader`的画像明确“订单范围仅属于订单事件”，不能把订单最大时间借给会员登录。
2. `PromptTemplate`规则14指定N个自然日，包含参照日D，区间为`[D-(N-1), D+1)`。未给参照时，历史快照以**所查业务事件的源事实时间列全表MAX**为参照，先确定参照，再筛业务子集；明确日期、今天/现在、时刻或参照范围可覆盖默认。
3. 现库会员登录参照D=`2018-10-23`，起点`2018-09-24`，排他终点`2018-10-24`。推荐SQL：

```sql
WITH anchor AS (SELECT MAX(last_login_date) AS d FROM members)
SELECT COUNT(*)
FROM members CROSS JOIN anchor
WHERE last_login_date >= d - 29
  AND last_login_date < d + 1;
```

数据库结果为`4321`。对DATE列，旧Gold的`> MAX(last_login_date)-30`在这个库里与上述自然日窗口等价；错误的`>= MAX(...)-30`会多含一天，算出`4458`，多出的边界有137人。

这是**给模型的输入契约**。SQL仍由模型生成，经过现有AST只读校验、数据库执行和结果检查。此次没有实现通用时间SQL证明器；模型仍可能生成不遵守窗口的SQL，不能把示例SQL成功执行冒充真实模型已修复。

## 4. 边界与设计权衡

- **自然日与滚动时长分开**：最近/近/最后N天默认自然日；明确“滚动N×24小时”或“从参照时刻A回溯N天”才使用`(A-N×24h, A]`。明确开闭边界优先。不能把所有窗口强改为左闭右开，恰好等于参照时刻的真实记录不能被默认排除。
- **N=1与闰日**：N=1只含参照当天；日期算术处理月份、闰年与跨年。窗口中的N须为正整数；本批没有通用自然语言参数校验器，非法N仍属于后续输入处理边界。
- **BETWEEN**：只包含SQL给出的两个端点。时间戳`BETWEEN '2024-02-29' AND '2024-03-01'`只到3月1日零点，不会包含3月1日整天。整月用下一月零点作排他边界。
- **NULL与空集**：全表时间均NULL时不换成今天；比较无匹配事实，COUNT为0，AVG/SUM保持SQL各自空集语义，不能全部补0。
- **过滤范围**：默认全表MAX防止每个州/状态自行取不同参照日；用户明确要求子集参照时必须服从。相同字段可能服务不同事件，复杂多事件问题仍需明确每个窗口归属；不是选一个最大时间套整条SQL。
- **时区**：现库相关DATE/无时区时间戳按存储的本地日期解释；没有新增业务时区配置、DST推导或跨时区转换保证。用户指定时区时服从；数据不含时区语义时不能声称能还原真实瞬间。
- **旧Gold冲突**：T3-013（dev）和T3-014（eval）用连续90天。自然日订单9,440，旧窗口9,529，差89单；首周商品金额80,898.44 vs91,737.32，差10,838.88。按新契约回答仍会被旧评分判错，原失分保持。不能暗中把“最后”特判为旧Gold窗口来追分。

未选“全部按最大时刻减N天”，因为DATE没有参照时分秒，而日级业务报表通常需要包含参照日的固定N个日期；未选“所有最近N天都先澄清”，因为已有合理、可公开的产品默认，明确要求可覆盖。未增加正则SQL重写器，因为任意CTE、多窗口、时区和子查询无法靠字符串替换可靠证明，错误改写比公开限制更危险。

## 5. 面试答辩

**问：左闭右开为什么还会多算一天？** 开闭符号本身不定义业务长度。含参照日D的30个日期从D-29开始；`[D-30,D+1)`有31个日期。必须同时交代参照、起点、终点和字段类型。

**问：如何证明模型已经会按这套规则生成？** 目前不能。工程测试证明输入传递和数据库表达式，真实模型需要在固定版本及允许时段另测；先解决[原验收标准互相冲突](EVALUATION_CONTRACT_ERRATA_20261119.md)，不能在一个条件上限86%的旧评分下花钱追89%。
