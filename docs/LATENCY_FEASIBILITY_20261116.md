# 阶段3：简单路由与上下文叶子裁剪的离线可行性

## 决策与范围

**不实现“仅简单请求关闭思考”的生产路由；不将叶子表裁剪接入生产。** 前者即使给定不现实的零耗时上界，也不能解决已有P95拖尾；后者只在离线缩短了用户消息，未证明模型更快或更准。阶段3未通过，不进入阶段4。

本轮只增加离线诊断脚本、探针与文档，业务代码和默认配置未改。没有改原200题、另100道候选题、Gold、few-shot文本或历史分数，没有新增评测题。**新增模型调用0次、Token 0、模型费用0元**。下面的历史记录、乐观推算和当前上下文检查分开解释，不能混成一次新模型实验。

证据目录：`reports/latency-routing-feasibility-20261116/`。当前业务源码来自`a963297`，运行时新增的离线探针/脚本源码由归档清单指纹标识，随本次提交一并版本化。用户演示文件的原有删除/未跟踪改动保留。

## 1. 简单题加速为什么动不了P95

`scripts/analyze_latency_routing_feasibility.py`先重审三个归档开发实验的报告、调用账目和输入指纹。每份取**原dev100的默认组**，不读eval结果调规则，不把三份合成300个独立问题。

对每一份100题的墙钟时延，使用与原评测相同的最近秩定义：排序后第 `ceil(0.95 × 100)=95` 个值。阶段门槛是严格小于8,000ms，因此最多允许5个请求达到或超过8,000ms。不是把95条“成功请求”单独取分位数。

乐观假设：T1单表基础、T2单表聚合和T3时间窗共54题都变成**零耗时**，分类完全正确、路由开销也为零；其余46题保持原观察。难度标签只用于这一离线边界计算，**生产没有这些标签**，不允许拿题目ID或Gold判断是否简单。

| 历史开发实验默认组 | 原P95 | 54题归零后的乐观P95 | 剩余≥8秒的复杂题 | 至少还要改善多少道复杂慢题 |
|---|---:|---:|---:|---:|
| generation-mode-screen | 11.198秒 | 11.198秒 | 12 | 7 |
| low-reasoning-screen | 15.001秒 | 13.690秒 | 12 | 7 |
| prompt-directive-screen | 15.004秒 | 15.004秒 | 14 | 9 |

最后一列是 `max(0, 剩余复杂慢题数 − 5)`，表示至少让这些请求跨过8秒界限的必要条件，不保证做到后准确率或费用就合格。不能把“几道最慢题优化一些”说成整体验收完成。

三份历史慢题的请求级记录中，MODEL阶段分别占慢题总墙钟的98.92%、99.17%、99.21%。MODEL包含服务端等待、网络与生成，并非供应商内部纯推理耗时的测量。记录支持先研究复杂请求的生成输入，而不是优化仅占毫秒的本地路由。

**限制**：这是不同历史提交上的观察。会员指标定义已在后续修正，未用本轮数据测当前模型P95；这些数字不是当前性能承诺，更不是新准确率。路由真实实现还可能误判并增加开销，上面给的是刻意过于乐观的假设。

## 2. 叶子表裁剪怎么检查

`ContextLeafFeasibilityProbe`读取当前真实库Schema与原dev100，构造与默认相同的实际检索、列剪枝、指标注入和两条示例；只在离线内存中构造候选上下文。它不创建模型客户端，也没有注册到生产Provider。

例如请求“订单总数”直接命中orders，同时关系扩展可能带入若干相邻表。候选不是把所有相邻表当作无关噪声直接删除，而是保留以下不同来源凭据：

- `directTables`：检索证据中排除了 `expandedTables` 的直接命中表。
- `metricTables`：本次适用指标所需的全部表。
- `valueTables`：实体/枚举取值提示所引用的表。
- `exampleTables`：本次参考示例SQL经JSqlParser解析得到的真实表。
- `protectedTables`：以上集合的并集；来源集合单独存储，没有压成无法解释的一个分数。

候选只迭代移除关系图中**不受保护、且当前邻居数≤1**的节点；按表名排序记录每轮删除集合。这类叶子不能成为另外两个保留节点之间的桥梁。多条列关联同一张邻表只计一个表邻居；度数是表级邻接，不是Join边条数。

这里不改检索分数、0.4扩展衰减、Top-K或比较器，不用低分截断“挤掉”受保护表，也没有以Gold表名单指导删除。桥接节点若仍连接多个保留节点便不会被当作叶子裁掉；若候选删除了推荐Join计划的端点，就回退原上下文。无检索证据、无保护目标、保护依赖不在原上下文也回退。密集环路可能全部保留，这是一项保守策略的局限。

之后才用Gold SQL解析出的期望表检查召回。Gold不参与候选选择；它只是开发阶段的离线检查。期望表不是业务必要表的完美标签，Gold里也可能有冗余Join，因此召回检查只能作为一道约束，不能代替真实SQL准确率。

## 3. 实测结果及新发现

| 检查 | 结果 | 解释 |
|---|---:|---|
| 开发问题数 | 100 | 对全部题离线组装上下文，包括在线可能先澄清的题 |
| 表全召回 | 原96/100，候选96/100 | 原4道缺表仍在，没有新增漏表；不是96%模型准确率 |
| 改变表集合的问题 | 36 | 总计移除83次表出现，不是83张不同物理表 |
| 用户消息长度之和 | 222,636→210,610 | 减少5.40%，包括Schema、示例等用户消息正文 |
| 三组历史慢题对应的当前用户消息缩减 | 1.25% / 2.68% / 1.15% | 以旧慢题ID定位当前上下文；没有测裁剪后的时延 |
| 安全回退 | 59/100 | 原上下文缺少受保护依赖；全部保留原文 |
| 当前默认消息与先前预捕获消息指纹 | 99/100一致 | 唯一变化T6-005对应已提交的会员指标修复 |
| 编译 | test-compile通过 | 编译了新离线探针，生产Java源码未修改 |
| Python离线审计 | 84/84 | 既有74项＋本轮10项分位数/边界/证据检查 |

长度单位是Java UTF-16 code unit，**不是Token**；总提示词还包含系统消息，整体缩减比例会更小。长度和生成耗时并非线性关系，因此既不宣称“加速5.40%”，也不凭缩短幅度证明一定无效。基于当前证据，该裁剪不作为下一项生产改造的优先方案。

59次回退均为 `PROTECTED_TABLE_OUTSIDE_CONTEXT`。`directTables`、本次适用指标和取值依赖已经约束在当前可用表内，额外依赖来自参考示例SQL。例如T1-004的当前Schema未包含support_tickets/ticket_categories，但选中的示例引用了它们。

`ExampleSelector`现有行为是：先按共同表数降序，再按Jaccard降序，最后按示例ID排序；不足两条时还会补充零重叠示例。**共同表多不等于所需表全部可用**，Jaccard也不是可用性保证。这里的0.4扩展衰减属于Schema检索，与示例Jaccard是两套机制，不能混为一个权重。

这是明确的上下文一致性风险，不能直接判定每条示例有害：跨表示例可能传授有用结构，硬过滤也可能丢掉有帮助的范式。没有真实对照，不能声称59题都答错，更不能给选择器造成的准确率损失编数字。

## 5. 设计权衡、面试答辩与下一步

**为什么不先把简单题提速再说？** 它可能改善平均耗时和成本，但阶段3首先要解决P95。当前样本即使给简单题零耗时，仍有12–14个复杂慢请求；必须处理复杂请求才能跨过门槛。这个决策不声称简单题路由永远无价值，只拒绝把它当作当前P95的解决方案。

**为什么不直接删所有扩展表？** 图上关联、用户直接提到和Join桥接是不同身份。删除所有扩展表可能切断必要连接或隐藏事实表；本轮保留来源、保护依赖，只裁叶子，且拿开发Gold检查新漏表。连通性得到保护也不等于SQL语义正确。

**为什么不因为表召回没降就发布裁剪？** 召回只是必要信息是否存在，无法证明模型遵循、聚合粒度正确或时延改善。当前收益主要落在非拖尾题，关键慢题的用户文本只减约1%–3%，没有真实模型证据。

下一步仍限阶段3：针对“参考示例引用本次Schema之外的表”建立可选的候选筛选策略，保留现有选择器为对照；优先明确空候选、SQL解析失败、大小写和CTE表名边界，再冻结开发集单因素实验。保持题目与示例文本不动，不在eval上挑规则，也不预先宣称这会解决P95。只有开发门槛通过才讨论正式三轮。

本轮无需用户新增配置。用户应能核对：P95为什么最多允许5个≥8秒请求；图里哪些表是直接命中、扩展、桥梁或示例依赖；本轮模型调用成本为什么为0。不要把“诊断排除两个方案”描述成“性能已经优化成功”。
