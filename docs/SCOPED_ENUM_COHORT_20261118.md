本批代码提交 `63256a9`。修的是生产输入链路，不是题库或评分。Java最终1,041/1,041、9组真实PostgreSQL反例通过、Gold执行自检200/200；模型0调用、Token 0、费用¥0。尚无本版本模型准确率，最新正式结果仍为78.00%＜89%，阶段2未验收，阶段3延迟优化继续暂缓。

用户已明确：只说“销售额”而未说明运费时，继续询问用户，不设置默认口径。本批保留该行为，不为减少澄清失分改变它。

## 1. 实质缺陷和请求数据流

例：“2018年每个月的GMV中，新客和老客各贡献多少？”

旧链路存在两处确定的输入问题：业务词典注释里的动态新老客定义没有渲染给模型，而“新客”无条件映射到静态标签`NEW_USER`；“GMV中”的“中”又被识别为工单优先级2。原始提示存在这些问题，不等于已经证明其中某一条独立导致了历史失分。

当前链路：

1. 原表检索照常进行，得到候选表及分数。词法检索仍可能召回user_tags、support_tickets，不能宣称本次消除了无关候选表。
2. `ValueRetriever.matchEvidence`逐个记录别名出现位置、目标表列、物理值、相邻字段证据和接受/拒绝原因。裸“新客”缺标签语境，拒绝静态映射；“中”缺工单优先级语境，拒绝过滤映射。
3. 只有`ACCEPTED`记录生成过滤提示、支持枚举列保留及相应JOIN目标。列剪枝与计数输出契约不再自行扫描原标签而“复活”被拒绝值。明确列名、主外键及其他保留理由仍独立有效。
4. `MetricRegistry`识别动态新老客，提供`customer_cohort`定义，依赖orders和customers。GMV由独立指标提供order_items及金额口径。
5. 模型收到完整历史首单月定义：通过订单的customer_id读取档案，再按customer_unique_id跨档案找首次有效下单月；之后才筛2018年报告期。首月的全部有效订单算新客贡献，后续月份算老客贡献。
6. 模型生成SQL，仍经过原只读校验、数据库执行和结果检查。预期响应形如“月份、新客GMV、老客GMV”，具体行列按用户请求决定；本批没有实测模型输出，不能把这个预期写成已达成结果。

另一请求“带新客标签的用户GMV”仍生成静态标签提示，局部标签语境排除动态定义。混合请求“新客标签用户中，按首次下单月区分的新客和老客GMV”可以同时保留标签过滤与动态分类，前一处标签提及不吞掉后一处动态提及。

## 2. 技术抓手与来源防线

| 组件 | 本批职责 |
| --- | --- |
| `AdjacentContext` | 有界相邻词证据，记录命中词与位置；共用局部规则 |
| `Glossary.EnumValue.requiredAdjacentContextAny` | 为歧义枚举配置必要语境，本批用于NEW_USER |
| `ValueRetriever.ValueEvidence` | 原文UTF-16起止位置、物理映射、上下文及Decision；拒绝记录可供诊断 |
| `ColumnPruner` | 枚举值只能凭已接受的valueMatches保留列，不从原始label补回 |
| `CountComparisonContract` | 标签绑定必须匹配已接受的表/列/值/出现位置；用户明确物理编码仍独立识别 |
| `Metric.excludedAliasContextAny` / `MetricRegistry` | 按别名每次出现的位置判断局部排除，其他指标保持原匹配方式 |
| `metrics.yml customer_cohort` | 首次有效下单月推荐查询、未知组与事实覆盖约定 |
| `Text2SqlOrchestrator.cacheSignature` | 加入`scoped-enum-v2`，包括关闭语义层时也隔离旧匹配缓存 |

身份不能混淆：`ValueEvidence`是枚举来源凭据，`MetricMatch`是指标命中/排除凭据；原表检索`directHits`/`expandedTables`是另一层来源。三个层次没有扁平混在一起。枚举记录保留原文偏移；指标局部检测使用原有空白归一化文本，不能把其内部位置宣称为用户原文位置。

本批没有新增权重或Top-K。原关系扩展0.4衰减、单字权重0.5、标识符权重1.5和排序策略不变；原200题的表列表、分数、扩展集合全部未变。枚举索引保留长别名优先：已接受长词包围的单字不会再变成第二个过滤值；去重键是`table.column=physicalValue`，同列中/高/低三种值不会互相挤掉。这不是分数提升或“保送”策略，而是匹配合法性检查。

## 3. 明确的边界，不能包装成通用语义理解

- 相邻证据最多跨32个UTF-16字符，只允许有限连接/赋值/枚举字符；字段在前时支持“优先级为中、高和低”。字段在后时只允许空白及“的”，不跨逗号倒连，支持“中优先级”。复杂长句可能漏识别。
- 当前是词法启发式，不是语法解析器。类似“GMV中优先级为高”这种无标点连续文本仍有歧义；不能声称所有“中/高/低”误匹配已经消灭。被拒绝值只是不提供确定性映射，模型仍可能自行猜错，SQL安全校验也不能证明业务口径正确。
- 显式“标签”语境才接受NEW_USER映射；直接写`NEW_USER`的计数对比保留显式编码路径。其他静态标签不在本次泛化范围内。
- 动态自然人身份用customer_unique_id，关联档案用customer_id，二者不能替换。订单状态默认排除canceled/unavailable，SQL `NOT IN`也会排除NULL状态；明确其他范围时首单判断与报告事实必须一致。
- 身份未知、客户关联缺失或时间缺失时分类为NULL，不能把它们合并为一个人或自动算老客；推荐结构保留有效事实。报告期日期过滤会自然排除缺时间行，不授权模型额外删去总量事实。
- 推荐结构只确定分类，不负责替模型证明金额关联无放大；商品金额、运费、GMV继续按各自事实粒度计算。
- 缓存策略版本是显式维护点；将来再次改变匹配语义需同步升级。语义资源原有SHA也继续参与启用语义层时的缓存隔离。

## 5. 替代方案与面试答辩

没有直接删除所有单字枚举：那会破坏明确“中优先级”查询。没有继续无条件子串命中：那会把普通介词“中”变成WHERE条件。没有按题号写特例或硬套静态NEW_USER：前者污染评测，后者混淆业务含义。没有引入额外模型分类调用：本次缺陷可用配置和有界证据修正，额外调用会增加延迟、费用及不确定性。

**追问：为什么先全历史找首单，不能先筛2018年？** 后者会把2017年买过、2018年再次购买的人错当新客；首单定义范围与展示报告期必须分开。答辩时拿跨客户档案、报告期前首单的数据库反例解释。

**追问：测试全绿为什么还不说准确率提高？** 这些检查证明配置被注入、映射来源被约束和推荐SQL的分类语义正确；它们没有观测模型是否服从。完整模型质量还受无关表、名称/编号输出契约、事实覆盖、超时和参考答案一致性影响，不能跨层推断。

## 6. 下一步验收路径与停止条件

1. 本批工程修复完成并提交，不因每次小编辑继续跑全套；无需用户配置外部服务。
2. 当前p18名称默认与原eval参考契约冲突、优惠参考重复计数等欠项仍未解决。本批对eval只去噪，不改变全局名称规则，不能承诺消除这些失分；先形成可执行的统一产品/参考契约处置，再固定下一模型候选，不按题号改行为、不改原Gold追分。
3. 只有下一候选与协议冻结后才在允许空闲窗口运行一次原dev100；门槛仍为总正确≥71、深层≥4/10、业务≥6/13、超时≤9。未达标不追加正式300请求，同候选不靠重复试跑等高分。
4. 晋级后原eval100三轮，均值≥89%才可关闭该准确率门槛；换行字节问题应在下一冻结前修正工作文件，不放宽旧审计。阶段3 P95暂缓及独立盲测欠项独立保留，不能用这次局部修复宣布项目整体验收。
