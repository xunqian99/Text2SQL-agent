# 阶段4：超时会话终态记录修复

## 问题、范围与验收

[20条HTTP验收](DEMO_HTTP_RESULTS_20261116.md)中，T5-002已向用户返回REQUEST_TIMEOUT，但会话turnCount=0。外层RequestBudgetRunner负责超时响应，内部工作线程负责历史追加，截止时间打断后内部末尾不再执行。纠错超时保留正确首答时也存在同样缺口。

本次只修复最终答案与内存会话收尾的一致性。不改模型、Prompt、检索/排序、Gold、原评测分数或15秒/2次调用参数，不恢复阶段3P95优化。旧20条85%及全部失败原样保留。

## 技术与设计导读

### 1. 一个请求怎样完成

例如同一会话提交“订单有哪些？”，生成阶段在15秒内未返回。预算线程先冻结耗时/账目，选定REQUEST_TIMEOUT，然后通过本请求的收尾器追加一条相同终态的历史，再把响应交给HTTP控制器。即使模型后来返回SQL，预算已经finished，工作线程不能重新完成请求；SQL不会变成第二条历史，也不会覆盖已返回的超时。

如果首答已成功，纠错阶段超时，选择器保留首答，历史也只追加首答SUCCESS与首答SQL；未知纠错调用仍保留在budget账目。若正常生成结束后只剩会话落库，先选定业务终态并写内存历史，再进入原有预算内SESSION_PERSIST。持久化超时不会将已经写入历史的REJECTED改成另一个REQUEST_TIMEOUT。

### 2. 来源标记与核心组件

- `RequestBudget.selectedOutcome`表示最终业务载荷，区别于可回退的首答`checkpoint`；前者只写一次，后者仍用于生成/纠错期间回退。它们不能混为同一份“最新结果”。
- `RequestBudgetRunner`在提交工作线程**之前**安装内存收尾器，因此工作线程容量拒绝也能进入收尾，不依赖模型线程先执行。
- `Text2SqlOrchestrator.ConversationOutcome`是单个请求独有的收尾对象，持有捕获的ConversationSession实例；`selected`保证幂等，volatile不可变metadata快照保存已完成改写、Schema复用与Schema来源。晚到线程最多更新它自己的未采用metadata，不再直接修改会话。
- 正常完成由`completeOutcome`检查截止时间后选定载荷；中断路径由`stopped`选择已完成终态、成功首答或失败响应，调用同一收尾器。选择过程受预算锁保护，不能同时写两个终态。
- 会话指针检查用对象身份`currentSession == capturedSession`，并要求尚未关闭；删除/同名重建优先，不会按字符串ID重新创建旧会话或把旧结果塞进新实例。没有新增持久化表列、依赖或跨请求幂等键。

本次没有打分、排序或Top-K改动，关系扩展0.4衰减与表来源追踪保持原样。一次完成的幂等范围是**同一进程内的一次请求**；客户端重新发送HTTP会形成新请求，不宣称跨进程exactly-once。

### 3. 效果与剩余边界

两条旧实现确定性失败从“返回1次、历史0轮”变为“返回1次、历史1轮”。纠错回退记录实际选中的SQL；正常路径无论预算开关都不重复；其他会话记录不受影响。费用与未知usage没有被历史修复抹掉。

收尾回调只允许有限内存操作，不能执行数据库、模型或网络请求，避免持有预算锁时阻塞。停止时的预算时钟在收尾前已冻结；少量内存收尾/HTTP开销不属于模型耗时，不能宣称精确硬实时。持久化仍是原有降级设计：在模型阶段超时前未进入关闭路径时，历史先保留内存，endSession不保证已经落库，调用方可随后显式关闭。重启前未持久化的历史仍可能丢失。

本次不证明同会话并发请求按发送顺序提交，不提供多用户授权/隔离；显式删除的旧会话不会被复活，因此这类操作后不强求旧请求仍显示在列表。未处理为AgentResponse的未知内部异常也不在此次终态契约范围内。

### 4. 设计取舍与面试预演

否掉的方案一是只在超时分支补一条历史：正常工作线程仍能晚到追加，容易得到两轮或错误SQL。方案二是等待工作线程写完历史再返回：不配合中断的驱动/模型会破坏预算。现在由等待线程与正常线程共享同一个只能选定一次的收尾入口，不等待晚到任务。

**问：为什么不用ConcurrentHashMap就解决？** 它只保护集合操作，不保证“选答、写历史、冻结状态”的跨步骤一致性；需要明确谁有权提交终态，以及截止时间后谁失去写权限。

**问：为何先定答案再落库？** 业务终态一旦发布给会话历史，就不能因后续收尾超时换成另一个业务状态。持久化是否及时完成由budget终止原因和关闭路径另行观察；它不应该让已知正确首答消失，也不能伪装成已持久化。

### 5. 用户核对

无需用户配置新环境变量。需能解释三个问题：超时由哪个线程返回、首答与最终终态用什么字段区分、为什么未知调用费用仍然存在。本轮没有替代干净环境、访问控制/限流、NULL语义契约和澄清误报的剩余验收。
