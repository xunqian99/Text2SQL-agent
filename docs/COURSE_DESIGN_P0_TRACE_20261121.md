日期：2026-11-21

阶段：课程设计实施计划 P0。变更性质：只读证据展示，不改变模型调用顺序、提示词、检索排序、评分器或业务数据。

## 1. 阶段结论

P0 已完成。`POST /api/ask` 的成功、需要澄清、校验拒绝、执行失败和请求超时五类终态现在都返回同一份可解释响应契约，前端在结果下方用可折叠的“执行证据”面板展示请求、检索来源、SQL、校验/执行状态、耗时、Token、费用和预算快照。

本阶段不宣称准确率提升。它解决的是“系统做了什么无法说明、失败只能看到一句错误”的展示和审计缺口。

## 2. 一个具体请求的数据流

以“2018 年每月 GMV”为例：

1. 浏览器把问题提交到 `AskController` 的 `/api/ask`。
2. `HybridSchemaProvider` 生成 `SchemaContext`。其中 `directHits` 记录问题词、别名或枚举直接命中的表；`expandedTables` 记录外键/Join 图扩展表；`metricDependencies` 记录 GMV 等业务指标依赖；`safetyBridges` 记录为连通性或安全约束加入的桥接表。四类集合保留原始身份，不压平为一个“相关表”列表。
3. `Text2SqlOrchestrator` 将同一份来源凭据挂到生成成功、澄清、校验拒绝、EXPLAIN 高风险拒绝、执行失败、生成失败和超时响应上。重试合并时沿用最终选中尝试的来源身份，避免把第一轮的表来源误报成第二轮结果。
4. `AskController.AskResponse` 将 `question` 和 `provenance` 序列化到 HTTP JSON。页面读取 `retrievedTables`、最终 SQL、`violations`、分段 `timings`、`llm`、`budget` 和四类来源集合，生成统一证据面板。
5. 如果 SQL 通过 AST、只读和代价护栏并执行成功，面板显示结果行和执行证据；如果生成失败、校验拒绝、执行失败或超时，面板仍显示已有来源和失败阶段，不伪造 SQL 或成本。

## 3. 核心实现与技术抓手

- `SchemaContext.SourceProvenance`：不可变的四类来源集合，以及 `fallback`、`traceable` 两个状态位。
- `AgentResponse`：把来源凭据作为响应的一等字段，并在 `withBudget`、`withUsage`、`withConversation`、`combineAttempts` 等复制/合并路径中继续传递。
- `Text2SqlOrchestrator`：在所有主要终态构造点附加来源凭据，保证失败也可追踪。
- `AskController.AskResponse.Provenance`：HTTP 层的只读 DTO，避免页面依赖内部检索对象。
- `index.html`：单一 `renderTraceEvidence` 渲染入口，五类终态共用同一面板；所有动态文本经过 HTML 转义。
- `AskResponseTraceTest`：验证五类终态均包含同一组来源字段，并验证重试组合不会丢失选中尝试的来源身份。

### 来源身份、权重和防挤压设计

直接命中与图扩展仍按原检索语义分开：扩展路径的分数含 `source × edge × 0.4` 衰减，Top-K 截断和二级比较器继续优先保送直接命中；指标依赖和安全桥接不参加同一 lexical Top-K。P0 只把这些已经存在的身份输出到响应，没有把扩展表重新排序，也没有让伴生表挤掉核心命中。

### 边界与安全兜底

- 旧调用点没有来源凭据时使用 `traceable=false` 的 `unknown`，页面明确显示“来源不可追踪”，不假装完成解释。
- 检索回退全量 Schema 时使用 `fallback=true`，仍保留可得到的指标依赖，并在页面提示“检索回退，来源凭据有限”。
- 没有可执行 SQL 的终态显示“本轮没有可执行 SQL”；超时保留已有 UNKNOWN 用量语义；校验拒绝和执行失败保留 `violations`/错误消息。
- 动态 SQL、问题、表名和错误信息统一 HTML 转义，避免证据面板把返回内容当成页面标记执行。

## 5. 设计权衡与面试追问

### 为什么先做证据展示，不继续调提示词

当前冻结候选的历史正式结果是 85.33% 和 78.00%，都低于原门槛。继续无证据调参会把模型问题、检索问题、校验问题和评测口径混在一起。先固定请求证据，后续任何候选才能按相同链路比较；P0 因此不承诺准确率、P95 或模型成本改善。

### 为什么不只返回 `retrievedTables`

`retrievedTables` 只能回答“最后用了哪些表”，不能回答“表为什么进来”。四类来源集合保留了直接命中、图扩展、业务指标和安全桥接的出身，才能定位是词法命中、关系扩展、口径依赖还是安全连通性导致的上下文变化。

### 面试官可能追问

1. **如何证明失败发生在哪一层？**  看终态和分段耗时：没有 SQL 多半是生成/超时；有 SQL 但被 `violations` 拒绝是 AST、只读或代价护栏；通过校验但数据库报错是执行层；执行成功但与 Gold 不一致才进入结果比较。`question`、会话 ID、模型调用记录和来源凭据共同构成一次请求的证据链。
2. **扩展表会不会把直接命中挤掉？**  不会因为 P0 而改变排序；原检索仍对扩展边使用 0.4 衰减，Top-K 及二级比较器继续优先核心命中，指标依赖和安全桥接也不参加同一 lexical 排序。页面只是把身份和结果一并展示。

## 6. 用户需要自己掌握的三件事

- **数据流**：问题 → Schema 检索/指标口径 → Prompt → 模型 SQL → AST/只读/EXPLAIN → 数据库执行 → 结果和证据。
- **调用成本**：看响应中的 `llm.promptTokens`、`completionTokens`、`totalTokens`、`costYuan` 和 `budget`；本次 Gold 自检没有模型调用，不能用 ¥0 推断真实模型成本。
- **错误归因**：先看 `status`、`violations`、`message` 和四类 provenance，再判断是表召回、SQL 生成、校验护栏、数据库执行还是结果口径问题。

本阶段不需要用户启动 Docker、提供 Key 或确认业务口径。P1 离线评测面板暂不自动开始，需在本阶段版本验收后单独推进。
