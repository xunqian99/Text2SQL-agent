# 同版本基线对照的时间门禁回补

隔离基线分支`codex/stage2-v3-baseline`以历史`1e3a11f`为起点，最终安全回补提交`3c0bda0`。它供之后同一V3参考对照使用，不改主生产、不覆盖历史91/90/92。独立审查核对13个受保护路径Git对象相同，原Prompt、检索、口径、Gold、评分、请求预算及公共运行参数保持。

实际请求先在评测入口检查北京时间；HTTP创建时再按实际目标URI检查，执行发送前再查时间。工作日09—12、14—18拒绝，保留至少120秒边界余量。比较副本保守限制所有非本机模型目标，仅本机测试替身可在高峰执行；这不表示其他供应商采用DeepSeek计费时段。

独立审查先后抓到两个真实可构造旁路：默认模型与实际覆盖模型不同、以及本机baseURL配绝对远程completionsPath。两轮失败报告完整保留；最终从实际URI决定门禁后，官方域、通用代理及绝对远程地址的高峰/跨界假发送均为0，本机和空闲假发送正常。探针注入假传输，没有访问供应商。

原完整测试490/490；两次集中相关补验64/64、65/65，最终集合492项无失败，但不是新跑一次完整492。最终JAR在北京时间11:08左右实际启动并于逐题循环前拒绝高峰，exit1、无逐题报告/调用记录；使用固定假Key而非用户Key。本批供应商调用0、Token0、费用¥0。精确时间以压缩日志为准。

边界拒绝可能被旧生成器包装为CALL_FAILED并记未知用量，这是保留的历史账目限制；不能将本地预留/未知用量当作真实计费。任何被时间门禁中断的批次保留为中断，不能拿剩余题数分母宣称准确率。安全回补后的版本也不能声称模型输出、缓存、延迟或价格与历史完全一样。

替代方案是只在外层脚本启动时看时间；它守不住排队跨高峰，因此不采用。面试问“为什么在真正发送前再检查”，答请求对象可以在空闲创建、高峰才发送；问“安全补丁是否污染基线”，答只改变准入时间，核心保护对象逐一核对，仍单列新提交与实测，模型对照必须重跑同一参考。

验证报告与原字节日志在`reports/stage2-v3-baseline-safety-20261119`，工作树保留用于后续对照。用户无需额外操作。此项只完成安全准备，阶段2和整体仍未验收，阶段3继续暂缓。
