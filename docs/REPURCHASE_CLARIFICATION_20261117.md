# 阶段4：复购率澄清改为检查显式分母证据

## 当前结论

旧规则有两个相反的问题：只要出现“分母”“两次及以上”“有效订单”就当作已澄清；而“下单2次及以上的用户占全部下单用户的比例”反而被拦住。前者把字段名、分子或过滤范围误当成分母，后者遗漏明确的除法关系。不是模型生成慢，也不是改评测集能解决。

本轮修改生产检测逻辑和业务规则，不修改原200道题、Gold、评分器或历史分数。Java670/670、66个套件，失败/错误/跳过0；新增30个分母正反例。原200题离线判定仅T6-003由需要澄清变为继续作答，其余199题不变；需澄清总数6→5。这个数字不是准确率提升。

真实protected HTTP链路8/8：明确原题及别名请求各进入模型一次，其余6条被澄清，模型调用0；8个会话均各记1轮。模型替身返回SELECT 1，只验证放行、拦截、会话和费用槽位，不是复购率生成准确率。外部调用0、费用¥0。完整20条真实模型复验尚未进行；原85%保留，阶段3 P95继续暂缓。

## 技术与设计导读

### 1. 一个请求怎么走

输入“复购率是多少？（下单2次及以上的用户占全部下单用户的比例）”：

1. 请求通过入口后，编排器在检索、首次生成之前调用`AmbiguityDetector.clarificationFor`。多轮改写在此之前，故不能把所有澄清响应都宣称为绝对0模型调用；本轮HTTP使用全新会话，不涉及改写。
2. 判定副本做NFKC、小写与去空白，兼容全角数字/空格；问题原文不被改写。命中复购率规则，其别名包括回购率、重复购买率。
3. `requiredEvidence.denominator`的模式识别到“占全部下单用户”，记录required-pattern来源、denominator组和匹配文本。没有否定、疑问或备选项，因此允许原流程继续。
4. SQL生成、AST、EXPLAIN、执行与结果检查沿用原逻辑。放行只表示分母已给出，不承诺模型生成正确或用户指定的分母一定能在本库实现。

反例“复购率只统计有效订单，下单两次及以上的用户”有过滤和分子，但没有分母证据，返回NEEDS_CLARIFICATION；“全部下单用户还是注册满30天用户做分母”即使出现正证据，仍因备选关系被拦住。

### 2. 组件、来源与判定公式

- `schema/ambiguities.yml`：复购率改为显式证据规则，新增别名、必需证据组及不确定/否定模式。销售额、活跃用户继续沿用旧hints规则，本轮没有把所有口径改成新的语义解析器。
- `AmbiguityDetector.load`：启动时编译可信配置中的正则，缺证据组名称、空模式、重复组或非法正则拒绝加载，避免每次请求编译。没有调用模型做意图判断，也没有新增依赖。
- `decisionsFor`：输出`Decision`，包含主规则term、实际matchedTerm、`evidence`、`missingGroups`、`unresolvedEvidence`。`Evidence.source`区分legacy-hint与required-pattern，保留组名和命中词句；判定不是扁平的true/false黑箱。
- `clarificationFor`：兼容原接口，返回第一个未解除歧义的规则提问。规则顺序与原配置一致；没有按题ID、SQL或Gold决定是否放行。

显式规则的布尔逻辑为：

```text
groupMatched[g] = OR(该组各pattern是否命中)
resolved = AND(所有必需组groupMatched[g]) AND NOT(任一unresolvedPattern命中)
needsClarification = term或alias命中 AND NOT resolved
```

复购率目前只有denominator一个必需组。没有分数、Top-K或“多几个关键词就补够分”的阈值；出现再多分子词也不能挤掉缺分母事实。否定/不确定证据有否决权，正证据不会靠数量冲掉它。未配置证据组的旧规则仍是hint OR，不借本次修复宣称它们已经具备完整语义能力。

没有改变`directHits`、`expandedTables`、检索分数或Join策略；规则在检索之前决定是否继续，旧规则误拦截时根本没进入表检索，不能归因为漏召回。

### 3. 效果、数字与边界

| 项目 | 数字 | 可得结论 |
|---|---:|---|
| Java全量 | 670/670 | 无失败/错误/跳过，原53条SQL对抗保留 |
| 新增边界用例 | 30/30 | 11个明确分母、16个缺失/不确定例、3个证据来源和优先级契约 |
| 原200题影响检查 | 199不变、1条解除误拦截 | T6-003可进入生成，不等于该题真实模型必然答对 |
| HTTP与会话 | 8/8 | 2个明确问题进入生成、6个需澄清问题不进入生成，8个历史各1轮 |
| 外部模型/费用 | 0 / ¥0 | HTTP使用2次合成模型调用；不算新模型准确率或生产延迟 |

必须正视边界：

- 模式只覆盖明确的“占/除以/作为分母/分母为”等表达及有限人群词；“基数取已购客户”等未覆盖表达可能继续澄清。系统没有完整中文语法解析，不能声称理解所有等价说法。
- 备选/疑问/否定模式偏保守；复杂长句或“不是A而是B”可能已给出答案却仍被澄清。本轮修复明确原题和反例，不承诺消除所有误报。
- 只识别注册满30天等具体人群表达，不证明当前数据有注册时间或该字段可用；后续Schema、安全与结果口径仍须独立验证。
- 检查的是分母，不是全面指标契约。比例/百分数、有效订单状态、用户去重仍依赖指标上下文与模型；放行不能冒充语义验收通过。
- 新会话缺分母时可在首次生成前拦住；已有会话的改写可能先耗费一次模型调用。费用账本与请求预算仍覆盖该调用，不能把NEEDS_CLARIFICATION等同“必然免费”。
- 规则变化不是把“复购率”全关掉：裸词与不确定问题仍询问；也没有关闭澄清开关追求更高通过率。

### 4. 取舍与面试追问

没只加“2次及以上”同义词：那仍把分子当分母，也解决不了“分母怎么选”误放行。没用模型判断歧义：会引入新费用、延迟和波动，且不能解释为什么这次放行。采用配置化证据组，是为了让正例、缺失、冲突及来源都可测试、可复核。

代价是规则覆盖有限、正则配置比关键词长。选择对未覆盖表达继续问，而不是用弱关键词直接放行；这是当前单域项目的边界，不扩成通用自然语言理解系统。

**问：出现“分母”为什么还要问？** 它只标识一个槽位，不提供取值。“分母怎么选”和“分母是全部下单用户”有不同证据结构；后者有明确人群和关系，前者缺值。

**问：怎么证明不是关澄清刷准确率？** 开关不变，原200题仅已知明确题T6-003改变；裸词、分子、有效订单、选择题和否定句仍被拦截。HTTP按实际模型调用数验证0或1，但真实业务准确率必须另跑冻结请求，不能由单元测试推出来。

### 5. 可验收路径与用户需要掌握的事

无需重新配置Key。复核生产规则和HTTP合成链路：

```powershell
mvn test
mvn -q test-compile dependency:build-classpath '-Dmdep.outputFile=target/demo-http-classpath.txt'
$clarifyCp = 'target/test-classes;target/classes;' + (Get-Content target/demo-http-classpath.txt -Raw).Trim()
java -cp $clarifyCp com.text2sql.agent.clarification.ClarificationHttpAcceptanceProbe reports/clarification-http-new
python reports/repurchase-clarification-20261117/audit_evidence.py
```

HTTP探针只绑定本机临时端口，独立随机应用口令、独立费用账本，供应商Key为空且端点指向本机不可用端口，只有模型被替换。`ClarificationScopeProbe`读取原200题并保存每题Decision，不调用模型。归档分别在`reports/repurchase-clarification-20261117/`及`reports/clarification-http-20261117/`。

用户应能解释：规则在生成前哪一步生效；Evidence的source、group和matchedText分别记录什么；为什么两次及以上不等于分母；放行后若比例单位或SQL错误，应归因到下一层而非宣称澄清修复失败。下一项是新的完整20条真实HTTP复验，旧成绩和失败继续保留；阶段3P95、独立盲测与完整新主机复现没有随本轮完成。
