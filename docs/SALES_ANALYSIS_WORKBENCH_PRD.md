> 需求编号（FR）、验收指标和阶段编号必须先于代码存在；实现、测试和路线文档都必须回链到这些编号。

- 文档状态：提案，待进入实现阶段
- 版本：v1.0
- 日期：2026-11-21
- 适用项目：Text2SQL Agent 电商经营分析平台
- 规格角色：产品规格（Product Specification）
- 配套规格：[技术与架构规格](SALES_ANALYSIS_WORKBENCH_TECHNICAL_ARCHITECTURE.md) · [实施路线规格](SALES_ANALYSIS_WORKBENCH_ROADMAP.md)

## 1. 需求背景

当前系统已经能把自然语言问题转换为 SQL 并执行，但用户体验仍然停留在“问一个问题，返回一个结果”。

本阶段把系统改造成一个围绕销售额的连续分析闭环：

1. 查询总销售额。
2. 查看按月份的销售趋势。
3. 查看按品类的销售排名。
4. 查看按地区的销售分布。
5. 从某个异常品类继续追问原因。

这不是增加几个快捷按钮，而是让后续分析继承同一个业务上下文：

`sessionId + metric + period + dimensions + filters`

业务用户只看到业务结果、图表和下钻操作；SQL、Schema、Token、模型调用和来源凭据进入独立的开发诊断界面。

## 2. 产品目标

### 2.1 业务目标

让业务人员无需重新组织完整问题，就能从一个销售额结果继续完成趋势、排名、分布和原因分析。

### 2.2 技术目标

- 复用现有指标注册表、Schema 检索、Join 规划、SQL 校验和只读执行链路。
- 将“上一轮结果”转换为结构化分析上下文，而不是把整段聊天记录原样塞回 Prompt。
- 支持最多 3 轮连续分析，且每轮都能追踪实际模型调用、Token、耗时和成本。
- 浏览器刷新或短暂断线后，可以通过 `analysisId` 恢复最终结果。
- 不连接真实生产交易库；当前阶段只访问 Olist 分析快照。

### 2.3 非目标

本阶段不做：

- 连接生产交易库。
- 订单、库存、商品写回。
- 多方言 SQL。
- 模型微调。
- MCP 接入。
- SSE/WebSocket 流式输出。
- React 重写。
- 多租户。
- 自动生成无人审核的经营决策。

## 3. 用户与使用场景

### 3.1 主要用户

业务分析人员、运营人员和产品经理。他们关心结果、趋势、异常和原因，不关心 SQL 的生成过程。

### 3.2 开发与测试用户

开发人员和测试人员使用独立诊断与评测入口查看：

- 最终 SQL。
- 实际检索表。
- 指标命中和口径来源。
- AST 校验结果。
- 模型调用次数。
- Token、耗时和成本。
- 失败归因。

这些内容不能出现在业务结果主界面中。

### 3.3 主场景

#### 场景 A：查询总销售额

用户输入：

> 2018 年销售额是多少？

系统识别：

- metric：`gmv_with_freight`
- period：2018 年
- dimensions：空
- filters：有效订单默认过滤

页面展示：

> 2018 年成交总额（含运费）：¥xxx

同时提供：

- 按月份查看
- 按品类查看
- 按地区查看

#### 场景 B：查看月度趋势

用户点击“按月份查看”。

系统复用：

- metric：`gmv_with_freight`
- period：2018 年
- dimensions：追加 `month`
- filters：沿用有效订单过滤

页面展示月度表格或图表，不要求用户重新输入完整问题。

#### 场景 C：查看品类排名

用户点击“按品类查看”。

系统复用：

- metric：`gmv_with_freight`
- period：2018 年
- dimensions：追加 `category`

页面展示：

- 品类名称
- 销售额
- 排名
- 占比（只有题目或指标契约明确要求时才展示）

#### 场景 D：继续追问异常原因

用户点击某个品类后输入：

> 这个品类为什么下降？

系统需要把当前品类、时间范围和已有筛选一起带入下一轮上下文，不能把“这个品类”当成没有指代的独立问题。

如果问题缺少比较周期，系统应先澄清：

> 你想和上个月、去年同期，还是前一个统计周期比较？

## 4. 核心业务规则

### 4.1 销售额口径

本阶段只允许用户明确选择或系统明确识别以下两种口径：

| 指标 | 业务含义 | 计算 |
|---|---|---|
| `gmv_with_freight` | 含运费成交总额 | `SUM(oi.price + oi.freight_value)` |
| `sales_without_freight` | 不含运费商品金额 | `SUM(oi.price)` |

“销售额”未明确含义时必须触发澄清，不能默认把含运费和不含运费混在一起。

### 4.2 默认订单范围

除非用户明确要求包含全部订单，默认排除：

- `canceled`
- `unavailable`

### 4.3 上下文继承

每一轮分析上下文至少包含：

```json
{
  "sessionId": "session-001",
  "analysisId": "analysis-003",
  "metric": "gmv_with_freight",
  "period": {
    "type": "YEAR",
    "value": "2018"
  },
  "dimensions": ["category"],
  "filters": [
    {
      "field": "category",
      "operator": "EQ",
      "value": "beleza_saude"
    }
  ],
  "sort": {
    "field": "metric_value",
    "direction": "DESC"
  },
  "metricDefinitionSha256": "..."
}
```

上下文中的字段必须有来源标记：

- 用户直接指定。
- 指标定义提供。
- 系统从上一轮继承。
- 系统为连通 Join 自动补充。

来源不能全部扁平化，否则无法解释“为什么这张表进入上下文”。

### 4.4 权重与 Top-K

本阶段不修改现有检索排序规则：

- `directHits` 与 `expandedTables` 分开保存。
- 扩展表继续使用 `0.4` 关系衰减。
- 直接命中优先于扩展表。
- 桥接表只在 Join 图不连通时补入。
- Top-K 截断不能让扩展表挤掉直接命中表。

### 4.5 空结果和异常结果

- 查询成功但结果为空：显示“当前口径下没有结果”，不能显示为系统失败。
- 单位不明确：先澄清，不强行把金额当百分比。
- 指标和维度不兼容：返回业务提示，不生成无意义 SQL。
- 数据时间范围之外：明确提示当前数据覆盖范围。
- SQL 安全拦截：业务端显示“查询无法执行”，开发端保留原始校验原因。

## 5. 功能需求

### FR-001 提交分析问题

用户可以提交自然语言问题。

验收：

- 问题长度上限保持 500 字符。
- 首轮自动创建 `sessionId` 和 `analysisId`。
- 重复提交相同幂等键不重复执行。

### FR-002 展示单值结果

当结果为单行单列时，页面优先展示业务结论卡片：

> 不含运费商品金额：¥13,591,643.70

验收：

- 首屏直接出现业务结果。
- 不显示 SQL、Token、Schema 和模型名称。
- 单位、金额格式和指标名称必须正确。

### FR-003 展示分组结果

当结果包含多个维度值时，页面展示：

- 维度名称。
- 指标值。
- 排名或排序方向。
- 表格和图表切换。

验收：

- 表头使用业务名称。
- 物理字段名只允许出现在开发诊断界面。
- 长文本、ID 和枚举值按现有展示字典转换。

### FR-004 一键下钻

结果页提供结构化下钻动作：

- 按月份查看。
- 按品类查看。
- 按地区查看。
- 查看明细。

下钻请求必须携带当前分析上下文，不依赖前端拼接自然语言。

### FR-005 多轮追问

用户可以基于当前结果继续提问：

> 这个品类为什么下降？

系统使用当前 `sessionId` 和上下文摘要完成指代消解。

验收：

- 连续 3 轮追问上下文正确。
- 早期轮次被压缩后，metric、时间范围和筛选条件不丢失。
- 会话关闭后不能继续修改已关闭会话。

### FR-006 口径澄清

当“销售额”无法判断含运费口径时，页面展示业务选项：

- 含运费 GMV。
- 不含运费商品金额。

用户点击选项后，继续当前会话，不重新创建独立问题。

### FR-007 结果恢复

服务端为每次分析保留最终状态：

```text
CREATED → RUNNING → SUCCESS
                  ↘ FAILED
```

页面刷新或短暂断线后，通过 `analysisId` 查询状态并恢复结果。

验收：

- 成功结果刷新后可恢复。
- 失败结果刷新后仍能看到业务失败提示。
- 重连不会重复调用模型。

### FR-008 开发诊断

业务页不展示技术详情。

开发诊断页单独展示：

- SQL。
- 实际检索表。
- `directHits`。
- `expandedTables`。
- `metricDependencies`。
- `safetyBridges`。
- 校验结果。
- Token、耗时、成本。
- 预算快照。

## 6. 接口需求

### 6.1 兼容现有接口

继续使用现有：

```http
POST /api/ask
```

现有 `question`、`sessionId`、`endSession` 字段保持兼容。

### 6.2 建议新增分析接口

后续新增业务分析接口，不让页面直接依赖内部 `AgentResponse`：

```http
POST /api/analysis/turns
GET  /api/analysis/{analysisId}
POST /api/analysis/{analysisId}/drilldowns
POST /api/analysis/{analysisId}/close
```

业务响应只返回：

```json
{
  "analysisId": "analysis-003",
  "sessionId": "session-001",
  "status": "SUCCESS",
  "title": "不含运费商品金额",
  "unit": "CNY",
  "summary": "¥13,591,643.70",
  "columns": ["品类", "销售额"],
  "rows": [],
  "availableDrilldowns": ["MONTH", "CATEGORY", "REGION"],
  "dataAsOf": "2018-12-31"
}
```

诊断响应通过独立权限接口返回，不在业务响应中暴露。

## 7. 页面需求

### 7.1 业务分析工作台

页面区域：

1. 问题输入区。
2. 当前分析上下文摘要：
   - 当前指标。
   - 当前时间范围。
   - 当前筛选条件。
3. 结果卡片。
4. 表格或图表。
5. 下钻操作。
6. 继续追问输入框。
7. 数据更新时间。

### 7.2 业务页面禁止出现

- SQL。
- Prompt。
- Schema。
- Token。
- 模型服务名称。
- `GENERATION_FAILED`。
- `RESOURCE_LIMITED`。
- `directHits`。
- `expandedTables`。

### 7.3 开发诊断页面

独立入口，只对开发和管理员开放。诊断页面可以复用现有执行证据数据，但不能通过 CSS 隐藏来代替权限控制。

## 8. 数据与安全边界

当前阶段使用本地 Olist PostgreSQL 分析快照，不连接真实业务交易库。

应用查询继续遵守：

- 只读账号。
- 最大连接池 5。
- 单条查询超时 10 秒。
- 返回最多 200 行。
- AST 只读校验。
- 自动补充或校验 LIMIT。
- SQL 执行失败必须终止本轮，不把异常结果当成功。

当前阶段不做实时生产同步。页面必须明确显示数据更新时间，不能把历史快照伪装成实时数据。

## 9. 可观测性与指标

每轮分析记录：

- 模型调用次数。
- 输入 Token。
- 输出 Token。
- 总 Token。
- 模型延迟。
- 检索耗时。
- 校验耗时。
- 数据库执行耗时。
- 端到端耗时。
- 估算费用。
- 失败阶段。

阶段验收目标：

| 指标 | 目标 |
|---|---:|
| 连续上下文轮数 | 3 轮 |
| 首轮单值结果首屏可见率 | 100% |
| 下钻请求继承上下文 | 100% |
| 刷新后成功结果恢复率 | 100% |
| 幂等重复请求产生重复模型调用 | 0 次 |
| 业务页出现 SQL 或 Token | 0 处 |
| 业务页实际生产库访问 | 0 次 |
| 单轮模型调用 | 以实际日志为准，禁止隐式重复 |
| 查询 P95 | 沿用项目目标，控制在 8 秒内 |

成本不能填估算值冒充真实成本。当前模型单价为 0 时，只报告 Token，不宣称真实费用。

## 10. 分阶段实施

### 阶段 A：上下文契约

只做后端模型和接口契约：

- `AnalysisContext`。
- `analysisId`。
- `metric`、`period`、`dimensions`、`filters`。
- 来源标记。
- 幂等键。
- 结果状态。

验收后仓库必须可运行。

### 阶段 B：销售额下钻

只实现：

- 总销售额。
- 月度趋势。
- 品类排名。
- 地区分布。

暂不实现异常检测和复杂报告。

### 阶段 C：多轮追问与恢复

只实现：

- 3 轮上下文。
- 指代消解。
- 刷新恢复。
- 重复请求去重。
- 会话关闭。

### 阶段 D：业务界面与开发诊断分离

业务页面只显示答案和下钻；开发诊断页面承载技术证据。

### 阶段 E：固定评测

使用固定候选版本统一验证：

- 结果正确率。
- 多轮上下文正确率。
- 延迟。
- Token。
- 成本。
- 失败归因。

评测启动器继续显式开启评测预算，正常业务运行不受评测调用上限影响。

## 11. 替代方案与取舍

### 方案一：继续在问答页增加按钮

不选。它只能改善演示页面，不能形成上下文、结果状态和分析对象。

### 方案二：迁移 React 后再实现

不选。React 不是业务需求，会把工作量转移到前端重写。

### 方案三：先做流式和 MCP

不选。当前分析请求主要是 SQL 生成和数据库执行，普通 HTTP 已足够；MCP 也不是当前数据源接入的必要条件。

### 方案四：先做分析上下文和下钻闭环

选用。它直接改变用户完成分析任务的方式，且复用现有 Java 编排、指标、Schema 和会话能力。

## 12. 面试答辩要点

### 为什么不把完整聊天记录全部交给模型？

因为聊天记录会造成 Token 增长、指代歧义和旧约束污染。系统保存结构化 `metric`、时间范围、维度和过滤条件，历史文本只作为辅助证据。

### 为什么不让前端直接拼接下钻问题？

因为前端拼接文本无法证明口径继承正确。下钻必须提交结构化上下文，由后端重新校验指标依赖、Join 路径和授权表集合。

### 为什么不直接让模型访问生产库？

只读权限不能消除慢查询造成的 CPU、IO 和连接池争用。当前系统只访问分析快照；未来若接入真实数据，应通过副本、同步库或数仓隔离。

## 13. 需要用户确认的业务口径

实现前只需要确认以下事项：

1. “销售额”默认使用含运费 GMV，还是默认先让用户选择。
2. 地区默认使用客户收货地、卖家所在地，还是必须每次澄清。
3. “异常品类”的比较周期是同比、环比还是上一统计周期。
4. 金额展示使用人民币符号，还是保留 Olist 原始货币口径。
5. 当前阶段是否只做分析快照，不接真实业务库。

在这些口径确认前，不应继续扩展异常检测和经营报告功能。
