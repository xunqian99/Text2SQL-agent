## 0.2 2026-11-09 两组对照实验（都是负结果，但都留了数据）

这一节记录两次「以为能提准确率、实测没有」的尝试。两组都是同一套 eval 100 题、
同一个 `deepseek-flash`、同一份数据，**唯一变量分别是自纠错开关和 prompt 措辞**。
写下来的目的不是证明做过，是让后面的人不用再试一遍。

### 实验一：给自纠错补「择优」逻辑 + 具象化反馈

**改了什么**（代码保留，见 `Text2SqlOrchestrator.retryIfFailed`）：

1. 原来只要第二次 `success()` 就采用第二次，不看首次是否本来正确。现在首次是
   「执行成功但被规则判可疑」时，第二次必须**也通过同一套校验**才配替换。
2. 反馈从「结果可疑，请重新生成」改成带上规则码、判定依据、问题原文、
   实际返回的行数与输出列，并要求最小修改。

**实测**：

| 组 | 准确率 | 触发重试 | 调用数 | 成本 |
|---|---:|---:|---:|---:|
| 对照（自纠错关） | **85%** (85/100) | 0 | 100 | ¥0.1983 |
| 实验（自纠错开） | **82%** (82/100) | 2 | 102 | ¥0.2033 |

**结论：改动没有造成回归，但收益仍然是 0。**

- 18 条失败里**没有一条**的 SQL 被重试替换过（首答 SQL 与最终 SQL 完全一致），
  说明 82% 与 85% 的差是采样波动，不是择优逻辑的问题；
- 差异集中在 T5（10 条题波动 3 条 = 30pp），这一层单次运行本来就不能下结论；
- 100 题只触发 2 次——**信号覆盖率 2%，而失败率是 15–18%，校验器根本没碰到真正的错误**。

**为什么保留**：它不提升分数，但堵住了一个真实存在的隐患（规则误报 → 重试 →
错误答案覆盖正确答案，比率越界规则上真实发生过）。触发成本可忽略（+¥0.005）。

### 实验二：修正 prompt 规则 10 的计数口径

**动机**：18 条失败里有 9 条涉及 `COUNT(DISTINCT)`，其中 5 条的 gold 用的是
`COUNT(*)`。而 prompt 规则 10 原文写的是「只要 join 之后再去重计数，就用
`COUNT(DISTINCT ...)`；单表且无 join 时才用 `COUNT(*)`」——**这条规则在主动
制造错误**：gold 里 23 条带 JOIN 的题用的就是 `COUNT(*)`。

**改法**：把判据从「有没有 join」改成「join 之后一行代表什么」，并给出反例
（`members JOIN orders` 一行仍是一个订单，加 DISTINCT 反而错）。

**实测**：

| 组 | 准确率 | 修好 | 弄坏 | prompt token | 成本 |
|---|---:|---|---|---:|---:|
| 对照（旧规则） | **85%** (85/100) | — | — | 1937 | ¥0.1983 |
| 实验（新规则） | **85%** (85/100) | T3-016 / **T4-013** / T6-002 | T2-019 / T2-037 / T6-022 | 2093 | **¥0.2723（+37%）** |

**结论：净收益 0，成本 +37%，已回滚。**

- **T4-013 确实被修好了**（正是针对的那条：`COUNT(*)` 被误写成 `COUNT(DISTINCT)`），
  说明规则方向是对的；
- 但「弄坏」的 3 条里，T2-037 是 gold 缺陷题、T6-022 是历史波动题，只有 T2-019 是真退步；
- 100 题样本的噪声就是 **±3 条**，单条规则的效果低于噪声，单次运行分辨不出来；
- 成本上涨不是文本变长（只多了约 150 token），主要是**改了 system prompt 中间一段，
  把它之后所有内容的 prefix cache 全冲掉了**。这是一次性代价，但长期仍有约 +7~8%
  （prompt 变长部分）。

**为什么回滚**：零成本的正确性修复可以留，有明确成本、却没有数据支撑的优化必须退。
这条规则如果要捡回来，需要同时修 T4-017、T5-003 等同类问题形成累积效应，
并且跑三次取平均——单条改动的期望收益撑不起这个成本。

### 实验三：Agent 模式改原生 function calling 后重测

**改了什么**：把 `[TOOL_CALL]` 文本协议换成 Spring AI 原生 `@Tool` + `tool_calls`，
删掉 `ToolParser`。过程中踩到三个坑（都已修）：

1. Spring AI 默认 `internalToolExecutionEnabled=true`，框架自己执行工具并循环，
   只返回最终文本——调用方永远看不到 `tool_calls`。这是之前误判「模型一次工具都没调」
   的真正原因。
2. DeepSeek 思考模式不支持 `tool_choice`（`400: Thinking mode does not support this tool_choice`），
   无法用协议强制首轮调用工具。
3. 最后一轮若把 tools 置空，模型会把想调的工具以内部 DSML 文本
   （`<｜｜DSML｜｜ calls>`）吐出来，被当成 SQL 送进校验层。

**实测（同一套 100 题）**：

| 配置 | 准确率 | 工具调用 | tokens | 成本 | p95 |
|---|---:|---:|---:|---:|---:|
| 对照（无 Agent） | **85%** | 0 | 1937 | ¥0.1983 | 15.9s |
| Agent + 强制首轮侦察 | 81% | 262 次 | 8158 | ¥0.3884 | 11.1s |
| Agent 不强制 | 81% | 164 次 | 6356 | ¥0.2747 | 9.0s |

**结论：Agent 在本评测集上是负收益（−4pp，成本 +38%），默认关闭。**

分层看更反直觉：业务语义 +1，但单表聚合 −2、深层关联 −2——**最该受益的深层关联反而掉得最多**。
逐条核对，6 条变错的题没有一条是被工具结果或重试替换的，首答即错。

**原因**：检索层已经把 72% 的题的 Join 拓扑、24% 的枚举值、15% 的指标口径
**提前写进了 prompt**，Agent 没有信息缺口可补；多出来的轮次只是引入噪声。
这也解释了为什么「强制侦察」和「不强制」结果完全一样——查不查都不改变结论。

**这个负结果的正确用法**：不是「Agent 没用」，而是「在信息已经喂足的场景里，
Agent 的边际价值为负」。要让它有价值，得先制造信息缺口（关掉注入），
或者换到真正的脏问题场景。

### 两个教训

1. **改 prompt 中段会破坏 prefix cache**。以后改 prompt 要么追加在末尾，
   要么接受一次性的成本跳变，不能拿「token 只多了 150」来估算成本影响。
2. **100 题样本的最小可检测差异约 ±3pp**。任何小于 3 个点的改动，单次运行都证明不了，
   必须多次运行或扩大样本——否则就是在噪声里挑数字。

## 4. 为什么归档 Top-8，而不是挑最高的历史准确率

开发集上的真实链路取舍：

| 配置 | 执行准确率 | 表全召回率 | 表平均召回率 | 平均召回表数 | 平均 DDL | 平均输入 token |
|---|---:|---:|---:|---:|---:|---:|
| dev Top-5 | 46% | 89% | 97.32% | 4.73 | 1167.00 | 595.73 |
| dev Top-8 | 48% | 96% | 99.20% | 6.68 | 1548.08 | 698.72 |

Top-8 在 dev 这轮多答对 2 题、完整召回多 7 题，代价是平均多约 103 个输入 token。
选择它是为多表关联留余量，并参考开发集结果，不是因为数字 8 本身有特殊意义。

必须同时保留一个不利证据：早期 **eval Top-5 为 54%，高于最终 Top-8 的 52%**。
它与最终 Top-8 的已记录配置主要差异是 K，不能编造“模型不同所以不可比”的理由，
也不能说 Top-8 已被证明在 eval 执行准确率上更好。单轮差异可能受到模型波动影响，
但没有重复实验就不能确定原因。

Top-K 是词法命中与关系扩展候选排序后的上限，**不是直接命中种子表的上限**。
选出 K 张之后，连通性修复最多再补 2 张桥接表；无词典命中时会回退全量 schema。
因此 K 不是任何情况下最终表数的硬上限，也不能用 K=5 推算一个简单的理论准确率上限。

## 5. 指标到底在测什么

- **执行准确率**：当场执行 `gold_sql` 得到期望结果，将生成 SQL 的结果规范化后比较。
  每题对/错二值计分；Java 运行器不以 `gold_results.json` 快照作为评分依据。
- **SQL 有效率**：状态为 `SUCCESS` 的占比，即通过护栏并执行成功；答案错也计入。
  不是“SQL 语法正确且业务口径正确”的比例。
- **表全召回率**：期望表全部被召回的题数 / 有效题数。期望表来自 gold SQL 的解析，
  排除 CTE 别名；gold 的关联选择会影响这个指标。
- **表平均召回率 / 精确率**：逐题算命中表 / 期望表、命中表 / 召回表，再取平均。
  不是把所有题的表合并后计算一个比例。
- **schema 10 张表**：`meta.schemaTableCount` 是本轮各题上下文表数的**最大值**；
  库仍有 37 张表，平均召回 6.69 张，不是每题固定给 10 张。
- **控制台 tokens**：`overall.avgPromptTokens`，只统计输入 token。
  API 响应里的 `llmCall` 另有 `completionTokens` 和 `totalTokens`；
  当前评估汇总并没有给出平均输出或总 token。
- **延迟**：编排层的检索 + 生成 + 校验 + 执行耗时；不包括评估器执行 gold 的耗时。
  P50/P95 使用最近秩法取实测值，不是整轮运行时间除以样本数。
- **金额**：输入 token / 1000 × 输入单价 + 输出 token / 1000 × 输出单价。
  当前单价配置为 0，所以报告没有有效金额估算。缺少 usage 或调用失败时 token
  也可能记录为 0，不能据此断言没有调用。

你需要到千帆控制台核实当前账户所用模型的实际计费，再填写本地的
`agent.llm.input-price-per-1k`、`output-price-per-1k`（单位：元 / 千 token）。
没有实际账单或价格配置，不能宣称“单次成本低于 0.05 元”。

## 6. 结果比较与时间规则

当前实现见 `ResultNormalizer`；Python 离线工具的规则应与 Java 保持同步。

1. 数字四舍五入到 4 位小数，并去掉多余零；`610.0` 与 `610` 可等价。
2. NULL 与空字符串区分；不把空字符串当作 NULL。
3. 完整日期与当天零点 timestamp 统一展示形式：
   `2018-01-01`、`2018-01-01 00:00:00.0` 都归一为 `2018-01-01 00:00:00`。
   保留时分秒；非零小数秒、带时区后缀的文本不做换算。
4. `2018-01`、`2018-Q1` 保留原样，不猜月初或季度首日。T3 gold 已改用完整日期/
   `DATE_TRUNC` 等输出，避免 `TO_CHAR` 产生有损月份标签后再让比较器补猜。
5. 行顺序由 gold SQL 判断：同时含 `ORDER BY` 与 `LIMIT` 才按有序列表比较，
   否则按保留重复行的多重集比较。
6. 列名不参与比较，但**列位置参与比较**；当前不支持自动把换序后的列对齐。

例如“每个州有多少订单”只要州与数量配对一致，少写展示用的排序不应判错；
“销量最高的 10 个”有排名语义，gold 的排序与 LIMIT 会要求顺序一致。
这是项目当前评分约定，不是所有业务的通用真理：顺序检测只是字符串启发式，
尚未做顶层 AST 分析；并列排名和题目明确要求排序的特殊情况仍需审核。

dry-run 的 100% 只表示已有 gold 样本经过链路自检通过，既不是模型成绩，
也不能证明规范化永远正确，更不能把所有真实失败一概归咎于模型。
