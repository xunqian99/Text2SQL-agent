## 技术与设计导读

### 1. 具体请求与数据流

例如“每种支付方式的评价平均分”：旧Gold把支付记录直接关联评价，同一订单同方式多次支付会重复加权。V3题面明确每条评价在订单使用的每种支付方式下各计一次；Gold先去重 `(order_id,payment_type)`，再关联全部评价，最后按方式求均值。当前voucher结果由旧4.00变为4.02。这是参考修复，不是模型已学会去重。

评测时读取冻结题面→生产检索与口径→模型生成→只读校验/数据库执行→按原评分算法比较V3预期结果。双方使用同一套V3，历史安全回补基线与p21候选才可比较。

### 2. 技术抓手与身份追踪

Gold明确自然人、订单、评价、发货单、退款明细等身份，避免多跳关联改变计数或金额。退款明细用完整 `(refund_id,order_id,order_item_id)`；支付方式去重身份不能代替评价身份，仍保留每条评价；库存出库另带 `records=COUNT(*)`，区分“无记录”与“有记录但数量全未知”，只给前者补0，后者SUM仍NULL。

TopN以业务指标为第一排序键，完整身份只在指标相等后裁决，不让ID压过指标；金额按最终展示精度排名。已知金额候选排除NULL，候选不足不补行。未改检索来源集合、0.4扩展衰减或最多2张桥接表。

六份YAML和生产契约/DDL均有SHA清单；`reference-seal.json`关联独立接受与作者变更谱系。原始报告字节另存ZIP，工作文本统一换行，不能把文本规范化误说为原始报告字节相同。原数据字节单独核验。

### 4. 设计权衡与面试答辩

没有直接改旧Gold重新计算旧成绩，因为那会破坏历史可比性；没有把每个缺月补0，因为数据的最早/最晚日期不能证明中间完整覆盖；没有为每次反馈重跑付费模型，因为参考未固定时的分数会混入基准变化。

问“参考答案修正后涨分，算模型提升吗？”——不算，必须在同V3上重跑基线和候选，再看差值；原78%正式失败保留。

问“LEFT JOIN后COUNT(*)为什么会错？”——无匹配子记录仍生成一条父记录行。数轨迹要 `COUNT(tracking_id)`；数父实体按其主键；AVG前先按每张发货单计0到多条，再让每单等权。
