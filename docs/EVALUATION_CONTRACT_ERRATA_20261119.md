# 原正式100题与产品契约的冲突审计（2026-11-19）

原正式89%门槛与当前产品契约不能同时作为可达验收条件：已核实14道互不重复的题，即便输出严格遵守当前契约，也无法匹配旧单轮答案。因此，**条件上限为86/100＜89**。这是逻辑上限，**不是新的模型实测准确率**；违反产品契约的模型仍可能碰巧取得更高旧分。

本次检查全部原eval100的问题、Gold及当前规则，执行44条只读SQL核对。9组Gold/契约对照均得到不同结果；另外5题由当前生产澄清组件确定拦截。没有供应商调用，没有改原题/Gold/评分器/门槛，也没有把旧失败改成通过。此审核由同一AI完成，**不是独立复核，更不是盲测**。未标出确定冲突的86题不等于全部得到业务签字认可。

## 3. 接下来的可审阅方案

1. 原v2原题、Gold、评分器和所有历史报告保持原样。68/100开发、78.00%正式失败、89%门槛继续留在记录中，不重新解释为过关。
2. 已生成[100题复核包](review/FORMAL_CONTRACT_REVIEW_PACKET_20261119.md)，逐题列原问题、原SQL、当前冲突和可审阅的诊断SQL；每条裁决留空。**需要未参与出题/调参的人员实际复核**，不能由本AI替自己签字。
3. 独立复核后才能冻结一个单独版本的验收协议：明确名称/编号、时间口径、并列、零事实覆盖；数值评测题给全口径，澄清能力用单独对话契约验证；修正已确认粒度缺陷并记录版本差异。当前只是提案，未创建替代题库、未降低旧门槛。
4. 新协议与原基准分开报告，先冻结题目/Gold/样本/门槛/运行配置，再在DeepSeek空闲时段统一评测。不能把新参考成绩与旧基线直接相减，当成模型收益。
5. 阶段1的独立未见盲测另行欠缺：审核这些已见题不能补齐盲测。外部人员需要保管尚未向实现方暴露的题目/Gold，先冻结后测。

这项真实外部复核无法由同一AI代劳。当前不继续花API费用重跑一个理论上达不到门槛的候选；也不切到阶段3做加速实验。阶段2及整体目标仍未完成。

## 4. 技术导读与面试追问

数据流例子：T6-013的`coupon_usages`每行是一笔用券事实，`order_items`每行是一条商品事实；直接按`order_id`连接会把一笔优惠复制到多条明细。诊断先各自聚合成一行一订单，再连接，保留有效且有明细的同一用券订单全集。这样只修优惠事实重复，不能靠`SUM(DISTINCT 金额)`误删同额的真实优惠。

证据来源单独保存：原问题/Gold哈希、当前Prompt与澄清资源哈希、当前源代码提交、每条只读SQL和返回结果。`confirmedConflictKinds`记录确定冲突，`current_data_coincidence`与`top_k_tie_ambiguity`单列；集合去重后才计算`100-14`，没有检索权重或按题号影响生产生成。

未选“改Gold后立即宣称准确率上涨”，因为参考改动与系统收益会混淆；未选“禁用澄清/让模型猜”，因为这违背已经确定的产品要求；未选“把89降低到86”，因为这是降低验收门槛，不能解决参考错误与盲测欠项。

**问：为什么以前90%以上现在反而过不了？** 历史分数属于各自模型、Prompt、数据与口径时点；本次发现当前产品要求与旧基准有确定冲突。历史数字不抹掉，也不把跨版本分差全归因于算法；先冻结共同定义再做可比实验。

**问：86%是不是在给差成绩找借口？** 不是实测成绩，也不抵消现有超时或错误。它只是在14个有来源、不重叠的约束下推导旧评分的条件上限。剩余错误仍要修；独立人员可以逐题推翻本审计，未经复核不能据此宣布验收。
