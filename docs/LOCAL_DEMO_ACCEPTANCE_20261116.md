## 技术与设计导读

### 1. 机制与数据流

执行`start_local.ps1 -Mode demo`后，脚本读取进程或User级`AGENT_LLM_API_KEY`，通过环境传给Maven子进程。Spring依次加载基础配置、local、demo；固定HTTP本机监听，不自动启动评测。

GET `/api/health`读取全局模型客户端标记、全量Schema快照、绑定后的实际配置，返回模式、14项能力与5项限制。字段采取白名单组装，不序列化全部配置，因此不会夹带API Key、持久化密码、数据源或异常详情。模式判断优先使用实际评测开关：Gold自检/evaluation优先于profile标签；demo和baseline冲突标为custom。命令行覆盖仍优先于profile，能力字段反映覆盖结果。

具体请求`{"question":"2018年有多少笔订单？","sessionId":"stage4-smoke-2018"}`经过会话/预算、检索、生成、AST/EXPLAIN、只读执行、结果检查，实际输出一行`order_cnt=54011`，预算标记COMPLETE、modelCalls=1。使用`requestId`关联HTTP响应与逐调用JSONL，避免将其他实验账目算进本次费用。输入缓存命中/未命中分别追踪，不能把所有输入Token都按缓存价计算。

### 2. 组件与边界

- `application-demo.yml` / `application-baseline.yml`：明确增强开关，保留AST、数据库只读、EXPLAIN和请求预算；不新增依赖。
- `HealthController`：只读配置与Schema快照；`LlmSqlGenerator.isGloballyConfigured()`只认服务器全局客户端，已有BYOK客户端不能给无Key服务制造就绪假象。
- `start_local.ps1`：Key不放命令行，缺local配置即明确提示；提供Preview与端口参数。
- `RequestBudgetTest`仅修正旧测试调度假设：队列64，最多2个任务运行，70次取消提交可能接纳64–66、拒绝4–6；断言所有执行/拒绝合计70，保留返回小于1秒的约束。生产预算类及其参数未改。

健康不运行检索、排序或Top-K，因此没有改变`directHits`、关系扩展/桥接来源、0.4衰减或原始排序规则。健康Schema可能命中缓存；`ready=true`不证明Key有效、余额充足、模型输出正确或数据库此刻在线。响应明确保留providerVerified/databaseLiveVerified=false。

### 3. 收益与限制

消除了“进程启动就误以为全部增强已开启”“一次BYOK调用后无全局Key却显示全局就绪”“本机演示配置与评测配置混用”的运行诊断问题。12项新契约、547项全量及1条真实问数提供运行证据，不宣称模型准确率提升或尾延迟优化。

demo刻意关闭查询缓存与持久化，让调用与会话表现容易解释；进程重启会丢失内存会话，不能拿它展示落库持久性。最多2次模型调用也不等于金额硬配额；多轮改写会消费调用预算，超时usage仍可能未知。

### 4. 取舍与面试追问

替代方案是继续复制完整local配置或仅按profile名称显示能力。前者容易复制个人凭据且配置漂移，后者看不到命令行覆盖，因此选择小型profile覆盖和有效配置白名单。不采用每次health真实问模型，因为会产生费用/额外调用，还不能保证下一次请求一定成功。

**问：为什么健康返回200却问数可能失败？** 200表示Schema快照可读，ready表示静态配置条件满足；API Key有效性、额度、传输、SQL语义要由真实请求覆盖，健康字段已经明确边界。

**问：只监听本机就安全了吗？** 仅收窄网络直连面，同机程序仍能调用，隧道也能重新暴露。远程模式必须保护问数和全部会话接口，并增加限流与费用配额。本次没有完成这些能力。

### 5. 用户核对与剩余工作

运行命令与数据准备见[LOCAL_DEMO](LOCAL_DEMO.md)。目前无需用户重新配置已永久保存的Key。需掌握并能解释：一次问数经过哪些步骤、requestId如何关联所有调用费用、失败发生在配置/检索/生成/执行哪一层。

剩余：20条冻结代表题连续HTTP运行与会话隔离、隔离新库初始化复现、鉴权/限流/总费用门禁、旧部署脚本权限收敛。旧Compose仍将5432映射全部网卡，旧deploy脚本有过宽授权，不能宣称远程部署安全。独立盲测、完整语义契约、阶段3原P95欠项同样保留。
