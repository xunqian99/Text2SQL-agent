# 2026-11-16：评测配置、输出截断与重试记账验收

本阶段只处理评测可信度与生成失败归因。业务范围仍是 PostgreSQL 只读 Text2SQL；不修改 Gold SQL、数据集切分和结果比较规则。

## 1. 已确认的问题

1. 启动时遗漏 `local` profile，会从 8192 输出预算退回 1024，同时关闭列剪枝、语义指标、few-shot，并将金额单价恢复为 0。模型名相同不代表配置相同。
2. 原 PowerShell 脚本只在传入 `-SelfCorrection` 时开启自纠错，未传时没有显式关闭，导致 local 配置里的 `true` 继续生效。结果检查也和自纠错绑定，无法独立做对照。
3. 模型 SQL 提取失败时已经消耗 token，旧响应却丢失调用记录；纠错失败或再次被判可疑时，保留首答也丢失重试费用。
4. 生成失败后的重试分支没有遵守 `max-attempts=1`；生成重试结束后还可能再进行一次 SQL 纠错，实际超过两次调用。
5. 服务端以 `finish_reason=length` 明确标识输出截断，但旧链路只报告“模型返回空内容”，或把截断的 SQL 交给语法校验器，错误归因失真。

## 2. 本次实现与边界

### 2.1 固定评测入口

`scripts/run_eval.ps1` 显式启用 local、deepseek-flash、temperature=0、8192 输出预算、Top-8 检索、列剪枝、Join 提示/规划、语义指标、两条示例。默认显式关闭生产自纠错和结果检查，并关闭缓存、模型升级路由、工具循环与多轮会话，避免隐藏的调用路径。

脚本从项目根目录执行 Maven；当前进程没有 Key 时，从 Windows 用户环境变量中读取，仅放入进程环境，不打印、不写入命令行。没有 Key 的真实评测在调用模型前失败；dry-run 不受影响。`-Preview` 只打印非敏感的启动参数。

报告新增 `meta.effectiveConfig` 白名单快照，记录输出预算、温度、三类单价、澄清/结果检查/语义/示例/剪枝等开关。没有序列化整个配置对象，避免把 API Key 和数据库密码写入报告。原 `correction.*` 仍表示评测器外层的重试统计，不能拿它当生产编排器的逐次重试记录；生产开关查看 `meta.productionSelfCorrectionEnabled`，实际重试结合本轮运行日志核对。

### 2.2 截断归因

例如用户问“数据里最后 90 天，每周的商品销售额分别是多少？”：澄清检测放行 → 检索相关表和列 → 模型返回响应 → 先构建 `LlmCallRecord` → 检查服务端结束原因。

- `finish_reason=length`：抛出携带账目的 `OUTPUT_TRUNCATED`，不执行半条 SQL；API 仍归类为 `GENERATION_FAILED`，消息说明输出预算问题，调用日志保留精确原因。
- 正常结束：再提取 SQL，进入 AST 校验、只读执行与结果比较。
- 没有结束原因：不凭 token 数猜截断，继续现有提取与校验。厂商不提供结束原因时，仍可能只能归为 `UNPARSEABLE`。

8192 是本项目已有 local 配置，不是“永不截断”的保证。推理模型可能把预算用在 reasoning 而未给出最终 SQL；异常分类和失败记账必须长期保留。不会无限增加预算或无限重试。

### 2.3 首答选择与调用记账

生成异常通过 `GenerationException.callRecord` 追踪实际调用；`LlmCallRecord.combine` 将输入 token、输出 token、缓存命中/未命中 token、模型耗时和费用分别相加。

`AgentResponse.combineAttempts(first, second, useSecond)` 明确区分两件事：用哪次答案，以及已经花了多少钱。第二次失败或仍可疑时取首答 SQL、状态和结果，但总账包含两次调用。生成重试耗尽两次机会后，不再追加 SQL 纠错。

本阶段没有修改检索打分、来源标记、衰减、排序和 Top-K 算法。输出 token 预算与检索 Top-K 是两种不同的限制：前者限制模型生成，后者限制检索上下文，不能用增加 K 修复 SQL 输出截断。

## 3. 验收路径

在 PowerShell 的项目根目录运行，Key 通过用户环境变量 `AGENT_LLM_API_KEY` 提供：

```powershell
# 查看实际参数，不调用模型。
./scripts/run_eval.ps1 -Preview

# 基线：澄清开启，自纠错与结果检查关闭。
./scripts/run_eval.ps1

# 只改变自纠错；结果检查仍关闭。
./scripts/run_eval.ps1 -SelfCorrection

# 单独增加结果检查，和上一组比较。
./scripts/run_eval.ps1 -SelfCorrection -ResultChecker

# 澄清对照：相对默认基线只关闭澄清。
./scripts/run_eval.ps1 -DisableClarification

# 验证 200 条 trusted Gold 执行链路；不是模型准确率。
./scripts/run_eval.ps1 -DryRun -Split all
```

判定顺序：

1. 参数预览与日志确认实际开关；非预期配置不得混入同组平均。
2. 报告的 Git 提交、数据指纹、样本指纹、prompt、模型及非实验参数一致；工作区 DIRTY 的来源应说明。
3. 全量测试通过，重点覆盖截断归因、首答保留时的重试账目、两次调用上限。
4. 实际评测保留全部失败题，不把澄清项从准确率分母中静默删除。
5. 按本轮日志起止时间统计调用 JSONL，与报告费用和输入 token 核对；费用是按配置单价估算，并非供应商实际扣款。
6. 单轮差异只能作为观察；要声称机制带来稳定收益，各配置需独立多轮，报告均值、波动、修复题和回退题。不要用 `-Repeat` 代替独立重复，它原本用于缓存重复负载。

## 5. 技术与设计导读

- **实现例子**：首答因 `length` 失败，携带 100 输入 / 1024 输出 token；纠错消耗 200 输入 / 20 输出。无论选哪次答案，最终账目都是 300 输入 / 1044 输出。若两次都失败，仍返回失败并完整计费，不伪造成功。
- **核心组件**：Spring AI 的 generation finish reason、`GenerationException`、`LlmCallRecord`、`AgentResponse`、`EvalRunner` 与 PowerShell 固定入口。不增加依赖。
- **为什么这样做**：单纯提高预算只能减少截断，无法区分半条 SQL 和真实语法错误；直接覆盖首答账目会漏成本。因此同时做结束原因检测、有限重试和费用合并。没有选择无上限重试，因为它无法给出明确的成本和延迟边界。
- **追问一：温度 0 为什么仍有波动？** 它降低采样随机性，但不保证厂商推理服务逐 bit 确定；必须固定参数、保留逐题记录并多轮复测，不能承诺一轮分数必现。
- **追问二：为什么重试失败还要增加成本？** 答案选择是产品质量决策，费用来自实际调用；首答被保留不代表第二次调用没发生。两次调用各自记录来源，随后按字段求和。
- **用户需掌握**：核对请求在哪一层失败、两次调用总 token/耗时/估算费用是否相加、这次运行是否实际用了 local 和 8192。现有 Key 与数据库可用，无需额外配置。
