# 阶段3：显式四步指令开发筛选冻结协议

本协议先提交、后运行。只检验删除系统消息的显式四步推理文字是否改善拖尾，保留介绍、全部18条业务/安全/输出规则与供应商默认模式。生产默认仍保留原Prompt，不预先接受候选。上一项low筛选存在未知用量而未晋级，本次不重跑low、不新增题目。

## 1. 假设、输入与顺序

原始题库200道，dev100用于本次开发筛选；另100道候选题不参与。本次只有100道不同问题，两种配置各一轮，共200次真实问答请求，不是200道新题，也不是600道题。

先用`PromptDirectivePairProbe`在真实Schema/检索/模板上捕获100组消息指纹，并做300次同进程重复比较，必须无漂移、无模型调用。随后运行原题库Gold自检200/200，模型调用0；再按`explicit-steps`→`no-explicit-steps`各独立JVM运行dev100。启动脚本检查每组的真实首答指纹，第一组不匹配预先捕获则立即终止，不继续花钱跑第二组。

默认版本`p9-mdl-alignment-v9`，系统长度2795；候选`p9-mdl-alignment-v9-no-explicit-steps-v1`，系统2536；差值恰好259个Java UTF-16代码单元。该差值约占原dev输入文本5.17%，不是Token数或已证实的延迟节省率。假设可能失败：模型仍可自主推理，复杂题也可能因提示不足退步。

## 2. 单因素与冻结范围

唯一允许变化为`agent.prompt.explicit-reasoning-enabled=true/false`及其派生的Prompt版本、系统文本/完整消息指纹和长度。两组`reasoning_effort`均为`provider-default`（客户端省略参数），不得同时改为none/low或改其他Prompt内容。

固定deepseek-flash、温度0、评测输出上限8192、总预算15秒、最多2次模型调用、重试准入剩余2秒、SDK最多1次；Top8、列剪枝、Join规划、指标、2条few-shot、澄清、生产纠错和结果检查开启。应用缓存、路由、工具循环、会话及评测器外层纠错关闭。输出8192是既有评测配置，不宣称生产1024也已改为8192。价格沿用每千Token未命中输入0.001元、命中输入0.00002元、输出0.004元，属于配置估价，不是供应商账单。

冻结源码、测试探针、pom、data/eval、执行/审计脚本及其依赖、本协议和私有配置SHA-256；私有配置只记哈希，不归档内容。每步前后检查保护路径状态、同一Git提交和原字节。消息配对文件在任何真实模型调用前生成并冻结哈希，后续不得按输出补改。运行目录必须新建，失败和中断也保存，不为了补出有利结果自动重跑。未参与的演示稿编辑不纳入保护路径。

## 3. 配对证据与错误归因

每个题目记录共同用户消息SHA-256、上下文SHA-256、两种完整消息SHA-256和长度；两种完整消息均包含系统/用户角色与顺序。探针调用同一生产检索，校验两模板的用户消息逐字相等，以及候选系统等于原系统仅删固定259单位。`tables`、`scores`、`expandedTables`、`evidenceOrder`保留检索事实与来源，不改打分/衰减/Top-K。

真实调用按题目ID与对应变体的预捕获完整消息指纹对齐；只证明“两个指纹不同”不算通过。即使首答超时且用量未知，已记录的发送指纹也须相同。无首答调用的题单列原因，不冒充对齐成功。配对证据不保存完整Prompt，不包含Gold结果，也不能证明模型一定服从业务规则。

`requestId/callNumber`把逐请求预算、应用调用记录与JSONL对应，原账目审计继续检查已知Token/缓存组成/费用、未知用量、超时、最终选答、重试恢复/退化与晚到记录。真实元数据、JSONL的`configuredPromptVersion`和供应商模式须与变体一致；配置标签只是意图，实际消息仍由指纹证明。

题目/Gold SQL/Gold结果指纹与同次Gold报告逐题核对。不得删除澄清、超时、拒绝或错误来缩小100题分母。错误SQL仍按表、列、Join、聚合粒度、过滤/时间和输出契约逐题分析，不把可执行率等同正确率，也不调整Gold来挽救候选。

## 4. 事先冻结的筛选门槛

候选进入正式确认须全部满足：

1. 正确数相对同期默认下降≤2/100；100题完整分母。
2. 请求墙钟P95至少降低10%；候选绝对P95是否小于8秒单列，不能替代正式门槛。
3. 新增截断请求≤1/100，按调用`OUTPUT_TRUNCATED`与生产尝试对齐，不凭Token数猜。
4. 候选完整配置估价≤0.30元/100题，未知用量必须0；缺失则费用门槛未确认，不把未知当免费。
5. 每请求最多2次模型调用、墙钟≤16秒工程容差、取消提交拒绝0；逐题输入/配对/配置/选答/账目审计通过。

报告全部T1至T6和表数分层、逐题失败、由对变错/由错变对、重试/恢复/退化、缓存命中/未命中、已知Token、未知调用、费用下界及P50/平均/P95/最大墙钟时间。P95取每轮完整100题墙钟第95顺位值，包含重试，不包含JVM启动或离线评分。

固定默认先跑，时间和供应商缓存会影响单轮结果；只能筛选，不能宣称稳定因果、独立盲测或泛化提升。若有利，另行冻结交替三轮eval确认协议；正式门槛保持准确率≥90%且相对同期退步≤2pp、三轮平均P95<8秒与每轮完整费用要求，不因dev分数低重设基线。筛选失败就拒绝晋级，阶段3不通过，不进入阶段4。

## 5. 验收路径与技术设计导读

`run_prompt_directive_screen.ps1`执行前置配对、Gold和两组请求，增量保存manifest；`summarize_prompt_directive.py`独立核对本协议，复用请求账目和既有筛选门槛，不修改旧生成模式审计。先验证新增12项临时合成夹具（不是模型结果），覆盖多因素混入、错误版本、候选误发默认、配对/Gold变动、缺失来源与未知费用。Java仅增加测试工具，应先test-compile；业务实现沿用`efca9f6`实际484/484证据，不冒充重新全量测试。

提交冻结后执行：

```powershell
./scripts/run_prompt_directive_screen.ps1 -OutputDir reports/prompt-directive-screen-20261116
python scripts/summarize_prompt_directive.py reports/prompt-directive-screen-20261116
```

未来代码变化后只读核验历史结果用`--evidence-only`，跳过当前工作区哈希检查、不覆盖summary；消息/题目/Gold/账目审计仍保留。此命令成功仅代表取证一致，候选是否通过还看`candidateForConfirmation`，`stageAccepted`固定false。

例如“订单有多少”：问题→原Schema/指标/示例→两种系统消息之一→默认模式供应商请求→SQL校验与只读执行→订单数量。核心抓手是模板区间裁剪、预捕获消息指纹、逐题配对、共享请求预算及既有结果评分。相比直接覆盖全局Prompt，多维护一个候选版本换取可归因、可回退、可核对；相比同时关闭模型思考，本次保持供应商参数一致。

面试追问：“文字删了就一定更快吗？”答：不一定，Token、推理输出与服务端调度不能由字符占比推导，必须看同期数据。“两组分数接近就能上线吗？”答：还要检查复杂层退步、未知费用、P95与正式重复验证，单次dev筛选不能代替验收。

用户无需重配环境。需要理解请求数据流、逐调用实际费用与错在检索/生成/口径/执行哪层。本轮不改题目、Gold、18条规则、生产默认、数据库业务数据或评分逻辑。
