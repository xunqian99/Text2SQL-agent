## 需要重新批准的范围

N1b 只允许从 B0 重新生成 **system prompt 的规则文本**，不允许改变以下内容：

- Schema、JOIN PLAN、数据画像、指标、枚举、示例和用户问题；
- `directHits`、`expandedTables`、`metricDependencies`、`safetyBridges` 四类来源集合、检索排序、Top-K 和桥接上限；
- 模型、思考设置、输出上限、15 秒单题预算、纠错次数、评分和题集；
- 旧 C1 的任何响应、费用、UNKNOWN 或中断状态。

候选机制是**规则表化的无损紧凑序列化**：保留 18 条系统规则及四步推理的逐项身份，把重复的“必须/不得/除非/默认/例外”措辞改为固定的 `条件 → 动作 → 例外` 结构。禁止按问题关键词删除规则，禁止把多条规则合并成无法逐项回溯的泛化句子。每条压缩后的规则必须能反向映射到 B0 的原文片段和 51 项语义义务。

这不是把 C1 的 p22 文本换个名字继续跑。C1 的 system 已从约 5,327 字符压到约 3,374 字符，但真实 DEV100 只有 87/100，N1b 必须重新生成候选、重新做语义审查和重新冻结 SHA。

## 技术与设计导读

1. **数据流**：请求先按原检索链得到带四类来源凭据的 `SchemaContext`，随后只替换 system 规则文本；用户消息、DDL、指标、示例和问题逐字保持，最后仍走原生成、AST、只读执行和账务链。
2. **核心实现**：`PromptTemplate` 负责候选 system 文本，规则映射表负责可追溯压缩，`SchemaContext.SourceProvenance` 负责四类来源身份。system 压缩不参与检索打分，不会改变 `directHits/expandedTables` 的权重关系。
3. **预期效果**：免费目标是总字符减少至少 20%、P95 不增加、51 项义务和 9 个危险负例零退化；真实准确率、Token、P95、超时和成本必须等 DEV100 后才能报告。
4. **设计权衡**：按关键词动态删规则看似更省字，但会在否定、复合指标、同名实体和缺失依赖时删除必要契约；固定规则表更容易逐项审计，代价是压缩率可能不够，达不到上界就停止。
5. **用户配合**：当前不需要 Key、Docker 或外部服务；需要的是明确批准或拒绝 N1b 范围。无批准不能修改生产 system 或发起付费请求。
