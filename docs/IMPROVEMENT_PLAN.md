## 1. 目标与边界

目标是把当前单库、单用户的研究原型推进为一个**结果可复现、失败可归因、演示有安全边界**的工程项目。当前已有 Schema 检索、Join 路径规划、指标语义、SQL AST 校验、只读执行、成本记录和离线评测。下一阶段的重点是证明这些能力稳定有效，而不是继续堆模块。

继续遵守 [ROADMAP.md](ROADMAP.md) 的范围约束：只读 SQL、PostgreSQL、单租户，不做模型微调、多方言、写操作或通用 BI 建模。向量检索和更复杂的 ReAct 编排暂不列入近期计划，除非盲测实验能证明当前方案存在明确瓶颈且替代方案有净收益。

## 3. 阶段计划

### 阶段 0：凭据与项目口径清理

**目的**：先处理凭据风险，并固定可复现的评测基准。

**工作范围**：

- 吊销并轮换曾出现在本地配置或对话记录中的模型凭据。
- 配置只从环境变量读取 API Key；缺少 Key 时应用可启动，但问数请求明确返回未配置状态。
- 固定 Benchmark v2 的版本和 Gold 清洗记录。任何 Gold 修改都记录题目 ID、修改前后内容、理由及审核人。
- 统一 README、EVALUATION 和其他文档里的测试数量与指标口径。
- 确认评测报告记录完整的模型、Prompt、代码版本、数据库数据版本和配置快照。若生产与评测使用不同的自纠错开关，要在报告和说明中明确区分。

**验收条件**：

- 源码、示例配置和当前 Git 历史中没有可用凭据；本地运行依赖环境变量，不提供内置 Key 回退值。
- 无 Key 启动时健康状态和 `/api/ask` 响应符合文档定义，响应与日志不包含凭据。
- Gold SQL 全量 dry-run 为 **200/200**。
- 测试数量来自一次实际 `mvn test` 结果，所有对外文档使用同一个数字。

**需要用户配合**：在模型服务控制台吊销旧 Key 并创建新 Key。这项外部操作不能靠代码改动替代。

### 阶段 1：评测可信度与复现门禁

**目的**：区分系统改进、Gold 修正和模型波动，避免把调参集成绩当成泛化结论。

**工作范围**：

- 冻结当前 Benchmark v2；后续 Gold 修正通过 Errata 记录，不覆盖历史结果。
- 保留现有开发集和 eval 集，额外准备约 100 条盲测题，使总规模仍在路线图建议范围内。盲测题不参与词典、Prompt 或规则调优。
- 固定模型、Prompt、配置和数据版本，对当前 eval 至少运行三次，保存逐次报告、失败题并集、分层结果、成本和 P50/P95。
- 报告明确区分执行准确率、SQL 有效执行率、表召回率和 Gold 自身错误；禁止用单一总分替代失败归因。

**验收条件**：

- 三次固定配置运行的报告元信息一致；任一差异都有说明。
- 报告给出三次总分及波动、逐层结果、失败案例并集、平均 Token、成本、P50/P95。
- 盲测集有独立版本和访问约束，调参记录不引用盲测结果。
- 新改动必须同时报告开发集和盲测集结果；不能只挑改善的难度层展示。

**数字门槛说明**：首轮盲测用于建立基线，不预先假定它必须达到 96%。后续优化以冻结盲测基线为比较对象，明确报告准确率变化及样本数。

### 阶段 2：业务语义契约与结果校验

**目的**：降低“SQL 合法且执行成功，但结果口径不符合题意”的错误。

**工作范围**：

- 扩展现有 `metrics.yml`，为重点指标定义计算表达式、过滤条件、分母、可用时间字段和起止边界。
- 定义结果契约：输出列、单位、NULL 处理、分组粒度、排序字段、排序方向及并列规则。
- 对题目中的歧义先澄清，不允许系统静默挑选一个业务口径后返回确定答案。
- 对照已有失败记录，选出明确目标案例逐题验证；不要一次性加入大量自然语言 Prompt 规则。

**验收条件**：

- 对开始阶段选定的目标失败案例，至少修复一半；逐题记录修复前后 SQL、结果与归因。
- 歧义用例返回澄清状态；明确口径用例返回满足结果契约的列和排序。
- 新增契约测试全通过，Gold 全量 dry-run 仍为 **200/200**。
- 固定配置的三次 eval 平均准确率相对冻结基线退步不超过 **2 个百分点**；目标案例的收益单独列出。

**设计约束**：本阶段不顺手重写 Schema 检索打分。检索评估继续区分直接命中、关系扩展和桥接补入的表，不能把不同来源扁平化后只报告总 Top-K。当前关系扩展衰减参数为 **0.4**，桥接修复额外表数上限为 **2**；若以后调整参数，必须同时报告直接命中保留情况、全召回率、精确率和最终上下文大小。测试覆盖无关联路径、桥接表超限和多条等长路径等边界，不能默默把缺失关联伪装成可生成 SQL。

### 阶段 3：P95 延迟与重试预算

**目的**：为慢请求找出实际瓶颈，并控制端到端耗时与重试成本。

**工作范围**：

- 基于请求级记录分解问题改写、检索、模型首答、每次重试、SQL 校验、数据库执行和结果检查耗时。
- 为一次请求设置总时间预算和最大模型调用预算，分别记录超时、重试前后 SQL、最终采用结果及花费。
- 按慢题类别进行小范围实验，例如减少深层题无关上下文、限制纠错次数或仅对特定失败升级模型；每次实验只改变一个主要因素。
- 保留原始逐调用 Token、缓存命中/未命中及成本数据，不能只统计最终调用。

**验收条件**：

- 在固定模型、机器、数据库和评测集下完成三轮 eval。
- 三轮 P95 的平均值低于 **8 秒**；若暂时达不到，报告每轮数值及拖尾题，不宣称达标。
- 三轮准确率平均值相对冻结基线退步不超过 **2 个百分点**。
- 100 题成本不超过 **¥0.30**，同时分列缓存命中与未命中成本、重试调用数和 Token。
- 超时请求在总预算内结束，不会因多次重试无界延长。

每个阶段按以下顺序交付：

1. 先说明本阶段改动范围和设计理由；一次只推进一个阶段。

测试命令以当前仓库脚本为准，例如 `mvn test`、`scripts/run_eval.ps1 -Split eval` 和 `scripts/run_eval.ps1 -Split all -DryRun`。真实 LLM 评测应记录模型服务、价格时段、Key 配置方式和调用成本；不应把 dry-run 数字冒充模型准确率。

## 5. 暂不推进的事项

- **向量检索**：先证明盲测中的主要失败确实由词典召回导致，再做独立消融；当前高召回、低精确率本身不足以证明向量检索会提升最终准确率。
- **更复杂的 ReAct 编排**：现有文档记录工具循环尚未证明有正向 ROI。先比较准确率、P95、调用数和成本，再决定是否启用。
- **多租户、RLS、多方言、写操作和模型微调**：均超出当前项目边界，不作为本轮完善目标。

## 6. 面试说明要点

- **96% 代表什么？** 它是指定模型、Prompt 和清洗后 Olist Benchmark v2 上的 96/100。Gold 清洗解释了 88% 到 96% 的差异，不能把这 8 个百分点说成系统优化收益；泛化能力还要用盲测或外部基准验证。
- **为什么不直接上向量库或 ReAct？** 因为需要先用独立评测证明它们解决当前主要失败，并同时核算延迟、成本和维护负担。增加组件不等于提高系统质量。
- **为什么强调语义契约？** SQL 执行成功只证明语法与数据库可执行；分母、时间边界、NULL、输出形状或排序不一致仍然会给出错误业务答案。
- **如何解释检索排序？** 区分直接命中、关系扩展和桥接表来源；说明扩展衰减、Top-K 与桥接上限如何影响候选集合，并用召回、精确率及上下文 Token 验证。必须同时交代无连通路径或补桥超限时的处理，不能只报一个总召回数字。
