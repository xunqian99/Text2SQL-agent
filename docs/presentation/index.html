Problem Analysis · 痛点与问题定义
业务现状与直接调用大模型的“三大致命陷阱”
02 / 10
数仓业务现状与提数瓶颈 业务端痛点
• 提数链路漫长： 业务人员提出需求 $\to$ 数据分析师排期 $\to$ 人工编写 SQL，单个指标问数响应通常需要 2~3 天。
• 数仓拓扑复杂： 电商数仓涵盖 37 张表，外键交织繁琐，业务口径黑话较多，非技术人员完全无法自主提取数据。
• 核心工程目标： 构建高可信的自然语言到生产级只读 SQL 转换系统，实现安全秒级自助式提数。
直接调用大模型（LLM）的工程死穴 质量失控风险
• 陷阱 1 · 拓扑断链（Schema 幻觉）： 超过 3 张表关联时，模型依靠概率拼凑外键，经常引入不存在的伪支路甚至死循环环路。
• 陷阱 2 · 物理击穿（Resource Exhaustion）： 偶发生成缺失 Join Filter 的隐式笛卡尔积或大表全扫，秒级打满只读库 CPU 与 Buffer Pool。
• 陷阱 3 · 数据越权（Security Escape）： 存在生成 DDL/DML 篡改数据风险，或利用别名与系统限定名跨库窃取元数据。
口播提示：“软件工程的第一步是问题定义。我们不仅解决提数慢，更要消除大模型在生产落地时的拓扑断链、物理击穿与越权逃逸三大风险。”
Requirements Engineering · 需求工程与规格矩阵
从功能性诉求到非功能工程红线（SRS）
03 / 10
功能性需求 (Functional) 意图转换
• 多表深度拓扑查询： 覆盖单表过滤、聚合汇总及 1~5 表长链路关联查询。
• PostgreSQL 方言适配： 严格输出符合物理数仓规范的标准只读 SQL。
安全性质量属性 (Security) 100% 只读
• 语法级绝对只读： 严禁任何 DDL（DROP/ALTER）与 DML（INSERT/UPDATE）操作。
• 元数据防逃逸： 彻底阻断访问 pg_catalog 等系统字典表。
可靠性与性能 (Performance) 物理熔断
• 执行计划代价预检： 执行前递归分析代价树，拦截大表无约束笛卡尔积。
• 语法归一化二级缓存： 热点查询直接命中缓存，延迟压降 50% 以上。
经济性与可观测 (Cost & Usability) 成本可控
• 极低推理成本： 精准 Schema 剪枝，单次查询调用成本压低至 0.002 元。
• 全链路日志归因： 耗时、Token 计费、SQL 执行日志全程透明可追溯。
口播提示：“软件工程强调质量内建。我们绝不停留在‘能跑就行’，而是将安全性、性能防击穿与成本作为刚性验收红线。”
System Architecture · 系统架构设计
三层纵深防御体系与单一职责解耦模型
04 / 10
Layer 1 · 输入前置拓扑规划 确定性图算法
• 领域词典精准匹配： 双路检索用户 Query 命中的物理表与核心字段。
• 斯坦纳树外键求解： 在数仓拓扑图中求解最小加权连通子树，补全桥接表。
• 动态 Schema 剪枝： 剔除无关表，仅将必要上下文注入 Prompt，消灭幻觉源头。
Layer 2 · 大模型受控推理 语义转换器
• 单一职责严格解耦： 大模型仅负责“自然语言 $\to$ 只读 SQL”转换，不承担安全职责。
• 结构化输出约束： 强制纯净 SQL 输出，剥离多余解释文本。
• 二级指纹缓存： 命中语法哈希指纹时直返结果，跳过大模型。
Layer 3 · 输出后置纵深安全防御 双重物理防护罩
• 防线 A · JSqlParser AST： 解析语法树根节点，强制纯读，阻断系统表限定名。
• 防线 B · EXPLAIN 预检： 递归代价树，识别无 Join 约束的 Nested Loop 笛卡尔积。
• 防线 C · 只读账号兜底： 数据库用户只读权限 + 10 秒硬超时保障。
口播提示：“遵循纵深防御思想。大模型只是受控黑盒翻译器；输入前用图算法补全外键，输出后用 AST 和 EXPLAIN 两道物理锁直接熔断恶意与慢查询。”
Algorithm Engineering · 核心算法工程
基于斯坦纳树（Steiner Tree）近似算法的外键路径规划
05 / 10
方案选型对比：为什么局部贪心算法会崩溃？ 技术权衡
• 被否方案 · 贪心 BFS / 最短路： 数仓存在大量环形外键网络。贪心搜索只能找到单对节点最优，在 3 表以上时极易走偏，产生伪支路孤岛。
• 采纳方案 · 斯坦纳树近似算法： 将 37 张表抽象为加权图，命中表作为终端节点，计算覆盖全部终端节点的最小边权生成子树，自动补全中间过渡表。
• 数学权重防挤压设计： 直接命中表赋予基准权，扩展伴生表施加 0.4 强衰减，比较器二级保送，确保核心目标不被边缘表挤占。

Defensive Engineering · 质量与安全防线
AST 静态语法白名单与 PostgreSQL 原生 EXPLAIN 熔断
06 / 10
防线 1 · JSqlParser AST 语法树审计 代码级审计
• 纯只读语法结构白名单： 严格校验 AST 根节点仅允许为 PlainSelect，绝对阻断 DDL、DML 与分号批处理注入。
• 系统表限定名穿透防御： 深度递归扫描所有 Table 节点，严禁通过 pg_catalog. 或 information_schema. 嗅探数仓元数据。
• 别名逃逸漏洞修复： 实测排查出 3 处利用子查询别名隐藏敏感表的安全逃逸漏洞，完成深度遍历全量封堵。
防线 2 · PostgreSQL EXPLAIN 物理代价拦截 物理级熔断
• 原生执行计划树递归解析： 调用 EXPLAIN (FORMAT JSON)，递归计算整棵树的 Total Cost 与预估扫描行数。
• 隐式笛卡尔积硬拦截： 重点识别节点为 Nested Loop 且无连接条件的大表交叉扫描，在数据扫描前物理熔断。
• 故障左移（Shift Left）： 相比于 10s 超时事后止损，毫秒级预检杜绝慢查询触碰磁盘 IO 与 Buffer Pool，保障生产库稳定。
口播提示：“回答‘敢不敢让模型生成的 SQL 直接执行’的问题：我们不敢！因此做了两道物理锁：AST 静态分析防越权，EXPLAIN 代价分析防宕机。”

Conclusion & Retrospective · 反思与展望
工程反思与总结：科学证伪决策与工程师角色进化
10 / 10
科学工程证伪：主动砍掉“启发式重试” 工程务实精神
• 初始技术设想： 设计了在 SQL 报错时将错误信息回传给模型进行启发式自动重试的机制。
• 实测数据残酷证伪： 在 200 题基准实测中发现，模型的盲猜二次纠错成功率接近于 0，反而使网络延迟翻倍、Token 消耗急剧膨胀。
• 果断止损下线： 不为了“功能看起来多”而保留无效功能，果断关闭重试。这体现了软件工程尊重实测数据、敢于做减法的科学态度。
工程师角色进化与开源资产沉淀 总结与展望
• 工程师的角色升维： 在 AI 时代，软件工程师不再是代码打字工，而是业务架构的裁决者与安全测试红队。软件工程方法论比以往任何时候都更加关键。
• 开源资产沉淀： 架构源码、测试套件与评测基准已全部开源于 GitHub（github.com/xunqian99/Text2SQL-agent）。
• 未来规划： 下一步将静态 Schema 字典升级为语义指标层（Semantic Layer DSL），统一口径治理。
口播提示：“敢于根据实测数据砍掉无效的启发式重试，体现了求实与反思。AI 是加速器，而软件工程是方向盘与刹车。谢谢各位老师！”
