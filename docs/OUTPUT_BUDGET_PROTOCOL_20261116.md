# 输出Token预算：开发集单轮筛选协议

本实验延续改进方案阶段3，针对模型生成占服务耗时约98.15%的观察，检验降低输出上限是否有收益。只改变评测运行参数，不修改生产默认值、题目、Gold、Prompt、检索、澄清、纠错或评分器。现有代码已支持`maxTokens`，无需新增依赖或业务实现。

## 题目数与运行次数

- 原始基准仍为`data/eval`的200道题，稳定切成dev100与eval100；另有候选v1的100道题，本次不用。
- 使用原始200题做一次无模型Gold自检，必须200/200且模型调用0。
- 同一批**100道dev题**：8192输出上限跑一次，2048输出上限跑一次。真实问答累计**200次**，不同问题仍为100道，不新增、不复制成新题库。
- 本轮是开发筛选，不是三轮验收，也不宣称独立盲测。不能用旧eval三轮分数替代本轮开发基线。

## 冻结、配置与顺序

协议及脚本先提交，再执行`scripts/run_output_budget_screen.ps1`。顺序固定为Gold → baseline-8192 → candidate-2048，每组独立JVM；禁止覆盖输出目录。每步前后核对同一Git提交、保护路径状态及原始SHA-256；包含本地配置的哈希，但不记录凭据内容。

两组都使用15秒请求总预算、最多2次模型调用、纠错准入剩余至少2秒，SDK最多1次尝试。模型`deepseek-flash`、温度0、Top-8、列剪枝、Join规划、业务指标、2条few-shot固定。开启澄清、生产自纠错和结果检查；关闭应用缓存、升级路由、工具循环、会话及评测器外层纠错。唯一主要变量是每次调用的`maxTokens=8192/2048`；总请求仍可能有2次调用，不能把2048误称为请求全部Token的硬上限。

8192先跑可能使2048组受益于供应商缓存/时间漂移，因此单轮不能建立稳定因果。筛选有利才另行冻结交替三轮验证；无利则保留失败证据并放弃该候选，不修改题库来挽救分数。

## 先验判定与完整分母

保留每组完整100题，超时、澄清、截断均计未完成；成功首答回退依然按最终结果与Gold比较，并单列。P95取墙钟排序第95个值，报告P50/平均/最大值及全量失败。

候选进入后续验证须同时满足：

1. 正确数相对同期8192组下降不超过2/100。
2. P95至少下降10%，且绝对P95是否低于8秒单列；相对变快不代表阶段通过。
3. 发生`OUTPUT_TRUNCATED`的请求数相对基线增加不超过1/100；单列截断调用数、重试次数/恢复、未知usage和最终生成失败。
4. 已知费用不超过¥0.30/100题；若任何候选用量未知，完整费用无法确认，不宣布本项达标或参数验收通过。
5. 输入题目、Gold SQL/结果、首答Prompt指纹及所有其他配置一致，调用数≤2，墙钟不超过16秒工程界限，取消提交拒绝0。

即使所有筛选条件满足，仍需固定候选做正式三轮验证，阶段3不会因这两轮自动完成。下降超过门槛就拒绝候选；不把失败请求剔除，不把Token用满推断成截断。

## 截断、身份与成本证据

现有`LlmSqlGenerator.requireComplete`只在服务端明确返回`finish_reason=length`时记`GenerationException.Reason.OUTPUT_TRUNCATED`，不把恰好用满预算的完整SQL误判成截断。半条SQL不进入执行；生成失败可在同一15秒/2次调用内重试。重试可能抵消首次调用变快的收益，必须计入总墙钟、Token与费用。

每次调用先写`IN_FLIGHT`，`requestId + callNumber`关联JSONL与晚到费用；超时`REQUEST_STOP`是停止证据，不是一条额外模型调用。缺失usage保留未知，仅报告已知下界。费用使用原配置单价估算，不等于供应商账单。

输出较短本身不能证明推理内容减少；本轮日志不存原始回复，也未单独记录供应商reasoning Token。不得把completion Token全称为“最终SQL Token”，也不假设降低上限必然让完整回答更快。只有实际P95、截断与正确数能支持下一步选择。

本轮无新增外部服务配置，也不等待未确认的候选集业务口径；那些问题不属于本次开发集调参范围。
