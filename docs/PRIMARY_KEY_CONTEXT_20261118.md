# 主键元数据补全与剩余失败只读复核

代码提交`7ed7a4a`。数据库读取层已经知道主键，模型输入渲染层却把它丢掉，这是本批确认并修复的结构缺陷。完整Java一次1,046/1,046、93套件、失败/错误/跳过均0；真实应用Gold执行自检200/200。原模型题库仍200道，没有改题、Gold或评分，没有新增付费评测。最新正式准确率仍78.00%＜89%，阶段2及整体未验收，阶段3延迟优化继续暂缓。

## 1. 一个具体请求经过哪些步骤

请求：“各退款原因对应的平均评分和低分率是多少？”

1. `DatabaseSchemaReader`使用只读账号，从`pg_catalog`读取评价表主键`(review_id, order_id)`，分别给两个列对象标记`primaryKey=true`。同表的全部主键分量共同定义唯一身份，标记不代表每个分量单独唯一。
2. `ColumnPruner`原本就会保全全部真实主键列，本批不改这条规则，也不改变表选择或列排序。
3. 旧`SchemaDdlRenderer`只输出列名、类型和注释，丢掉主键标记。新渲染在表的列清单之后输出一条完整元组：

   ```text
   PRIMARY KEY (review_id, order_id)  -- 组合唯一，单列不保证唯一
   ```

4. 全量与检索两条路径共用这段渲染，最终`PromptTemplate.userPrompt`携带完整主键。系统提示仍为p18；没有额外改动全局业务规则。
5. 如果模型确需按评价记录去重，就有信息区分不同订单里的同名review_id；正确身份应保留order_id。本批不自动改写SQL，也不擅自决定所有多对多指标都应去重。返回仍是退款原因、平均评分、低分率，不能把额外身份列强行投影给用户。

## 2. 为什么这是实质问题

现库评价记录99,224条，独立review_id只有98,410个，完整`(review_id, order_id)`组合99,224个。单独用review_id去重会丢掉814条不同订单评价；这是身份丢失的数据库证据，不是声称此前所有模型查询都错814条。

上轮正式T6-024的r2实际SQL使用`DISTINCT reason_code, review_id, review_score`。现库确有同一退款原因下，两笔不同订单的评价共享review_id及分数，导致一条事实被合并；质量问题类目的低分率变为14.61%，原参考14.60%。只在DISTINCT中补上完整身份order_id，四组值即与原参考相同。这里确认了部分主键去重的实际错误；主键信息漏传与该错误方向一致，不能据此证明漏传是模型出错的唯一原因，也不能宣称提示补全后模型必然服从。

真实主键例子还包括`inventory(warehouse_id, product_id)`和`product_brand_map(product_id, brand_id)`。本次按数据库元数据通用渲染，不按表名或题号特判，不把所有`*_id`都猜成唯一键。

## 3. 来源、权重与边界防线

**来源凭据。** 数据库主键来自`pg_index.indisprimary`，通过`Column.primaryKey`传到剪枝后的表对象，再由渲染器组成元组。列名启发式只是旧剪枝逻辑在缺元数据时的列保留兜底，它不会把`primaryKey`改成true，因此本次不会把猜测身份输出成真实数据库约束。外键、词典关联和实体业务身份也不会被提升为主键。

**没有新分数。** 不改directHits/expandedTables、扩展0.4衰减、Top-K或桥接上限。原200题的表集合、列集合、检索分数、扩展集合、指标文本、枚举提示和示例全部不变；只补真实主键元数据，不靠提高某表权重实现修复。

**安全边界。** 一个复合主键只输出一条元组，不把两个列各写成独立PRIMARY KEY。没有真实标记时不输出猜测主键；这不代表已证明该表没有其他唯一约束。当前不读取所有UNIQUE约束，也不解析部分唯一索引；主键唯一也不能证明任意关联一对一。真实完整schema进入正常剪枝时所有主键分量已保全；如果未来外部调用方手工构造不完整表对象，当前布尔字段无法识别“遗漏了一个未知分量”，不能宣称渲染器能恢复缺失元数据。

没有更改数据库schema、约束或业务数据。缓存签名追加`schema=primary-key-tuple-v1`，即使关闭指标语义注入，旧输入生成的SQL也不能跨版本命中。格式版本将来变化需要同步维护；会话若保留旧上下文，应在部署重启后建立新会话。

## 6. 设计取舍与面试答辩

没选再加一句“注意复合主键”然后继续不给实际主键：模型仍不知道是哪几列。没选按review_id或表名硬编码：真实数据库已经有权威来源。没选把DDL全部贴入输入：当前只需补紧凑的主键元组，避免类型细节和其他约束文本扩散。代价是提示字符增加约3.6%，它不是免费优化，是否改善模型必须另行实测。

**面试追问一：有外键为什么还要主键？** 外键说明可关联，不证明子表关联列唯一；主键定义源事实身份，复合键必须保留所有分量。拿review_id跨两个订单重复的实例解释“关联合法但统计仍错”。

**面试追问二：元数据修复为什么不直接报准确率提升？** 读取、保留、渲染与模型服从是四个不同环节。本次前三级已有真实链路测试，最后一级未调用模型。28条控制查询用于确定错误来源，不能冒充模型修复结果。
