## 实现、证据与设计导读

以“订单总数”为例：问题→原有检索与Prompt→`LlmSqlGenerator.optionsBuilder`→Spring AI请求体。默认配置不包含`reasoning_effort`；none配置包含`reasoning_effort:"none"`，输出上限仍为8192。模型回复继续走原来的SQL提取、只读校验和数据库执行，结果与Gold比较。

`AgentProperties.Llm`校验并归一化可选模式，四个生成入口共用builder；全局客户端和BYOK都采用同一选项构建路径。`EvalRunner.effectiveConfig`及`LlmCallLog`的JSONL新增`configuredReasoningEffort`；数据库日志表不迁移。`requestId + callNumber`标识每次调用，Prompt哈希只标识消息输入，模式单独追踪。既没有扁平化身份，也没有添加排序权重。

Java全量**459/459**，失败/错误/跳过均0；新增23项，其中16个实际HTTP组合覆盖两种模式×四入口×两种Key来源，另外检查3种思考强度、归一化及3种非法配置。离线审计**46/46**，新增6项使用明确标记的合成协议夹具。真实报告的输入、配置、首答指纹、选答、预算与逐调用账目审计通过。原始JSON、JSONL、运行日志及[清单](../reports/generation-mode-screen-20261116/manifest.json)、[汇总](../reports/generation-mode-screen-20261116/summary.json)已归档。

[DeepSeek官方说明](https://api-docs.deepseek.com/api/create-chat-completion/)支持none关闭思考及默认开启思考的配置语义；本地捕获证明客户端发送了字段，不证明供应商内部实际采用了某个模式。因此字段始终叫configured，不能把配置记录写成供应商内部推理的证明。temperature=0也不保证结果确定；当前文档说明思考模式忽略温度。

未选“在Prompt里要求别思考”，因为它不能可靠控制协议模式；未把生产默认直接改none，因为复杂题可能退化，需要三轮确认。若供应商不支持显式值，保留真实失败，不静默降级；总15秒/最多2次调用和截断拒绝防线不变。

面试追问一：“P95变快84.52%是否已经优化成功？”答：只通过开发筛选，默认先跑存在时间漂移和缓存影响，复杂层有退步，须按预注册协议再做同eval三轮对照。

面试追问二：“回复短了为何不能直接报省钱？”答：输入命中比例也变化，默认组有3次未知usage，重试也计费；只能报告各组已知账目，不能伪造完整节省率。

影响范围仅为生成参数与审计字段，题库、Gold、检索、Prompt、纠错策略未变。下一步仍属于阶段3，使用原eval100题交替三轮确认；用户无需重新配Key或启动新服务。用户应核对具体请求的数据流、完整调用费用和错误层级，不能只记P95总数。
