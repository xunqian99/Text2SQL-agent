## 四、高频问答

### Q1 数据是怎么流的？

一次请求经过五步，每步都有明确的输入输出：

```
问题 → [1] 口径歧义检查（可关闭）      → 命中则反问，不生成 SQL
     → [2] 语义缓存（L1 内存 / L2 数据库）→ 命中则跳过模型
     → [3] Schema 检索（词典 + 词法 + 连通性修复）→ Top-8 张表
     → [4] 口径注入（关键词命中 metrics.yml）→ 拼进 prompt
     → [5] 生成 → 校验（表/列/函数/LIMIT）→ 执行
                                     → 失败则升级重试一次
```

具体例子：「2018 年每个月的销售额是多少？」
→ 归一化后查缓存未命中 → 检索命中 `orders`、`order_items`
→ 「销售额」命中口径注册表 → 生成 SQL → 校验通过 → 执行 → 返回 12 行。

### Q2 准确率是怎么算的？为什么不用字符串比对？

**执行结果集比对**。同一个问题有无数种正确写法（列顺序、别名、join 写法都会变），
字符串匹配会把大量正确答案判错。

具体做法：当场执行标准 SQL 拿期望值，再执行模型 SQL 拿实际值，规范化后比。
规范化包括数值精度、时间格式、行顺序是否承载语义（**只有 ORDER BY 和 LIMIT 同时出现
才算顺序有意义**——「每个州有多少订单」少写排序不该判错，「销量最高的 10 个」顺序错了才该判错）。

### Q3 为什么先做 Schema 检索而不是直接调 prompt？

因为 37 张表全塞进去时输入是 **2315 token**，检索后是 **709**，降了 69%，
而准确率还涨了 5pp。上下文变短本身不是目的，**减少噪声表对模型的干扰**才是。

### Q4 Join 路径规划为什么默认关闭？

实现了列级关系图 + 从根节点延伸的连接树，实测确实修好了「join 列猜错」
（这类错误 4 条降到 1 条），但**整体准确率 52%→52%，零变化**，token 反涨 29%。

原因是修好 5 条、新坏 5 条：新增的候选边让模型顺手多 join，而标准答案不需要。
**确定的成本换不确定的收益，工程上不成立**，所以默认关闭，代码保留可复现。

### Q5 「业务口径注册表」是什么？为什么不叫语义层？

它做三件事：按关键词**子串匹配**命中、按依赖表过滤、把人工预写的口径文本拼进 prompt。
**不做语义理解、不生成 SQL、不改写 SQL**。叫「语义层」会让人误以为它有语义理解能力，
是过度宣称，所以统一叫「口径注入」。

它在 prompt v2 下的净贡献是 **+10pp**（67%→77%），而且**全部落在 T6**，
T4/T5 完全不受影响——这是「口径层」应有的边界。

### Q6 口径注册表会不会把模型带偏？

会，而且真发生过。第一版给「不含运费销售额」配了别名 `[销售额, 商品销售额]`，
结果注入了 4 道普通题、弄坏 3 道。原因是普通题的 gold 没有「排除取消订单」的过滤，
模型照抄指标里的 filter 反而错了。整体从 62% 掉到 61%。

判据定为：**别名只放业务黑话（GMV、复购率、动销率），普通描述词让模型按字面写**。
这条有单元测试固定。

### Q7 怎么防止删库？

三层，**不依赖任何单一层正确**：

1. **AST 校验**：只允许 SELECT、表/列白名单、危险函数黑名单（`pg_read_file`、
   `pg_sleep` 这类只读但有副作用的函数是最容易漏的攻击面，含子查询和 CTE 递归检查）；
2. **只读账号**：应用连库用 `text2sql_ro`，只有 SELECT。实测 `DELETE FROM orders`
   和 `CREATE TABLE` 都被数据库拒绝；
3. **超时与行数上限**：查询 10 秒超时、结果 200 行上限。

44 条对抗性用例全部拦截，覆盖写操作、多语句注入、危险函数、系统目录探测、列级越界。

### Q8 自纠错提升了多少？

**0**。首答 SQL 有效率长期在 96–100%，线上只有「校验拒绝 / 执行失败 / 返回空内容」
三种真实错误信号可回灌，实测 100 条里触发 1 次、救回 0 条。

即使给一个**完美的结果校验器**（评估器里用 gold 结果触发重试），也只多救 4 条。
结论是：**自纠错的收益上界由结果校验器决定，而我没有结果校验器**。

第一版实现还踩过一个坑：我把标准答案的样例行写进了反馈提示，70 条就跑到 95.7%。
那是答案泄露不是模型变强；删掉标签后同配置回落到 72%。**凡是「加了自我反思就大幅提升」
的结果，先查提示里有没有混进标签。**

### Q9 为什么说有 ±3 个百分点噪声？

同一份代码、同一份配置、temperature=0，三次独立评估是 **71% / 68% / 70%**。
所以**小于 3 个点的改动不能用单轮结果下结论**。这也意味着「77% vs 71%」这个 +6pp
需要复现才能认——我跑了四次（77/77/75/77）才敢说它成立。

### Q10 70% 左右的准确率，剩下错在哪？

按层看：单表 95%、时间窗口 87.5%、多表 join 72.7%、**深层 join 10%**、口径 91.7%。

最大缺口是 T5 深层 join（1/10）。那是个**结构问题**——四张表以上怎么连，
而阶段 3 已经证明「把连接树给模型」这条路零收益。所以我没有继续在 join 上硬磕。

另外发现评估集自身有一处口径不一致：多数题四舍五入到 2 位，但 T2-004、T2-039、
T6-020 是 4 位。这属于**评估集质量问题**，需要人工定口径，我在文档里如实标注了。

### Q11 缓存放哪？为什么不直接用 Redis？

两级：L1 进程内 LRU（纳秒级，热路径零网络），L2 数据库表（跨实例共享、重启不丢）。

没上 Redis 的理由：这个项目是单实例，共享缓存要解决的问题此刻不存在；
而 Redis 要多一个中间件、一次网络往返和一个新失败模式。**缓存不可用时必须降级成
「没有缓存」，绝不能变成「请求失败」**——这条在 Redis 上更容易写错。

扩到多实例时命中率会大致摊薄到 1/N，那时候才值得上——**迁移范围很小**，
因为 `normalize()` 和配置指纹是设计、`store` 才是存储。

### Q12 缓存的为什么是 SQL 不是结果集？

结果集缓存会把**过期数据当正确答案返回**，而且没有信号能发现——SQL 正确、格式正常，
只是数字是旧的。缓存 SQL 只省模型调用，数据每次现取。

另外缓存键必须带**配置指纹**（模型、prompt 版本、检索开关和 K、口径开关）：
只拿问题文本做键的话，改完 prompt 旧答案会继续命中，表现成「我改了配置但数字一点没动」。

### Q13 这个项目最难的地方是什么？

**判断力，不是代码量。** 最值钱的产出是那张消融实验表——它把「我做了很多优化」
变成可验证的事实，也把「哪些优化其实没用」暴露出来（join 路径规划就是零收益）。

能说清「我故意不做什么、为什么」比「我什么都做了」更有说服力。

### Q14 有哪些没做？为什么？

- 没做多方言、没做写操作、没做模型微调、没做多租户——范围一旦放开就做不完；
- 整体 78% 目标**未达成**（现在 77%），自纠错 +3pp 目标**未达成**（实测 0）；
- 成本金额**没有数字**，因为单价没填。报告里的「成本 0 元」是**没算**，不是免费；
- 分层型号路由实现完成但**量不出收益**，触发率约 2%，和自纠错是同一个原因。

### Q15 Few-shot 动态示例库是怎么建的？怎么防止数据泄露？

1. **示例来源**：基于 Hash 确定性切分，仅从 **开发集（Dev 100 条）** 筛选 35 条高质量示例，**绝对不触碰 Eval 评估集**；
2. **选择算法**：两段式匹配——先按「命中的 Schema 表重叠数量」过滤，同等表重叠下按问题分词的 Jaccard 相似度排序，取 Top 3；
3. **去重防泄漏**：选择器内嵌过滤条件，严格剔除与当前输入问题文本完全相同的示例，防止评测命中原题。

### Q16 自纠错在线上没有错误信号，后来是怎么破局的？

自纠错过去最大的瓶颈是：91% 的错误属于「执行成功但逻辑写偏」的静默错误，线上没有标准答案，系统以为跑成功了。

我们落地了 **启发式结果校验器（`ResultChecker`）**，基于 5 组通用数据常识规则进行异常探查：
- **空结果**：有过滤条件但返回 0 行；
- **聚合 NULL**：COUNT 为 0 或 SUM 为 NULL（往往表连错或字段选错）；
- **比率越界**：百分比指标不在 0~100 范围内（分子分母写反）；
- **负数指标**：金额/客单价等非负字段出现负值；
- **无关联笛卡尔积**：多表查询漏写 ON 条件。
一旦触发可疑告警，将具体原因包装成错误反馈，回灌给大模型触发精准自纠错。

### Q17 为什么把系统升级为 Agent 模式？工具调用为什么不用 LangChain 或框架？

1. **为什么需要 Agent 化**：单次盲写 SQL 对 4 表以上的深层 Join 准确率极低（仅 10%）。Agent 模式让模型具备「先侦察、再求证、最后定稿」的能力，通过 `INSPECT_TABLE` 查看样例行、`CHECK_JOIN` 验证连表是否出数据；
2. **为什么不用框架**：
   - 依赖过重、不可控：现成框架黑盒封装深，日志和 Prompt 难以逐层归因；
   - 工具集固定：我们只有 5 个明确的 SQL 探查工具，纯 Java 手写状态循环（Act-Observe-Reason-Finalize）仅需百行代码，性能极高且无额外学习/运维成本；
   - 严格安全沙箱：所有探查 SQL 强制注入 `LIMIT 5`、10秒超时并复用只读数据库连接，框架往往做不到这么精细的护栏。

### Q18 多轮会话的指代消解怎么做？会话为什么在结束时才入库？

1. **指代消解与补全**：不采用把多轮历史全部塞进 Prompt 的笨办法（防止表名污染和 Token 膨胀），而是将追问（如“那2017年的呢？”）重写补全为**自包含独立单句**（“2017年销售额最高的前5个州是哪些？”）。下游检索与生成完全复用标准链路；
2. **Schema 0ms 复用**：识别到针对同一实体的追问时，直接复用上一轮会话已缓存的 `SchemaContext`，检索延迟直接降至 0ms，杜绝表召回漂移；
3. **双层存储（内存 + 结束落库）**：
   - 问答进行中走 `ConcurrentHashMap` 内存缓存，保证问数链路毫秒级响应，避免高频 DB I/O 阻塞；
   - 用户主动调接口结束、或 30 分钟超时淘汰、或应用优雅停机（`@PreDestroy`）时，批量落库到 `conversation_session` 与 `conversation_turn` 表，既干净又支持审计追溯。

## 五、被问住时的兜底

如果某个细节记不清，**不要编**。可以说：

> 这个数在我们的评估报告里，报告文件名带时间戳，可以现场翻。
> 项目原则是每个数字都绑定配置——模型、prompt 版本、数据集切分都记在同一份文件里，
> 因为数字离开配置就没有意义。

这句话本身就是加分项：它说明你做过可复现的实验，而不是凑了几个数。
