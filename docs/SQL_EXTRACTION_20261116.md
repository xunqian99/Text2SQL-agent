## 2. 技术与设计导读

### 具体请求与数据流

请求“订单状态有多少种？”经过检索取得 `orders.order_status`，模型返回上述带孤立尾部围栏的查询。流程如下：

1. `LlmSqlGenerator` 保留原始 `rawOutput`，按原有逻辑生成调用用量与输入指纹。
2. `SqlExtractor` 只删除整段回复边界的独立围栏行，输出原有 `COUNT(DISTINCT ...)`，不追加 `LIMIT 1`、不改字段或聚合。
3. `SqlValidator` 检查单语句、SELECT、函数和表列；随后仍需执行计划护栏与只读数据库执行。
4. 该样本可在首答路径成功，不因格式残留触发纠错。真实 PostgreSQL 的只读账号直接执行这条清理后的 SQL，结果为 `status_count=8`。
5. 新增的 `SqlExtractionPipelineTest` 使用真实生成器、提取器、校验器和编排器，模型与数据库为替代实现：在开启纠错时确认成功、模型调用 1 次、尝试 1 次、`retryTrigger=NONE`、`selectedAttempt=1`，响应账目等于该次调用记录。它不是一次付费线上问答。

### 核心组件与边界规则

- `SqlExtractor` 的首行匹配只接受独立的三反引号行，可带大小写不敏感的 `sql` / `postgresql`；末行只接受独立三反引号。支持配对、仅开头、仅结尾三种包装。标签 `SQL:` / `SQL：` 可以位于包装外或包装内。
- SQL 内部不再按分号、空行或关键词截断。去掉外层包装后，正文中所有字节保持不变，仅修剪整体首尾空白。
- 轻量词法状态仅判断残留围栏是否属于 SQL 内容：记录单/双引号、`E'...'` 转义、逐行注释、嵌套块注释深度以及 dollar quote 的完整标签。引号双写和同标签闭合均需处理；普通 PostgreSQL 字符串中的反斜杠不按 E 字符串规则处理。
- 不在字符串或注释中的残留三反引号抛 `GenerationException.UNPARSEABLE`。不认识的语言围栏、行内围栏、多个代码块以及带前后说明的围栏回复不再“挑第一块”执行。
- 没有围栏的解释文本完整保留给下游校验拒绝，不推测它从哪个空行开始。多语句完整传给 `SqlValidator`，由单语句护栏拦截。

这里没有排序、Top-K 或权重。记录器仍用 `calls[].number`、`productionAttempts[].number`、`selectedAttempt` 分别追踪调用、尝试和选答；不能将“字符串里出现三个反引号”直接当成外层包装，也不能靠 SQL 字符串相同猜最终选答。原始文本与规范化 SQL 的来源由 `GeneratedSql.rawOutput/sql` 分开表达；正文日志仍受原有隐私开关控制。

### 极端边界与安全兜底

- 多行字符串、dollar quote、注释和双引号标识符中的围栏是正文，不删除、不截断。嵌套注释用深度而非单个布尔值追踪；dollar quote 必须同标签闭合。
- 缺一侧围栏只允许发生在回复最外层。残留内部围栏失败时不会搜索下一个看起来合法的 SELECT。
- 未闭合引号/注释、方言解析限制、未知别名、业务语义正确与否，仍由现有校验、数据库和评测负责。词法扫描不是完整 PostgreSQL 解析器，也没有放宽危险函数或数据库只读权限。
- 旧版会接受的“代码块后附一句解释”现在会拒绝。这是明确的兼容性收紧，可能影响真实模型完成率；本轮缺少原始模型回复正文，无法量化这种格式出现频率，不能保证新一轮总准确率必然上涨。
- 单侧围栏仍不能证明模型语义完整。例如缺失 WHERE 但已形成可解析查询，不能仅凭解析判为截断；现有服务端截断信号与语义契约仍各负其责。

### 为什么这样实现

没有选择全局删除反引号：会改变字符串或标识符。没有选择截到第一个分号：字符串、CTE、注释和多语句都可能被误处理。没有继续扩展“SQL 续行关键词白名单”：SQL 可以在任意合法词法位置换行，有限列表无法证明后文可以安全删除。

外层包装归一化和 SQL 校验分别负责格式与执行边界；词法状态只保护正文，不复制 SQL 语法分析器。代价是拒绝含糊包装和额外解释，收益是不会默默选取模型输出中最容易通过的一段。

**追问：为什么不把模型叫回来重新输出？** 明确的外层包装可在本地确定性处理；不能为每个格式问题支付一次重试。无法确定边界时才报错，并继续服从既有调用预算。

**追问：去掉围栏后是否安全？** 不是。格式处理不授予执行权限；多语句、写操作、危险函数、未知表列、计划成本和只读账号仍是独立防线。测试必须同时证明正常 SQL 正文保留和危险正文仍被拦截。
