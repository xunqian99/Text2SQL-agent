# 澄清短回复接续：实现、验收与技术导读

## 本批解决什么

生产与测试提交 `80d3667` 修复“系统问了口径，用户只回几个字却接不上”的链路缺口。销售额未说明是否含运费时，继续先询问用户，**不设置默认口径**。配置中的“含运费”和“不含运费”是用户可选答案，不是自动选择。

本批集中修改后只运行一次完整 Java 回归，**1,118/1,118 通过**，其中新增18项；真实受保护 HTTP 检查 **28/28**，包括此前17项与新增11个接续请求。12次模型替身调用只返回 `SELECT 1`，供应商调用0、供应商Token 0、实际供应商费用¥0。不能将接口通过率称为SQL生成准确率。

原200题逐项结构比较，澄清决策 **200/200不变**，仍10题需要澄清；没有新增评测题，没有改题、Gold、评分、历史失败或门槛。最新真实开发筛选70/100、正式三轮均值78.00%＜89%的结论保留；阶段2仍未整体验收，阶段3延迟目标继续暂缓。本批没有启动付费筛选或后台评测。

## 具体请求的数据流

在同一个 `sessionId` 下发送：

1. `2018年每月销售额是多少？`：编排器在检索前发现运费口径未定，返回 `NEEDS_CLARIFICATION`；会话保存原问题，确认列表为空。此次不生成SQL。
2. `不含运费`：在当前待确认规则的配置答案中精确匹配，记录 `term=销售额`、`group=legacy-hint`、原回复与服务端确认语句。模型最终接收原问题加“销售额按不含运费的商品金额计算”。
3. 澄清已经解除，重新检索Schema，再走既有生成、只读校验、预算与执行链路；最终响应的 `rewrittenQuestion` 可检查完整请求。终态被选定后清除待确认状态，并保存本轮历史。

另一条需要连续补充的链路：`2018年按类目统计价格平均涨跌幅，只看涨价记录` → `百分比` → `每条记录等权`。第二步只补单位，仍缺平均粒度，不调用模型；第三步同时具备两项后才进入生成。原年份、类目与涨价过滤不被短回复覆盖。HTTP检查断言完整请求确实进入生成提示，并非仅看状态码成功。

## 技术组件与来源追踪

| 组件 | 职责 |
| --- | --- |
| `ClarificationState` | 不可变的原问题与确认列表；相同term/group用最新确认替换，列表不无限累加 |
| `ambiguities.yml` 的 `replyOptions` | 配置允许的精确短回复、所属证据组和服务端规范表达；启动时检查组名和非空配置 |
| `AmbiguityDetector.replyTo` | 仅在当前仍未解决的规则内匹配答案；不在所有规则间随意解释短句 |
| `decisionsForState` | 回放原问题证据和已确认选择，判断还有哪些必需组未解决 |
| `ConversationSession.pendingClarification` | 保存当前会话的待确认快照；不使用跨会话全局“最近问题” |
| `Text2SqlOrchestrator.ConversationOutcome` | 只有被选中的终态能写入状态；请求修订号阻止旧请求恢复过期待确认问题 |

**身份凭据：** 原问题命中的 `required-pattern`、适用场景 `trigger-pattern/applicability`、旧规则 `legacy-hint` 与新增 `confirmed-reply` 分开记录。确认对象保存规则term、证据group、用户原回复和服务端canonical。原问题存在“客户还是卖家”等未决选择时，候选表达只标记为 `unresolved-base-pattern`，不能冒充已经确认。

**判定逻辑：** 没有打分、Top-K或概率权重。组内OR，必需组之间AND。价格单位已确认不能抵消平均粒度缺失。原问题含未决选择时，保守要求相关规则的所有必需组分别确认；原问题没有未决选择时，已经明确的另一组证据可继续使用。检索的直接命中、关系扩展、权重和截断机制均未修改。

**短回复匹配：** NFKC规范化、小写、去空白，允许去掉末尾句号/问号/感叹号，然后精确匹配配置。拒绝靠子串把“不要含运费”识别为“含运费”。长度超过120字符不作为短回复。`随便`、否定、候选二选一和未登记答案不变成确认。配置没有登录活跃用户的短选项，避免假装数据集存在登录事实。

## 会话边界与代价

- 待确认期间绕过通用LLM追问改写及旧Schema复用，确认后重新检索，避免短句检索漂移及沿用不匹配的表。代价是多一次本地检索，本批没有测出真实模型延迟或成本改善值。
- 识别为完整新请求或完整重述时，放弃旧待确认上下文，直接检查新问题。该识别使用关键词/长度启发式，**不是通用意图识别**；某些陌生短句带“统计/平均”等词可能被当作新请求，未知表达也可能多问一次。最可靠的换题方式是发送完整问题。
- 支持名单有限；`百分比，每条记录等权`这类组合回复没有登记时不保证解析，按两次短回复或完整重述使用。确认中途可以覆盖同一组，整条规则已解决并进入生成后，不再提供专门的短选项编辑模式。
- 多条价格指标用不同口径、跨句否定、未登记说法仍受原规则边界限制；本批没有实现每个输出指标的独立语义作用域。
- 无sessionId不保存待确认；不同会话分别保存。关闭时清空状态，同ID新建会话不继承旧状态。会话仅在内存，进程重启或缓存淘汰后需要完整重述，**不承诺澄清状态持久化恢复**。
- 请求超时使用现有“终态只选一次”的机制，迟到工作不能再次写入本次结果；只有最新准入请求能更新待确认状态。并发短回复不做事务合并，可能以后到请求的快照为准；客户端应等待上一轮响应后再补下一项。
- 明确口径只是给生成器正确输入，模型仍可能写错字段、分母或Join。SQL只读护栏无法证明统计正确，真实模型准确率必须另验。

## 为什么这样做与面试追问

没有让模型先把每条短回复改写成完整问题：那会增加一次调用，还可能悄悄更改年份、过滤条件或已选口径。也没有用全局“上一条问题”：它会让不同会话串用数据。选择有限配置答案加会话状态，收益是可解释、可审计、无需额外模型判断；代价是表达覆盖有限，需要完整重述兜底。

**追问：只把原问题和回复拼接不就行了吗？** 直接拼接无法区分“客户还是卖家”中的候选与已确认答案，反问也可能永远解除不了。这里用term/group与 `confirmed-reply` 明确覆盖对应选择，原业务约束仍保留，确认身份和规则判定分开。

**追问：并发或超时会不会把旧问题写回来？** 状态写入挂在现有终态选择处，校验当前会话实例、关闭状态和最新请求修订号；旧完成不能恢复待确认快照。不过这不是同会话并发事务合并，当前交互约定是一问一答，不能宣传为强一致多端协同会话。

## 后续与需要掌握的内容

这批接续功能已完成工程与免费接口验收；不据此关闭阶段2。后续应固定完整候选版本，在空闲时段执行既定一次开发筛选，过门槛才追加正式回归，不能每个小修复付费跑一遍。原严格评分中的澄清仍计错，不私自排除分母；阶段3加速和第三方独立盲测仍是欠项。

无需用户重新设置Key或启动额外服务。用户需要能解释：原问题怎样和短回复关联；哪一组证据尚未确认；为何此处无需LLM改写；一次澄清0供应商调用与后续生成的真实费用如何区分。28个HTTP检查和1,118项工程测试都不是新增评测题，原基准仍是200题。
