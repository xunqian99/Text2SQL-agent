# P1：离线评测面板阶段报告

日期：2026-11-21

阶段：课程设计实施计划 P1。变更性质：只读读取与展示，不启动模型、不执行评测、不改业务数据、不改题集、Gold 或评分器。

## 1. 阶段结论

P1 已完成。页面新增“离线评测面板”，后端提供 `GET /api/evaluation/reports`，从配置白名单读取历史 JSON/JSONL 报告，按配置条目重新聚合，并把题集身份、代码版本、Prompt 版本和每个源文件 SHA-256 一起返回。面板现在同时展示固定候选的 **85.33%** 和后续候选的 **78.00%**，没有把不同版本拼成一个“最好成绩”。

P1 的目标是固定评测证据，不是提高准确率。历史正式结果仍低于原 89% 门槛，不能把面板展示数字写成当前生产准确率。

## 2. 一个具体请求的数据流

用户打开页面并点击“离线评测面板”后，浏览器发送 `GET /api/evaluation/reports`：

1. `EvaluationReportController` 只调用 `EvaluationReportReader.read()`，接口没有 `path`、题目或模型参数，浏览器不能指定任意本地文件。
2. 读取器从 `agent.eval.dashboard.reports` 白名单取得三个条目：p15 三轮 JSON、p18 三轮 JSON、P0 Gold dry-run JSON。每个条目可绑定多个源文件。
3. 每个文件先读取原始字节并计算 SHA-256，再用 Jackson 解析。对象根节点按 `json` 处理，数组根节点按 `jsonl` 处理；JSONL 每行独立解析，空行跳过。
4. 对正式 JSON，读取 `overall`、`itemEvidence` 和 `byLayer`；对 JSONL，逐行累加状态、正确数、Token、费用和难度层。准确率按 `sum(correct) / sum(total)` 计算，避免三轮平均百分比产生分母偏差。
5. 返回只读 `DashboardSnapshot`。页面的 `loadEvaluationReports()` 将摘要渲染为 KPI、失败分类、难度层、Token/费用和源文件 SHA 列表；页面逻辑没有模型调用入口。

以 p15 三轮为例，三份 100 题报告被聚合为 `total=300`、`correct=256`，因此准确率是 `256/300=85.33%`；三份源文件路径和 SHA 仍逐个保留，不能把它误认成一份新生成的评测文件。

## 3. 核心技术与组件

- `EvaluationReportController`：Spring Boot REST 只读入口。
- `EvaluationReportReader`：Jackson 解析、JSON/JSONL 分支、状态分类、难度层聚合、Token/费用累加、SHA-256 指纹和缺失文件告警。
- `AgentProperties.Eval.Dashboard`：评测面板白名单配置；面板配置和评估运行器的 `outDir` 分离。
- `EvaluationReportReaderTest`：多 JSON 聚合、JSONL、缺失文件、HTTP 契约、历史 85.33%/78.00% 和 JSON 格式识别。
- `index.html`：原生 HTML/CSS/JavaScript 面板，不引入新的前端构建链；动态文本统一经过 `escapeHtml`。

来源身份不是一串扁平的“历史数字”：每个面板条目有 `id/label`，每个源文件有 `path/sha256`，摘要还保留 `datasetSha256`、`sampleIdsSha256`、`promptVersion`、`codeCommit` 和 `model`。这些字段共同证明数字来自哪一版题集、哪一版代码和哪几份原始报告。

面板没有 Top-K 表排序算法。这里的防挤压设计体现在统计聚合：正确数、题数、SQL 有效数和 UNKNOWN 调用数全部按源报告累加后再计算比例；p50/p95 使用源报告百分位的算术平均，并在页面明确标注“不是把不同版本单题延迟拼成新分布”。这样不会让某一轮题数较少的百分比挤压其他轮次，也不会把 UNKNOWN 用量静默当成零成本。代价是聚合延迟不是重新计算的全量样本百分位，不能拿它替代原始单题延迟分布。

## 4. 边界与安全兜底

- 配置为空、路径为空、文件缺失、内容为空或 JSON 解析失败时，条目被跳过并进入 `warnings`；不会伪造 0 分报告。
- JSONL 的坏行会触发该文件读取告警；已有文件不会被改写，面板也不会自动修复历史账本。
- `unknownUsageCalls` 单独展示；p15 为 15，p18 为 26。未知用量不会被计入已知费用，也不会被渲染成成功成本。
- 报告路径只来自服务端配置，不接受 HTTP 参数；读取过程没有模型客户端调用，也没有业务 SQL 写入口。
- Spring 启动检查发现读取器存在多个构造器但没有明确注入构造器，已用 `@Autowired` 固定生产构造器。否则单元测试可过而真实应用启动失败，这类问题不能留到演示现场。
- 页面补充内联 favicon，避免浏览器因为缺少图标产生无意义的 500 控制台错误；它不改变业务接口。

## 6. 设计取舍与面试追问

### 为什么不让浏览器传报告路径

如果接口接受任意路径，离线面板会变成本地文件读取器，既破坏只读边界，也无法证明页面数字来自登记版本。配置白名单牺牲了运行时灵活性，换来可审计、可复现的来源身份；新增版本必须改配置并重新验收。

### 为什么按三轮原始报告重聚合，而不是直接展示报告里的平均值

直接平均三轮百分比会在各轮题数不同或报告缺题时产生分母错误。读取器先累加题数和正确数，再计算 `correct/total`；延迟百分位保留“源报告百分位的平均”这一明确口径，避免假装拥有合并后的单题延迟分布。

### 面试官可能追问

1. **为什么 P0 Gold 是 100%，能否证明模型准确率 100%？** 不能。P0 是 dry-run，执行的是 Gold SQL 自检，Token 和费用均为 0；它只能证明数据库、题集和执行比较链路可用，不能替代付费模型评测。
2. **为什么 p15/p18 的费用只是“已知费用”？** 超时或供应商没有返回 usage 时，系统保留 UNKNOWN 调用并只累加已知 usage。把未知调用填成 0 会低估成本，所以页面单列 UNKNOWN，报告也不把它包装成完整账单。

## 7. 用户需要自己掌握的三件事

- **数据流**：白名单路径 → 原始字节 SHA → Jackson JSON/JSONL → overall/itemEvidence/byLayer 聚合 → 只读 HTTP → 页面证据卡片。
- **调用成本**：p15 已知 938,617 Token、¥0.591321，另有 15 个 UNKNOWN；p18 已知 953,880 Token、¥0.528084，另有 26 个 UNKNOWN。P1 自身没有新增模型调用。
- **错误归因**：结果不匹配说明执行成功但与 Gold 不同；超时说明请求在模型/预算阶段终止；澄清说明系统拒绝在口径不足时伪造 SQL。校验拒绝、执行失败、生成失败分类保留为独立边界，不能把所有失败都叫“模型答错”。

## 8. 需要用户配合的事项

本阶段不需要启动 Docker、提供 DeepSeek Key 或重新跑付费评测。若后续要接入新的历史版本，用户需要确认题集身份和报告路径，再把文件加入白名单；P2 请求回放属于可选阶段，当前没有自动开始。
