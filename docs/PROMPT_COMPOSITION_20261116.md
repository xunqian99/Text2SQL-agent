## 2. 具体请求的数据流与归因边界

T5-019输入：“发生过价格变动的商品，按类目统计平均涨跌幅和关联订单数，取订单数前20。”

`EvalItemLoader`选中dev题目后，`HybridSchemaProvider`经真实检索和上下文组装，`PromptTemplate`生成系统消息与用户消息。探针在生成器之前截取两条消息的长度、组成与`PromptFingerprint`，没有创建模型客户端，也不生成或执行答案SQL。初始化会读取数据库Schema元数据，因此这是“不调用模型”的本地诊断，并非完全不依赖数据库。

该题总长5444单位：系统2795、DDL及Join提示1713、数据画像187、示例618、问题37、其他94，指标和取值提示为0。选入8张表：`orders`、`product_price_history`、`products`、`product_category_translation`、`customers`、`order_items`、`order_payments`、`order_reviews`。这只是当前检索结果的记录，不宣称每张表都必要，也不证明所需连接全部正确。

本地指纹与low筛选两组的该题真实首答指纹相同：`ecaf654b0a4e97b5e4757cf9346d14a8272a443c62546e721befd9fda97b83c6`。此前默认与low都在MODEL阶段约15秒超时，没有取得SQL，没有进入答案SQL执行或纠错。5444并非本split最大长度6442，因此不能据此认定“最长上下文导致超时”，更不能归咎于数据库慢查询。

数据身份由`split`、题目ID、数据文件指纹、选中ID指纹、系统消息指纹和首答消息指纹分别追踪；报告中的`tables`、`retrievalTables`、`scores`、`expandedTables`、`evidenceOrder`与`columns`保留检索来源和顺序。本次只观察这些字段，没有改打分、衰减或Top-K，也没有用长度给表重新排序。

## 4. 技术与设计导读

**机制与技术抓手**：`PromptDeterminismProbe.capture()`调用生产检索与模板，按渲染后的八项互斥内容计长；四步指令是system内部的子集，单列观察而不再加进总和。审计脚本按ID连接捕获报告与真实`itemEvidence.calls[0]`，避免把纠错Prompt当首答。Java字符串计长简单且可复现，代价是不能直接换算供应商Token或费用。

**实际收益**：200条组成核对、600次重复比较、194条真实首答对齐均通过；新增模型调用和模型费用为0。结论收窄了下一项实验：不能再笼统把输入体积都归到DDL，更不能宣称删除259单位就能解决P95。本次不产生新的准确率数字，亦无已证实的模型加速收益。

**替代方案与边界**：没有直接砍Schema、减少示例或关闭所有推理和护栏；这些会同时改变能力与输入，无法定位收益来源。后续可先在dev100做“仅去除显式四步推理指令”的单因素实验，保留18条规则、相同用户消息与检索结果，独立记录候选版本并先冻结协议。它可能减少模型推理，也可能损害复杂题正确率，尚未验证。只有完整费用、准确率和P95同时满足原门槛，才值得进入正式三轮，不能因为文本短了就上线。

**面试追问一：为什么55%的文本占比不能推导55%的延迟占比？** 文本长度不是Token数，生成耗时还受推理与输出、缓存、供应商调度等影响；需要同输入的同期对照和逐调用账目。

**面试追问二：指纹相同为什么仍会一轮对、一轮错？** 指纹只证明应用传入的消息一致，不证明供应商的内部模式、输出或执行调度确定；必须保留逐轮结果，重复运行也不增加不同题目数。

用户无需配合重配环境。需要掌握的三点仍是：请求在哪一步产生Prompt、每次实际调用花多少、错误发生在检索/生成/口径/执行哪一层。本次T5-019定位到MODEL等待超时；尚未取得SQL，不能继续给它编造Join或聚合错误归因。
