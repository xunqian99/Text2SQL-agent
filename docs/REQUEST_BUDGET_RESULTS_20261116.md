## 4. 瓶颈与证据边界

关闭组生成时间约占总服务墙钟98.15%；开启组`budget.stageMs.MODEL`约占98.15%（包含等待超时的模型阶段）。关闭组29/300题超过8秒，开启组33/300。15秒截止能截断极慢尾部，但无法让8–15秒的大批正常模型首答更快。当前主要瓶颈在生成，继续调数据库索引或关闭澄清没有本轮依据。

下一项实验仍属于阶段3：在开发集上单独降低输出Token上限，统计`INCOMPLETE_RESPONSE`、正确数、已知/未知费用和P95；不得同时调检索、改题或换评分器。若输出截断损伤准确率，需要回退，不能只报更快的请求。先做小规模筛选，再冻结验收，不为了过8秒直接把请求超时改成8秒。

相同新代码下比较off/on，包含JDK传输与SDK `maxAttempts=1`，因此历史旧SDK三轮不是同期基线。98个实际首答问题在全部六轮的Prompt哈希一致；另2题澄清无Prompt。输入题目、Gold SQL和结果哈希、调用编号、停止尝试、选答与总账均已核对。原始报告SHA-256见[manifest](../reports/request-budget-matrix-20261116/manifest.json)，归档按原字节保存。

模型供应商权重、负载和输入缓存未被完全固定。机器/数据库保持同一环境，但部分运行时间与子agent的内部只读核查重叠，没有提供独占资源隔离；本轮不是并发吞吐压测。整体工作区DIRTY源于用户演示稿和非被测输出，保护的生产路径、题库、本地配置字节保持冻结。3轮不足以给出强统计因果结论，P95上升0.777秒不能单凭该均值归因于预算线程开销。

## 5. 技术与设计导读

**具体请求**：“2018年订单数”进入`RequestBudgetRunner`，创建`requestId`和单调时钟截止点，检索、生成、SQL校验/执行与纠错共用预算。网络前记`IN_FLIGHT`并占次数。假如模型迟迟不答，15秒左右停止等待并触发连接关闭，返回HTTP504；`REQUEST_STOP`封存评分证据，未知usage保留为未知。本轮5个超时全部在MODEL阶段，最大返回偏差13ms。

**技术抓手**：`RequestBudget`维护共享时钟/账本；16个工作线程和无等待队列限制后台增长；`BudgetHttpRequestFactory`取消真实响应体；`BudgetJdbcGuard`先cancel再abort并用资源锁保护已归还连接；`EvaluationTrace`与`LlmCallLog`以`requestId + callNumber`追踪停止与晚到记录。调用完成时，已知账目和内存证据在同一预算锁内更新，避免截止瞬间一边算已知、一边仍记未知。

**收益和代价**：关闭组曾有30.835秒请求，开启组最大15.013秒；但P95仍11.842秒，没有实现目标响应速度。未知费用是取消的可观测性代价，不是免费请求。真实数据库取消、滴流HTTP、16线程饱和、首答回退与晚到日志均有工程测试；生产真实评测只观察到模型首答超时。

**方案权衡**：只加单次HTTP超时会让多次调用上限相加，只cancel Future不能证明数据库已停，因此采用共享截止+资源钩子+有界工作池；仍承认驱动不响应、清理排队和供应商继续计费的边界。剩余2秒只用于重试准入，不预测模型2秒必能完成。

面试追问：“为什么有截止点，P95反而没过？”回答应拆开资源上限与响应效率；给出98.15%的模型耗时、8秒以上请求数量及全量失败分母，承认截尾机制不是生成加速。“为什么不能说费用降了？”回答应说明5次未知usage、已知下界、晚到记录和供应商账单是不同证据，不能凭应用收到的Token证明最终计费。
