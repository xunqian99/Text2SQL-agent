# B：完整授权目录校验与本地工程基座

范围：只修复生成上下文与执行白名单混用的问题。A已接受；B候选已完成免费验证，独立审查结果另见本包decision。阶段2、阶段3和整体目标均未完成，V4仍不准入付费评测。

## 实现与数据流

具体请求：“列出工单与类别”。受控HTTP集成让生成上下文只含`support_tickets.ticket_id`，模拟检索遗漏`ticket_categories`且剪掉`support_tickets.category_id`。模型替身返回：

```sql
SELECT st.ticket_id, tc.category_name
FROM support_tickets st
JOIN ticket_categories tc ON st.category_id=tc.category_id
LIMIT 5
```

旧边界用这一张表/一个列的检索子集校验，会把真表真列当成不存在。新链路依次为：鉴权及费用预留 → 原检索/剪枝上下文生成 → `fullSchema()`取得37张授权业务表的完整列 → 原AST护栏校验 → 原EXPLAIN代价保护 → 真实只读PostgreSQL执行。HTTP返回200及5行，`schemaTableCount`仍为1，检索统计不会冒充37表全召回。实际首答输入的另一组证据经真实`ask→LlmSqlGenerator→ChatModel.call`捕获；模型替身与SQL执行替身不访问供应商，不能称为供应商已发送输入。

两种对象不混写：`schema`保存生成时原始检索上下文，继续进入`RequestBudget.schema`、会话和检索统计；`validationSchema`只是执行前完整目录的局部变量。`FullSchemaProvider`和`HybridSchemaProvider`仍委托同一个`SchemaCatalog`。目录来源为只读角色可见的`public`基础业务表，读取器排除`schema_chunks/semantic_cache/llm_call_log/conversation_session/conversation_turn`五类内部表；完整目录不等于任意数据库对象。

缓存SQL也必须重新经过完整目录。缓存命中遇到目录故障直接返回，不回退生成。首答遇到目录故障不进入纠错；首次生成异常、自动纠错和显式纠错均在发送可选模型调用前检查目录，可用才准入。目录正常时原可恢复生成失败仍允许最多两次调用。纠错时遇到故障优先返回该终止结果，不用先前成功但可疑的答案掩盖故障。已经发生的首答/纠错调用费用照常合并；如第一次已执行，后次故障只能保证后次执行为0，不能倒抹第一次执行历史。目录正常后才发送纠错，但发送后目录可能新近失效；此时保留已发生两次调用并终止后续执行，不伪称能预知未来故障。

五个数据库工具每次调用只取一个完整目录快照，SAMPLE/CHECK/EXPLAIN不再拿剪枝目录校验；INSPECT两种工具也共用同一入口。`ToolResult.schemaUnavailable`是本地布尔控制信号，`AgentToolFunctions`在本轮保存粘滞故障标记；`AgentLoop`每个工具后检查，立刻终止同轮后续工具、下轮模型和最终收口。错误观察文本不承担终止判断，因此模型文字无法伪造这一标记。循环抛出的`SCHEMA_UNAVAILABLE`带上已发生的合并调用记录，编排层返回带该违规码的REJECTED（HTTP422，沿用现有状态映射）。

## 组件与边界

- `SchemaProvider.fullSchema()`：默认明确抛出未实现异常，禁止用空问题检索伪装全量目录。
- `BusinessSchemaUnavailableException.require`：拒绝null、空目录、损坏表/列；普通运行异常隐藏连接详情并归为目录故障；原请求预算中断继续上抛。
- `Text2SqlOrchestrator.validateAndExecute`：最终、固定SQL、缓存、纠错共用完整目录，原解析器、LIMIT、执行计划和只读连接保护继续生效。
- `ToolExecutor/AgentToolFunctions/AgentLoop`：目录故障与模型可纠正的普通工具错误分开，禁止额外模型重试与绕行执行。

没有改检索排序或提示词。原检索仍保留直接命中与`expandedTables`来源：扩展分数为源分×0.4×关系边权，多条路径取最大而不累加，直接命中分数不被扩展覆盖；排序先分数、同分直接命中优先，再按表名字典序，TopK=8，桥接最多2表。这里并无“所有直接命中都保送”的保证：高分扩展仍可能压过低分直接命中，2表也未必能补通关系。B没有用全目录伪造召回率，也没有调这些权重追分。

保留的能力边界：既有列校验按`columnsOfTable`及`aliasToTables`核对已识别限定列，不把全库列名压平；裸列、派生表及跨作用域复用的不可判定别名仍非完整SQL类型推导。部分虚构裸列会通过静态校验，再由只读数据库拒绝。B不扩充此解析器，也不把“能执行”当作业务口径正确。显式`public.orders`仍按原保守规则拒绝；不借本包放宽名称解析。目录是进程内缓存快照，运行中DDL/授权变更须重启重建，不宣称在线权限刷新或解决元数据/执行之间的竞态。只读角色与数据库权限仍是最后一层防线。

## 为什么这样设计，以及面试追问

替代方案一：把37表全部塞回模型。会增加输入且削弱检索收益，仍不能代替权限校验。替代方案二：遇到UNKNOWN_TABLE就关白名单或放行给数据库。会把内部/跨schema授权边界一并撤掉。替代方案三：每次实时重读全库目录。本包使用共享缓存快照，减少请求链路元数据开销，代价是显式承认DDL变更需重建快照；没有把缓存当作动态授权系统。

面试问题1：“为什么模型没看见的表也允许执行？”回答必须区分检索相关性与对象授权：生成少看信息是降低输入的策略，授权目录才决定可访问哪些物理对象；漏检导致生成错误仍会影响答案，完整目录只消除本地误拒，不保证生成正确。

面试问题2：“目录断了为什么不让模型修复，费用怎么算？”模型不能修复数据库元数据或授权故障，因此该故障是不可纠错的控制信号；缓存故障0模型，生成后故障保留已发生用量，工具故障停止后续调用。费用预留已知结算、未知继续占用；不能因为最终失败就把账抹为0。本包的供应商费用0来自使用内存替身与禁外网端点，而非宣称每次真实失败免费。
