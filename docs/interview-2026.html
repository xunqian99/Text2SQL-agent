Part 0 · 三版项目介绍

5 题
考点你有没有「评测驱动」的意识，而不是只会调 API。
我做了一个 Text2SQL Agent，把中文业务问题翻译成只读 PostgreSQL SQL。它不是一个「生成 SQL 的 demo」，重点在可评估：我自建了 200 条六层评测集，三次独立运行执行准确率 84/85/86，SQL 有效执行率 100%；16 条失败逐条归因，没有一条是检索错误，7 条是输出列形状。工程上是 Java 21 + Spring Boot，词典检索 + Join 拓扑 + AST/只读账号/超时三层护栏，280 项测试、53 条对抗。
项目解决的是「中文问题 → 可执行 SQL」这条链路。难点不在写 SQL，而在四件事：选表、业务口径、Join 拓扑、结果形状。 链路是：问题进来先做多轮改写/澄清/缓存；然后 Schema 检索，从 37 张表里召回 Top-8，并做连通性修复；再注入 metrics.yml 的业务口径和枚举值对齐；Prompt 里放 schema、指标、枚举、问题，调 DeepSeek 生成 SQL；生成后过 JSqlParser AST 白名单、EXPLAIN 代价护栏、只读账号执行；最后做 8 条启发式结果检查和必要的错误回灌重试。 评测是执行准确率：gold SQL 和生成 SQL 都执行，ResultNormalizer 规范化后比结果集，不是字符串匹配。三次运行 84/85/86，T1 100%，T5 40–60%。失败里检索 0 条、输出形状 7 条，所以瓶颈在「模型和 gold 的结果约定」，不是「找不到表」。 我知道它的边界：T5 深层 Join 只有 40–60%，P95 12–17s 没达到 8s，单租户、无 RLS，不做写操作和多方言。
追问为什么不直接说「准确率 86%」？

单次最高值不可复现；三次 84/85/86，12 条稳定失败、6 条波动，写范围比写最高值诚实，也经得起对照报告。

答（按「问题 → 设计 → 数字 → 边界」讲）：

  1. 问题：37 张表、201 列、13 条真实外键；中文和物理 schema 之间没有词边界，模型容易选错表、猜错列、写错口径。
  2. 检索：领域词典最大匹配（长词优先、单字权重 0.5）→ 关系扩展（源分数 × 0.4 衰减 × 边强度，取 max）→ 全序排序（分数 → 直接命中 → 表名）→ Top-8 → BFS 最短桥接修复（最多补 2 张）。表全召回 98.00%、平均召回 99.55%、精确率约 28%。
  3. Join：外键 1.0、词典关联 0.5；以最相关表为根，对每张目标表求加权最短路并取并集，再按「强度 → 相关度 → 表名」做 Prim 式生长，输出 JOIN PLAN。
  4. 口径：metrics.yml 维护 GMV、复购率、客单价等 23 条可注入指标；按关键词 + 依赖表过滤，T6 三次 34/36。
  5. 护栏：AST 只允许单 SELECT、表/列白名单、函数黑名单归一化、CTE 数据修改 / FROM 表函数检查；只读账号 text2sql_ro；10s 超时 + 200 行上限；53 条对抗全绿。
  6. 评测：200 条六层，id 哈希切 dev/eval；执行 gold + 生成 SQL，规范化后比结果集；三次 84/85/86；16 条失败全是 SUCCESS，检索 0 条。
  7. 成本：第三次 cache-aware 102 次调用，prompt 199,436 + completion 48,992，cache 命中 89.27%，¥0.221/100 题，单题 ¥0.002209。
  8. 边界：T5 40–60%、P95 12–17s、单租户无 RLS、28 张扩展表是合成数据、eval 有泄漏风险。
难的不是让模型写出一条能跑的 SQL，而是让它在 37 张表里选对表、连对路、用对口径、输出对形状；更难的是一旦错了，你能说清错在哪一层。我的 16 条失败里检索 0 条，7 条是输出列形状——这句话就是这个项目的价值。
不做写操作、多 SQL 方言、模型微调、多租户/RLS；P95 没达到 8s；成本只算 LLM API，不含数据库/机器/人工。这些不是「没做完」，是明确的范围取舍，写在 README 的「已知局限」里。

Part 1 · 总览与数据流

8 题
考点你能不能按数据流讲，而不是按类名堆。
  1. AskController 收 JSON，校验 question 长度、sessionId 格式，映射 HTTP 状态码。
  2. Text2SqlOrchestrator.ask()：多轮场景先判断是否追问，做改写/澄清/缓存；再取 Schema。
  3. SchemaProvider：FullSchemaProvider（baseline）或 HybridSchemaProvider（检索 + Join 拓扑 + 口径 + 枚举 + 列剪枝 + few-shot）。
  4. LlmSqlGenerator + PromptTemplate：拼 system/user prompt，调 OpenAI 兼容模型，记录 token/延迟/成本。
  5. SqlValidator：多语句 → AST → 必须 SELECT → 函数黑名单 → 表/列白名单 → 补 LIMIT maxRows+1。
  6. QueryPlanAnalyzer（可选）：EXPLAIN JSON 代价/笛卡尔积护栏。
  7. SqlExecutor：只读连接、10s 超时、200 行上限，多取 1 行判截断。
  8. ResultChecker / 自纠错：8 条启发式规则，命中可疑就把错误回灌重试；失败保留首次结果。
  9. AgentResponse：SQL、列/行、召回表、分阶段耗时、token/成本、会话字段。
追问为什么编排层不放在 Controller？

HTTP 和 EvalRunner 两个入口必须共用同一条链路，否则评估测的不是线上行为；Controller 只做协议转换。

评估要证明「线上真实行为」，不是另一套复制逻辑。EvalRunner 直接调 orchestrator.ask()，和 /api/ask 走同一条检索、生成、校验、执行、记账链路；差异只在入口和报告聚合。这样报告里的 84/85/86 才能代表线上。

  • 我需要精确控制每一阶段的失败分类和耗时：检索错、生成错、校验拒、执行错、结果口径错，这五类要分开统计；框架黑盒会把它们揉成一个「Agent 失败」。
  • 评估要求同一条链路可复现，手写 Pipeline 的输入输出都是显式的，报告 meta 能记录每个开关。
  • Spring AI 只用来做 OpenAI 协议适配，编排、重试、缓存、会话都是自己写的；不是「不用框架」，是「不用框架接管控制流」。
追问手写 Pipeline 的代价是什么？

要自己处理状态、重试、超时、并发和可观测性；换来的是可解释和可测试。这个项目里 280 项测试和逐条失败归因，就是这笔交易的收益。

baseline 必须随时可复现。检索、口径注入、few-shot、缓存、多轮、Agent、自纠错、代价护栏默认都是 false；application-local.yml 才打开。这样「加了检索提升多少」才是干净的对照，而不是默认值悄悄生效。代价是第一次跑的人容易以为「怎么只有 baseline」——README 写清了要用 local profile。

  • 9 张是真实 Olist 表（orders、order_items、customers、products 等），28 张是扩展表（会员、优惠券、退款、结算、库存、工单等），数据按真实订单反推生成。
  • 影响：T5/T6 大量跑在扩展表上，真实库的脏数据、空值、口径冲突覆盖不足；所以 84–86 只能当内部回归基线，不能宣称跨库泛化。
  • 我没有把扩展表说成「37 张真实业务表」；简历和 README 都写了 9 真实 + 28 扩展。
  • AgentLoop + ToolParser + ToolExecutor 实现了 5 个只读侦察工具（INSPECT_TABLE / INSPECT_COLUMN / SAMPLE_QUERY / CHECK_JOIN / EXPLAIN_QUERY），最多 3 轮，模型用 [TOOL_CALL] / [FINAL_SQL] 交互。
  • 但默认 tool-use.enabled=false：主链路是确定性 Pipeline，不是自主 Agent。评估集上 Agent 模式没有量出增益，所以 84–86 不算它的功劳；保留它是为了证明「37 表上工具侦察不划算」这个负结果。
追问那你还叫它 Agent？

叫「Agent 编排链路」可以，叫「自主 Agent」不行。我的简历写的是「Agent 问数系统」，但我会主动说明默认是 Pipeline。

  1. LLM 调用：同步阻塞、单次 2–20s，先撞限流/超时；没有队列、限流、熔断。
  2. 数据库连接池：Hikari 只读池 5 个连接，慢查询会占满。
  3. 内存：会话 LRU 1000、缓存 LRU 1000、BYOK 客户端 LRU 32，目前有上限，但单实例。
  4. 没有鉴权/租户隔离：公网部署前必须加。
追问怎么改？

异步化 + 队列削峰、按 token/并发限流、连接池按负载调、加 requestId/trace、把评估和线上隔离。

  1. 输出形状：把「每个指标返回哪些列、精度、聚合口径」做成 metric registry 的显式字段，而不是靠 18 条 prompt 规则猜——这是 7 条失败的最大类。
  2. T5 桥接表：把 4+ 表的桥接路径和输出形状单独评测，不要只用整体 84–86 掩盖 40–60%。
  3. 可复现/CI：固定 profile、seed、数据 hash，CI 带真库跑集成测试；现在的 CI 无库会跳过 9 条。

Part 2 · 评测体系与数字

12 题

把 gold SQL 和生成 SQL 都执行，ResultNormalizer 规范化后比较结果集；每题对/错二值。不比字符串，因为同一个问题有无数种正确写法（JOIN/子查询、别名、大小写），字符串匹配会把正确答案判错。也不是 LLM 裁判，裁判本身有偏差。

  1. 数字统一四舍五入到 4 位小数，去掉多余零；禁止科学计数法（610 不能变 6.1E+2）。
  2. NULL 与空字符串区分；JDBC null 归一成 NULL。
  3. 完整日期和当天零点 timestamp 归一成 yyyy-MM-dd HH:mm:ss；2018-01、2018-Q1 不展开。
  4. 行顺序：只有 gold 同时有 ORDER BY 和 LIMIT 才按有序列表比；否则按多重集比。
  5. 列名不参与比较，但列位置参与；不支持自动换序列对齐。
追问为什么列名不比？

业务关心数字和列位置，不关心别名；但列位置参与，因为「多一列/少一列/列换序」都是结果形状错误。

200 条按 Math.floorMod(id.hashCode(), 2) 切 dev/eval 各 100；few-shot 只从 dev 取。按 id 而不是按行号，是为了排版/顺序调整不改变样本归属；不按难度层切，是因为那样 dev 全是单表题，多表和业务语义没法调参。

追问这能保证无泄漏吗？

不能。开发期看过全量 200 条，eval 也跑过多组配置；只能作内部回归参照，不能宣称无泄漏泛化。

  • T2-004：gold ROUND(AVG(cnt),4)，模型 ROUND(...,2)；逻辑一样，只差精度。
  • T2-015：gold 输出 level_id，模型输出 level_name 并多 join 了 member_levels；输出列形状错。
  • T3-018：gold 用 orders.order_delivered_customer_date - order_purchase_timestamp，模型用 shipments.delivered_at - shipped_at；「配送时长」口径不同。
  • 另外 T4-013 的 COUNT(*) vs COUNT(DISTINCT order_id)、T5-018 的「成对行」vs「same/diff 两列」也是典型。

Part 3 · Schema 检索

10 题

实测 PG 的 to_tsvector('english','统计每个州的订单数量') 把整串当一个 token，simple 也一样；pg_trgm 的 show_trgm('订单数量') 返回空数组。中文没有空格，PG 内置分词对中文是死的。我没有引入 embedding/pgvector，因为检索的难点不是「相似度」，是「中文词 → 哪张表」的领域映射；词典最大匹配零依赖、可审阅、可增删，先拿一个干净 baseline。以后要加向量，是增量，不是替换。

把 glossary 里的表别名、列别名、枚举 label 展开成 MatchTerm，按词长降序；从左到右扫描问题，在每个位置找最长匹配，命中后跳到词尾，避免「订单明细」同时命中 order_items 和 orders。单字别名（州/券/仓）权重 ×0.5，兼顾召回和误命中。不用 jieba，是因为通用分词能把「复购率」切成「复购」「率」，但它不知道「复购」对应哪张表；难点是领域映射，不是切词。

从直接命中的表出发，delta = 源表分数 × 衰减(0.4) × 边强度；同一张表可能有多条路径可达，取最大分数而不是累加。累加会让「邻居多的表」靠数量堆分数，而我们要的是「最强的那条路径有多可信」。扩展只从分数最高的 3 张表出发，避免一个宽泛问题扩出十几张表。

Top-8 选出来后，先在「已选表」内部做 BFS 求连通分量；如果多于 1 个分量，就从 0 号分量做多源 BFS，第一次碰到属于其他分量的已选表，就是最短桥；把路径上的中间表补进来。预算最多 2 张，装不下就整条放弃，保留不连通（模型会报错，错误可见），而不是悄悄把上下文撑爆。它和「把 topK 调大」的区别：只补能消除不连通的那几张，已经连通的一张不补。

评估集里 4 表以上的题只占 20 条，gold SQL 最多用到 6 张表，8 留了余量；dev 上 Top-5 和 Top-8 做过对照：Top-8 多答对 2 题、完整召回多 7 题，代价是平均多约 103 个 prompt token。但我也保留不利证据：早期 eval Top-5 是 54%，高于最终 Top-8 的 52%；单轮差异不能证明 Top-8 更好。

这是召回优先的取舍：Top-8 先保证「该用的表在里面」，代价是上下文有噪声表。精确率 28% 意味着平均召回 6.85 张里只有约 2 张是 gold 表；噪声靠生成、AST 和执行兜底。我不宣称精确率，因为在这个任务里「漏表」比「多表」更致命：漏了必然错，多了只是浪费 token、可能干扰模型。

追问为什么不把精确率做高？

可以做 rerank/分类器，但需要标注和评估；当前优先级是召回和结果正确，精确率是下一迭代的事。

剪枝只裁「明显无关」的列，以下永远保留：

  1. 主键、外键（数据库元数据里的真实主键，不靠列名猜）；
  2. ValueRetriever 命中的枚举/实体列；
  3. 命中指标 expression/filter 引用的列；
  4. 问题文本里直接出现的列名/中文别名；
  5. 时间语义问题的日期/时间列；
  6. 度量措辞问题的数值列；
  7. 少于 minColumns 时按注释和原顺序补齐。

裁掉主键/外键，join 直接断；裁掉指标列，模型只能猜列名；裁掉枚举列，WHERE 会写中文值。这些都是实测踩过的坑。

从 glossary 的 enum 定义和巴西 27 州映射里建倒排索引（别名 → 表/列/物理值），按别名长度降序做包含匹配；命中后注入「问题中的『圣保罗』对应 customer_state = 'SP'」这样的提示。它解决的是「模型把州写成『圣保罗』、把状态写成『已取消』」的静默错误——SQL 能跑，但结果恒为 0。

失败模式有四类：词典没收录（OOV）、单字误命中、桥接表漏召回、精确率低。词典一个词都没命中时，回退全量 schema（37 张表），宁可多给上下文，也不能因为词典没收录就把必要表筛掉；回退率本身是要监控的指标，回退高说明词典覆盖不足。

三步：1）用 gold 表构造正样本、用 Top-8 里的非 gold 表构造硬负样本，训一个轻量 reranker（逻辑回归/GBDT 即可）；2）加表级特征：词典命中类型/权重、与已选表的连通距离、是否被指标依赖、是否在问题里出现英文标识符；3）在 dev 上做消融，确认召回不掉。不会直接上大模型 rerank，成本和延迟不划算。

Part 4 · Join 拓扑规划

8 题

边列表只回答「哪两列能连」，不回答「先连谁、后连谁」。多表题里同一组表可能有多条路径都连通，比如 T5-001 的 orders → customers → members → member_levels 和 orders → coupon_usages → members 在图上都通；只给边，模型眼里两条路径等价，容易选错。生成树给的是「推荐顺序」，边列表给的是「备选关系」，两者都要有。

  1. 以检索分数最高的目标表为根；
  2. 对每张其他目标表，在「外键权重 1.0、词典关联 2.0」的图上跑 Dijkstra，取最短路径；
  3. 把所有路径的边取并集，得到候选子图；
  4. 在候选子图上做 Prim 式生长：每轮从边界挑一条边，优先级是「边强度降序 → 新连表的相关度升序 → 表名」；
  5. 输出 from.col = to.col -- table [FK]/[约定] 的等式形式，模型可以直接抄进 ON。

外键是数据库强制约束的硬事实，强度 1.0；词典关联是人工核对的软知识，0.5。强度只能区分「硬/软」，不能区分「软知识里哪条更该走」；T5-001 第三轮出现三条 0.5 的候选边，如果按表名字母序，coupon_usages 会排在 members 前面，主干就变成「经优惠券到会员」——正是错的那条。加上检索相关度做第二键后，members 排名更高，主干回到 gold 的路径。

树是给模型照着写 SQL 的，从事实表（orders、order_items）出发符合 SQL 自然写法；从维表（regions）出发会得到语义别扭的树。检索分数已经排好「哪张表最相关」，直接复用，不再造启发式。

Plan.incomplete() 会判断「树覆盖的表数 < 上下文表数」，渲染时加一行「注意：还有 N 张表与起点不在同一连通分量，本段未给出连接顺序；它们的关联见上面的 JOINS」。这不是装饰，是防止模型把 JOIN PLAN 当成「全部 join」而漏表；漏表的错误是「SQL 能跑、结果错」，最难查。

三件事：1）只为「核心目标表」规划，核心表不足 2 张就完全不输出 JOIN PLAN，杜绝单表题被强行 join；2）JOINS 列表和 JOIN PLAN 两个开关独立，阶段 3 实测过「给多了」和「规划错了」要能拆开；3）prompt 明确「只连问题需要的表」。过度 join 的代价是行数放大和口径偏移，不是语法错，所以必须单独评测。

只要 join 后可能一对多，就用 COUNT(DISTINCT 主键)；单表、无 join 才用 COUNT(*)。T4-013 差评订单按州统计，评价表一单多评，COUNT(*) 会重复计数；T4-017 会员等级订单数同理。这不是「写法偏好」，是口径错误——计数口径错了，分组结果整体偏移。

两者都有，但输出形状更大。T5 的失败里既有桥接表漏召回（T5-007 漏 member_levels、T5-018 漏 order_items），也有输出形状完全不同（T5-018 gold 是成对行，模型是 same/diff 两列）。Join 规划解决「能不能连」，输出形状解决「连完输出什么」；后者是 prompt 和指标注册表该管的，当前没完全管好。

Part 6 · 校验与安全

10 题

prompt 是概率性约束，模型 99% 遵守，剩下 1% 可能给你 DROP TABLE orders；在生产库里 1% 就是灾难。正确心智模型是：LLM 输出等价于不可信的用户输入。既然不会把用户输入直接拼进 SQL，也不该把模型输出直接执行。所以 AST 校验的定位不是「提升准确率」，是「让错误无害化」。

  1. 多语句检查：先剥尾部分号，parseStatements 数量 > 1 就拒；
  2. 解析 AST，解析失败一律拒绝（fail-closed）；
  3. 必须是 Select，挡住 DROP/UPDATE/DELETE/INSERT/ALTER/TRUNCATE；
  4. 递归遍历函数黑名单，函数名归一化（小写 → 取最后一个 . 之后 → 去首尾双引号）；
  5. 表白名单 + 带别名列白名单；再检查 CTE 数据修改 / FROM 表函数；
  6. 强制 LIMIT：需要 LIMIT 且没有时，APPEND maxRows+1 或 REJECT。

用解析器而不是数分号，因为分号可能出现在字符串字面量里（WHERE name = 'a;b'）。解析器会把结尾多一个分号也算成一条语句，所以先循环剥掉尾部分号再 parseStatements；SELECT 1; DROP TABLE orders 会被解析成两条，直接拒。

黑名单里是裸名 pg_sleep，但 JSqlParser 的 Function#getName() 可能返回 pg_catalog.pg_sleep、"pg_sleep"、pg_catalog."pg_sleep"；直接比裸名，加一个前缀或一对引号就能绕过。归一化顺序：小写 → 取最后一个 . 之后 → 去掉首尾双引号。这三个洞是实测出来的，不是假设。

裸列名的合法来源太多：SELECT 别名、GROUP BY 位置、CTE 输出列、派生表列、集合操作两侧同名列；一旦判错，正常查询会被拦下，护栏就从「防护」变成「故障源」。带前缀的列（o.customer_id）能精确归属到某张表，判定是确定的，所以先把这一半做扎实。

追问别名作用域问题怎么处理？

T6-016 里外层 FROM brands bp、CTE 内 FROM brand_products bp，同一别名指两张表；压平后会误杀。修法不是实现完整词法作用域，而是承认边界：只要某个别名被绑定到过 CTE/派生表，该别名的列一律不判定；多个候选表都没有这一列时才报错。少拦几条，换不误杀。

  • WITH x AS (DELETE FROM orders RETURNING *) SELECT * FROM x 最外层是 PlainSelect，只判 instanceof Select 会放行；真正的 DELETE 藏在 WithItem 里。对 DML CTE 调 WithItem.getSelect() 会抛 ClassCastException（内部裸强转 ParenthesedSelect），必须用 WithItem.getStatement() 拿到原始语句，再判是不是 ParenthesedSelect。
  • FROM dblink(...) / pg_ls_dir(...) 走 FromItemVisitor，函数黑名单的 ExpressionVisitor 覆盖不到；在 FromItemVisitor 里遇到 TableFunction 直接拒。
  • 这两条是 H2/H4，已补 6 条对抗用例（3 条 DML CTE + 3 条 FROM 表函数），AdversarialSqlTest 47→53。

第二层（AST → 只读账号 → 超时/行数）。text2sql_ro 只有 SELECT，没有 INSERT/UPDATE/DELETE/TRUNCATE/CREATE；就算 AST 被绕过，数据库也会拒绝写。它不能防「合法 SELECT 越权读」：没有 RLS、没有列级权限，单租户；公网部署前必须加鉴权和行级/列级授权。

执行层要知道「结果是被上限截断的，还是恰好这么多行」。如果补 maxRows，数据库最多返回 maxRows 行，执行层无论怎么多读一行都读不到，truncated 永远是 false，调用方会以为拿全了。补 maxRows+1，执行层取到第 201 行就判定截断，再把多出来那行丢掉，对外仍然最多 200 行。

CHECK_JOIN 的连接条件来自模型输出，等于不可信输入；直接拼进 ON 子句会开注入面（任意 SQL 片段、ON 1=1 笛卡尔积）。现在强制 表.列 = 表.列 的正则，表名必须命中 catalog 且不能相同，列必须真实存在，等值两侧必须分别来自两张表；不满足就拒绝。这样既防注入，也防「自己连自己」。

提示注入方面，AST + 只读账号能保证「不能写、不能执行危险函数」，但不能保证「不泄露合法表里的数据」；如果用户诱导模型查薪资表，只要表在白名单里，就是合法 SELECT。当前没有 RLS/列级权限，这是明确边界；公网部署要加鉴权、租户隔离、行级授权、限流。语义错误（SQL 合法但口径不对）不属于安全漏洞，属于准确率问题。

Part 7 · 执行、结果与自纠错

8 题

1）只读事务 setReadOnly(true)，PostgreSQL 在协议层拒绝写；2）setQueryTimeout(10s) 防慢查询占连接；3）setMaxRows(maxRows+1) 防大结果集打爆内存，多取一行判截断。形态合法 ≠ 资源可控，所以超时和行数上限不依赖校验层。

setReadOnly 是数据库层面的兜底，不依赖代码正确性；10s 是防止一条没写好条件的 join 把连接占满几十秒；200 行是评估集最大 gold 结果 73 行，200 有足够余量，同时 200 行 × 若干列的 JSON 只有几十 KB。三者是正交的：权限、时间、空间。

AgentResponse.Status 六态：SUCCESS、NOT_CONFIGURED、GENERATION_FAILED、REJECTED、EXECUTION_FAILED、NEEDS_CLARIFICATION。分开的原因：NOT_CONFIGURED 是环境问题，重试没用；GENERATION_FAILED 是模型侧；REJECTED 是护栏拦下；EXECUTION_FAILED 是数据库/方言/超时；NEEDS_CLARIFICATION 是问题没问清。混成一类，评估数字换环境就会漂移。

  1. 空结果：有 WHERE 且 0 行，问题又不是「没有/未/零」；
  2. 单行聚合全 NULL；
  3. 比率越界：只检查列名像 rate/ratio/pct/percent/占比/比例/率的列，排除增长率；
  4. 负数指标：金额/GMV/费用/价格/数量/笔数/人数出现负数；
  5. JOIN 缺 ON/USING；
  6. 时间维度丢失：问题要按月/周/年，SQL 没有 DATE_TRUNC/EXTRACT/GROUP BY；
  7. 金额题只用 COUNT 没用 SUM；
  8. 退款金额聚合了 refund_qty 而不是 refund_value。

线上只在 !success() 时重试——校验拒绝、执行失败、模型返回空内容，这三类有明确错误信号；「执行成功但结果不对」在线上没有信号（没有 gold），所以不重试。评估器里有 ERRORS_AND_MISMATCH 档，是上限实验，不是线上策略。实测 ERRORS_ONLY 触发 0 次，因为首答 SQL 有效率已经 96–100%。

把一次糟糕的重试当成最终答案，会让系统比不重试更差；实测出现过「首次能跑通、重试反而执行失败」。所以只有第二次成功才采用，否则原样返回第一次结果。重试的 token/延迟仍要合并记账，不能因为失败就不算成本。

LlmCallRecord.combine(first, second) 把两次的 prompt/completion/total token、延迟、成本相加；AgentResponse.combineAttempts 把两次 Timings 逐项相加。结果取第二次，账目记两次之和——否则成本被低估一半，报告和账单对不上。

QueryPlanAnalyzer 用 EXPLAIN (FORMAT JSON) 拿 Total Cost 和 Plan Rows；笛卡尔积检测不是「看到 Nested Loop 就杀」，而是要求：没有 Join Filter、没有 Hash Cond、子节点没有 Index Cond、不是单行标量子查询广播、预估行数 > 1000，才判高危。这样避免把「索引嵌套循环」「标量广播」误判成笛卡尔积。护栏默认关，local/评估配置开。

Part 8 · 缓存、成本与可观测

8 题

结果集会过期，而且过期了没有信号——业务库更新后，缓存结果仍然“看起来正确”，这是最危险的错误。缓存 SQL 则不同：命中后仍然走完整校验和执行，数据变了结果自然变；SQL 跑不通会回退重新生成。缓存的是“生成成本”，不是“执行结果”。

L1 是进程内 LinkedHashMap LRU（上限 1000，accessOrder），纳秒级；L2 是 PostgreSQL 的 semantic_cache 表，跨实例、重启不丢。key = 归一化问题（小写、去空白、去末尾标点）+ \u001F + 配置指纹。分隔符用 ASCII Unit Separator，因为第一版用 \u0000 在 PostgreSQL text 列会报 invalid byte sequence 0x00，这个 bug 只在加持久化后暴露。

只要一个开关会改变“模型看到的内容”或“最终 SQL 的形状”，它就必须进指纹，否则改了配置仍命中旧 SQL，表现为“配置改了但数字一点没动”。指纹包含：模型、prompt 版本、retrieval 的 enabled/topK/joinHints/joinList/joinPlan/bridgeRepair/columnPruning、semantic、fewshot、dataProfile、foreignKeys、toolUse、limitMode、maxRows、routing。踩过的坑：最初漏了 few-shot，打开 few-shot 重跑消融，数字纹丝不动。

缓存的是 SQL，不是结果；不执行就无法知道当前数据下的结果。命中省的是模型调用（输入 token 归零），不是数据库执行。所以延迟降到“数据库执行耗时”，不是 0ms；README 里明确写了这一点。

这是“20 题重复 2 遍 = 40 次请求、50% 重复”的负载：缓存开，平均延迟 1106→521ms（−52.9%），输入 token −50.0%，准确率 95.0% vs 92.5%（样本内波动）。标准 100 题 eval 问题互不重复，命中率是 0；所以这个收益只在“高频重复提问/看板”场景成立，不能当普适结论。

第三次 cache-aware 全量：102 次调用，prompt 199,436 + completion 48,992；官方空闲价 1.0 / 4.0 元每百万，缓存命中 0.02；成本 = miss×1.0 + hit×0.02 + completion×4.0，除以 1e6，得到 ¥0.2209 / 100 题，单题 ¥0.002209。前两次没有 cache 字段，按“全部未命中”算上限 ¥0.370 / ¥0.363；报告金额 0 是当时单价没配，不是免费。

DeepSeek 的自动前缀缓存：系统提示词在 100 次调用里高度重复，命中 178,036 / 199,436 输入 token（89.27%），未命中 21,400。命中价只有未命中的 1/50，所以成本比上限低很多。JSONL 现在记录 cacheHitTokens / cacheMissTokens，成本按分段算；历史两次没有这两个字段，只能算上限。

控制台账单是账号级，无法按项目隔离；所以不看控制台，直接用项目自己的 JSONL：每次调用记 prompt/completion/cache hit/miss，scripts/report_llm_cost.py 按时间窗过滤、按官方单价算，结果只含本项目。这是“逐条 token 账本”而不是“账号账单”，也是为什么成本能精确到 ¥0.002209/题。

Part 9 · 多轮与 Agent

QuestionRewriter.isFollowUp() 三段：1）前缀词（那/那么/然后再/再看/换成/改成/只看/如果/去掉/加上/其中/按照/按/除了/对比）；2）代词（这个/这些/上述）；3）长度 ≤ 20 且带语气词（呢/怎么样/如何）或含“前/top/排序/升序/降序/最高/最低”。命中才改写；不是追问就按新问题走。

用了四个：record（AgentResponse、LlmCallRecord、SchemaContext 都是 record，天然不可变、自动 equals/hashCode，正好适合"一次响应的快照"）；pattern matching for instanceof（usage.getNativeUsage() instanceof OpenAiApi.Usage u 直接绑定变量，省掉强转）；switch expression（状态映射，无 break 不穿透）；text block（SQL 和 prompt 模板，避免几十个 \n 拼接）。

追问虚拟线程用了吗？

没用。评估是串行的、LLM 调用是阻塞 IO，虚拟线程解决的是"高并发阻塞 IO 下线程不够"，我这个场景并发度是 1，换虚拟线程收益为零，反而多一层不确定性。我不用它不是因为不会，是因为不需要。

三个原因：字符串常量池要复用（可变的话池里的值会被改坏）、hashCode 可以缓存（HashMap 的 key 大量是 String）、天然线程安全（不可变对象发布即安全）。final 修饰类和 private final char[]（JDK 9 后是 byte[] + coder）保证内部状态不可改。

项目里拼 prompt 不用 + 也不用 String，用 StringBuilder——PromptBuilder 要顺序追加 schema、指标、few-shot、问题四段，中间还有条件分支；用 + 每拼一次生成一个新 String，在 7401 字符的 DDL 上会放大成几十次拷贝。拼完 .toString() 一次性产出。

追问那 StringBuffer 呢？

StringBuffer 每个方法都加 synchronized，单线程下是纯开销。PromptBuilder 是方法内的局部变量，不可能被多线程共享，所以用 StringBuilder。

约定是「equals 相等则 hashCode 必须相等」，反过来不成立。破坏它的后果很具体：对象放进 HashMap 后 get 不到——因为 get 先用 hashCode 定位桶，桶里再用 equals 比对，hashCode 不一致连桶都进不去。

项目里真用到了：dev/eval 切分用的是 Math.floorMod(id.hashCode(), 2)。为什么不用 id.hashCode() % 2——因为 hashCode 可能为负，% 在 Java 里结果跟着被除数符号走，会得到 -1，切分就漏了一半。floorMod 保证结果非负。这个坑我是写完测试才发现的，不是背来的。

追问record 的 equals 是怎么实现的？

编译器按所有组件字段逐个 equals（数组字段用 Arrays.equals），hashCode 用 Objects.hash。所以我给 LlmCallRecord 加 cacheHitTokens 字段时，它的 equals/hashCode 自动跟着变——这是 record 的好处，也是坑：如果拿 record 当 HashMap 的 key，加字段会让历史 key 失效。

ArrayList 是数组，随机访问 O(1)、尾部插入摊还 O(1)、中间插入 O(n)；LinkedList 是双向链表，头尾插入 O(1)、随机访问 O(n)，而且每个节点多两个指针 + 对象头，内存开销大约是三倍。实践里 99% 用 ArrayList，因为 CPU 缓存友好性带来的常数优势远大于理论复杂度差异。

结果集用 List<Map<String,Object>> 是因为 JDBC 的 ResultSet 是游标式的、必须边走边取，而我要先做结果规范化（列名归一、数值精度统一、行序无关比较）再比对，必须把它物化成内存结构。代价是内存——所以我用 200 行硬上限把上界钉死，不是"先查出来再看有多少"。

追问为什么不用 List<Entity>？

因为 SQL 是模型生成的，返回哪些列、什么别名，运行时才知道，没有固定的实体可以映射。硬造一个"万能实体"（201 个字段）比 Map 更糟。

数组 + 链表 + 红黑树。hash = h ^ (h >>> 16) 让高 16 位参与运算（否则 (n-1) & hash 只用到低位，高位全浪费）；容量取 2 的幂，用 (n-1) & hash 代替取模；0.75 是"空间 vs 冲突"的经验平衡点——再高冲突概率陡增，再低浪费一半空间；链表到 8 且容量 ≥ 64 转红黑树（O(n) → O(log n)），退化到 6 转回链表，留 2 的缓冲避免在边界反复转换。

追问为什么容量必须是 2 的幂？扩容时元素怎么移动？

两个好处。一是 (n-1) & hash 等价于取模但快得多（位运算 vs 除法）；二是 n-1 的低位全 1，散列更均匀。扩容时因为容量翻倍，元素的新下标只有两种可能：留在原位，或者移动到 原下标 + oldCap——判据就是 hash & oldCap 是不是 0，不需要重新算 hash。这是 JDK 8 相对 JDK 7 的重要优化。

JDK 7 是分段锁（Segment 继承 ReentrantLock，锁 1/16 的桶）；JDK 8 改成 CAS + synchronized 锁单个桶头节点——put 时桶为空就 CAS 直接放，有冲突才 synchronized 锁住链表头，锁粒度从"段"降到"桶"，并发度大幅提高。扩容支持多线程协助迁移（helpTransfer）。

项目里 SqlCache 的 L1 是 LRU 32，我用的是 LinkedHashMap 加 removeEldestEntry 重写，外面套同步——不是 ConcurrentHashMap。原因是：LRU 的"访问顺序"语义要求每次 get 都要改链表结构（把节点移到队尾），ConcurrentHashMap 根本不维护顺序；而且 get 变成写操作后，它的无锁读优势也没了。32 个元素的临界区极短，synchronized 足够。

追问那高并发下 synchronized 不会成瓶颈吗？

会，但要看量级。我的场景是单机、评估串行，QPS 个位数；临界区里只做一次链表移动，纳秒级。如果是高并发，正确解法不是换 ConcurrentHashMap，而是换 Caffeine——它用 W-TinyLFU 做淘汰、分段锁 + 读缓冲，专门解决这个问题。我不上 Caffeine 是因为不想为 32 个元素引一个依赖。

集合的 modCount 在结构修改时自增，迭代器每次 next() 校验它，不一致就抛 ConcurrentModificationException——目的是尽早暴露并发修改的 bug，而不是保证安全。ArrayList、HashMap 都是 fail-fast；CopyOnWriteArrayList、ConcurrentHashMap 的迭代器是 fail-safe（弱一致，遍历的是快照）。

项目里我刻意避开：ResultNormalizer 做规范化时新建列表而不是在原列表上 remove/add，因为结果集要保留原样做对比，原地改既踩 fail-fast 又破坏可比性。

追问怎么安全地边遍历边删？

用 Iterator.remove()，或者 removeIf()（内部就是 Iterator），或者收集到新集合。for-each 里直接 list.remove() 必炸。

corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。执行顺序是：核心线程 → 队列 → 非核心线程 → 拒绝策略。最容易答错的是顺序——不是"先扩到最大再排队"，是"先排队，队列满了才扩线程"，所以用无界队列（LinkedBlockingQueue 默认容量 Integer.MAX_VALUE）时 maximumPoolSize 永远不生效。

项目主链路是单请求同步、评估串行，没有自建线程池。有个常见混淆要说清：Hikari 是连接池不是线程池（只读 5、持久化 4），它管的是数据库连接的生命周期，不是任务调度。如果将来要并行跑评估，我会用固定大小线程池 + 有界队列 + CallerRunsPolicy（降速而不是丢弃），而不是 Executors.newFixedThreadPool（无界队列会 OOM）。

追问线程数怎么定？

CPU 密集约 N+1，IO 密集约 2N 起步、按"等待时间/计算时间"的比例放大。但这个公式只在"任务是均匀的"时成立；LLM 调用是长尾 IO（P95 是均值的好几倍），真正该做的是限流 + 超时，不是调线程数。

每个 Thread 持有一个 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是强引用。泄漏的原因：key 被 GC 后变成 null，但 value 还被 Entry 强引用着，线程不死（线程池里的核心线程）value 就永远不回收。所以用完必须 remove()——remove 会清掉 key 为 null 的 Entry。

项目里没有直接用 ThreadLocal。会话状态是 ConcurrentHashMap<sessionId, Session>，因为会话要跨请求、跨线程存活，放 ThreadLocal 反而错（下一个请求可能是另一个线程）。但我知道 Spring 在用它：TransactionSynchronizationManager 用 ThreadLocal 绑连接（这也是"事务在子线程失效"的根因），RequestContextHolder 用 ThreadLocal 存当前请求。

三个不同层次。volatile 解决可见性和有序性（写立即刷主存、读强制从主存读、禁止指令重排），不保证原子性——i++ 依然不安全。CAS 解决原子性：compareAndSwap(expected, new) 由 CPU 指令保证"比较 + 交换"不可分割，失败就重试（自旋），代价是 ABA 问题和自旋开销。AQS 是更高层的框架：用一个 volatile int state 表示同步状态，加一个 CLH 双向队列排队，ReentrantLock/CountDownLatch/Semaphore 都基于它。

项目里没有直接用 AQS，但间接依赖：ConcurrentHashMap 的桶头用 CAS + synchronized，Hikari 内部用 AtomicInteger 管连接数。不要硬编"我用了 AQS"——面试官问一句"你继承 AbstractQueuedSynchronizer 实现过什么"就穿帮了。

追问ABA 是什么？怎么解？

值从 A 改成 B 又改回 A，CAS 以为没变过。解法是加版本号，AtomicStampedReference 就是干这个的。

synchronized 是 JVM 层面（monitorenter/monitorexit 指令），自动释放、非公平、不可中断、不支持超时；ReentrantLock 是 AQS 实现，可公平/非公平、可 tryLock(timeout)、可中断、可多条件队列，但必须 finally 释放。JDK 6 之后 synchronized 有偏向锁/轻量级锁/锁消除等优化，简单场景性能不差。

项目里用的是 synchronized，在 LlmCallLog 写 JSONL 那一段——文件追加不是线程安全的，且是低频写（每次 LLM 调用一次）。不用 ReentrantLock 是因为没有"需要超时或中断"的场景，用更简单的那个。

追问锁升级的过程？

无锁 → 偏向锁（同一线程重入，只在对象头记线程 ID）→ 轻量级锁（CAS 自旋）→ 重量级锁（monitor 阻塞）。注意 JDK 15 起偏向锁默认关闭、JDK 18 移除——如果面试官问"现在还有偏向锁吗"，答"已经移除了"比背四级升级更加分。

JMM 定义的是多线程下读写的可见性规则，不是硬件内存模型。核心是 happens-before：如果 A happens-before B，那 A 的写对 B 可见。八条规则里最常用的四条：程序顺序、监视器锁（解锁 hb 后续加锁）、volatile（写 hb 后续读）、线程启动/join。

项目里最接近可见性问题的是 LlmCallLog 的计数和 SqlCache 的读写——它们靠 synchronized 和 ConcurrentHashMap 提供的 happens-before 保证。如果我图省事改成"普通 HashMap + 一个 boolean 标志位"，就会出现"写线程已经写完了，读线程还看到旧值"，而且这种 bug 在 x86 上大概率复现不了，最难查。

堆（Eden + 2×Survivor + 老年代）、元空间（JDK 8 起取代永久代，在本地内存）、虚拟机栈、本地方法栈、程序计数器。对象优先在 Eden 分配，熬过 MaxTenuringThreshold 或同龄对象超过 Survivor 一半就晋升老年代。GC 分 Minor/Full，收集器有 Serial/Parallel/CMS/G1/ZGC。

项目里没调过 GC——单实例、低 QPS、堆压力小，-Xmx 用的默认值。硬讲调优参数是给自己挖坑，我会直接说"没调过，因为没遇到压力"，然后讲我知道该看什么。

追问那你怎么排查 OOM？

三步：-XX:+HeapDumpOnOutOfMemoryError 让它在崩的时候留 dump；jmap/MAT 看 dominator tree 找最大持有链；定位到是"一次取太多"还是"该释放没释放"。这个项目最可能 OOM 的点就是全量结果集入内存，所以我从源头掐掉——200 行硬上限 + maxRows+1 探测，不是等 OOM 了再治。

CPU 飙高：top -Hp <pid> 找最耗 CPU 的线程 → 线程 ID 转 16 进制 → jstack <pid> | grep -A 20 <nid> 看栈 → 判断是死循环、频繁 GC（jstat -gcutil 看 FGC 次数）、还是锁竞争自旋。

接口变慢：先分层定位，不要一上来就看代码。入口层看 P50/P95/P99 分位（只看均值会被长尾骗）；依赖层看是 DB 慢、LLM 慢、还是自己算得慢——我的 LlmCallRecord 里记了每次调用的延迟，AgentResponse 里带分段耗时，能直接切开；DB 层看 EXPLAIN 是不是走了全表扫。

这个项目 P95 12–17s 就是靠分段耗时定位的：瓶颈在 LLM 生成（占 80%+），不在检索、不在执行。所以优化方向是"少调一次"（缓存、合并改写与生成），不是"把检索写得更快"。

双亲委派是"收到加载请求先交给父加载器，父加载器加载不了才自己加载"。Bootstrap → Extension/Platform → Application。好处是安全（java.lang.String 永远是核心库那份，不会被自定义的同名类顶掉）和避免重复加载。

Spring Boot 的 fat jar 是个特殊场景：BOOT-INF/lib/*.jar 是嵌套 jar，标准 URLClassLoader 只能读 jar 里的文件，读不了"jar 里的 jar"。所以 Boot 自己实现了类加载器（2.x 是 LaunchedURLClassLoader，3.2 起换了新的 nested jar 实现），把嵌套 jar 映射成可读的 URL。双亲委派仍然保留，只是层级多了一层——LaunchedURLClassLoader 的 parent 是应用类加载器。

追问怎么打破双亲委派？

重写 loadClass 不调 super（Tomcat 的 WebappClassLoader 就是这样，Web 应用优先加载自己的类）；或者用线程上下文类加载器（JDBC 的 DriverManager 就是这么找到厂商驱动的）。

IoC 是控制反转——对象的创建和依赖装配交给容器，你只声明"我需要什么"（构造器参数/@Autowired），不自己 new。AOP 是面向切面——把横切逻辑（事务、日志、权限）从业务代码里抽出来，靠动态代理织入：目标类有接口用 JDK 动态代理，没接口用 CGLIB 生成子类。

项目里没有自定义切面，这是实话。我用到的是 Spring 提供的现成切面：@Transactional（虽然这个项目只读，没真用上）。如果要加，最合适的是"给每次 LLM 调用统一埋点"——但我没加，因为 LlmCallRecord 是显式记账，切面拿不到 token 数、cache 命中数这些只有响应体里才有的东西。可观测性要的是准确，不是优雅。

实例化（构造器）→ 属性填充（依赖注入）→ Aware 回调 → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct / InitializingBean.afterPropertiesSet → postProcessAfterInitialization（AOP 代理在这里生成）→ 使用 → @PreDestroy。

三级缓存：singletonObjects（成品）、earlySingletonObjects（半成品）、singletonFactories（ObjectFactory）。A 依赖 B、B 依赖 A 时：A 实例化后把"能产出 A 早期引用的工厂"放进三级缓存 → 去创建 B → B 注入 A 时从三级缓存拿到 A 的早期引用（如果 A 需要代理，这一步就提前生成代理）→ B 完成 → A 完成。核心是"提前暴露未完成的对象"。

追问为什么需要三级而不是两级？

为了延迟决定要不要生成代理。如果 A 需要 AOP 代理，正常情况下代理是在初始化后生成的；两级缓存必须在"提前暴露"时就生成代理，那所有 Bean 都会被提前代理，违背"尽量晚"的原则。三级缓存的 ObjectFactory 让 getEarlyBeanReference 在真被依赖时才决定。

追问构造器注入的循环依赖能解决吗？

不能。构造器注入要求"创建 A 之前先有 B、创建 B 之前先有 A"，死锁在实例化阶段，三级缓存还没生效。Spring Boot 2.6+ 默认禁止循环依赖（spring.main.allow-circular-references=false），出现就启动失败——这是好事，逼你把设计改对。

五类：1）自调用——同类内部 this.method() 不走代理，注解形同虚设；2）方法非 public（CGLIB 代理下）；3）异常被吞——catch 了没抛，或抛受检异常而 rollbackFor 没配（默认只回滚 RuntimeException）；4）类没被 Spring 管理——自己 new 出来的对象；5）多线程——事务绑在 ThreadLocal 上，子线程拿不到同一个连接。

追问你这个项目有事务吗？

业务查询是只读，不需要事务；持久化是单条 INSERT/UPDATE，也不需要。所以我没有"用了事务"可以吹。但我知道这五类失效——因为这是 Java 后端必考项，不是项目专属。

七种。REQUIRED（默认，有就加入、没有就新建）、REQUIRES_NEW（挂起外层、自己开新的）、NESTED（嵌套，靠 savepoint，外层回滚会带着它回滚）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。

必须用 REQUIRES_NEW 的场景："业务失败也要留痕"——比如下单失败要写一条失败日志，如果和业务同一个事务，业务回滚会把日志一起滚掉，就查不到为什么失败了。这个项目里对应的是 LlmCallLog：LLM 调用失败我也要记一条（状态、耗时、错误），这条记录不能跟着失败一起回滚。我现在是用独立的连接直接 INSERT 绕开的，本质上就是 REQUIRES_NEW 想要的效果。

@SpringBootApplication = @EnableAutoConfiguration + @ComponentScan + @Configuration。@EnableAutoConfiguration 通过 AutoConfigurationImportSelector 读 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（Boot 2.7 之前是 spring.factories），拿到候选配置类后按 @ConditionalOnClass、@ConditionalOnMissingBean、@ConditionalOnProperty 等条件过滤，最后才注册。

项目里刻意关掉了 Spring AI 的自动配置（spring.ai.model.chat=none），改成手工装配 OpenAiApi + OpenAiChatModel。原因很实际：自动配置在没有 API Key 时会让应用启动失败，而我的项目要支持"没有 Key 也能跑测试、跑 dry-run"。手工装配可以把"缺 Key"变成一个运行时的明确错误，而不是启动期的崩溃。

追问@ConditionalOnMissingBean 有什么用？

让自动配置可被覆盖——你只要自己声明一个同类型的 Bean，自动配置就退让。这是 Spring Boot"约定优于配置但不锁死"的关键机制。

请求 → DispatcherServlet → HandlerMapping 找到 handler（含拦截器链）→ preHandle → HandlerAdapter 调用方法（参数解析、@RequestBody 反序列化）→ 返回值经 HttpMessageConverter 写出 → postHandle → afterCompletion。异常走 HandlerExceptionResolver。

区别：Filter 是 Servlet 规范、在 DispatcherServlet 之前，拿得到 ServletRequest 但拿不到 handler 信息；Interceptor 是 Spring MVC 的、在 DispatcherServlet 之内，拿得到 handler 和 ModelAndView，也能在 afterCompletion 里做清理。

项目里两者都没自定义——Spring Boot 内嵌 Tomcat，我直接用 @RestController。如果要做鉴权或限流，选 Filter（更早、能拦掉静态资源）；要做"按接口维度记耗时"，选 Interceptor（能拿到 handler 方法）。

最大的结构差异：InnoDB 是聚簇索引（数据就存在主键 B+ 树的叶子节点上），PostgreSQL 是堆表 + 独立索引（索引叶子存的是 ctid，指向堆里的物理位置）。所以 PG 的"回表"是 index scan 之后再 heap fetch，代价比 InnoDB 的"二级索引→主键→聚簇"更直接，但 PG 没有"按主键物理有序"这回事。

执行计划我用的是 EXPLAIN (FORMAT JSON)——因为要程序化判断代价，不是给人看。QueryPlanAnalyzer 解析 JSON 里的 Total Cost，超过阈值就判 HIGH_RISK_COST 直接拒掉，这是"防写"之外的第二道成本护栏。MySQL 的 EXPLAIN 默认是表格，也有 FORMAT=JSON，但字段名完全不同。

追问PG 的 index-only scan 需要什么条件？

索引里要有查询涉及的所有列，并且 visibility map 标记该页 all-visible（靠 VACUUM 维护）。所以 PG 的"覆盖索引"比 MySQL 更依赖维护动作——表更新频繁时 index-only scan 会退化成 index scan + heap fetch。

回表是"二级索引查到主键，再回主键索引取整行"；覆盖索引是"查询要的列都在索引里，不用回表"。EXPLAIN 里 MySQL 显示 Using index，PG 显示 Index Only Scan。

和列剪枝的关系是"副产品"：ColumnPruner 的 7 条保全规则是为了压缩 DDL（7401 → 约 1271 字符，−82.7%）和减少列名歧义，不是为了性能。但列少了确实更容易命中覆盖索引——这是顺带的，不是我当初的目的。面试时把"目的"和"副产品"分清，比硬把两件事说成因果更可信。

LIMIT 100000, 20 的语义是"扫过前 100000 行，丢掉，再取 20 行"——扫描量随偏移量线性增长，越翻越慢。优化两条路：延迟关联（先用覆盖索引查出主键，再 join 回表，减少回表次数）；游标/keyset 分页（WHERE id > :lastId ORDER BY id LIMIT 20，走索引定位，O(1) 起跳）。

项目里没有这个问题，因为我压根没做分页——结果集是 LIMIT 201 硬上限（取 201 行是为了判断"是否超 200"，多取一行做探测），没有 OFFSET。如果将来要给用户翻页，必须上 keyset，不能用 OFFSET。

四个级别：读未提交、读已提交、可重复读、串行化，分别解决脏读、不可重复读、幻读。MySQL InnoDB 默认可重复读，靠 undo log + read view 实现 MVCC，快照读不加锁；当前读（FOR UPDATE）加 next-key lock 防幻读。PostgreSQL 默认读已提交，同样是 MVCC，但它的"可重复读"实现是快照隔离（SI），幻读也不会出现；串行化用 SSI（可串行化快照隔离），靠检测冲突而不是加锁。

项目里业务查询全是只读，不需要事务；持久化是单条 INSERT/UPDATE，靠单语句的原子性就够。所以我没有"处理过高并发事务"的经验可以吹，这块只能讲原理。

四个真的用了：

  1. 策略——SchemaProvider 是接口，FullSchemaProvider（全量）和 HybridSchemaProvider（检索）可替换。好处是 dry-run 时能切成全量校验 gold SQL，而主链路仍走检索，同一套编排代码不用改。
  2. 工厂方法——LlmCallRecord.of(...) 有多个重载（带 cache / 不带 cache），把"怎么算成本"收在工厂里，调用方不需要知道计价公式。
  3. 建造者——PromptBuilder 顺序追加 schema、指标、few-shot、问题，中间有条件分支；用构造器会变成十几个参数的重载地狱。
  4. 单例——Spring Bean 默认单例，SchemaCatalog、SqlCache 都是，因为它们是"进程内共享状态"，多实例会重复加载元数据。

没用的：责任链。SqlValidator 是一组 check 方法顺序执行、把 Violation 收集到 List 里，没有 next 指针，严格说不是责任链。面试官如果问"你这算责任链吗"，我会说"不算，它是收集式校验，好处是一次能报出所有问题而不是第一个就返回"——这个区别是真的，硬套反而露怯。

追问策略模式比 if-else 好在哪？

三点：开闭（加一种实现不改调用方）、可测（每个策略单独单测，不用构造巨型分支）、依赖倒置（编排层依赖接口不依赖实现）。但策略不是无脑用——只有 2 个分支且不会增长时，if-else 更直白。

饿汉（类加载即创建，简单但可能浪费）、懒汉 + 同步（性能差）、双检锁（volatile + 两次 null 检查）、静态内部类（利用类加载机制保证线程安全，最推荐）、枚举（《Effective Java》推荐，天然防反射和反序列化破坏）。

双检锁必须加 volatile，原因是指令重排：instance = new Singleton() 不是原子的，分三步——分配内存、初始化对象、把引用指向内存。2 和 3 可能重排，导致另一个线程在第一次检查时看到非 null 但未初始化完成的对象。volatile 禁止这个重排。

项目里没手写单例——Spring Bean 默认就是单例，容器保证。但 SqlCache 的 L1 是每个实例一份的 LinkedHashMap，如果将来要保证全局唯一，我会用静态内部类而不是双检锁。

五件事，缺一个就出事：

  1. 超时——必须设连接超时和读超时两个，且读超时要按 P99 设（LLM 生成慢，设 3s 会把正常请求全掐死）。不设超时等于把线程永久借出去。
  2. 重试——只对幂等 + 可重试的错误重试（超时、5xx、429），指数退避 + 抖动，且要有上限。4xx 不重试（参数错了重试一万次还是错）。
  3. 连接复用——底层用连接池，不要每次 new 一个 client。BYOK 场景下我按 Key 缓存 client（LRU 32），避免每个请求都重建。
  4. 熔断/降级——连续失败到阈值就快速失败，别让请求排队把线程池打满。我的降级是"明确报错 + 缓存兜底"，不返回半成品 SQL，因为错的 SQL 比没有 SQL 更危险。
  5. 可观测——每次调用记模型、token、延迟、状态、成本。没有这层，你连"慢在哪"都说不出来。
追问超时时间怎么定？

从下游的 P99 往上取，不是拍脑袋。这个项目 P95 是 12–17s，说明单次生成本来就要十几秒，超时设 3s 是自残。同时要有总预算（一次请求最多允许多少次 LLM 调用），否则"重试 2 次 × 改写 1 次 × 生成 1 次"会把延迟乘起来。

Part 13 · 设计题与开放追问

12 题
这一部分没有标准答案，考的是“你能不能把已有经验迁移到新约束上”。答法统一是：先问清约束 → 说方案 → 说代价 → 说怎么验证。

先崩的不是模型，是检索。现在 Top-8 靠领域词典 + 关系扩展，37 张表时词典能覆盖大部分业务词；1000 张表时词典维护不动、同义词爆炸、Top-8 里塞不下真正需要的表。方案是分两级：先用 embedding/BM25 把 1000 张粗筛到 50 张（召回优先），再用现在的词典 + 连通性修复做精排到 8 张（精度优先）。代价是多一次召回、多一层不可解释性。

追问那你怎么验证 1000 张表下没退化？

造“干扰表”——保留 200 条 gold，另外灌 800 张语义相近但不该被选中的表，看表全召回率和执行准确率的差值。差值小说明抗干扰，差值大说明粗筛把对的表筛掉了。

四处：1）方言层——标识符引用（"col" → `col`）、LIMIT/OFFSET、日期函数（date_trunc → DATE_FORMAT）、EXPLAIN 格式（PG 是 JSON，MySQL 是表格）；2）元数据层——information_schema 查询要按方言分支，主键读 KEY_COLUMN_USAGE；3）AST 层——JSqlParser 本身方言无关，但函数黑名单要按方言扩；4）schema 文本——DDL 渲染要换类型名。所以我会抽一个 SqlDialect 接口，而不是到处 if (isPg)。

按链路倒着查，四步：1）看 SQL——AgentResponse 里带 generatedSql 和 retrievedTables，先确认它查的是不是该查的表；2）看口径——metrics.yml 里这个指标的定义（分子分母、去重口径、时间窗），大概率是口径理解错而不是 SQL 语法错；3）跑 gold——同一问题跑人工 gold SQL，两边结果比对，差异就是归因点；4）看数据——如果是扩展表，可能是合成数据本身的问题。这四步能覆盖我 16 条失败里的全部类型。

三件事：1）把 SQL 给用户看——不是藏在后端，而是展示出来，让懂业务的人能核对；2）把口径写出来——“订单量 = 去重 order_id 计数，不含 canceled”，比 SQL 本身更能建立信任；3）把不确定性标出来——检索到的表、是否复用 schema、是否走了改写，都回传。可解释性不是“解释模型怎么想的”，是“让用户能自己验证”。

不看总数，看失败结构。现在 16 条失败里输出形状 7 条、深层 Join 4–6 条、gold 缺陷 3 条。所以路线是：1）输出形状契约化（7 条里能救 5 条左右，+2.5pt）；2）T5 桥接表专项（补中间表识别，+1.5pt）；3）gold 修正（3 条，但会破坏历史可比性，要另开一套 eval v2）。剩下的长尾（歧义问题、数据本身脏）不建议硬刚，边际收益低。我不会承诺 95，因为 200 条样本的置信区间本身就有 ±2.5pt。

分三层：1）输入侧——用户问题只作为“数据”拼进 user message，不拼进 system；schema 文本做白名单渲染，不让库里的注释/表名注入指令；2）输出侧——AST 校验是硬闸，注入成功让模型写 DROP TABLE 也会被拦（H2/H4 就是这么补的）；3）权限侧——只读账号兜底，即使前两层都破，也写不了库。核心观点：prompt 注入在 Text2SQL 里的危害被 AST + 只读账号这两层削掉了大半，真正危险的是“合法越权读”（读别的租户的数据），那个要靠 RLS，我现在没有。

单轮 eval 测不出来，得单独造集：每条样本是“首轮问题 + N 轮追问 + 最终期望 SQL”，评分看“最终轮执行准确率”和“追问轮次”。我现在的 200 条是单轮的，多轮只有手工验证——这是缺口，我在“接下来怎么迭代”里没把它排进前三，因为多轮不是当前主战场。

四层：1）重试——只对超时/5xx 重试，指数退避，最多 2 次；2）改写降级——多轮改写 LLM 失败就退规则改写（已实现）；3）生成降级——生成失败直接返回明确错误，不返回半成品 SQL，因为错的 SQL 比没有 SQL 更危险；4）缓存兜底——命中缓存的问题不依赖 LLM。注意“降级到模板 SQL”这种方案我不做，模板在 37 张表上覆盖不了，会产出看似成功实则错误的答案。

不加在生成侧，加在结果侧。理由：让模型同时输出 SQL 和图表配置，会显著拉低 SQL 准确率（多任务互相干扰）。更好的做法是 SQL 执行完之后，拿“结果集的列类型 + 指标元数据”做规则推断：单行单列 → 指标卡；一维 + 一维数值 → 柱/折线；两维 + 数值 → 分组柱或热力。模型只在规则推不出来时兜底。这样图表错了不影响 SQL 对。

问题 → QuestionRewriter（是否追问）→ SchemaRetriever（词典匹配 + 关系扩展 + 连通性修复，Top-8）→ JoinPlanner（Dijkstra 最短路 + Prim 生长）→ ColumnPruner（7 条保全规则）→ PromptBuilder（schema + 指标 + few-shot）→ LLM → SqlValidator（AST 白名单 + 函数黑名单）→ QueryExecutor（只读账号 + 10s + 200 行）→ ResultNormalizer → 返回。旁路两条：SqlCache（L1 LRU + L2 PG）在检索前查、LlmCallRecord 在每次 LLM 调用后记账。画的时候一定要标出"哪一步失败会导致什么错误类型"，这是加分项。

骨架相同，检索对象不同。两者都是"检索 → 拼上下文 → 生成 → 校验"，但 RAG 检索的是文本块，Text2SQL 检索的是结构（表/列/关系）。

能迁移的三点：① 检索质量决定上限——RAG 里 chunk 切坏了，再强的模型也答不对；这里表选错了，SQL 一定错。② 上下文预算是硬约束——RAG 要控 chunk 数，我要控表数（全量 DDL 7401 字符压到 1271）；③ 评测方法——分层集 + 失败归因 + 执行准确率，这套方法论换个领域照样能用。

不能迁移的一点：RAG 没有"可执行的真值"。Text2SQL 的 gold SQL 一跑就知道对错，是天然的强监督；RAG 的答案对不对要靠人判或者 LLM 判，评测成本高一个量级。这也是我选 Text2SQL 做项目的原因之一——它有干净的评测信号。

不做功能，做"能被人放心试"的最小闭环。

  1. 第 1 周：接一个真实业务库（不是 Olist 合成数据），看词典和指标注册表在脏数据上崩在哪。
  2. 第 2 周：加鉴权和租户——不是加个登录框，是把"这个用户能看哪些表/列"做成检索的前置过滤，而不是生成后再拦。这决定了架构，晚做要重构。
  3. 第 3 周：可观测 + 反馈闭环——每次回答记 SQL、耗时、用户是否点了"有用/没用"。用户点"没用"是最便宜的标注数据，比我再造 200 条评测集有用。
  4. 第 4 周：灰度给 5 个人用，只开只读 + 只开 3 个主题域，收集 100 条真实问题再决定下一步。
追问为什么不先做性能优化（P95 12–17s）？

因为现在还没人用。12–17s 在"等人试用"阶段是可接受的，在"天天用"阶段才是致命的。优化要跟着真实痛点走，不然优化的可能是个假问题——这也是我为什么不把"降到 8s"排在第一位。

Part 14 · Agent 开发通用追问（2026 面经扩展）

20 题
这一部分不是“项目事实”，而是 2026 Agent 岗的通用题：Agent vs Workflow、Function Calling、MCP、A2A、记忆、多 Agent、评测、可观测、生产化。每题都落回“我们做没做、为什么不做”，避免背通用答案却接不住项目追问。 参考：阿里云 65 题、腾讯 27 题、youngyangyang04/llm-master、cdavid817/agent-interview、DataCamp MCP 面试题、腾讯云 Agent 工程化。

LLM 是“会说”，Workflow 是“流程写死在代码里”，Agent 是“模型自己决定下一步”，RAG 是“给模型补知识”。 我们项目主链路是 Workflow + 可选的 ReAct 工具循环：检索→生成→校验→执行是固定编排，只有 3+ 表且 tool-use.enabled=true 时才进 AgentLoop。三次 84/85/86 都是 tool-use=false，所以是 Workflow 单次生成，不是 Agent 跑出来的。

追问没有多步自主决策，凭什么叫 Agent？

严格说主链路是 Workflow。Agent 的特征是“模型决定下一步动作”，我们的 [TOOL_CALL]→执行→Observation→再推理符合这个特征；但它默认关、只覆盖 3+ 表，所以我不把整个系统叫 Agent，只说“有 Agent 能力”。

常见六模块：感知、记忆、规划、推理、行动/工具、反思。映射到项目：感知=问题解析/改写；记忆=会话 + 摘要；规划=检索/Join 规划（确定性算法，不是 LLM Planner）；推理=LLM 生成；行动=SQL 执行；工具=5 个只读侦察工具；反思=8 条 ResultChecker + 有限重试。缺的是开放式 Planner、长期向量记忆、多 Agent 协作。

追问没有 Planner 也能叫 Agent 架构吗？

严格说我们不是完整 Agent 架构，是“Workflow 为主 + 局部 ReAct”。我只会说“有 Agent 能力”，不会说“是通用 Agent 平台”。

我们用的是 ReAct 的窄版（AgentLoop，最多 3 轮工具侦察）+ Reflection 的窄版（ResultChecker 触发一次重试）；没有 Plan-and-Execute 的全局计划，也没有 Multi-Agent。SQL 问数步骤固定，让模型先写一份“计划”只会多一次调用，还可能计划错。

追问ReAct 和 Plan-and-Execute 的 Token 差多少？

ReAct 每步都带完整上下文重新推理，Token 随步数线性涨；Plan-and-Execute 规划一次、执行阶段可以用便宜模型/脚本。通用面经常说 ReAct 约 4–8 倍 Token，但这是量级，不是本项目实测。

模型不执行函数。 它只按工具 schema 生成结构化调用指令（工具名 + 参数 JSON），由应用解析、执行，再把结果作为 tool 消息回传，模型继续推理。四步：定义工具 schema → 模型输出 tool_calls → 应用执行 → 结果带 tool_call_id 回传。模型可能幻觉工具名/参数、JSON 不合法，所以应用侧必须校验。

追问Function Calling 和 Prompt + 正则解析有什么区别？

Prompt + 正则也能让模型输出工具调用，但格式靠模型自觉，解析脆弱；原生 Function Calling 由模型侧保证结构化输出，应用侧仍有 schema 校验。我们项目用的是文本协议，因为只有 5 个工具、要兼容任意 OpenAI 兼容模型。

我们是文本协议：模型输出 [TOOL_CALL] 工具名(参数)，ToolParser 解析，ToolExecutor 执行，再把结果拼成 Observation 回灌。原生 Function Calling 是协议级结构化输出：模型直接返回 tool_calls JSON，应用不需要从自然语言里抠格式。前者简单、兼容任意模型，但解析脆弱、没有 schema 校验、不能原生并行；后者更稳，但依赖模型/厂商支持。

追问文本协议具体会出什么错？

工具名拼错、参数括号截断、把解释写进参数、一次输出多个工具但只解析第一个。ToolParser 要做容错，ToolExecutor 要返回结构化错误，让模型下一轮修。如果重做，我会优先原生 Function Calling，模型不支持时再降级文本协议。

MCP 是工具/数据源接入的标准化协议：MCP Server 暴露 Tools/Resources/Prompts，MCP Host 里的 Client 通过 JSON-RPC 2.0 发现并调用。它把“每个应用 × 每个工具都要写一套适配”的 N×M 变成“应用接协议 + 工具实现 Server”的 N+M。传输本地用 stdio，远程用 HTTP+SSE。

追问MCP 和 Function Calling 什么关系？

Function Calling 是模型输出调用指令的机制；MCP 是工具接入的协议。模型仍然通过 Function Calling（或文本协议）决定调用哪个 MCP 工具，MCP 负责“工具怎么被发现/连接”。MCP 不解决安全/权限。

四层分工：Function Calling 负责“怎么调”；MCP 负责“怎么接”；Skills 负责“怎么想/怎么做”（领域方法论/流程封装）；A2A 负责“Agent 之间怎么协作”（Agent Card、Task、Message/Artifact）。我们只用了最底层的文本版 Function Calling，没有 MCP、没有 Skills 体系、没有 A2A。

追问为什么不用 Skills？

当前只有 SQL 一个领域，规则直接写进 prompt 最简单；Skills 的价值在多领域/多流程复用，等有第二个领域再做，否则只是多一层抽象。

常见三层：工作记忆（当前步骤临时状态）、短期记忆（本次会话的对话/工具结果）、长期记忆（跨会话的用户偏好/知识，通常向量库 + 结构化库）。我们只有前两层：ConversationSession 存最近 5 轮 + SessionContextCompressor 把早期轮次压成摘要；没有向量长期记忆，用户偏好/历史知识不会跨会话召回。

追问会话落库算长期记忆吗？

不算。落库是为了审计/列表/恢复素材，不是每次请求前检索；长期记忆的关键是“写进去 + 按当前问题召回”，我们只有写，没有召回。

三种主流：滑动窗口（只留最近 N 轮，简单但丢旧信息）、摘要压缩（把旧对话压成摘要，保留主线但会丢细节、要额外 LLM）、向量检索（历史 embedding 后按需召回，能跨会话但依赖 embedding/向量库、可能召回噪声）。我们用滑动窗口 + 正则摘要：最近 5 轮完整，早期抽状态/地域/年份/指标/表名压成 40–70 token；不用 LLM 摘要，也不做向量召回。

追问为什么不用 LLM 摘要？

LLM 摘要更懂语义，但多一次调用、成本和延迟都涨，而且摘要本身可能幻觉；当前会话短、约束结构化，正则够用。等长会话/复杂约束再换。任何摘要都会丢信息，正确说法是“保留关键约束，非语义无损”。

多 Agent 只在任务可分解、子任务有清晰契约、可并行/专业分工/权限隔离时值得；代价是通信、状态一致性、冲突仲裁、分布式观测。我们不用，因为 Text2SQL 是单目标、强顺序、共享上下文的任务：选表→生成→校验→执行，拆成多个 Agent 只会增加协调成本，37 张表的上下文也不需要“专家隔离”。

追问如果面试官说多 Agent 更高级？

多 Agent 是架构选项，不是成熟度标志。工业界也提醒不要过早引入多 Agent；单 Agent 往往更稳、更便宜。要看任务是否可分解、并行收益是否大于协调成本。

三道防线：调度去重（task_id + 输入哈希 + 唯一约束/租约）、执行幂等（幂等键/唯一索引/状态机）、结果去重/版本校验。死循环靠 DAG 环检测 + 任务指纹 + 最大步数/预算 + 无进展检测；状态冲突靠 CAS/版本号/租约 fencing/人工仲裁。

追问SQL 审查 Agent 怎么设计？

Executor + Reviewer 两角色：Reviewer 只读、拿最小证据包（问题、候选 SQL、schema、计划、结果摘要），按 Rubric 输出 {blocking, warnings, suggestions, confidence}；Blocking 回灌生成器重写，最多 1–2 轮，不能无限否决。Reviewer 只做门禁，不替 Executor 重写，否则是双写不是审查。

A2A 是 Agent 之间委托任务/交换状态的互操作协议：Agent Card 声明能力/端点/认证，Task 有生命周期（Created→Processing→Completed/Failed），Message 传过程、Artifact 传最终产物。它和 MCP 互补：MCP 管 Agent↔工具，A2A 管 Agent↔Agent。多 Agent 通信要有统一消息信封（message_id/task_id/correlation_id/schema 版本/幂等键/Trace）、状态库做权威、超时/重试/熔断、幂等消费、Trace 关联。

追问A2A 和 MCP 能互相替代吗？

不能。MCP 是纵向工具接入，A2A 是横向 Agent 协作；一个 Agent 可以内部用 MCP 调工具、外部用 A2A 找别的 Agent。我们项目没有 A2A，只有单进程 ToolExecutor 调用。

三类失败要分别有检测信号 + 硬预算 + 降级路径：死循环看重复动作/任务指纹/无进展；目标漂移看当前子目标与原始目标的相似度、以及是否偏离验收条件；上下文溢出看 token 预算（80% 压缩、90% 停止、95% 异常）。我们只做了最基础的三条：maxRounds=3、SQL 10s 超时/200 行、会话 max-turns=5；没有动作哈希、目标漂移检测、token 预算器。

追问最大轮数 3 够吗？

对当前 3+ 表侦察够；复杂任务可能不够。轮数不是越多越好，要配合预算/进展检测，否则只是更贵地死循环。

不够。只读账号只防“写”，不防“读不该读的数据”和“被注入后外发”。通用防线：数据/指令分离、工具输出当不可信输入、最小权限、网络出口限制、Human-in-the-Loop、审计/脱敏。我们项目有 AST 白名单、只读账号、10s/200 行、函数黑名单；没有 RLS/列级权限、没有出站限制、没有工具输出注入检测。

追问只读账号能挡住什么？

挡住写操作和 DDL；挡不住越权读、函数副作用（如 pg_read_file，需黑名单）、以及把读到的东西发出去（需出口/权限）。工具返回可能包含用户/第三方写入的文本，模型会当上下文；里面藏指令就是间接注入。

单轮 QA 评“最终答案对不对”；Agent 评测还要评过程：任务是否完成、轨迹是否合理、工具选对没、参数对不对、步数/成本/延迟、是否违规、能否恢复。我们的 EX 是最终结果集准确率，属于“结果评测”；另有 SQL 有效率、表召回、P50/P95、token，但没有轨迹/工具调用准确率/任务成功率/LLM-as-judge。

追问为什么不能只看最终答案？

最终对可能是蒙对的，也可能绕了 10 步/高成本。Agent 要看过程是否可接受：工具选错但结果碰巧对，生产不可复制。通用基准有 AgentBench、WebArena、SWE-bench、GAIA、τ-bench，我们没跑外部基准，只有自建 200 条。

三层信号：Trace（一次任务跨 Planner/Agent/LLM/Tool 的因果链）、Metrics（成功率/P95/Token/成本/重试/工具错误率）、Logs（状态迁移、错误、决策原因）。我们只有 LlmCallLog 的 JSONL（model/token/latency/status/cache hit/miss）和 AgentResponse.timings，没有 trace_id/span、没有工具调用 span、没有任务级成功率/成本聚合。

追问为什么默认不记 prompt/回复？

prompt 含用户问题，回复含 SQL，落盘就是不受控副本；默认只记规模，需要复现时显式开 include-content。改进：先加 traceId + toolName + step 三个字段，就能把一次 Agent 的工具链串起来。

按收益排序：能用 Workflow 就不用 Agent（省 4–8 倍 Token）→ 工具子集/按需加载 → 上下文压缩 → 模型路由 → 缓存 → 预算/限流。我们的缓存只在“重复提问”实验里有效；DeepSeek 前缀缓存第三次命中 89.27%，成本 ¥0.221/100 题；路由触发率约 2%，没量出准确率/成本收益，所以不能当亮点。

追问缓存命中为什么不是 0ms？

缓存的是 SQL，仍要校验+执行；省的是模型调用。延迟降到数据库执行耗时，不是 0。缓存收益只在重复提问/看板场景成立，标准 100 题 eval 问题互不重复，命中率是 0。

八个面：身份/权限、状态与幂等、可靠性与预算、工具治理、安全、可观测、成本/容量、发布/回滚。我们项目是单租户、单实例、只读、无鉴权/RLS/限流/队列/每步 checkpoint，离“生产级多租户 Agent”还有明显距离；但“只读 SQL + AST + 只读账号 + 超时”这条安全链路是完整的。

追问如果明天上线给外部客户，先补什么？

先鉴权/租户隔离 + RLS + 限流，再补 trace/告警和回滚；安全边界优先于准确率。准确率可以迭代，数据泄露是一次性的。

因为链路固定（检索→生成→校验→执行→有限重试）、只有 5 个工具、要求逐层归因；框架会把控制流藏进黑盒，出问题难定位。纯 Java 手写 Act-Observe-Reason 约百行，状态可控、日志可读、依赖少。Java 生态可以用 Spring AI（ChatClient/@Tool/MCP Client）、LangChain4j（AiServices/Tool）、Semantic Kernel Java；我们只用了 Spring AI 的模型客户端，工具循环手写。

追问什么时候改用框架？

链路变长、需要人工审批/断点恢复、多模型/多工具路由复杂、团队协作需要统一抽象时。当前不用的理由：固定链路 + 5 工具 + 归因优先。如果重做 Java 版，我会用 Spring AI 的 @Tool + 原生 Function Calling，减少 ToolParser。

先承认，再解释为什么。 “对，主链路是 Workflow；Agent 只用在 3+ 表的局部侦察，而且默认关闭。84–86 是 Workflow 单次生成的成绩，不是 Agent。我选择 Workflow 是因为 SQL 问数步骤固定、错误代价高、需要逐层归因；Agent 的开放式规划在这里收益不明确，反而增加延迟/成本/不确定性。”

追问那 MCP/A2A/Skills 呢？

直接说没做，再说清“是什么、为什么没做、要做怎么接”。MCP 是 Agent↔工具标准化，A2A 是 Agent↔Agent，Skills 是领域能力包；当前 5 个进程内工具、单 Agent，没有跨应用复用/多 Agent 协作需求。硬接只会增加协议/权限/部署复杂度；要做的话先把 ToolExecutor 包成 MCP Server，再补权限/审计，不会用 MCP 替代安全层。不编“我们内部实现了 MCP”，追问 tools/list、JSON-RPC、stdio/SSE 就穿帮。
