Part 0 · 项目介绍与边界

6 题

我做了一个把中文业务问题翻译成 SQL 的工具。比如运营问“2018 年销售额最高的 5 个州是哪些”，它会自己找表、连表、写一条只读 SQL，执行后把结果表返回。

它不是聊天机器人，重点在可评估：我自建了 200 道题，分六种难度，实测准确率从早期基线的 84–86% 稳步提升突破至 96.00%（未清洗基线 88.00%）；每次错在哪一层，我能拆开讲。

技术上是 Java 21 + Spring Boot + PostgreSQL，接 DeepSeek 这类大模型；但我做的主要不是“调模型”，而是把模型包进一条能选表、能校验、能拦风险、能归因的工程链路。

追问为什么强调“只读”？

因为模型输出不能直接信。它可能写 DROP TABLE，也可能写一条合法但会拖垮数据库的查询。只读是产品边界，不是功能限制。

我用一个例子讲：用户问“2018 年销售额最高的 5 个州”。

  1. 看懂问题：先把“那 2017 年呢”这种追问补成完整句子；如果问题有歧义，可以先反问。
  2. 找表：数据库有 37 张表，不可能全给模型。系统先用业务词典把“州”“销售额”“订单”映射到表，选出最相关的 8 张，再把连不上的表用中间表补通。
  3. 连表：告诉模型“订单怎么连客户、客户怎么连地区”，给它一棵推荐的连接树，避免它自己乱连。
  4. 写 SQL：把选中的表结构、业务口径（比如销售额到底含不含运费）、字段枚举值（比如“圣保罗”在库里是 SP）一起放进给模型的说明书，让它生成一条 SQL。
  5. 检查：用 SQL 解析器检查是不是单条 SELECT、表/字段是否存在、有没有危险函数、有没有 LIMIT；再让数据库 EXPLAIN 彩排，拦掉笛卡尔积和超高代价。
  6. 执行：用只读账号跑，10 秒超时，最多返回 200 行。
  7. 验结果：结果为空、比率超过 100%、金额为负等异常会触发一次重试；最后返回表格、SQL、耗时和 token。

这条链路里，检索、生成、校验、执行、评估是分开的，所以错了我能说清是“表选错”“字段选错”“连表错”还是“口径错”。

追问哪一步最贵？

调模型最贵，一次 1–3 秒、上千 token；检索和校验是毫秒级。所以优化优先级是先减少模型调用，而不是把检索写得更快。

不是让模型写出一条能跑的 SQL，而是三件事：

  1. 选对表：37 张表、英文表名、中文问题，模型很容易选错；选错后面全错。
  2. 落对口径：“销售额”可能含运费、可能排除取消订单、可能按订单数或人数算；不同口径结果差很多。
  3. 输出对形状：标准答案要 3 列，模型给 2 列；标准答案要 id，模型给 name；标准答案要 4 位小数，模型给 2 位。SQL 能跑，但结果不算对。

我 84 那轮 16 条失败里，检索类 0 条，7 条是输出列/形状；这说明“选表”已经不是最大瓶颈，“结果约定”才是。

追问那为什么不继续优化检索？

因为继续调 Top-K、关系跳数，实测一条都没救回来；瓶颈已经换了。优化要跟着失败结构走，不是跟着感觉走。

起点是一个很具体的痛点：电商数仓有 37 张表，业务同学问一个“上个月各州销售额”要等数据开发排期；直接丢给大模型，它会在几十张表里选错、漏连表、把“销售额”算成“订单数”，更麻烦的是错了看不出来——SQL 能跑，结果像模像样。

我想做的不是“让模型写 SQL”，而是把模型放进一条可评估、可拦截、可归因的链路：选错表能看出来，写错口径能归因，危险 SQL 能被拦。

追问为什么不做成通用 BI？

范围守不住就会烂尾。我明确不做写操作、多数据库方言、模型微调、多租户；先把一个垂直域做到能评估，比铺十个功能更有价值。

四类不做：

  • 不做写操作：只生成只读 SELECT，不碰插入/更新/删除，也不做建表/改表这类结构操作；
  • 不做多数据库方言：只支持 PostgreSQL；
  • 不做模型微调：只做给模型的说明书、检索和工程约束；
  • 不做多租户/行级权限：当前是单租户、单只读账号，没有“同一张表不同用户只能看自己行”的行级权限。

还有三个没达到的指标：4 张表以上的深层题只有 40–60%；最慢的 5% 请求要等 12–17 秒，目标 8 秒没达到；成本只算模型调用，不含数据库和机器。

这些不是“没做完”，是明确的范围取舍。面试时主动说边界，比假装生产级更可信。

追问没有权限控制，能上线吗？

不能直接给外部客户。上线前先补鉴权、租户隔离、行级权限和限流；当前的安全链路只保证“不能写”和“不能执行危险 SQL”，不保证“只能看自己该看的数据”。

绝对不是。面对这种质疑，先给死守的底线，再给两步归因证据链：

“我坚守了三条绝对不可逾越的评测底线： 1. 中文业务问题文本一个字没改； 2. Dev/Eval 的 Hash 划分算法一行没动，没有数据泄漏； 3. Dry-Run 跑 Gold SQL 保持 200/200 验证器全通。 96% 的提升是由清晰的两步技术归因构成的： - 第一步（算法升级收益，84%→88%）：在完全不改评测集的前提下，引入基于外键图的斯坦纳树（Steiner Tree）近似规划算法，消除局部贪心伪支路，并将指标口径解耦为规范的 MDL。这纯靠工程和算法重构把准确率从 84% 推到了 88.00%，4 表以上关联从 50% 跃升至 90.91%，3 表关联达到 100%。 - 第二步（基准数据治理，88%→96%）：对剩余 12 条失败用例做严格归因，发现其中 8 条属于早期 AI 自动生成基准时的标注私货与口径死锁（例如：题目只问‘下过单的会员’，Gold 标注却私加未提及的 HAVING count >= 2；或者同一口径下要求一会儿返回 level_id 一会儿返回 level_name）。我们进行的是基准数据清洗（Data Cleansing），抹掉评测尺子上的铁锈，才让物理执行准确率恢复到真实的 96.00%。”
追问那为什么依然有 4 条答不对？

这 4 条错在深层时序逻辑（如连续跨年同比的复杂子查询窗口），模型在当前零样本/少样本 Prompt 下对复杂嵌套业务语义的理解出现偏差。这属于模型的推理边界，我不通过在 Prompt 里针对具体题目打地鼠硬编码来刷满分，真实记录 96% 比虚假的 100% 更具备工程说服力。

低分回答：“因为我们算法越来越强了”“模型自己学会了”。——没有归因、回避测试集清洗事实、不敢面对剩余错误。

Part 1 · 数据流与开关

8 题

问题进来 → 改写/澄清 → 查缓存 → 选表 → 补口径/枚举/示例 → 模型写 SQL → AST 检查 → EXPLAIN 彩排 → 只读执行 → 结果检查 → 必要时重试 → 返回表格和耗时。

这条链路里，每一步都可以单独关掉；默认配置几乎全关，是为了让“最朴素的基线”随时可复现。84–86 是在本地配置打开检索、口径、几个示例、结果检查、自纠错、执行计划彩排之后跑出来的。

追问哪些默认是关的？

检索、列剪枝、join 提示、业务口径、few-shot、结果检查、自纠错、缓存、Agent 工具、多轮、澄清、模型路由、EXPLAIN 护栏、持久化，默认都是 false。默认开的只有数据画像、外键、列白名单、连通性修复、LIMIT 补齐、调用日志。

这句话会命中三张核心表：订单 orders、订单明细 order_items、客户 customers；“州”对应 customers.customer_state；“销售额”对应 order_items.price 的求和。

系统会先选表，再补“州”的枚举值（库里存的是 SP、RJ 这种两位代码，不是“圣保罗”），然后让模型生成类似：

sql SELECT c.customer_state, ROUND(SUM(oi.price)::numeric, 2) AS sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id JOIN order_items oi ON o.order_id = oi.order_id WHERE o.order_purchase_timestamp >= '2018-01-01' AND o.order_purchase_timestamp < '2019-01-01' GROUP BY c.customer_state ORDER BY sales DESC LIMIT 5;

然后过 AST 检查、EXPLAIN 彩排、只读执行，最后返回 5 行。

追问销售额要不要排除取消订单？

这是业务口径，不是 SQL 语法。如果指标注册表里定义了“销售额 = 排除取消/不可用订单”，就照抄；没定义就要反问或注明。不同标准答案对这件事的定义可能不同。

因为全给会“又贵又吵”。

  • 37 张表的建表语句大约 7400 个字符，检索后只给 8 张，约 1200–1300 字符，输入 token 降了约 82%；
  • 更重要的不是省钱，是减少噪声：表越多，模型越容易选错、连错；
  • 检索后表全召回 98%、平均召回 99.55%，说明“该用的表基本都在”。
追问检索会不会漏表？

会，全召回 98% 意味着还有 2% 的题漏表；所以有“连通性修复”兜底：选出来的表如果连不成一张图，就补最短的中间表。

没有。准确说是“检索选表 + 一次模型生成”，不是一个请求调两次模型。原来规划过“先让便宜模型选表、再让强模型写 SQL”，但检索层表全召回已经 98%，16 条失败里检索类 0 条；再加一次模型调用，收益没有证据，成本和延迟却确定增加。

所以我在文档里把“两段式”写成“检索一段、生成一段”，面试时会主动说清，避免被误解成两次模型调用。

追问那为什么不让模型自己选表？

37 张表全给，模型会选错；检索是确定性的，能复现、能评估、能解释。选表用算法，写 SQL 用模型，各干各擅长的。

为了让基线可复现。如果默认就开检索、开缓存、开自纠错，那“baseline 47%”就跑不出来了；改一个默认值，历史数字全不可比。

所以优化必须显式打开；评估报告里要记录模型、prompt 版本、检索开关、Top-K、是否 few-shot、是否自纠错、LIMIT 模式、最大行数。数字离开配置就没有意义。

追问84–86 是“全开”吗？

不是。84–86 打开了检索、列剪枝、Join 提示、口径注入、few-shot、结果检查、自纠错、EXPLAIN；但缓存、Agent 工具、模型路由、澄清、持久化没有开。说“全开”会被读配置的面试官纠正。

同一份代码、同一个数据快照、同一个模型 deepseek-flash、temperature=0、prompt 版本 p8-semantic-pruning-v8、本地配置打开主要优化、评估集取 eval 的 100 条。

三次报告分别是 eval-20261108-210214（85）、212550（86）、221405（84）。报告里记了模型、prompt 版本、检索开关、Top-K、自纠错等，但还没有记代码 commit 和数据 hash，这是复现性的缺口。

追问为什么三次不一样？

模型服务有波动，100 条里单题噪声就有 ±1–2 题；三次 84/85/86，12 条稳定失败、6 条单次波动。写范围比写最高值诚实。

最贵的是调模型：一次 1–3 秒、上千 token；检索、校验、执行是毫秒到几十毫秒。最容易错的是语义，不是语法：SQL 有效执行率 100%，但执行准确率 84–86%，错在输出列、聚合口径、时间窗口。

所以优化优先级不是“再把检索写快”，而是“减少模型调用 + 把结果约定写清楚”。

追问最慢的 5% 请求（P95）为什么 12–17 秒？

尾部被重试和多表 Agent 侦察拉长；平均 3–4 秒，一半请求在 1.9 秒内（P50），但最慢的 5% 要等十几秒。这个指标没达到 8 秒目标，我不回避。

同步串行是刻意选择：链路短、状态清晰、计费准确、调试简单；并行会引入“谁先返回、失败怎么合并、token 怎么记账”的复杂度，而当前瓶颈是模型延迟，不是这几毫秒的检索。

扩展时先做无状态化：会话/缓存从进程内迁到 Redis 或 PostgreSQL，API 才能水平扩；再加限流/队列保护模型和数据库；读库加只读副本；评估与线上隔离。当前是单实例、连接池 5、会话在内存，直接加机器会话会漂移。

Part 2 · 选表：37 张表里先选对 8 张

10 题

不靠模型自己看 37 张表，而是先用业务词典做“最大匹配”：

  1. 把表名、字段名、中文别名、枚举值做成词条；
  2. 从问题里找最长的词，命中“订单明细”就不再命中“订单”，避免短词误伤；
  3. 命中的表按类型加分：枚举值 3 分、表别名 2.5 分、字段别名 2 分、英文标识符 1.5 分；单字词打五折；
  4. 从得分最高的 3 张表出发，沿关系图带 1 跳邻居，分数乘 0.4 衰减；
  5. 取前 8 张；如果这 8 张连不成一张图，补最多 2 张中间表；
  6. 最后做列剪枝，只保留主键/外键、问题提到的列、指标列、度量数值列。
追问一个词都没命中怎么办？

回退全量 schema，宁可多给 token，也不因词典漏词把必要表筛掉；回退率本身是要监控的指标。

因为 PostgreSQL 内置的分词器不切中文。实测 to_tsvector('english','统计每个州的订单数量') 把整串当一个 token；换 simple 也一样；show_trgm('订单数量') 返回空数组。中文问题没有空格，全文索引这条路对中文是死的。

通用分词器（jieba/HanLP）能切词，但切出来的“复购率”仍然不知道对应哪张表——真正的难点不是切词，是“中文词 → 哪张表”的领域映射。所以我把切词和映射合成一步：业务词典最大匹配。

追问词典漏词怎么办？

三层兜底：英文标识符直接命中、关系扩展带邻居、一个词都没命中回退全量。词典是人工维护的，漏词是常态，所以要有兜底和监控。

三个原因：依赖为零（不用 embedding 服务、不用向量库、不联网）、37 张表规模用不上、可解释（词典命中能直接说“因为‘复购率’这个词命中 customers”）。

向量能解决同义词/近义表达，但会引入 embedding 成本、索引维护和“相似但不该命中”的误召回；收益要用评估集证明，我没做。简历里写 pgvector 是容易撞车的：镜像带扩展，但代码没有 embedding、没有向量索引。

追问那“销售额”和“GMV”这种近义词怎么处理？

词典里显式配别名，GMV、销售额、成交额 都指向同一个指标。这比向量可控：业务确认过的同义词才加，不会因为语义相近误命中。

四块：表别名、字段别名、枚举值（库里存的值 + 中文含义）、表之间的约定关联。维护原则是“写用户会怎么问，不写字段的正式中文名”；同义词越多召回越好，但不要写“数据/信息”这种太泛的词。

新表至少要补：表别名、关键字段别名、枚举值、关系边；如果有业务指标，再补指标定义。关系两端必须在 schema 里存在，有测试会校验。

追问词典写错了会怎样？

会把问题带到错的表/错的枚举值，SQL 能跑但结果错；所以词典要 review、要测试，枚举值必须和库里的物理值对齐。

简单 contains 会对每个别名独立判断，必然误命中：问“订单明细里有多少商品”时，“订单明细”命中 order_items，“订单”又命中 orders，而 orders 是被“订单明细”包含的噪声。

最大匹配从左到右取最长词，命中“订单明细”后直接跳过这四个字，不会再命中“订单”。单字词（“州”“券”“仓”）不是禁用，而是权重打五折：禁用会丢掉“各州的订单量”这种真实问法，打折让长词在排序上赢。

追问最大匹配会漏重叠词吗？

会。一个句子同时需要“订单”和“订单明细”时，最长匹配只取长的；但这两个词通常指同一组表，关系扩展会把 orders 带进来。真需要时可以在词典里配组合词条。

权重按“命中携带多少确定信息”排：枚举值 3 分（同时确定表和值）、表别名 2.5 分（明确指向一张表）、字段别名 2 分（字段可能跨表重名）、英文标识符 1.5 分（可能是巧合）。单字词再打五折。

关系扩展的分数 = 源表分数 × 0.4 衰减 × 边强度；同一张表有多条路径时取最大值，不累加。累加会让“邻居多”的表靠数量堆分数，而我们要的是“最强的那条路径有多可信”。

追问这些数字是拍脑袋吗？

是人工先验，不是学习出来的；调参只看开发集，不能拿评估集调，否则就是过拟合。

检索是按“词像哪张表”选的，它不保证选出来的表能连起来。典型例子：问“每个大区的商品销售额”，用户不会说“客户”，但 customers 是 regions 和 orders 之间唯一的通路；漏了它，SQL 根本连不出来。

连通性修复就是在关系图上找一条最短桥，把断开的表接上，最多补 2 张。它和“把 Top-K 调大”的区别是：后者无差别加表，会让精确率一起掉；前者只补能消除不连通的那几张。

追问补桥接表会不会引入噪声？

会，所以有预算上限 2，而且只补断开的场景；已经连通的问题一张都不补。代价是最终表数可能变成 Top-K + 2，报告里如实记。

8 是开发集上的取舍：Top-5 全召回 89%，Top-8 到 96%，代价是多约 100 个 token；评估集多表题的标准 SQL 最多用到 6 张表，8 留了余量。

但要承认一个不利证据：早期 eval Top-5 是 54%，高于最终 Top-8 的 52%。所以不能说“8 已被证明最优”；单轮差异可能来自模型波动。K 也不是硬上限：连通性修复还能加 2 张，无词典命中会回退全量。

追问那到底该选 5 还是 8？

只看单轮，5 的准确率更高；但 5 的全召回只有 89%，多表题更容易漏表。我偏向召回，因为漏表会让 SQL 跑不通，错误更硬。要真正定 K，需要多轮重复实验 + 分层看多表题。

列剪枝是在表选完之后，裁掉不相关列，降低建表语句长度和噪声。保留：主键、外键、问题提到的列、指标依赖列、度量数值列；最少保留 4 列，避免把表裁得没法用。

所谓“只做一半”，是指不裁裸列名的语义判断：裸列名可能来自 SELECT 别名、CTE、派生表，裁错是静默错误。带表前缀的列（o.customer_id）能精确归属，才做白名单。

追问列剪枝踩过什么坑？

主键靠列名猜，support_tickets.ticket_id 被裁掉，表 join 不出去；外键只在对端是核心表时保留，桥接表的外键被裁；度量列被误裁，问“佣金合计”时模型只能猜列名。后来改成读真实主键/外键，并在问题含度量词时保留数值列。

因为召回不是瓶颈。84 那轮 16 条失败里，检索类 0 条；7 条是输出列/形状，3 条聚合/去重，2 条时间口径，1 条精度，2 条 join 类型，1 条标准答案多余 join。

表全召回 98%、平均 99.55%，说明表基本都在上下文里；错在“选对表之后，结果形状和口径没对齐”。所以优化方向不是继续提高召回，而是把输出列、聚合粒度、精度、口径做成显式契约。

追问那 2% 的漏召回不影响吗？

影响，但不是当前最大瓶颈。漏召回会让 SQL 跑不通或 join 错，属于硬错误；16 条失败里没有一条是漏表导致的。先把 16 条形状/口径错修掉，收益更大。

Part 3 · 连表：把“边列表”变成“能照着写的树”

8 题

四件事：

  1. 路径多：6 张表有七八条边，多条路径都能连通，模型不知道哪条是推荐的；
  2. 连接键歧义：region_code 和 region_name 都在表里，写错也能跑，但结果错；
  3. 行数放大：一对多 join 后行数变多，SUM/COUNT 会被放大；
  4. 错误静默：SQL 能跑、结果错，没有报错。

所以 Join 规划的目标不是“找一条最短路”，而是“给模型一棵可读、可解释、不过度 Join 的树”。

追问让模型自己看建表语句不行吗？

阶段 1 就是全量建表语句，深层多表只有 10% 左右；只给边列表，模型不知道“先连谁、后连谁”。Join 规划是把推荐顺序显式告诉它。

外键是数据库强制约束的硬事实，比如 orders.customer_id → customers.customer_id；约定关联是数据库没声明外键，但业务上确实存在的关联，比如 refunds.order_id → orders.order_id，由人工核对后写进词典。

项目里真实外键只有 13 条，大量业务关联没有外键；只依赖外键，Join 路径会断。所以关系图 = 外键（强度 1.0）+ 约定关联（强度 0.5），渲染时用 [FK] 标出哪条更可靠。

追问约定关联写错了怎么办？

有测试校验两端表/字段存在，但“数据上是否真的成立”要人工核对；写错会导致推荐路径错，属于高风险人工资产。

把表想成城市，关联想成公路：

  • 生成树：用最少的路把所有城市连起来，不形成环；
  • 最短路：从起点城市到某个目标城市，走代价最小的那条路；
  • Prim：从起点出发，每轮挑一条“一端已连、一端未连”的边，慢慢长成一棵树；
  • Steiner 树：允许新建中转城市来让总路最短，理论最优但计算很难，项目不用。

项目生产入口是“以最相关的表为根，对每张目标表求加权最短路，取并集，再按强度/相关度/表名做 Prim 式生长”。不是“全对最短路”，也不是“把所有表都连上的最小生成树”。

追问为什么不直接输出边列表？

边列表只回答“哪两列能连”，不回答“先连谁、后连谁”；多条路径都能连通时，模型会选错。树给的是推荐顺序。

我们的 Join 规划经历了三次演进，当前生产采用的是基于外键图的斯坦纳树（Steiner Tree）近似算法：

  1. 定目标终端：从语义检索证据、枚举值匹配、MDL 指标依赖里提取“核心目标表集合”（Terminals）；少于 2 张直接返回空，避免单表题过度 Join。
  2. 候选根与度量图：以检索相关度靠前的目标表为候选根，外键边权重设为 1.0，弱关联设为 2.0。
  3. 斯坦纳树近似生长（Takahashi-Matsuyama 算法）：
  4. 算法从根节点集合出发，每轮在剩余未连通的目标终端表中，利用 Dijkstra 寻找距当前树节点集合最近的最短路径并入树中；
  5. 这样避免了独立最短路各自为战的缺陷，使后续目标表能够复用前面已经铺设好的桥接节点（如 customers），消除了局部贪心伪支路。
  6. 生成排序与约束渲染：
  7. 将选出的极小边集交给 Prim 树生成器，按“边强度（外键优先）→ 目标表相关度 → 表名字母序”确定遍历主干；
  8. 最终向 Prompt 输出形如 orders.customer_id = customers.customer_id 的推荐连接树。

实测在 37 张表规模下，该算法运行耗时稳定在 1~2ms，直接将 3 表关联准确率推到 100.00%，4 表以上复杂关联推到 90.91%。

这是被一个真实的线上失败用例 T5-001 逼出来的深刻架构教训。

  • 阶段一（全量最小生成树 MST）为什么失败？

把 Top-8 召回的所有表强行连成一棵树，会把检索进来的无关噪声表（如日志表、推荐表）也作为叶子节点强行连上，模型看到边就会写进 JOIN，导致严重的“过度 Join（Over-joining）”。

  • 阶段二（单源 Dijkstra 独立最短路）为什么失败？

以单一主表为根分别向各个目标表找最短路，会导致局部贪心死锁。 例如在 T5-001 中，目标表是 customer_level 与 sellers。如果根选了 sellers，Dijkstra 会先向 orders、order_items 连，再从局部向 customers 连，把毫无关联的交易主表强制揉成了两根独立路径的并集，生成了包含 5 张表的伪支路。

  • 阶段三（斯坦纳树近似算法）为什么是正解？

斯坦纳树问题是图论中连接指定终端节点子集（Terminals）的极小权重连通子图。在我们的场景中，终端节点就是用户问题涉及的核心表（通常 2~4 张），其余 33 张表都是可选的 Steiner 候选点。 通过动态最小距离扩展，算法能自动挑选代价最小的公共桥接表（例如仅通过 customers 将两端打通），彻底消除了伪支路，让多表关联准确率实现了质的跃迁。

因为树是给模型照着写 SQL 用的，从事实表出发符合 SQL 的自然写法；从维表出发会得到一棵语义别扭的树。

比如从 regions 出发，树可能是“地区 → 客户 → 订单 → 明细”，读起来像“从地区找订单”；从 orders 出发是“订单 → 客户 → 地区”，更自然。根必须来自核心目标表，不能是扩展表，否则整棵树被带偏。

Plan 只覆盖根所在的那一个连通分量，规划表数可能小于选中表数。这时渲染会明确写一行：“还有 N 张表与起点不在同一连通分量，本段未给出连接顺序；它们的关联见上面的 JOINS。”

这不是装饰，是给模型的警示信号，防止它把“推荐连接计划”当成“全部连接”而漏表。这类遗漏会以“SQL 能跑、结果错”的形式出现，是最难查的一类。

追问为什么不生成森林？

多棵树会让模型不知道先写哪个 FROM，反而更容易漏表；多分量通常意味着检索漏了桥接表，正确做法是先修复连通性。

要分两个版本说。第一版是对所有召回表做生成树：52% → 52%，token 反涨 29%，修好 5 条、新坏 5 条，其中 2 条是过度 Join；所以默认关闭。

现在的 planForTargets 是后来改的：只连核心目标表，剔除无关边，避免过度 Join；它在本地全开配置里启用，但我没有单独做它的消融，不能把 84–86 的增量归给它。

保留代码的理由：1）它修的是真实错误类型，换一个 Join 更密集的数据集可能划算；2）“做了、测了、无效、关掉”本身是可信度证据。

Part 4 · 让模型写对 SQL

8 题

prompt 就是给模型的“说明书 + 资料”。我们分两段：

  • 系统提示词：告诉模型“你是 PostgreSQL 数据分析助手，只输出一条 SELECT，必须带 LIMIT，按四步思考：识别表、规划连接、对齐过滤、确定聚合”；
  • 用户提示词：按顺序放表结构、数据画像、业务指标、字段枚举值、示例、最后才是用户问题。

不是把所有东西一股脑塞进去，而是“先给背景，再给规则，最后给问题”。问题放最后，是因为长上下文里模型对末尾更敏感，能减少答非所问。

追问prompt 越长越好吗？

不是。规则越多越容易互相冲突；我们有两处规则和标准答案冲突：统一两位小数、配送时长用 shipments。规则要少而硬，能做成配置的不要写成自然语言。

因为模型对上下文末尾的注意力更强。前面放表结构、口径、枚举、示例，最后放问题，模型更容易把“当前要回答什么”和前面的资料对上。

这不是玄学，是长上下文里常用的“recency”经验；我没有做严格的顺序消融，所以只能说“当前 84–86 是在这个顺序下跑的”，不能说“换顺序一定掉点”。

因为 prompt 是软约束，模型 99% 遵守，剩下 1% 可能给你 DROP TABLE；生产库里 1% 就是灾难。AST 是硬约束：解析成语法树后，必须是一条 SELECT，表/字段在白名单里，函数不在黑名单里，必须有 LIMIT。

正确心智模型是：模型输出等于不可信的用户输入。我们不会把用户输入直接拼进 SQL，也不该把模型输出直接执行。

追问那 prompt 还有用吗？

有用，它降低出错概率、减少重试；但安全不能靠它。prompt 让模型“想对”，AST 让模型“错得无害”。

口径就是“这个指标到底怎么算”。同一个词，不同团队可能定义不同。

比如“销售额”：

  • 含不含运费？
  • 要不要排除取消/不可用订单？
  • 按订单金额算，还是按订单明细的商品金额算？
  • 退款要不要扣？

项目里把业务方确认过的口径写进 metrics.yml，比如 GMV、复购率、客单价、动销率；模型生成时“照抄表达式”，不要自己发挥。这样同一个问题不同人问，结果一致。

追问口径写错了怎么办？

结果会系统性错，而且 SQL 能跑、看不出来。所以口径要业务方确认、要版本化、要测试；不能靠模型猜。

库里很多字段存的是代码，不是中文。比如 customer_state 存 SP，不是“圣保罗”；order_status 存 delivered，不是“已送达”。

用户说中文，模型可能写 WHERE customer_state = '圣保罗'，SQL 能跑，但一行都查不到。所以系统会先从问题里识别实体，再映射到库里的物理字段和值，把“圣保罗 → customer_state = 'SP'”作为提示放进 prompt。

追问模型自己想不到吗？

有时能，有时不能；尤其小写/大小写、缩写、中文译名不一致时。枚举对齐是确定性的，能减少这类静默错误。

指 SQL 能跑、结果也对，但返回的列和标准答案对不上。常见四种：

  1. id 还是 name：标准答案要 level_id，模型给 level_name；
  2. 多一列/少一列：标准答案 3 列，模型 2 列；
  3. 行/列转置：标准答案按“收货州 + 登记州”成对出行，模型做成 same/diff 两列；
  4. 增长量还是增长率：标准答案要“增长了多少”，模型给百分比。

这类错误最麻烦：SQL 有效、结果看起来合理，但评估判错。修法不是再加一句 prompt，而是把“返回哪些列、什么精度、什么聚合”做成显式契约。

先确定“数的是什么”：

  • 数订单/记录行数：COUNT(*)；
  • 数“去重后的实体”（比如一个订单有多条评价，数订单）：COUNT(DISTINCT order_id)；
  • 一对多 join 后直接 COUNT(*) 会把行数放大，结果偏大。

时间窗口统一用“左闭右开”：>= 起点 AND < 终点。不要用 BETWEEN，它会把终点那一天也算进去；按周期分组用 DATE_TRUNC，不要用 to_char 把时间转成字符串。

追问那 COUNT(DISTINCT) 一定更安全吗？

不一定。它更贵，而且问题问“多少条评价”时，去重反而错。关键是先确定计数对象，再选函数。

few-shot 是给模型几个“问题 + SQL”的示例，让它照格式写；示例只从开发集取，不能碰评估集，否则等于漏题。项目里最多放 2–3 条，按表重叠和相似度选。

temperature 是采样随机性；我们设 0，让同样输入尽量同样输出。但温度 0 不等于完全确定：模型服务端的批处理、并行、模型版本更新仍会带来波动，所以三次 84/85/86 是正常范围。

Part 5 · 安全：把模型输出当不可信输入

9 题

正则有三个洞：注释里出现 DROP 会误杀；关键字中间插注释、大小写混写、Unicode 同形字能绕过；拿不到结构信息，判断不了有没有 LIMIT、用了哪张表。

AST 是把 SQL 解析成语法树，“是不是 SELECT”变成一次类型判断，没有歧义；还能拿到表名、函数名、LIMIT。代价是解析器可能不认识某些方言，所以解析失败必须拒绝，不能放行。

追问JSqlParser 解析不了怎么办？

解析失败一律拒绝，这是安全组件唯一正确的默认值。宁可误杀，不可放行。

先检查是不是多条语句，再解析。因为 SELECT 1; DROP TABLE orders 会被解析成两条合法语句，如果只校验第一条，第二条就漏了。

实现上先剥掉末尾分号，再用 parseStatements 数语句数；大于 1 就拒绝。不能简单数字符串里的分号，因为 WHERE name = 'a;b' 里的分号不是语句分隔符。

从本次请求的 schema 上下文里取表名，用 AST 取出 SQL 里所有表，逐个比对；不在白名单就拒绝。

它挡两类问题：攻击者引用系统表/其他库表；模型臆造不存在的表。后者能在执行前暴露，省一次数据库往返，也让错误归因更准确。

追问检索漏表导致合法 SQL 被拒怎么办？

先看 retrievedTables 和表召回：如果是漏召回，修检索/桥接；如果是模型引用了上下文外的表，拒是对的。不能为了让这题过而放宽白名单。

裸列名的合法来源太多：SELECT 别名、CTE 输出列、派生表列、集合操作两侧同名列；做全了必然误杀正常查询。

带前缀的列（o.customer_id）能精确归属到某张表，判定是确定的，所以先做这一半。它挡住的是 sellers.region_name 这种“列存在但不在那张表”的真实错误。

追问CTE 里同名别名怎么办？

项目里踩过：外层 brands bp、CTE 内 brand_products bp，同一个 bp 指两张表。修法不是实现完整词法作用域，而是承认边界：只要别名绑定过 CTE/派生表，该别名的列一律不判定；宁可少拦，不可误杀。

黑名单里是“只读但能造成副作用”的函数：pg_read_file、pg_sleep、pg_terminate_backend、dblink、set_config、nextval 等。光有名单不够，因为解析出来的函数名可能带 schema 前缀或引号（pg_catalog.pg_sleep、"pg_sleep"），直接比对永远不相等。

所以先归一化：小写、取最后一个点之后、去首尾引号，再比对；而且必须递归遍历整棵语法树，子查询、CTE 里的函数也要查。

新增的 CTE 数据修改（WITH x AS (DELETE ... RETURNING *) SELECT * FROM x）最外层是 SELECT，只判 instanceof Select 会放行；FROM 表函数也可能藏副作用。所以补了 6 条对抗用例：3 条 DML CTE、3 条 FROM 表函数。

追问为什么用 getStatement() 而不是 getSelect()？

对 DML CTE 调 getSelect() 会抛 ClassCastException，内部是裸强转；必须用 getStatement() 拿原始语句，再判断类型。

如果查询可能返回多行且没有 LIMIT，就在语法树上补 LIMIT maxRows + 1；执行时最多取 201 行，如果读到第 201 行，说明被截断，丢掉第 201 行并标记 truncated=true。

多取一行是为了区分“恰好 200 行”和“还有更多”；只取 200 行永远判断不出截断。单行聚合（无 GROUP BY、全是聚合函数）不补 LIMIT。

追问LIMIT 能防慢查询吗？

不能。LIMIT 只限制返回行数，不限制扫描/计算；COUNT(*) 大表仍可能很慢。所以还要超时、EXPLAIN 代价护栏。

应用连库用 text2sql_ro，只授 SELECT，显式 REVOKE 掉 INSERT/UPDATE/DELETE/TRUNCATE 和 CREATE；连接设置只读、10 秒查询超时、最多 200 行。

它挡住的是写操作和资源耗尽：最坏情况是读到不该读的数据，而不是删库。挡不住的是合法 SELECT 的数据泄露，那需要行级/列级权限。

追问只读账号能挡住 pg_read_file 吗？

不一定。pg_read_file 是函数权限，某些版本/角色可能允许；所以还要函数黑名单。只读账号挡的是 DML/DDL，不是所有副作用。

覆盖六类：写操作（INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE）、多语句注入、危险函数（含 schema 前缀、引号标识符绕过）、系统目录探测、列级越界、注释/大小写/CTE/表函数绕过。

53 条不是“写几条看着像攻击的 SQL”，每条对应一个真实绕过或真实错误；新增绕过时先加用例、让测试红，再修代码。测试总数 280。

追问53 条够吗？

不够证明绝对安全，但能守住已知回归。安全测试是“已知攻击集”，不是“所有攻击”；还要靠只读账号、超时、审计兜底。

最坏情况是读到不该读的数据，而不是删库：写操作被只读账号挡住，资源攻击被 10 秒超时/200 行挡住，但合法的 SELECT 仍可能读到敏感行/列，或者调用有副作用的函数。

只读账号不够：它只防写，不防越权读，也不防“读到数据后发出去”。要继续收敛，需要行级安全（RLS）、列级授权/脱敏视图、函数白名单、审计日志、网络出口限制。

追问为什么不做 RLS？

项目是单租户、单只读账号，RLS 的收益场景不存在；而且会增加 schema/查询计划复杂度。范围外，不是忘了。上线给外部客户前必须补。

Part 6 · 代价：不是 token，是 SQL 执行代价

6 题

不是。项目里说的“代价”是数据库执行这条 SQL 的代价，不是模型 token。

  • 代价：EXPLAIN 里的 Total Cost、扫多少行、怎么 Join、是不是笛卡尔积；
  • 成本：调模型花了多少 token/多少钱；
  • 延迟：端到端耗时。

“选表、口径、安全、代价、错误归因”里的代价，指的是执行代价，对应 EXPLAIN 预执行护栏；token 我单独叫“模型成本/用量”。

追问为什么容易混？

英文都叫 cost。PostgreSQL 的 EXPLAIN 输出 Total Cost 是优化器的相对代价单位，不是毫秒也不是钱；模型的 cost 是 token 账单。

EXPLAIN 是让数据库“彩排”一遍：告诉你会用哪个索引、怎么 Join、预估多少行、总代价多少，但不真正执行（不带 ANALYZE 时）。

我们用它做两件事：看总代价有没有超阈值；递归看执行计划里有没有“无约束的嵌套循环”（笛卡尔积）。它比直接执行安全，但计划是估算，统计信息过期会偏。

追问EXPLAIN 有开销吗？

有，多一次数据库往返和规划开销；所以护栏默认关闭，本地配置才开，阈值也要按库标定。

笛卡尔积是两张表每行都互相配对，行数爆炸；索引嵌套循环是正常的 Join：外层每行，按内层索引直接找匹配行。

PostgreSQL 会把连接条件下推到内表索引，放在 Index Cond 里；这时顶层的 Nested Loop 节点没有 Join Filter。如果只看“顶层有没有 Join Filter”，会把所有索引连接误判成笛卡尔积。

所以判定要递归看子节点：只要有 Index Cond / Recheck Cond，就说明连接谓词下推了，不判笛卡尔积；同时要求没有 Hash Cond、没有单行标量子查询、预估行数大于 1000。

追问这个细节为什么重要？

不递归看 Index Cond，正常的多表查询会被护栏误杀，表现为“SQL 没错但被拒绝”。这是护栏最容易犯的错。

两个独立条件：

  1. 总代价：Total Cost > maxAllowedCost（默认 100000）→ 拒绝；
  2. 笛卡尔积：节点是 Nested Loop、自身没有 Join Filter、没有 Hash Cond、所有子节点递归都没有 Index Cond/Recheck Cond、没有单行标量子查询、Plan Rows > 1000 → 拒绝。

拒绝不是直接报错给用户，而是把风险诊断回灌给 Agent，触发一次反思重规划；重试仍失败才返回。

追问阈值 100000 怎么定？

先验值，按本库规模/评估集标定；不是通用阈值。不同库、不同统计信息要重新标定。

不能说零误杀。代码和测试只能证明“覆盖的用例里没有误杀”，不能证明所有 SQL；统计信息过期、Merge Join、分区表、方言差异都可能误判。

rejectCartesianProduct 默认 true，但 explainCostGuardEnabled 默认 false——护栏默认不生效，本地配置才打开。线上要先标定阈值、观察误杀率，再开。

追问那默认配置下笛卡尔积不是没拦吗？

是。默认只靠 AST + 只读账号 + 超时；EXPLAIN 护栏是可选增强。线上应该开，但要先标定。

三个不同维度：

维度回答的问题项目指标
代价这条 SQL 执行起来重不重EXPLAIN Total Cost、Plan Rows、笛卡尔积
成本这次问数花了多少 token/多少钱prompt/completion token、¥0.221/100 题
延迟用户等了多久P50 1.9s、P95 12–17s

优化时不能混：降 token 不一定降延迟（模型调用次数可能没变）；降执行代价不一定降成本（模型才是大头）。面试时要把这三个词分开说。

Part 7 · 结果检查与自纠错

7 题

静默错误是“SQL 能跑、结果不报错，但答案是错的”。比如连表条件写偏、过滤条件大小写不匹配、金额列和数量列搞反；数据库不会报错，用户也看不出来。

项目里 84 那轮 16 条失败全是这种：SQL 有效执行率 100%，但结果不对。它比语法错误危险，因为没有信号；所以要有结果检查、评估归因、必要时重试。

8 条人工规则：

  1. 有 WHERE 却返回 0 行；
  2. 单行聚合结果全是 NULL；
  3. 比率列超出 0–100；
  4. 金额/数量出现负数；
  5. JOIN 没有 ON/USING；
  6. 问按月/周/年却没有时间分组；
  7. 问金额却只 COUNT 没有 SUM；
  8. 问退款金额却 SUM 了退款数量。

它不是“答案检查器”，只是“结果看起来可疑”的熔断器；触发后把原因回灌模型重试一次。

追问这是量纲引擎吗？

不是。没有量纲元数据、没有单位换算、没有 LLM Critic，就是 8 条关键词/统计规则。说“量纲守恒引擎”会被追问穿。

第一版对结果集每个单元格做数值判断：问“各州订单占比”时，结果里有一列 order_count（SP 州 4 万单），40000 > 100 被判定“比率越界”，触发重试；而重试策略是“第二次成功就采用第二次”，结果把原本正确的答案覆盖掉了。

修法：先按列名认出“像比率的列”（rate/ratio/pct/percent/占比/比例/率），认不出来就不判；增长率/环比/同比还额外排除（允许负数/超过 100%）。

教训：误报的代价不是多一次调用，而是正确答案被打挂；规则要窄，宁可少报。

因为首答 SQL 有效率已经 96–100%，线上只有“校验拒绝/执行失败/空内容”三种信号，能回灌的错误很少。实测 100 条触发 1 次、救回 0 条。

即使打开结果检查，触发率也很低；收益上界由“结果校验器能发现多少错”决定，而当前校验器只有 8 条关键词规则，很弱。所以自纠错不是没用，是没有足够信号；默认关闭。

追问那为什么还保留？

它覆盖执行失败的长尾；保留代码、默认关闭，等有更强校验器或更弱模型时再评估。不能把 84–86 的功劳归给它。

第一版把标准答案的样例行写进了反馈提示，模型等于看到了答案，70 条跑到 95.7%；删掉标签后同配置回落到 72%。这不是模型变强，是答案泄露。

教训：凡是“加了自我反思就大幅提升”的结果，先查提示里有没有混进标签/标准答案。现在反馈只给问题、上一条 SQL、数据库报错、模型自己结果的前 3 行，不给标准答案。

追问那 95.7% 还能用吗？

不能作为模型成绩，只能作为“泄露会让数字虚高”的反面案例；简历/汇报里绝对不能用。

因为要先证明“有没有用”。项目实测自纠错收益 0，说明当时最大瓶颈不是“校验器不够聪明”，而是“没有足够错误信号”；先上 LLM Critic 会多一次模型调用、增加成本/延迟，而且 Critic 本身也会错。

量纲引擎需要字段语义元数据（金额/数量/时间/比率）、单位换算、非负性等；项目只有 8 条字段名关键词规则，没有元数据。要做可以以后做，但不能把没做的说成做了。

同一个问题有无数种正确写法：列顺序、别名、Join 写法、子查询 vs join 都会变；字符串匹配会把大量正确答案判错。执行准确率是“两条 SQL 都执行，规范化结果集后比较”，更接近事实。

但标准答案也可能有缺陷：T2-037 问“订单数”，标准答案却数客户；T5-007/018 多 join 了不产出列的表；T6-013 的优惠券和订单明细一对多，SUM 会被放大，模型先按订单预聚合反而更对。

追问那为什么不改标准答案？

改了会让 47→52→62→71→84 的历史曲线失去可比性，等于“改标准答案让系统变好看”。正确做法是记录成评估集缺陷，等整体重跑时统一修正。

Part 8 · 评估：84/85/86 到底怎么来的

9 题

六层难度：单表基础 40、单表聚合 40、时间窗口 30、多表 Join（2–3 表）45、深层 Join（4+ 表）20、业务口径 25，共 200。

每题有标准 SQL、标准结果、难度标签、能力标签、备注；标准 SQL 当场执行拿结果，不读快照。200 道按 id 哈希切开发集/评估集各 100，few-shot 只从开发集取，评估集只在验收时跑。

追问200 够吗？

对内部对照够用，对“统计显著”不够；100 条里 1 条就是 1 个百分点，置信区间很宽。所以我说“可复现”，不说“显著提升”。

不是比 SQL 字符串，而是两条 SQL 都执行：

  1. 标准 SQL 执行，拿期望结果；
  2. 模型 SQL 执行，拿实际结果；
  3. 规范化：数字四舍五入到 4 位、NULL 和空串区分、日期/当天零点统一；
  4. 行顺序：只有 ORDER BY 和 LIMIT 同时出现才保留顺序，否则按多重集比；
  5. 列名不参与，但列位置参与；列换序会判错。

一致就是 1，不一致就是 0；84 就是 100 条里 84 条一致。

追问为什么列名不参与？

同一个答案可以起不同别名，列名不承载语义；但列位置承载语义，所以换序会判错。更完善的做法是按语义列名对齐，当前没做。

字符串匹配会把正确写法判错：别名、列顺序、Join 写法、子查询都会变；LLM 裁判成本高、非确定、可能被提示注入，而且裁判本身也会错。

执行结果比对是当前最接近“事实”的方式；代价是标准答案有缺陷时会把好答案判错。LLM 可以辅助解释失败原因，但计分仍用执行结果。

按 Math.floorMod(id.hashCode(), 2) 切成 100/100；few-shot 只从开发集取，评估集只在验收时跑。

缺陷不是“不同 JDK 会变”——String.hashCode 的算法在 Java 规范里是固定的，跨 JDK 稳定；真正的问题是：它不是随机分组、可能和 ID 命名/难度相关、没有分层保证、ID 改了切分就变。更稳的做法是显式 split 字段或按稳定内容哈希 + 分层抽样。

追问那 84–86 有没有数据泄漏？

有风险。开发期看过全部 200 条，评估集也跑过多组配置；所以只能作内部回归参照，不能宣称无泄漏泛化。要证明泛化，需要另建未见测试集。

追问那 86 是不是最好成绩？

Part 9 · 缓存、多轮与成本

7 题

缓存结果会把过期数据当正确答案返回，而且没有信号能发现：SQL 没问题、格式正常，只是数字是旧的。缓存 SQL 只省模型调用，数据每次现取；SQL 描述“怎么查”，不拥有数据。

命中后仍然走完整校验和执行；如果缓存 SQL 这次跑不通，回退重新生成。缓存的是“生成成本”，不是“执行结果”。

同一个问题在不同配置下应该得到不同 SQL：换模型、换 prompt、开关检索/列剪枝/few-shot/口径/工具、改 LIMIT/行数，都会改变模型看到的东西或最终 SQL 的形状。

只拿问题文本做键，改完配置旧答案会继续命中，表现成“我改了配置，数字一点没动”。指纹要覆盖所有影响生成结果的开关，项目里是 17 项。

追问漏字段会怎样？

最初漏了 few-shot，打开 few-shot 重跑消融，数字纹丝不动——命中的全是关掉 few-shot 时缓存的 SQL。报告格式正常，只是数字是上一次配置的。

L1 是进程内 LRU（上限 1000 条），热路径零网络；L2 是 PostgreSQL 的 semantic_cache 表，跨重启、跨实例共享。

不用 Redis 的理由：项目是单实例，共享缓存的问题此刻不存在；Redis 多一个中间件、一次网络往返、一类新失败模式。缓存不可用时降级成“没有缓存”，不能变成“请求失败”。

追问L1/L2 的坑？

第一版缓存键用 \u0000 分隔，PostgreSQL 的 text 列不允许 NUL，落库报 invalid byte sequence 0x00；换成 \u001F。还有 L2 查询在锁内做网络 I/O，把缓存读写串行化；后来移到锁外。

不是，两个不同层面的缓存。

  • 应用层 SQL 缓存：20 题重复 2 遍，50% 重复；命中后省模型调用，平均延迟 1106→521ms（−52.9%），输入 token −50%；这是“重复提问/看板”场景，标准 100 题问题互不重复，命中率是 0。
  • DeepSeek 前缀缓存：系统提示词在 100 次调用里高度重复，命中 178,036/199,436 输入 token（89.27%）；这是模型厂商的自动缓存，不是我们写的 SQL 缓存。

不要把两个 50% 混着说；也不要说“缓存 0ms 响应”——SQL 还要执行。

把“那 2017 年的呢”改写成完整问题“2017 年销售额最高的 5 个州是哪些”，再走标准链路。优先用 LLM 改写，失败/超时降级规则改写（年份替换、前 N 名、条件切换、剥离语气词）。

不全塞历史的原因：历史里的表名/SQL 会污染当前检索，导致表召回漂移；token 随轮次线性涨；模型可能把上一轮 SQL 当模板。改写后的问题仍要重新生成 SQL，不是改 SQL 字符串。

上一轮的 SchemaContext 缓存在会话里；追问且 reuse-schema=true 时，直接取上一轮表上下文，跳过检索，检索耗时 0ms。

但不是整轮 0ms：问题变了仍要重新调模型生成 SQL。当前复用判定是粗粒度的：只要判定为追问就复用，没有校验“是否同一业务域”；主题突然切换时可能复用错表，这是已知风险。

追问为什么会复用错？

canReuseSchema() 只看 isFollowUp()，没有实体/主题一致性校验；用户说“那退款率呢”仍以“那”开头，可能复用上一轮的订单/客户表，漏掉退款表。更稳的做法是加主题校验，或只在时间/排序/LIMIT/同实体时复用。

内存是 synchronizedMap + LinkedHashMap 的 LRU（上限 1000），持有最近 5 轮和上一轮 schema；关闭/30 分钟超时/应用关闭时批量落 PostgreSQL 的会话表。

重启后内存态丢失；已关闭会话只在库里用于列表/审计，不会自动恢复成对话上下文；上一轮 schema 也不持久化，恢复后第一轮要重新检索。多实例更直接：两个实例各有各的 LRU，同一个会话打到不同实例就读不到上下文；要做就得把会话挪 Redis/共享库。

Part 10 · Agent 通用题（面试官不懂 AI 也能听懂）

11 题

用“实习生”打比方：

  • 普通大模型：你问一句，它答一句，不会自己查资料；
  • Workflow：一条写死的流水线，第一步查表、第二步写 SQL、第三步检查，顺序由代码决定；
  • Agent：你给它一个目标，它自己决定下一步做什么、要不要调工具、查到什么再继续；
  • RAG：先查资料再回答，解决“模型不知道”的问题。

我项目的主链路是 Workflow：选表→写 SQL→检查→执行，步骤是代码写死的；只有遇到 3 张表以上的复杂问题，才可选地进入 AgentLoop，让模型自己决定“先查哪张表、要不要验证连表”。三次 84/85/86 都没有开 Agent，所以它们是 Workflow 的成绩，不是 Agent 的。

追问没有 Agent 也能叫智能问数吗？

能。智能不等于“让模型自由发挥”；选表、连表、校验、执行这些确定性步骤用 Workflow 更稳、更可解释。Agent 只用在“需要环境反馈”的局部。

六个模块：

  1. 感知：看懂问题、识别实体；
  2. 记忆：记住当前对话和长期偏好；
  3. 规划：把任务拆成步骤；
  4. 推理：决定下一步；
  5. 行动/工具：查数据库、调 API；
  6. 反思：检查结果、纠正错误。

项目里：感知是问题改写/枚举对齐；记忆是最近 5 轮对话 + 摘要；规划是选表和连表的算法；推理是模型生成 SQL；工具是 5 个只读侦察工具；反思是 8 条结果检查 + 一次重试。

缺的是：开放式任务规划、跨会话长期记忆、多 Agent 协作。不是忘了做，是当前 SQL 任务不需要；硬加会多一层复杂度和不确定性。

四种工作方式：

  • ReAct：想一步、做一步、看结果，再想下一步；适合需要边查边改的任务；
  • Plan-and-Execute：先写完整计划，再按计划执行；适合步骤多、可并行的长任务；
  • Reflection：先做一版，再审查、重写；适合有明确评价标准的任务；
  • Multi-Agent：多个角色分工，比如一个查资料、一个写、一个审。

我项目用的是 窄版 ReAct（3 张表以上、最多 3 轮工具侦察）+ 窄版 Reflection（结果可疑时重试一次）；没有全局 Plan，也没有 Multi-Agent。因为 SQL 问数步骤固定，先写计划只会多一次调用，还可能计划错。

追问那为什么还保留 Agent 工具？

为了验证“复杂多表时，模型是不是缺真实数据”；实测评估集上没量出增益，所以默认关闭。保留是为了以后换数据集时能复测，不是为了好看。

不是。模型只负责“说要调哪个工具、传什么参数”，真正执行的是应用。

流程是：应用先告诉模型“有哪些工具、每个工具要什么参数”；模型输出一段结构化的调用指令（工具名 + 参数）；应用解析、校验、执行；再把结果回传给模型，模型继续回答。

所以模型像“点菜”，应用像“厨房”；模型不会自己进厨房。生产上必须校验工具名、参数类型、业务权限，不能模型说什么就执行什么。

追问参数类型不对怎么办？

先按工具定义校验；能安全转换的转换（比如字符串 “10” 转数字），不能的返回结构化错误让模型重试；不能硬塞进下游。

我项目用的是“文本协议”：模型输出 [TOOL_CALL] 工具名(参数)，我们用自己的解析器从文本里抠出工具名和参数。原生 Function Calling 是模型直接返回结构化的 tool_calls，应用不用解析自然语言。

文本协议的好处是简单、兼容任意模型；坏处是解析脆弱：工具名拼错、参数括号截断、参数里带逗号/括号都可能出错，而且没有 schema 校验。

如果重做，我会优先原生 Function Calling；模型不支持时再降级到文本协议。当前 5 个工具、兼容多家模型，是历史取舍。

MCP 是“工具接入的通用插座”。没有它时，每个应用要接每个工具，都要写一套适配，N 个应用 × M 个工具 = N×M 套；有了 MCP，应用接协议、工具实现服务端，变成 N+M。

MCP 里有三个角色：Host（你的应用）、Client（应用里负责通信的模块）、Server（工具服务）。Server 暴露工具、资源、提示模板；Client 用一套标准的远程调用格式（JSON-RPC）发现和调用。本地走标准输入输出（stdio），远程走 HTTP + 服务器推送（SSE）。

追问MCP 能解决安全吗？

不能。MCP 只解决“怎么接”，权限、审计、沙箱、AST 校验仍要自己做；工具描述本身也可能被篡改，不能盲信。

分三层：

  • 工作记忆：当前这一步的临时状态；
  • 短期记忆：这次对话的历史；
  • 长期记忆：跨会话的用户偏好/知识，通常放向量库或数据库，按当前问题召回。

项目只有前两层：最近 5 轮对话 + 早期轮次的摘要；会话结束落库，但只用于列表/审计，不在下次请求时召回。所以用户上次说“只看 SP”，新会话不会自动继承。

追问上下文太长怎么办？

三种办法：只留最近几轮（滑动窗口）、把早期对话压成摘要、把历史做成向量按需召回。项目用“窗口 + 正则摘要”，便宜、确定，但会丢自然语言条件，不是无损。

多 Agent 适合“任务能拆、子任务能并行、需要不同专业/权限”的场景，比如一个查法律、一个查财务、一个写报告。代价是通信、状态同步、冲突处理、调试变难。

Text2SQL 是单目标、强顺序、共享上下文：选表→写 SQL→检查→执行，拆成多个 Agent 只会增加协调成本，不会让 SQL 更对。所以项目是单 Agent/单编排器。

如果真要加，我会加一个“SQL 审查 Agent”：它只读，不改 SQL，只按规则给出“阻断/警告/建议”；最多 1–2 轮，不能无限否决；审查和生成用同一个模型会有共同盲点，所以先跑确定性规则，再让模型补充。

三类最常见：

  1. 死循环：反复调同一个工具、反复改同一条 SQL；防法是最大轮数、重复动作检测、预算上限；
  2. 跑题/目标漂移：越查越远，忘了最初问题；防法是每轮对照原始目标、限制子任务范围；
  3. 上下文爆掉：工具返回太多、历史太长；防法是截断工具结果、摘要历史、设 token 预算。

项目只做了最基础的三条：最多 3 轮、SQL 10 秒超时、会话最多 5 轮；没有动作哈希、没有 token 预算器、没有目标漂移检测。这些是下一阶段要补的。

普通问答只看“最后答案对不对”；Agent 还要看“过程”：

  • 任务有没有完成；
  • 工具选得对不对、参数对不对；
  • 走了几步、花了多少 token/时间；
  • 有没有违规操作；
  • 失败了能不能恢复。

项目现在只有执行准确率（最后结果集对不对）、SQL 有效率、表召回、P50/P95、token；没有轨迹指标、没有工具调用准确率。所以我能说“结果对不对”，不能说“过程好不好”。

追问怎么补？

先给每次请求加 traceId，记录每一步的工具名、参数摘要、结果状态；再抽 100 条人工标“该用什么工具、该查什么表”，算工具选择准确率和步数效率；成本大约 3–5 小时。

先承认，再解释，不要硬装。

“对，主链路是 Workflow；Agent 只用在 3 张表以上的局部侦察，而且默认关闭。84–86 是 Workflow 的成绩，不是 Agent。我选 Workflow 是因为 SQL 问数步骤固定、错误代价高、需要逐层归因；Agent 的开放式规划在这里收益不明确。”

MCP/A2A 没做也直接说：

“MCP 是工具接入的通用协议，A2A 是 Agent 之间协作的协议；我项目只有 5 个进程内工具、单 Agent，没有跨应用复用/多 Agent 协作需求，所以没接。硬接只会增加协议、权限、部署复杂度；要做的话，先把工具执行器包成 MCP 服务，再补权限和审计。”

不编“我们内部实现了 MCP”。面试官追问 tools/list、JSON-RPC、stdio/SSE 就穿帮；诚实 + 知道什么时候该做，反而加分。

Part 11 · Java / Spring / PostgreSQL 基础

8 题

主要用了：

  • record：不可变数据对象，比如接口响应、连接计划；自动生成构造器、getter、equals/hashCode；
  • text block：多行字符串，比如 prompt 模板、SQL 示例；
  • switch 表达式/模式匹配：把状态映射成 HTTP 状态码、判断 SQL 类型；
  • List.getFirst()：Java 21 的顺序集合 API，取排名第一的表；
  • instanceof 模式匹配：判断 Select/PlainSelect 等类型。

虚拟线程没有用：当前瓶颈是模型 I/O 和数据库连接池，不是平台线程数量。

Spring Boot 会根据依赖和配置自动创建对象（Bean）。比如引入 Spring AI 的 OpenAI starter，它会自动创建一个聊天模型客户端。

问题在于：没配 Key 时，它会在启动阶段报错，导致“只想跑数据库/校验/评估”的人被卡死。所以我用配置显式关掉自动配置，改成手写装配：有 Key 才建客户端，没 Key 也能启动，只是问数接口返回“未配置”。

追问自动装配和包扫描有什么区别？

包扫描扫的是你自己写的 @Component/@Service；自动装配是 starter 提供的、按条件生效的默认对象。来源不同，优先级也不同。

用 OpenAI 兼容协议：配 base-url、completions-path、model、api-key 四项；DeepSeek、通义、千帆只要兼容这个协议，改配置就能换。

端点是 base-url + completions-path 拼起来的，所以不要把 /v1 写进 base-url，否则会拼成 /v1/v1/... 404。判断端点对不对：带假 Key 请求，返回 401 说明路对了，返回 404 说明路径错。

追问没 Key 能启动吗？

能。没 Key 时客户端为空，问数接口返回 503；数据库、校验、评估链路仍可离线跑。这是刻意的“可检查状态”，不是异常。

依赖注入用构造器注入：依赖不可变、启动就暴露循环依赖，单测可以直接 new。AOP 在项目里用得少，主要是全局异常处理；探味志项目里用拦截器做登录校验和续期。

三者的区别：过滤器在 Servlet 容器层，拦截器在 Spring MVC 层，AOP 在方法调用层。拦截器能拿到 Controller 方法信息，AOP 适合日志/事务这类横切逻辑。

项目里并发点不多：缓存用 synchronized + LinkedHashMap 做 LRU；BYOK 客户端池、会话缓存也用同步包装的 LRU；检索器/关系图用 volatile 做惰性缓存；数据库连接池是 Hikari，最大 5 个连接；评估是串行，没有自定义线程池。

ThreadLocal 主要用在探味志的登录上下文：拦截器里 set 用户，请求结束 finally remove；线程池复用线程，不 remove 会串用户/内存泄漏。

追问synchronized 会不会成为瓶颈？

缓存读写是内存操作，锁竞争很低；真正慢的 L2 数据库查询已经移到锁外。QPS 上来可以换 Caffeine/分段锁。

最大风险是 SELECT * FROM geolocation 这种百万行结果把堆打满。项目三层防：SQL 层补 LIMIT maxRows+1；执行层 setMaxRows(201)；读完最多保留 200 行，多的一行用来判断截断。

另外 schema 元数据只加载 37 张表，缓存/会话都有 LRU 上限，调用日志默认不记 prompt/回复内容，避免“输入决定内存”。

追问setMaxRows 和 SQL LIMIT 有什么区别？

setMaxRows 是 JDBC 驱动层限制，数据库可能仍算完再返回；SQL LIMIT 是数据库层限制，能减少计算/传输。项目两者都用。

因为评估要连续跑 100 条，任何一条抛异常都会中断整轮；而且失败类型本身就是要统计的数据。统一返回状态（成功、被校验拒绝、生成失败、执行失败、未配置、需要澄清），Controller 再映射 HTTP 状态码。

这样日志里不会出现“同一类错误两种形态”，评估报告也能按状态统计。

追问内部未知异常怎么办？

全局异常处理器兜底，返回 500；已知失败都翻译成状态，不吞异常，记录上下文。

选 PostgreSQL 的原因：分析型 SQL 更顺手（窗口函数、CTE、DATE_TRUNC、FILTER）、EXPLAIN 的 JSON 格式方便程序分析、只读角色/权限模型清晰。MySQL 也能做，但在“JSON 计划树 + 复杂分析查询”上 PG 更直接。

索引：MySQL InnoDB 主键是聚簇 B+ 树，二级索引叶子存主键；PostgreSQL 是堆表 + B-tree 索引，索引叶子存行指针。联合索引遵循最左前缀；覆盖索引是查询需要的列都在索引里，不用回表。

多版本并发控制（MVCC）：PG 给每行保留版本号（xmin/xmax），更新产生新版本，旧版本由 vacuum 清理；MySQL InnoDB 用 undo log + read view。默认隔离级别 PG 是 Read Committed，MySQL 是 Repeatable Read。

追问为什么 PG 的 COUNT(*) 慢？

MVCC 要判断每行对当前快照是否可见，不能只读一个行数计数器；大表只能扫可见行。近似计数可以走统计信息/物化视图。

Part 12 · 行为面与开放题

6 题

最大的失败不是某个 bug，是几次“以为有用、实测没用”的误判：

  • 第一版 Join 规划：52%→52%，token 反涨 29%，还引入过度 Join；我把它默认关掉；
  • 自纠错：首答有效率高，100 条触发 1 次、救回 0 条；我如实写收益 0；
  • 答案泄露：把标准答案样例写进反馈，70 条跑到 95.7%；删掉后回落到 72%。

学到三件事：先证伪自己的假设、任何提升都要有对照、别用修改标准答案让系统变好看。

先修“决定天花板”的两层：4 张表以上的深层题（40–60%）和输出形状（7 条失败）；再做评估集口径统一/标准答案审计；然后建未见测试集证明泛化；最后才考虑向量检索、多方言这些增量。

顺序原则：先修正确性瓶颈，再修评估可信度，最后做新功能。不是先上 Agent、也不是先做性能。

因为链路固定（选表→生成→校验→执行→有限重试）、只有 5 个工具、要求逐层归因。框架会把控制流藏进黑盒，出问题难定位；手写编排约百行，状态可控、日志可读、依赖少。

Java 生态可以用 Spring AI（@Tool/MCP）、LangChain4j；但当前链路简单，框架收益小于理解成本。等链路变长、需要人工审批/断点恢复/多 Agent 时再上。

优势是工程闭环和归因：能把一个不确定的模型能力包进检索、校验、评估、成本账本里，能说清每个数字的条件和每个失败的层。

短板是模型侧理论深度不够：embedding、向量检索、模型微调没有真正落地；项目也是单实例，没有多租户、数据权限、真实高并发的考验。这些是下一阶段要补的，不是嘴上说“学习能力强”。

问三类：
