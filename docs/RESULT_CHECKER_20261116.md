## 1. 复现到的实际问题

旧规则的问题不是“开了自纠错”本身，而是提供给自纠错的异常信号错误：

1. 问题包含 GMV、金额、价格、数量等词时，扫描整行所有数值；负增长率、价格差额、未知数值列都可能被当成负金额。
2. 比例规则遇到问题包含同比、环比、增长，就跳过整个结果集；同一结果里的真正异常退款率也被豁免。
3. 用 `contains("rate")` 判断比率列，会把 `separate_value` 这样的名称也认成比率。
4. 使用 `Double` 比较会把 `-1e-400` 舍为负零，或把 `100.000000000000000001` 舍为 100，漏掉边界外数值。

真实数据库回放旧代码的 200 条 Gold SQL，发现两处报警：

| 题目 | 实际输出列 | 旧规则误报值 | 为什么允许为负 |
|---|---|---:|---|
| T5-019：类目平均价格涨跌幅与订单数 | `avg_price_change` | -9.93 | `AVG(new_price - old_price)` 是价格变化量 |
| T6-022：2017/2018 各月 GMV 与同比 | `yoy_pct` | -99.98 | 增长率允许下降，不受金额非负约束 |

这些是固定 Gold 查询上的可复现误报。此前真实模型那次 T6-022 没保存生产首答 SQL，本阶段仍不能倒推“那次首答本来正确、纠错把正确答案改错”。

## 2. 新机制：先确定列的规则，再读取值

新增 `ResultColumnPolicy`。每个输出列按位置生成独立记录：

`index + label + kind + source + rule`

- `index` 是列身份，不依赖列名唯一；同名列仍对应不同位置。
- `label` 来自 `QueryResult.columns()`，即 JDBC 输出列标签。
- `kind` 为 `GROWTH`、`SIGNED`、`BOUNDED_RATIO`、`NON_NEGATIVE` 或 `UNKNOWN`。
- `source=OUTPUT_LABEL` 表示依据列名线索，**不是数据库约束或 SQL 血缘证明**；未知列为 `source=NONE`。
- `rule` 记录具体分类规则，如 `GROWTH_LABEL`、`SIGNED_LABEL`、`NON_NEGATIVE_LABEL`。新旧回放报告保留分类结果；报警反馈带行、列位置与规则依据。

### 分类冲突如何处理

分类依次检查增长线索、有符号线索、比例线索、非负指标线索，最后返回未知。这是明确的规则优先级，没有用不透明的置信度分数：

| 列标签示例 | 分类 | 比例/负数检查 |
|---|---|---|
| `yoy_pct`、`growth_rate`、`同比增长率` | GROWTH | 允许负数和超过 100 |
| `net_amount`、`avg_price_change`、`price_diff` | SIGNED | 允许负数 |
| `refund_rate`、`pct`、`占比` | BOUNDED_RATIO | 沿用 [0,100] 范围 |
| `gmv_2018`、`amount`、`order_count`、`unit_price` | NON_NEGATIVE | 检查负数 |
| `mystery`、`sum`、`bucket_id`、`separate_value` | UNKNOWN | 跳过这两条数值规则 |

因此 `net_amount` 不会因为含 `amount` 再被升级为非负金额；`gmv_yoy_pct` 不会因为含 GMV 或 pct 而覆盖增长身份。英文按词边界匹配，支持常用 camelCase 和同比缩写；中文使用明确线索。

检查器按列位置访问单元格，只扫描被分类到对应规则的列。问题里出现“同比”不再让整张结果表获得豁免。例如同一行 `gmv=100`、`yoy_pct=-30`、`refund_rate=150`，仍会针对第三列触发比例越界；若 GMV 本身为 -100，仍会触发负金额检查。

数值解析使用 `BigDecimal` 的 `signum` 与精确比较，保留科学计数法和十进制边界。`-0.0` 视为零；NULL、非数值、NaN、Infinity 不参与这两条数值规则。稀疏行跳过不存在的列位置，不把其他列的值错配过来。

## 3. 纠错链路与影响范围

例如用户问“GMV 与同比增长率是多少”：

1. 正常生成 SQL，经过已有 AST 安全校验、只读执行，得到 `gmv=100`、`yoy_pct=-99.98`。
2. 列策略分别为 NON_NEGATIVE、GROWTH；金额非负，增长率有符号，两项数值规则均不报警。
3. 没有其他异常时，编排器直接保留首答，不追加模型调用。
4. 若 GMV 为 -100，则针对 GMV 列报警，反馈说明列名、位置、实际值及 `OUTPUT_LABEL/NON_NEGATIVE_LABEL` 来源，并提醒不要为消除异常改动增长率或时间范围。
5. 编排器沿用最多两次调用、重试结果再检查、两次成本合并的既有机制。报警规则码仍为 `NEGATIVE_METRIC_VALUE` / `RATIO_OUT_OF_BOUNDS`。

反馈是提示词软约束，不能保证模型绝不改坏时间范围。是否真的修复 SQL，仍需执行与结果评测。没有修改 API 响应结构、数据库表、检索排序、SQL 生成模板、自纠错开关或费用计算。

## 5. 设计取舍、遗漏与面试边界

没有选择“问题包含同比就关闭金额检查”：混合输出中的真正负 GMV 会漏报。没有关闭整个结果校验器：负金额、负数量和真正比例越界仍能产生信号。没有扫描所有负数后再根据题干猜列身份：必须先绑定输出列位置和分类依据。

本阶段也没有实现完整 SQL 列血缘。完整推断要处理 CTE、子查询、窗口函数、集合操作和函数签名，当前指标配置又没有完整的类型与单位约束。先用有来源、可验收的列名启发式控制已知误报，**不把弱证据包装成强证明**。若要覆盖任意别名，应补指标类型/单位和投影血缘，而不是继续无限堆关键字。

仍存在的边界：

- 模型若把净额错误命名为 `amount`，仍可能误报；把金额命名为 `net_amount` 或未知 `v`，又可能漏报。命名线索不是可信契约，也不是安全防线。
- 比例仍沿用宽松的 [0,100] 检查，尚未区分 0–1 比率与百分比。`ratio=1.5` 可能被漏掉；不能宣称比例单位已完整校验。
- 非数值、未知列跳过不代表结果正确；正常返回只是“当前规则未发现问题”。
- 其他空结果、全 NULL、时间维度等规则仍是独立启发式，不能用本轮数字证明它们没有误报。
- 30 个样例是针对性的边界契约，不是随机生产样本；200 条 Gold 的误报从 2 到 0，既不证明模型执行准确率提高 2 个百分点，也不证明对错误 SQL 的召回率达到 100%。

**面试追问一：为什么能证明负同比合法？** 本轮用固定同比公式、真实返回值和业务边界用例验证已知场景；运行时依据仍是列名启发式，不能声称理解了所有 SQL。关键是区别明确来源与推断强度。

**面试追问二：未知列为什么不强行检查？** 错误报警会额外调用模型并可能改变原本正确的业务口径。没有类型依据就跳过，并保留 UNKNOWN 身份；业务只读安全依然由 AST、只读账号与执行护栏保证，不能让启发式冒充安全组件。
