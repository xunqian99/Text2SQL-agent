# 项目术语手册（面试口语版）

> 用法：先看“一句话”，再看“项目里指什么”，最后看“面试怎么说”。
> 目标不是背定义，而是被追问时能用大白话把机制讲穿。

---

## 0. 先记住 7 组最容易混的

| 容易混 | 一句话区分 |
|---|---|
| 召回率 vs 精确率 | 召回 = 该来的有没有来；精确 = 来的里面有多少真有用 |
| SQL 有效率 vs 执行准确率 | 有效率 = 车能不能发动；准确率 = 有没有开到目的地 |
| 生成树 vs 最短路 | 生成树 = 用 n-1 条边把所有表连起来；最短路 = 从根到某张表走代价最小的路 |
| 笛卡尔积 vs 索引嵌套循环 | 笛卡尔积 = 两张表每行互相配对；索引嵌套循环 = 按索引直接找匹配行，是正常 Join |
| 语义缓存 vs 结果缓存 | 语义缓存存 SQL；结果缓存存数字。前者不会过期，后者会 |
| Schema 复用 vs 整轮 0ms | Schema 复用只省“检索表”这一步，生成 SQL 仍要调模型 |
| 自纠错 vs 模型路由 | 自纠错 = 同一个模型看错误再做一遍；路由 = 换一个更强的模型做 |

## 1. 数据与口径

| 词 | 一句话解释 | 在你项目里指什么 | 面试怎么说 |
|---|---|---|---|
| Schema | 数据库的“目录说明书”：有哪些表、哪些列、什么类型、谁和谁怎么连 | 37 张业务表；`SchemaContext` 是本次请求裁剪后的那部分 | “Schema 不是数据，是数据结构；模型写 SQL 前必须先看到它” |
| DDL | 建表语句，比如 `CREATE TABLE ...` | `SchemaDdlRenderer` 把表/列/外键渲染成 prompt 里的 DDL 文本 | “给模型的不是整库，是裁剪后的 DDL” |
| 主键 | 一行数据的唯一身份证 | 如 `orders.order_id` | “主键用来唯一标识一行，Join 和去重都靠它” |
| 外键 | 一张表指向另一张表的“身份证号” | 如 `orders.customer_id -> customers.customer_id` | “外键是数据库保证的硬关联；但本库只有 13 条，很多关联得靠词典补” |
| Join | 按关联键把两张表拼起来 | `orders JOIN order_items ON order_id` | “Join 不是越多越好；多连一张表可能放大行数” |
| 事实表 | 记录“发生了什么”的表 | `orders`、`order_items`、`payments` | “事实表通常是 Join 的起点，因为它有业务事件和时间” |
| 维表 | 描述“是谁/在哪/什么”的表 | `customers`、`products`、`regions` | “维表提供分组维度，事实表提供度量” |
| 桥接表 | 两张表连不上时，夹在中间的“中转表” | `customers` 连着 `regions` 和 `orders` | “问‘每个大区销售额’时，用户不会说客户，但 customers 是唯一通路” |
| 扇出 | 一对多 Join 后行数变多，SUM/COUNT 被放大 | 一个订单多条明细、多条评价 | “Join 后计数要用 COUNT(DISTINCT)，否则会重复计数” |
| 枚举 | 字段里固定的代码值 | `order_status='delivered'`、`customer_state='SP'` | “用户说‘已送达’，库里存的是 delivered；要做值对齐” |
| 口径 | 业务上“这个指标到底怎么算”的定义 | GMV 是否含运费/取消订单；复购率分母是人数还是订单数 | “口径不是 SQL 语法，是业务约定；项目用 metrics.yml 显式写死” |
| GMV | 成交总额，通常是商品金额求和 | `SUM(order_items.price)` | “GMV 要不要扣退款、含不含运费，是口径问题，不是模型问题” |
| 复购率 | 重复购买的用户占比 | 复购用户 / 总用户 | “分母是人数还是订单数，必须先定义” |
| 动销率 | 有销量的商品占全部商品的比例 | 有订单的商品 / 全部商品 | “时间窗和‘有销量’的定义都要写清” |
| 客单价 | 平均每单/每人的金额 | 销售额 / 订单数（或客户数） | “分母不同，数字差很多；这是典型口径歧义” |
| 有效订单 | 排除取消/不可用之后的订单 | `order_status NOT IN ('canceled','unavailable')` | “不同团队对‘有效’定义不同，不能靠模型猜” |

## 2. 检索与图

| 词 | 一句话解释 | 在你项目里指什么 | 面试怎么说 |
|---|---|---|---|
| Top-K | 只把得分最高的 K 张表交给模型 | K=8；连通性修复最多再加 2 张 | “K 是候选表上限，不是最终表数的硬上限” |
| 召回率 | 该用的表，有没有被选进来 | 全召回 98.00%；平均召回 99.55% | “全召回 = 所有需要的表都在 Top-K 的题目比例；平均召回 = 每题命中表/需要表的平均” |
| 精确率 | 选进来的表里，有多少真有用 | 平均表精确率 28.42% | “Top-8 是召回优先，精确率不高；噪声表靠生成/校验兜底” |
| 最大匹配 | 从问题里找“最长的词”，避免短词误命中 | “订单明细”优先于“订单”；单字词权重 ×0.5 | “它本质是词典驱动的实体链接，不是通用分词” |
| 领域词典 | 把中文说法映射到表/列/枚举值 | `glossary.yml`：表别名、列别名、枚举 label、关系边 | “通用分词器不知道‘复购率’落哪张表，领域词典知道” |
| 关系扩展 | 命中表之后，沿关系图带上它的邻居 | 1 跳、衰减 0.4、最多 3 个种子 | “扩展分数 = 源表分 × 衰减 × 边强度，不是无差别加表” |
| 连通性修复 | Top-K 表连不起来时，补最短桥接表 | 多源 BFS 找桥；最多补 2 张 | “它只补断点，不是把 topK 调大” |
| 关系图 | 表与表之间的边，带列名和强度 | `JoinGraph`：13 条外键 + 36 条约定关联 | “外键是硬事实，约定关联是人工核对的软知识” |
| 生成树 | 用 n-1 条边把所有表连起来，没有环 | `JoinPathPlanner.plan()` 的 Prim 式生长 | “生成树解决‘都连上’，不解决‘哪条路最优’” |
| 最短路 | 从根到某张表，走代价最小的路径 | `findShortestPath`：FK 代价 1.0，推断边 2.0 | “生产入口是根到各目标表的最短路并集，再排成树” |
| Dijkstra | 求单源最短路的经典算法 | 用在 `findShortestPath` | “边权非负，用优先队列；这里边权只有 1 和 2” |
| Prim | 从根往外长树，每轮挑一条边界边 | `plan()` 的“强度 → 相关度 → 表名” | “它不是标准最小生成树，排序键是业务相关度，不是权重和” |
| Steiner 树 | 允许加中间点，让总边数最少 | 项目没用；NP-hard | “为省几条边不值得，而且最优是按边数，不是按业务语义” |
| 根节点 | 连接树从哪张表开始 | 检索排名最高的核心目标表 | “从事实表出发，SQL 写法最自然” |

## 3. 安全与执行

| 词 | 一句话解释 | 在你项目里指什么 | 面试怎么说 |
|---|---|---|---|
| AST | 把 SQL 解析成“语法树”，能看结构 | JSqlParser 解析后判断是不是 SELECT、用了哪些表 | “AST 不是字符串匹配，它能拿到结构和类型” |
| JSqlParser | Java 的 SQL 解析库 | 解析、表白名单、函数黑名单、LIMIT 改写 | “选它是因为只需要解析+校验，Calcite 太重” |
| 白名单 | 只允许清单里的东西 | 表/列白名单；只允许 SELECT | “白名单比黑名单安全，因为默认拒绝” |
| 黑名单 | 明确禁止清单里的东西 | 28 个危险函数：`pg_sleep`、`pg_read_file` 等 | “黑名单不可能穷举，所以还要只读账号兜底” |
| fail-closed | 解析不了就拒绝，默认安全 | `parse` 失败直接 `PARSE_ERROR` | “安全组件的默认值必须是拒绝，不是放行” |
| 只读账号 | 数据库用户只有 SELECT 权限 | `text2sql_ro` | “AST 可能有洞，只读账号是物理兜底” |
| EXPLAIN | 让数据库只给执行计划，不真正执行 | `EXPLAIN (FORMAT JSON)` | “它回答‘这条 SQL 大概会怎么跑、代价多大’” |
| 执行计划 | 数据库打算怎么扫表、怎么 Join | `Node Type`、`Total Cost`、`Plan Rows`、`Index Cond` | “看计划比看 SQL 更接近真实代价” |
| Nested Loop | 两层循环：外层每行，内层找匹配 | 计划树里的 `Nested Loop` 节点 | “有 Index Cond 的 Nested Loop 是正常索引连接” |
| Index Cond | 连接/过滤条件下推到索引 | `Index Cond: order_id = orders.order_id` | “有它说明走索引了，不能判成笛卡尔积” |
| Join Filter | 连接条件在 Join 之后才过滤 | 顶层 Nested Loop 上的 `Join Filter` | “没有 Join Filter 且没有 Index Cond，才可能是无约束笛卡尔积” |
| Hash Cond | Hash Join 的连接条件 | Hash Join 节点上的 `Hash Cond` | “有 Hash Cond 说明不是无约束 Join” |
| 笛卡尔积 | 两张表每行都互相配对，行数爆炸 | `FROM orders, customers` 漏写 ON | “AST 合法，但执行会打爆内存，所以要用 EXPLAIN 拦” |
| Cost Guard | 执行前的代价护栏 | `QueryPlanAnalyzer`：总代价阈值 + 笛卡尔积检测 | “它拦的是‘合法的灾难’，不是语法错误” |
| 超时/行数上限 | 查询最多跑 10s、返回 200 行 | `setQueryTimeout(10)`、`setMaxRows(201)` | “形态合法不等于资源可控，这是另一层防线” |

## 4. 评估

| 词 | 一句话解释 | 在你项目里指什么 | 面试怎么说 |
|---|---|---|---|
| gold SQL | 标准答案 SQL | 评估集里人工写的 `gold_sql` | “gold 不是绝对真理，它是当前业务约定” |
| 执行准确率 EX | 生成 SQL 的结果集和 gold 是否一致 | 84/100（复跑 85/100） | “不是比 SQL 字符串，是执行后比结果集” |
| SQL 有效率 | SQL 能不能通过校验并执行成功 | 100/100 | “有效 ≠ 正确；它只说明车能发动” |
| 结果集规范化 | 把数字/时间/NULL/行序统一后再比 | `ResultNormalizer`：4 位小数、NULL 区分、日期归一 | “不规范化会把正确答案判错” |
| dev/eval | 调参集 / 验收集 | 200 条按 id hash 切 100/100 | “few-shot 只从 dev 取，eval 只在验收时跑” |
| dry-run | 用 gold SQL 当模型输出，跑下游链路 | 默认配置 200/200；检索+剪枝 194/200 | “它验证评估器/校验器本身，不是模型成绩” |
| 消融实验 | 一次只改一个开关，看指标变化 | 47/52/62/71/84 那张表 | “跨模型不能直接相减；同模型才能看增量” |
| 分层 T1–T6 | 按难度/能力分组 | T1 单表基础、T2 聚合、T3 时间、T4 多表、T5 深层、T6 口径 | “整体 84%，但 T5 只有 50%，不能只报总数” |
| 过拟合 | 针对评估集调参，数字好看但泛化差 | 用 eval 调 prompt 就是过拟合 | “调参只看 dev，eval 只验收” |
| 数据泄漏 | 模型/提示里混进了评估答案 | few-shot 只从 dev 取；反馈不带 gold | “自纠错提示里混 gold，70 条能跑到 95.7%，那是泄漏” |
| P50 / P95 | 50%/95% 请求的延迟上限 | P50 1743ms；P95 10.31s | “P95 看尾部；5% 请求比 10.31s 还慢” |
| ±3pp 噪声 | 同配置多轮也会波动约 3 个百分点 | 71/68/70 三次 | “小于 3pp 的改动不能单轮下结论” |

## 5. Agent、缓存与多轮

| 词 | 一句话解释 | 在你项目里指什么 | 面试怎么说 |
|---|---|---|---|
| prompt | 给模型的指令 + 上下文 | system 的 18 条规则 + user 的 schema/指标/示例/问题 | “prompt 是软约束，硬约束在 AST” |
| token | 模型计费/上下文单位 | prompt 2029、completion 461、total 2490/题 | “token 是真实统计；金额为 0 是单价没填” |
| temperature | 采样随机性 | 0.0 | “Text2SQL 要确定性，但 provider 仍有波动” |
| few-shot | 给模型几个“问题+SQL”示例 | 35 条示例库，取 Top 2–3，只从 dev | “示例能提升格式/口径，但会占 token，也可能泄漏” |
| ReAct | Reason + Act：先想，再调工具，再看结果 | `AgentLoop` 的 Act–Observe–Reason | “不是所有问题都值得 Agent；3+ 表才触发” |
| Agent Loop | 模型调工具、系统回灌结果的循环 | 最多 3 轮；`[TOOL_CALL]` / `[FINAL_SQL]` | “工具错误也是 Observation，模型下一轮自己修” |
| 工具调用 | 模型输出工具名+参数，系统执行 | 5 个：INSPECT_TABLE/COLUMN、SAMPLE_QUERY、CHECK_JOIN、EXPLAIN_QUERY | “工具只读、LIMIT 5、10s 超时、过 AST” |
| 幻觉 | 模型编造不存在的东西 | 编表名、编列名、编 join 条件 | “AST 白名单能拦编造的表/列，但拦不住语义错” |
| 静默错误 | SQL 跑通、结果错，没有报错 | 16 条失败全是 `SUCCESS` 但结果不对 | “这是线上最危险的，因为没有信号” |
| Zero Signal | 线上没有标准答案，不知道对错 | 没有 gold，只能靠启发式/用户反馈 | “自纠错收益 0，就是因为没有足够信号” |
| 自纠错 | 把错误/可疑结果回灌模型再试 | 校验拒绝/执行失败/ResultChecker 可疑时重试一次 | “首答有效率高，触发少；实测救回 0 条” |
| 模型路由 | 失败后换更强模型重试 | `routing.escalation-model` | “和自纠错共用一次重试；触发率约 2%，没量出收益” |
| ResultChecker | 结果看着不合理就报警的规则检查器 | 8 条关键词启发式：空结果、全 NULL、比率越界等 | “它是负向熔断器，不是答案检查器” |
| 语义不变量 | 业务上“不可能出现”的约束 | 比率 0–100、金额非负、时间维度不能丢 | “项目只有 8 条关键词规则，不是通用引擎” |
| 量纲 | 金额/数量/时间等单位 | 金额不能和件数直接相加 | “项目没有量纲元数据/引擎，别吹‘量纲守恒’” |
| 语义缓存 | 缓存“问题 → SQL”，不是结果 | `SemanticCache`：归一化问题 + 配置指纹 | “命中省模型调用，但仍要执行 SQL” |
| 配置指纹 | 模型/prompt/开关的签名 | 模型、prompt 版本、检索开关、few-shot、LIMIT 等 | “配置变了，键就变，避免命中旧 SQL” |
| L1/L2 | 进程内缓存 / 数据库缓存 | L1 LRU 1000 条；L2 `semantic_cache` 表 | “L1 热路径零网络；L2 跨重启/多实例” |
| LRU | 最近最少使用，先淘汰最久没用的 | `LinkedHashMap(accessOrder=true)` | “缓存必须有上限，否则就是内存泄漏” |
| Schema 复用 | 多轮追问直接复用上一轮表上下文 | `ConversationSession.lastSchema` | “只省检索，不省生成；0ms 指检索 0ms” |
| 指代消解 | 把“那 2017 年的呢”补成完整问题 | `QuestionRewriter`：LLM 改写 + 规则降级 | “改写后再走标准检索/生成，不让历史污染 prompt” |
| 滑动窗口/摘要压缩 | 只留最近几轮，早期压成摘要 | max-turns=5；早期压 40–70 token | “正则摘要，会丢信息；不是语义无损” |
| BYOK | Bring Your Own Key，用户自带模型 Key | 前端 LocalStorage + 后端客户端池 | “BYOK 不是鉴权，只是密钥透传” |

## 6. 后端与中间件（简历第二项目）

| 词 | 一句话解释 | 在你项目里指什么 | 面试怎么说 |
|---|---|---|---|
| Spring Boot 自动装配 | 按依赖/配置自动创建 Bean | `spring-ai-starter` 会自动建 ChatModel | “本项目显式关掉，改手写装配，为了没 Key 也能启动” |
| Bean | Spring 容器管理的对象 | `@Component/@Service` | “Bean 的生命周期由容器管，不是自己 new” |
| DI | 依赖注入 | 构造器注入 | “构造器注入依赖不可变，循环依赖启动就报错” |
| AOP | 方法级切面 | 项目里用得少；可用在 LLM 日志/耗时 | “AOP 适合横切关注点，不适合核心业务编排” |
| 拦截器 | Spring MVC 请求前后处理 | 探味志的 Token 校验/续期 | “拦截器能拿 HandlerMethod，过滤器更靠容器层” |
| ThreadLocal | 线程内共享变量 | 探味志的用户上下文 | “线程池复用线程，必须 finally remove，否则串用户/泄漏” |
| Hikari | 数据库连接池 | maximum-pool-size=5 | “连接池不是线程池；池子开大不一定更好” |
| ConcurrentHashMap | 线程安全的 Map | BYOK 客户端池/会话缓存 | “复合操作仍要原子方法/锁，不是用了就线程安全” |
| Redis BitMap | 用 bit 存布尔状态 | 签到：1 bit/人/天 | “365 bit≈46B；key 本身也有开销” |
| Redis ZSet | 有序集合 | 点赞排行榜 | “跳表+哈希表，ZSCORE O(1)，ZRANGE O(logN+M)” |
| Redis Lua | Redis 内原子脚本 | 秒杀查库存+扣减+记用户 | “单线程执行，查/判/扣不会被并发打断” |
| Redisson | Redis 分布式锁客户端 | 一人一单 | “看门狗续期；最终还要 DB 唯一索引兜底” |
| RocketMQ | 消息队列 | 下单后异步发券/积分/通知 | “削峰、解耦；消息 at-least-once，消费要幂等” |
| 幂等 | 重复请求结果一致 | 订单号唯一索引/去重表 | “MQ 重复消费靠业务幂等，不是靠 MQ 保证 exactly-once” |
| 缓存穿透 | 查不存在的数据，缓存永远不命中 | 空值缓存/布隆过滤器 | “穿透是‘查不存在’，不是‘热点过期’” |
| 缓存击穿 | 热点 key 过期瞬间打爆 DB | 互斥锁/逻辑过期 | “击穿是单点热点，雪崩是大面积” |
| 缓存雪崩 | 大量 key 同时过期/Redis 挂 | 随机 TTL/多级缓存/熔断 | “雪崩要加随机 TTL 和高可用” |
| 延迟双删 | 先删缓存、更新 DB、延迟再删 | 缓存一致性 | “延迟要大于一次读+回填的耗时” |

## 7. 项目里没有的词：别说，会被追问穿

| 词 | 真实情况 | 正确说法 |
|---|---|---|
