## 1. 本阶段改动范围

增加生产尝试的评测取证链路，不修改 SQL 生成提示词、纠错触发条件、最终选答规则、检索权重、评测题目、Gold SQL 或结果比较器。API 响应保持原结构；评测报告增加 `itemEvidence`。新增 Java 组件均使用已有依赖；Python 汇总只用标准库，不新增 Web 服务。

验证已完成：Java **354/354**，失败/错误/跳过均为 0，其中 SQL 对抗测试 **53/53**；独立汇总审计测试 **5/5**。正式矩阵完成后，在同一提交上复跑 [200 条 Gold 自检](../reports/ablation-20261116/gold-preflight/eval-20261116-121034-dryrun.json)，**200/200**，产生 200 条逐题证据，模型调用为 0。这是执行链路自检，不是模型准确率。

## 2. 技术与设计导读

### 一个具体请求如何流转

用户请求查询当前会员等级与最新快照不一致的会员分布。第一轮 checker 组的 T5-014 产生了基于 `JOIN LATERAL` 的查询：

1. 模型返回首答，已有 `LlmCallLog` 记录消息 SHA-256 和独立用量。
2. AST 校验通过，但 EXPLAIN 预估代价 **107355.7 > 100000**，首答以 `REJECTED/HIGH_RISK_COST` 返回，并未作为业务查询执行。
3. 生产编排器依据真实拦截信息触发自纠错；反馈不含 Gold。模型改用 `DISTINCT ON (member_id)` 获取最新快照。
4. 第二次校验与执行成功，返回 3 行；编排器选择第 2 次答案，并累计两次模型费用。
5. 生产调用返回、记录范围关闭之后，评测器才比较 Gold：首答管道未成功，最终答案正确，因此记为一次执行路径恢复。

这次触发源是执行计划护栏，不能因为发生在 checker 组就归为“结果检查器修复”。首答被拦截而未执行，也不能声称已经证明其 SQL 业务语义错误。

### 核心组件与身份追踪

- `EvaluationTrace`：以 `ThreadLocal` 在 try-with-resources 范围内保存同步调用事实；`calls[].number` 标识模型调用，`productionAttempts[].number` 标识生成失败或 SQL 尝试，`selectedAttempt` 明确记录最终采用哪次。
- `LlmCallLog`：向当前范围追加消息指纹和用量；即使关闭正文/文件日志，评测范围仍能收集指纹。提示词正文和原始回复不额外写入评测证据。
- `Text2SqlOrchestrator`：在首答、生成异常、纠错响应和选答分支上追加事实标记，不从 Gold 推导是否重试。
- `EvaluationEvidence`：范围关闭后，用已有 `ResultNormalizer.equivalent` 对各次答案评分，保存 SQL、列名、行数和结果指纹，不额外保存结果数据行。
- `run_ablation.ps1`：四组各三次独立启动，按预定顺序轮换组别；每轮启动前检查评测相关源码和提交，发现变化即停止。
- `summarize_ablation.py`：核对题目、Gold、结果、首答消息指纹、实际参数、调用预算、选答以及请求/JSONL/报告三层账目。

这里没有新增检索打分或权重。身份绑定靠顺序编号与显式选答标记，不靠 SQL 字符串是否相同来猜。当前矩阵关闭工具、缓存、升级路由和会话改写，因此实际模型调用与生产尝试应一一对应；超出这个受控范围，必须重新定义调用层级和上下文传播。

### 为什么选择这个设计

没有选择从旧 `failures[].firstSql` 倒推生产首答：它实际记录生产编排完成后的答案，无法还原内部尝试。新数据应读取 `itemEvidence.productionAttempts[0]`；旧 `correction` 仍表示评测器外层纠错，本矩阵关闭该机制。

没有选择只打开所有 prompt/response 日志再按时间戳拼接：这会多存正文，也容易把不同题目或失败调用配错。限定范围的内存记录使调用与题目天然绑定；报告写盘放在生产调用之外。

没有引入完整分布式追踪平台：当前需要测量的是单 JVM 同步请求，新增部署依赖不能替代明确的尝试身份。代价是 `ThreadLocal` 不自动跨异步线程传播，不能直接声称具备跨服务链路追踪。

### 边界与保底

- 普通 HTTP 请求不打开评测范围；范围外的标记不会留存额外结果。嵌套范围显式拒绝，正常或异常退出后均清除线程上下文，并测试线程之间不串证据。
- 传输失败且未返回用量时，调用用量为 null，表示未知，汇总不能按免费处理；账目认证会失败。
- 应用层 `ChatModel.call` 次数不是供应商实际 HTTP 次数。SDK 可能内部重试，供应商扣款需额外账单核对。
- 当前查询结果指纹证明本轮参考查询的返回结果一致，不等于完整数据库的版本快照。
- 每轮源码检查不能检测检查间隙“修改又还原”的短暂变动。本轮操作者保持评测源码不变，结束后也核对相关源码无 diff。工作区始终为 DIRTY，来源包括用户既有演示稿变动和实验报告/文档，不伪称整洁 checkout。
- 固定的是客户端模型名称和参数，不能凭配置快照证明供应商内部权重版本和调度实现固定。输入相同而输出不同是本轮观察，服务端具体原因未被证实。
- Gold 先执行可能预热数据库。本轮是串行、固定流程的服务层 `ask` 计时，不包含 HTTP 传输、序列化、JVM 启动、Gold 执行和事后评分，也不是冷库或并发压测。旧分阶段计时尚未独立列出 EXPLAIN、结果检查的全部开销，以调用边界墙钟时间补足。
- 原有结果检查仍依赖输出列名启发式，比例单位与未知别名的局限见 [列边界验收](RESULT_CHECKER_20261116.md)。本阶段没有把弱证据升级成语义证明。

## 3. 统计口径

每次 100 题，澄清保持在分母中且不计为答对。三次分数报告均值、范围及样本标准差；仍是相同 100 题重复测量，不能当作 300 道未见题。

每轮单独计算 P50/P95；三轮 P95 均值是三个分位数的算术平均，不是合并 300 次请求再取 P95。既报告已有响应计时，也报告 `ask` 调用边界实测墙钟时间；后者包含结果检查、选答等开销，不含 Gold 执行和事后评分。

跨组总分相减只作为观察。真正的重试恢复与退化只依据同一请求内首答和最终答案：错/未成功→对为恢复，对→错为退化。不同轮首答 SQL 或结果指纹不相同，可能只是别名、写法或行顺序不同，不等于业务语义改变。

首轮 baseline 与 correction 的 98 个模型输入指纹一致，baseline 为 93/100、correction 为 94/100；后者实际重试 **0 次**，所以这 1 分不是自纠错收益。此例说明单次总分不足以归因。

### 4.3 澄清的评分代价

开启澄清的九轮均只对 T4-004、T4-006 反问，共 18 次，无模型调用；这两道在三个关闭澄清轮次中 **6/6 匹配 Gold**。因此这六个已观察的强制作答机会都能得分，而反问按本轮单次 SQL 准确率口径计为未答对。

但全组均分差是 1 分，而非固定 2 分：其余 98 题也在波动。不能把全组均分差当作澄清的纯因果效应；更不能把“匹配一个 Gold 口径”视为用户已确认真实含义。本轮未测用户回答澄清之后的多轮任务完成率或独立标注的歧义检测精度，不建议仅为提高单轮分数而关闭澄清。

## 5. 用户需要掌握与面试追问

核对三件事：Gold 评分发生在生产链路之后；未采用的重试仍收费；失败先看生成、校验、执行还是结果规则，不能把 checker 组里的所有恢复都归给 checker。

**追问：温度为 0，为什么同样输入仍有不同答案？** 输入指纹能排除本地上下文漂移，但不控制供应商后端实现或保证逐位确定性。使用独立重复与实际尝试记录，避免将服务侧输出变化冒充系统收益。

**追问：如何保证评测没有把标准答案偷偷用于纠错？** 范围记录器和生产编排器不接收 Gold；生产调用返回并关闭范围后才评分。重试触发记录应是数据库/安全护栏/结果规则的可见信号，而非结果不匹配信号。

当前不需要额外配置。独立盲测、请求总时间预算以及 P95 <8 秒仍是整体改进计划中的未完成要求。
