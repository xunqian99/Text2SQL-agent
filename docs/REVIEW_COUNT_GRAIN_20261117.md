# 阶段2：评价记录与订单身份的计数粒度

## 已证实的矛盾与本轮范围

旧Prompt规则10把“订单与评价”举作不引起行膨胀的关联，这是错误的数据模型假设。当前只读数据库证据：评价99,224条，对应98,673笔订单；547笔订单有多条评价，单订单最多3条；1–2分评价14,575条，涉及14,533笔订单。order_reviews主键是(review_id,order_id)，order_id仅有普通索引，外键关联不证明子表唯一。

原T4-013问“差评（1分或2分）的订单里，各州分别有多少笔”，Gold却COUNT(*)计关联评价行。按订单单位理解应去重，且42条差额在现库真实存在。本轮不把生产改成评价重复计数来匹配旧参考：原题、Gold、评分、三轮失分全部保留，明确记录参考粒度与题面订单单位不一致。Gold执行自检200/200只说明参考能执行并与自身冻结结果一致，不能证明它符合题意。

本轮只改系统规则10，版本p14-count-grain-v14，不改客户配置、指标定义、低分率表达式、检索、评分、纠错、超时预算或数据库。明确“低分评价”措辞可能命中现有low_score_rate指标（其单位为评价比例），这是已有别名范围风险；本轮不顺手修改它，实际计数请求必须服从显式计数单位，并在真实验证中如实观察。

## 技术与设计导读

### 1. 一个请求的数据流

“至少收到一条1分或2分评价的订单有多少笔，每单一次”→原检索返回orders/order_reviews及关联键→规则10首先要求确认计数对象为订单→生成COUNT(DISTINCT orders.order_id)或以EXISTS筛选订单→AST/EXPLAIN→只读执行返回14,533。若明确问评价记录条数，源事实换为评价记录，返回14,575；同请求要求两个单位时分别计算，不能把DISTINCT套到所有列。

这只是生成前软约束，不是已经实现了SQL血缘证明器或请求意图分类器。模型仍可违反；AST安全层证明可执行和只读边界，不证明业务粒度。原题按原Gold仍可能严格失分，不能再用“跑通了”宣称问题解决。

### 2. 核心技术和身份凭据

PromptTemplate规则10按对象、源表完整主键及业务身份区分计数；外键不代表一对一。源表记录无重复时COUNT(*)；关联可能重复记录时先聚合、按完整主键去重或用EXISTS。评价的记录身份是(review_id,order_id)，订单身份是order_id；只按review_id去重也可能丢记录，字符串拼接组合键可能碰撞。

Prompt版本及systemPromptSha256/promptSha256追踪发送输入；冻结p13系统原字节快照，测试证明只有规则10正文改变，其他规则字节不变。历史p9/p10/p11快照不重写，跨版本范围测试明确允许已有差异及新规则10。客户v2政策和metrics.yml原字节不变。

本轮不读取directHits/expandedTables来推断计数粒度，不加权、打分或Top-K截断；原来源标签、0.4扩展衰减、桥接表上限不变。没有为orders或review表加分，也没有给某题硬编码SQL。

### 3. 数学、边界与验收范围

对低分评价集合L，记录数为|L|，订单数为|{order_id(r):r∈L}|。一单含两条低分评价时分别是2和1，含一条低分一条高分时订单仍只算1。关联更多明细后记录也可能重复，需要保护源评价的完整复合身份；不能用SUM(DISTINCT 金额)掩盖明细膨胀。

新增8项只读PostgreSQL反例以Java集合/计数独立构造答案：两低分同订单、同单评分混合、review_id跨订单复用、组合键拼接碰撞、NULL评分/州、无低分、无评价、孤儿评价不属于订单连接覆盖。分别核对评价行、订单集合、EXISTS、复合主键防放大及空集0。孤儿场景只用于说明覆盖边界，不声称现库外键允许孤儿。每组6次SQL比较仍只算1项参数化测试，不虚增测试数。

Java850/850、79套件，失败/错误/跳过0；Gold200/200、模型0次/费用0。原200题系统提示和完整Prompt全部改变；用户问题、Schema/列/来源/分数、指标与政策、值提示、示例及Join上下文200/200不变，同进程重复无漂移。全局规则具有影响面，不能说只影响评价题；这也不等于新的全量准确率。

### 4. 为什么这样修与面试追问

不统一用COUNT(*)，否则将多评价订单算重；不统一COUNT(DISTINCT order_id)，否则把评价记录丢掉；不修改原Gold让历史分数好看。修复的是可证伪的数据模型假设，保留原参考冲突的工程代价。

问“外键为什么不保证一对一？”——它约束子行引用有效父行，不限制多个子行引用同一父行；还须检查子侧关联键的唯一约束。问“为什么代码更正确却仍可能不通过旧评测？”——题面单位、参考粒度及结果评分是不同层；用真实反例证明差异并保留两套诊断，不偷偷把原评分改成新口径。后续评测治理需要版本化处理参考缺陷，不能在本次开发修复中抹掉旧分数。

### 5. 可验收路径与配合

先提交源码、反例和只读证据→冻结提交8条单次真实验证参考：原题原Gold、显式州评价记录、显式州去重订单、全库低分评价记录、全库低分去重订单、同请求两个计数、原评分分组、订单总数。另在调用前明确：原题仍按原Gold严格计分，可独立观察它与显式订单参考是否一致，这个诊断不代替原分数。
