# Text2SQL Agent 面试题库（2026 · 人话版）

> 这版只遵守一个原则：**不假设面试官懂 AI**。
> 每个术语第一次出现，先用一句人话解释；先讲人话，再讲技术；数字必须带条件。
> 上一版 172 题里有重复、有术语堆砌，这一版合并成 **103 题**，按“项目 → 选表 → 连表 → 生成 → 安全 → 代价 → 结果 → 评估 → 缓存 → Agent → Java → 行为面”组织。
> 当前数据：三次独立运行 **84/85/86**，280 项测试，53 条对抗，¥0.221/100 题。

## 先记住这些词

| 词 | 人话解释 |
|---|---|
| Schema | 数据库的“目录”：有哪些表、哪些字段、表和表怎么关联 |
| 检索 | 先翻目录，挑出跟问题最相关的几张表，而不是把 37 张表全塞给模型 |
| prompt | 给模型的“说明书 + 资料”，包括表结构、业务口径、示例和问题 |
| token | 模型按字计费的单位；输入叫 prompt token，输出叫 completion token |
| AST | 把 SQL 拆成“语法树”，像检查句子主谓宾，而不是用关键字瞎猜 |
| EXPLAIN | 让数据库先“彩排”一遍，告诉你会怎么查、代价多大，但不真正执行 |
| Agent | 会自己决定下一步、会调工具的模型；Workflow 是步骤写死的流水线 |
| MCP | 工具接入的“通用插座”，让不同应用用同一种方式接工具 |
| 第 1–6 类题 | 把 200 道题按难度分六层：单表基础、单表聚合、时间窗口、2–3 表、4 表以上、业务口径；文中“第 5 类”指 4 表以上 |
| P95 / P50 | 把请求按耗时排队：P95 是最慢的 5% 的起点，P50 是一半请求比它快 |
| RLS | 行级权限：同一张表，不同用户只能看到自己有权的行 |
| CTE | SQL 里的 `WITH` 子句，先把一段查询起个名字，后面复用 |
| few-shot | 给模型看几个“问题 + 答案”的示例，让它照格式写 |

## Part 0 · 项目介绍与边界

### Q0.1 30 秒介绍这个项目 ★

**答**：我做了一个把中文业务问题翻译成 SQL 的工具。比如运营问“2018 年销售额最高的 5 个州是哪些”，它会自己找表、连表、写一条只读 SQL，执行后把结果表返回。

它不是聊天机器人，重点在**可评估**：我自建了 200 道题，分六种难度，三次独立运行分别答对 84、85、86 道；每次错在哪一层，我能拆开讲。

技术上是 Java 21 + Spring Boot + PostgreSQL，接 DeepSeek 这类大模型；但我做的主要不是“调模型”，而是把模型包进一条能选表、能校验、能拦风险、能归因的工程链路。

**追问**：为什么强调“只读”？
**追问答**：因为模型输出不能直接信。它可能写 `DROP TABLE`，也可能写一条合法但会拖垮数据库的查询。只读是产品边界，不是功能限制。

### Q0.2 2 分钟介绍：一个问题从进来到出结果，经过哪几步 ★★

**答**：我用一个例子讲：用户问“2018 年销售额最高的 5 个州”。

1. **看懂问题**：先把“那 2017 年呢”这种追问补成完整句子；如果问题有歧义，可以先反问。
2. **找表**：数据库有 37 张表，不可能全给模型。系统先用业务词典把“州”“销售额”“订单”映射到表，选出最相关的 8 张，再把连不上的表用中间表补通。
3. **连表**：告诉模型“订单怎么连客户、客户怎么连地区”，给它一棵推荐的连接树，避免它自己乱连。
4. **写 SQL**：把选中的表结构、业务口径（比如销售额到底含不含运费）、字段枚举值（比如“圣保罗”在库里是 `SP`）一起放进给模型的说明书，让它生成一条 SQL。
5. **检查**：用 SQL 解析器检查是不是单条 SELECT、表/字段是否存在、有没有危险函数、有没有 LIMIT；再让数据库 `EXPLAIN` 彩排，拦掉笛卡尔积和超高代价。
6. **执行**：用只读账号跑，10 秒超时，最多返回 200 行。
7. **验结果**：结果为空、比率超过 100%、金额为负等异常会触发一次重试；最后返回表格、SQL、耗时和 token。

这条链路里，检索、生成、校验、执行、评估是分开的，所以错了我能说清是“表选错”“字段选错”“连表错”还是“口径错”。

**追问**：哪一步最贵？
**追问答**：调模型最贵，一次 1–3 秒、上千 token；检索和校验是毫秒级。所以优化优先级是先减少模型调用，而不是把检索写得更快。

### Q0.3 这个项目最难的地方是什么 ★★

**答**：不是让模型写出一条能跑的 SQL，而是三件事：

1. **选对表**：37 张表、英文表名、中文问题，模型很容易选错；选错后面全错。
2. **落对口径**：“销售额”可能含运费、可能排除取消订单、可能按订单数或人数算；不同口径结果差很多。
3. **输出对形状**：标准答案要 3 列，模型给 2 列；标准答案要 id，模型给 name；标准答案要 4 位小数，模型给 2 位。SQL 能跑，但结果不算对。

我 84 那轮 16 条失败里，检索类 0 条，7 条是输出列/形状；这说明“选表”已经不是最大瓶颈，“结果约定”才是。

**追问**：那为什么不继续优化检索？
**追问答**：因为继续调 Top-K、关系跳数，实测一条都没救回来；瓶颈已经换了。优化要跟着失败结构走，不是跟着感觉走。

### Q0.4 为什么做这个项目 ★

**答**：起点是一个很具体的痛点：电商数仓有 37 张表，业务同学问一个“上个月各州销售额”要等数据开发排期；直接丢给大模型，它会在几十张表里选错、漏连表、把“销售额”算成“订单数”，更麻烦的是**错了看不出来**——SQL 能跑，结果像模像样。

我想做的不是“让模型写 SQL”，而是把模型放进一条**可评估、可拦截、可归因**的链路：选错表能看出来，写错口径能归因，危险 SQL 能被拦。

**追问**：为什么不做成通用 BI？
**追问答**：范围守不住就会烂尾。我明确不做写操作、多数据库方言、模型微调、多租户；先把一个垂直域做到能评估，比铺十个功能更有价值。

### Q0.5 这个项目的边界：什么不做 ★

**答**：四类不做：

- **不做写操作**：只生成只读 SELECT，不碰插入/更新/删除，也不做建表/改表这类结构操作；
- **不做多数据库方言**：只支持 PostgreSQL；
- **不做模型微调**：只做给模型的说明书、检索和工程约束；
- **不做多租户/行级权限**：当前是单租户、单只读账号，没有“同一张表不同用户只能看自己行”的行级权限。

还有三个没达到的指标：4 张表以上的深层题只有 40–60%；最慢的 5% 请求要等 12–17 秒，目标 8 秒没达到；成本只算模型调用，不含数据库和机器。

这些不是“没做完”，是明确的范围取舍。面试时主动说边界，比假装生产级更可信。

**追问**：没有权限控制，能上线吗？
**追问答**：不能直接给外部客户。上线前先补鉴权、租户隔离、行级权限和限流；当前的安全链路只保证“不能写”和“不能执行危险 SQL”，不保证“只能看自己该看的数据”。

### Q0.6 面试官说“84–86% 不高”，怎么答 ★★★

**答**：先定性质，再给证据，最后给上线路径。不要一上来就说“虽然不高但是……”。

> “84–86% 我不会包装成生产级，它是**内部基线**，不是上线验收。条件是 37 张表、200 道六层题、单模型单轮、含 28 张合成扩展表；三次独立运行 84/85/86，失败 16/15/14，其中 12 条三次都失败。
>
> 这个数字的价值不在绝对值，在**误差结构**：检索类 0 条；84 那轮 16 条里 7 条是输出列/形状，3 条聚合/去重，2 条时间口径。单表基础题 100%，4 张表以上的深层题 40–60%。
>
> 说明系统已经过了‘选表’这一关，瓶颈在‘模型和标准答案的结果约定’。如果明天上线，我不会做开放域 90% 的承诺，而是先限定主题域、把输出列/精度/聚合口径写进指标注册表，再用未见过的题验收。”

**追问**：84% 就是低，你怎么证明不是模型不行？
**追问答**：同一个模型下，系统从 62% 到 84%，检索类失败 0 条；如果是模型不行，单表基础题不会 100%、SQL 有效也不会 100%。但 4 张表以上的深层题只有 40–60%，这部分确实是深层结构没解决，我不甩锅给模型。

**追问**：那你三个月做什么？
**追问答**：先做输出契约，直接打 7 条形状失败，预期 +4~5 个百分点；再补 4 表以上题目的桥接表；然后建未见题集、审标准答案；最后才是性能。顺序是“先修正确性瓶颈，再修评估可信度，最后做新功能”。

**低分回答**：“84% 已经不错了”“模型再强一点就行”“我们用了大模型所以很智能”。——没有边界、没有误差结构、没有上线路径。

## Part 1 · 数据流与开关

### Q1.1 完整链路用一句话怎么说 ★

**答**：**问题进来 → 改写/澄清 → 查缓存 → 选表 → 补口径/枚举/示例 → 模型写 SQL → AST 检查 → EXPLAIN 彩排 → 只读执行 → 结果检查 → 必要时重试 → 返回表格和耗时。**

这条链路里，每一步都可以单独关掉；默认配置几乎全关，是为了让“最朴素的基线”随时可复现。84–86 是在本地配置打开检索、口径、几个示例、结果检查、自纠错、执行计划彩排之后跑出来的。

**追问**：哪些默认是关的？
**追问答**：检索、列剪枝、join 提示、业务口径、few-shot、结果检查、自纠错、缓存、Agent 工具、多轮、澄清、模型路由、EXPLAIN 护栏、持久化，默认都是 false。默认开的只有数据画像、外键、列白名单、连通性修复、LIMIT 补齐、调用日志。

### Q1.2 用“2018 年销售额最高的 5 个州”走一遍 ★★

**答**：这句话会命中三张核心表：订单 `orders`、订单明细 `order_items`、客户 `customers`；“州”对应 `customers.customer_state`；“销售额”对应 `order_items.price` 的求和。

系统会先选表，再补“州”的枚举值（库里存的是 `SP`、`RJ` 这种两位代码，不是“圣保罗”），然后让模型生成类似：

```sql
SELECT c.customer_state, ROUND(SUM(oi.price)::numeric, 2) AS sales
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.order_purchase_timestamp >= '2018-01-01'
  AND o.order_purchase_timestamp < '2019-01-01'
GROUP BY c.customer_state
ORDER BY sales DESC
LIMIT 5;
```

然后过 AST 检查、EXPLAIN 彩排、只读执行，最后返回 5 行。

**追问**：销售额要不要排除取消订单？
**追问答**：这是业务口径，不是 SQL 语法。如果指标注册表里定义了“销售额 = 排除取消/不可用订单”，就照抄；没定义就要反问或注明。不同标准答案对这件事的定义可能不同。

### Q1.3 为什么先做选表，而不是把 37 张表全给模型 ★★

**答**：因为全给会“又贵又吵”。

- 37 张表的建表语句大约 7400 个字符，检索后只给 8 张，约 1200–1300 字符，输入 token 降了约 82%；
- 更重要的不是省钱，是**减少噪声**：表越多，模型越容易选错、连错；
- 检索后表全召回 98%、平均召回 99.55%，说明“该用的表基本都在”。

**追问**：检索会不会漏表？
**追问答**：会，全召回 98% 意味着还有 2% 的题漏表；所以有“连通性修复”兜底：选出来的表如果连不成一张图，就补最短的中间表。

### Q1.4 你说的“两段式生成”，真的调了两次模型吗 ★★

**答**：没有。准确说是“**检索选表 + 一次模型生成**”，不是一个请求调两次模型。原来规划过“先让便宜模型选表、再让强模型写 SQL”，但检索层表全召回已经 98%，16 条失败里检索类 0 条；再加一次模型调用，收益没有证据，成本和延迟却确定增加。

所以我在文档里把“两段式”写成“检索一段、生成一段”，面试时会主动说清，避免被误解成两次模型调用。

**追问**：那为什么不让模型自己选表？
**追问答**：37 张表全给，模型会选错；检索是确定性的，能复现、能评估、能解释。选表用算法，写 SQL 用模型，各干各擅长的。

### Q1.5 默认配置为什么几乎全关 ★★

**答**：为了让**基线可复现**。如果默认就开检索、开缓存、开自纠错，那“baseline 47%”就跑不出来了；改一个默认值，历史数字全不可比。

所以优化必须显式打开；评估报告里要记录模型、prompt 版本、检索开关、Top-K、是否 few-shot、是否自纠错、LIMIT 模式、最大行数。数字离开配置就没有意义。

**追问**：84–86 是“全开”吗？
**追问答**：不是。84–86 打开了检索、列剪枝、Join 提示、口径注入、few-shot、结果检查、自纠错、EXPLAIN；但缓存、Agent 工具、模型路由、澄清、持久化没有开。说“全开”会被读配置的面试官纠正。

### Q1.6 84–86 的复现条件是什么 ★★

**答**：同一份代码、同一个数据快照、同一个模型 `deepseek-flash`、`temperature=0`、prompt 版本 `p8-semantic-pruning-v8`、本地配置打开主要优化、评估集取 `eval` 的 100 条。

三次报告分别是 `eval-20261108-210214`（85）、`212550`（86）、`221405`（84）。报告里记了模型、prompt 版本、检索开关、Top-K、自纠错等，但还没有记代码 commit 和数据 hash，这是复现性的缺口。

**追问**：为什么三次不一样？
**追问答**：模型服务有波动，100 条里单题噪声就有 ±1–2 题；三次 84/85/86，12 条稳定失败、6 条单次波动。写范围比写最高值诚实。

### Q1.7 链路上哪一步最贵、哪一步最容易错 ★★

**答**：**最贵的是调模型**：一次 1–3 秒、上千 token；检索、校验、执行是毫秒到几十毫秒。**最容易错的是语义，不是语法**：SQL 有效执行率 100%，但执行准确率 84–86%，错在输出列、聚合口径、时间窗口。

所以优化优先级不是“再把检索写快”，而是“减少模型调用 + 把结果约定写清楚”。

**追问**：最慢的 5% 请求（P95）为什么 12–17 秒？
**追问答**：尾部被重试和多表 Agent 侦察拉长；平均 3–4 秒，一半请求在 1.9 秒内（P50），但最慢的 5% 要等十几秒。这个指标没达到 8 秒目标，我不回避。

### Q1.8 为什么整条链路是同步串行？怎么扩展 ★★

**答**：同步串行是刻意选择：链路短、状态清晰、计费准确、调试简单；并行会引入“谁先返回、失败怎么合并、token 怎么记账”的复杂度，而当前瓶颈是模型延迟，不是这几毫秒的检索。

扩展时先做无状态化：会话/缓存从进程内迁到 Redis 或 PostgreSQL，API 才能水平扩；再加限流/队列保护模型和数据库；读库加只读副本；评估与线上隔离。当前是单实例、连接池 5、会话在内存，直接加机器会话会漂移。

## Part 2 · 选表：37 张表里先选对 8 张

### Q2.1 37 张表，你是怎么选表的 ★★

**答**：不靠模型自己看 37 张表，而是先用**业务词典**做“最大匹配”：

1. 把表名、字段名、中文别名、枚举值做成词条；
2. 从问题里找最长的词，命中“订单明细”就不再命中“订单”，避免短词误伤；
3. 命中的表按类型加分：枚举值 3 分、表别名 2.5 分、字段别名 2 分、英文标识符 1.5 分；单字词打五折；
4. 从得分最高的 3 张表出发，沿关系图带 1 跳邻居，分数乘 0.4 衰减；
5. 取前 8 张；如果这 8 张连不成一张图，补最多 2 张中间表；
6. 最后做列剪枝，只保留主键/外键、问题提到的列、指标列、度量数值列。

**追问**：一个词都没命中怎么办？
**追问答**：回退全量 schema，宁可多给 token，也不因词典漏词把必要表筛掉；回退率本身是要监控的指标。

### Q2.2 为什么不用 PostgreSQL 的全文索引 / 中文分词 ★★

**答**：因为 PostgreSQL 内置的分词器不切中文。实测 `to_tsvector('english','统计每个州的订单数量')` 把整串当一个 token；换 `simple` 也一样；`show_trgm('订单数量')` 返回空数组。中文问题没有空格，全文索引这条路对中文是死的。

通用分词器（jieba/HanLP）能切词，但切出来的“复购率”仍然不知道对应哪张表——真正的难点不是切词，是“中文词 → 哪张表”的领域映射。所以我把切词和映射合成一步：业务词典最大匹配。

**追问**：词典漏词怎么办？
**追问答**：三层兜底：英文标识符直接命中、关系扩展带邻居、一个词都没命中回退全量。词典是人工维护的，漏词是常态，所以要有兜底和监控。

### Q2.3 为什么不用向量检索 / pgvector ★★

**答**：三个原因：依赖为零（不用 embedding 服务、不用向量库、不联网）、37 张表规模用不上、可解释（词典命中能直接说“因为‘复购率’这个词命中 customers”）。

向量能解决同义词/近义表达，但会引入 embedding 成本、索引维护和“相似但不该命中”的误召回；收益要用评估集证明，我没做。简历里写 `pgvector` 是容易撞车的：镜像带扩展，但代码没有 embedding、没有向量索引。

**追问**：那“销售额”和“GMV”这种近义词怎么处理？
**追问答**：词典里显式配别名，`GMV`、`销售额`、`成交额` 都指向同一个指标。这比向量可控：业务确认过的同义词才加，不会因为语义相近误命中。

### Q2.4 词典里有什么？怎么维护 ★★

**答**：四块：表别名、字段别名、枚举值（库里存的值 + 中文含义）、表之间的约定关联。维护原则是“写用户会怎么问，不写字段的正式中文名”；同义词越多召回越好，但不要写“数据/信息”这种太泛的词。

新表至少要补：表别名、关键字段别名、枚举值、关系边；如果有业务指标，再补指标定义。关系两端必须在 schema 里存在，有测试会校验。

**追问**：词典写错了会怎样？
**追问答**：会把问题带到错的表/错的枚举值，SQL 能跑但结果错；所以词典要 review、要测试，枚举值必须和库里的物理值对齐。

### Q2.5 最大匹配和简单 contains 有什么区别 ★★

**答**：简单 `contains` 会对每个别名独立判断，必然误命中：问“订单明细里有多少商品”时，“订单明细”命中 `order_items`，“订单”又命中 `orders`，而 `orders` 是被“订单明细”包含的噪声。

最大匹配从左到右取最长词，命中“订单明细”后直接跳过这四个字，不会再命中“订单”。单字词（“州”“券”“仓”）不是禁用，而是权重打五折：禁用会丢掉“各州的订单量”这种真实问法，打折让长词在排序上赢。

**追问**：最大匹配会漏重叠词吗？
**追问答**：会。一个句子同时需要“订单”和“订单明细”时，最长匹配只取长的；但这两个词通常指同一组表，关系扩展会把 `orders` 带进来。真需要时可以在词典里配组合词条。

### Q2.6 检索权重和关系扩展为什么这么设 ★★

**答**：权重按“命中携带多少确定信息”排：枚举值 3 分（同时确定表和值）、表别名 2.5 分（明确指向一张表）、字段别名 2 分（字段可能跨表重名）、英文标识符 1.5 分（可能是巧合）。单字词再打五折。

关系扩展的分数 = 源表分数 × 0.4 衰减 × 边强度；同一张表有多条路径时取最大值，不累加。累加会让“邻居多”的表靠数量堆分数，而我们要的是“最强的那条路径有多可信”。

**追问**：这些数字是拍脑袋吗？
**追问答**：是人工先验，不是学习出来的；调参只看开发集，不能拿评估集调，否则就是过拟合。

### Q2.7 连通性修复是什么？为什么需要 ★★★

**答**：检索是按“词像哪张表”选的，它不保证选出来的表能连起来。典型例子：问“每个大区的商品销售额”，用户不会说“客户”，但 `customers` 是 `regions` 和 `orders` 之间唯一的通路；漏了它，SQL 根本连不出来。

连通性修复就是在关系图上找一条最短桥，把断开的表接上，最多补 2 张。它和“把 Top-K 调大”的区别是：后者无差别加表，会让精确率一起掉；前者只补能消除不连通的那几张。

**追问**：补桥接表会不会引入噪声？
**追问答**：会，所以有预算上限 2，而且只补断开的场景；已经连通的问题一张都不补。代价是最终表数可能变成 Top-K + 2，报告里如实记。

### Q2.8 候选表数量（Top-K）为什么是 8 ★★

**答**：8 是开发集上的取舍：Top-5 全召回 89%，Top-8 到 96%，代价是多约 100 个 token；评估集多表题的标准 SQL 最多用到 6 张表，8 留了余量。

但要承认一个不利证据：早期 eval Top-5 是 54%，高于最终 Top-8 的 52%。所以不能说“8 已被证明最优”；单轮差异可能来自模型波动。K 也不是硬上限：连通性修复还能加 2 张，无词典命中会回退全量。

**追问**：那到底该选 5 还是 8？
**追问答**：只看单轮，5 的准确率更高；但 5 的全召回只有 89%，多表题更容易漏表。我偏向召回，因为漏表会让 SQL 跑不通，错误更硬。要真正定 K，需要多轮重复实验 + 分层看多表题。

### Q2.9 列剪枝做了什么？为什么只做一半 ★★

**答**：列剪枝是在表选完之后，裁掉不相关列，降低建表语句长度和噪声。保留：主键、外键、问题提到的列、指标依赖列、度量数值列；最少保留 4 列，避免把表裁得没法用。

所谓“只做一半”，是指不裁裸列名的语义判断：裸列名可能来自 SELECT 别名、CTE、派生表，裁错是静默错误。带表前缀的列（`o.customer_id`）能精确归属，才做白名单。

**追问**：列剪枝踩过什么坑？
**追问答**：主键靠列名猜，`support_tickets.ticket_id` 被裁掉，表 join 不出去；外键只在对端是核心表时保留，桥接表的外键被裁；度量列被误裁，问“佣金合计”时模型只能猜列名。后来改成读真实主键/外键，并在问题含度量词时保留数值列。

### Q2.10 表召回 98%，为什么准确率只有 84% ★★

**答**：因为召回不是瓶颈。84 那轮 16 条失败里，检索类 0 条；7 条是输出列/形状，3 条聚合/去重，2 条时间口径，1 条精度，2 条 join 类型，1 条标准答案多余 join。

表全召回 98%、平均 99.55%，说明表基本都在上下文里；错在“选对表之后，结果形状和口径没对齐”。所以优化方向不是继续提高召回，而是把输出列、聚合粒度、精度、口径做成显式契约。

**追问**：那 2% 的漏召回不影响吗？
**追问答**：影响，但不是当前最大瓶颈。漏召回会让 SQL 跑不通或 join 错，属于硬错误；16 条失败里没有一条是漏表导致的。先把 16 条形状/口径错修掉，收益更大。

## Part 3 · 连表：把“边列表”变成“能照着写的树”

### Q3.1 多表 Join 到底难在哪 ★★

**答**：四件事：

1. **路径多**：6 张表有七八条边，多条路径都能连通，模型不知道哪条是推荐的；
2. **连接键歧义**：`region_code` 和 `region_name` 都在表里，写错也能跑，但结果错；
3. **行数放大**：一对多 join 后行数变多，`SUM`/`COUNT` 会被放大；
4. **错误静默**：SQL 能跑、结果错，没有报错。

所以 Join 规划的目标不是“找一条最短路”，而是“给模型一棵可读、可解释、不过度 Join 的树”。

**追问**：让模型自己看建表语句不行吗？
**追问答**：阶段 1 就是全量建表语句，深层多表只有 10% 左右；只给边列表，模型不知道“先连谁、后连谁”。Join 规划是把推荐顺序显式告诉它。

### Q3.2 外键和“约定关联”有什么区别 ★★

**答**：外键是数据库强制约束的硬事实，比如 `orders.customer_id → customers.customer_id`；约定关联是数据库没声明外键，但业务上确实存在的关联，比如 `refunds.order_id → orders.order_id`，由人工核对后写进词典。

项目里真实外键只有 13 条，大量业务关联没有外键；只依赖外键，Join 路径会断。所以关系图 = 外键（强度 1.0）+ 约定关联（强度 0.5），渲染时用 `[FK]` 标出哪条更可靠。

**追问**：约定关联写错了怎么办？
**追问答**：有测试校验两端表/字段存在，但“数据上是否真的成立”要人工核对；写错会导致推荐路径错，属于高风险人工资产。

### Q3.3 生成树、最短路、Prim 分别是什么（用人话） ★★

**答**：把表想成城市，关联想成公路：

- **生成树**：用最少的路把所有城市连起来，不形成环；
- **最短路**：从起点城市到某个目标城市，走代价最小的那条路；
- **Prim**：从起点出发，每轮挑一条“一端已连、一端未连”的边，慢慢长成一棵树；
- **Steiner 树**：允许新建中转城市来让总路最短，理论最优但计算很难，项目不用。

项目生产入口是“以最相关的表为根，对每张目标表求加权最短路，取并集，再按强度/相关度/表名做 Prim 式生长”。不是“全对最短路”，也不是“把所有表都连上的最小生成树”。

**追问**：为什么不直接输出边列表？
**追问答**：边列表只回答“哪两列能连”，不回答“先连谁、后连谁”；多条路径都能连通时，模型会选错。树给的是推荐顺序。

### Q3.4 生产入口的连接规划完整讲一遍 ★★★

**答**：四步：

1. **定目标**：从检索证据、值匹配、指标依赖里提取“核心目标表”；少于 2 张直接返回空，避免单表题过度 Join。
2. **定根**：在检索排名里找最靠前的目标表；根选事实表（订单/订单明细），SQL 写法最自然。
3. **求路径并集**：对每张目标表跑加权最短路；外键边代价 1.0、约定关联代价 2.0；把根到各目标的路径边放进集合。
4. **生长排序**：从根出发，每轮从边界挑一条边，优先级是“边强度 → 新连表的相关度 → 表名”；输出一棵从根向外的树，渲染成 `表.列 = 表.列` 的等式。

**追问**：为什么第二优先级是相关度，不是表名？
**追问答**：有一道 4 表题，`coupon_usages`、`members`、`regions` 三条候选边的强度都是 0.5；如果只按表名排，`coupon_usages` 会排在 `members` 前面，主干变成“经优惠券到会员”——正是错的那条。加上“这张表跟问题有多相关”做第二排序后，`members` 排名更高，主干回到标准答案的路径。

### Q3.5 为什么不用全对最短路 / Steiner / 最小生成树 ★★★

**答**：三个方案都被否过：

- **全对最短路**：6 张表要输出 15 条路径，比边列表更难读，模型要在 15 条里自己挑；
- **Steiner 树**：理论最优但 NP-hard，为了省几条边不值得，而且“最优”按边数，不是按业务语义；
- **最小生成树**：会把 Top-K 里所有表都连上，包括噪声表；模型看到边就会 Join，实测出现过度 Join。

我要的是“连通核心目标表的最小主干”，不是“连通所有表”。当前方案是工程折中：覆盖核心、剔除噪声、输出可读。

**追问**：那会不会漏掉最优连接？
**追问答**：可能。最短路只保证“核心目标连通”，不保证“业务语义最优”；所以 Join 规划是提示，不是保证，最终还要靠评估和人工归因。

### Q3.6 根为什么选“最相关的表” ★★

**答**：因为树是给模型照着写 SQL 用的，从事实表出发符合 SQL 的自然写法；从维表出发会得到一棵语义别扭的树。

比如从 `regions` 出发，树可能是“地区 → 客户 → 订单 → 明细”，读起来像“从地区找订单”；从 `orders` 出发是“订单 → 客户 → 地区”，更自然。根必须来自核心目标表，不能是扩展表，否则整棵树被带偏。

### Q3.7 规划只覆盖一个连通分量，剩下的表怎么办 ★★

**答**：`Plan` 只覆盖根所在的那一个连通分量，规划表数可能小于选中表数。这时渲染会明确写一行：“还有 N 张表与起点不在同一连通分量，本段未给出连接顺序；它们的关联见上面的 JOINS。”

这不是装饰，是给模型的警示信号，防止它把“推荐连接计划”当成“全部连接”而漏表。这类遗漏会以“SQL 能跑、结果错”的形式出现，是最难查的一类。

**追问**：为什么不生成森林？
**追问答**：多棵树会让模型不知道先写哪个 FROM，反而更容易漏表；多分量通常意味着检索漏了桥接表，正确做法是先修复连通性。

### Q3.8 第一版 Join 规划零收益，为什么还保留 ★★★

**答**：要分两个版本说。第一版是对所有召回表做生成树：52% → 52%，token 反涨 29%，修好 5 条、新坏 5 条，其中 2 条是过度 Join；所以默认关闭。

现在的 `planForTargets` 是后来改的：只连核心目标表，剔除无关边，避免过度 Join；它在本地全开配置里启用，但我没有单独做它的消融，不能把 84–86 的增量归给它。

保留代码的理由：1）它修的是真实错误类型，换一个 Join 更密集的数据集可能划算；2）“做了、测了、无效、关掉”本身是可信度证据。

## Part 4 · 让模型写对 SQL

### Q4.1 你说的 prompt 是什么？里面放了什么 ★

**答**：prompt 就是给模型的“说明书 + 资料”。我们分两段：

- **系统提示词**：告诉模型“你是 PostgreSQL 数据分析助手，只输出一条 SELECT，必须带 LIMIT，按四步思考：识别表、规划连接、对齐过滤、确定聚合”；
- **用户提示词**：按顺序放表结构、数据画像、业务指标、字段枚举值、示例、最后才是用户问题。

不是把所有东西一股脑塞进去，而是“先给背景，再给规则，最后给问题”。问题放最后，是因为长上下文里模型对末尾更敏感，能减少答非所问。

**追问**：prompt 越长越好吗？
**追问答**：不是。规则越多越容易互相冲突；我们有两处规则和标准答案冲突：统一两位小数、配送时长用 shipments。规则要少而硬，能做成配置的不要写成自然语言。

### Q4.2 为什么把用户问题放在最后 ★

**答**：因为模型对上下文末尾的注意力更强。前面放表结构、口径、枚举、示例，最后放问题，模型更容易把“当前要回答什么”和前面的资料对上。

这不是玄学，是长上下文里常用的“recency”经验；我没有做严格的顺序消融，所以只能说“当前 84–86 是在这个顺序下跑的”，不能说“换顺序一定掉点”。

### Q4.3 prompt 已经写了“只读”，为什么还要 AST 检查 ★★

**答**：因为 prompt 是**软约束**，模型 99% 遵守，剩下 1% 可能给你 `DROP TABLE`；生产库里 1% 就是灾难。AST 是**硬约束**：解析成语法树后，必须是一条 SELECT，表/字段在白名单里，函数不在黑名单里，必须有 LIMIT。

正确心智模型是：**模型输出等于不可信的用户输入**。我们不会把用户输入直接拼进 SQL，也不该把模型输出直接执行。

**追问**：那 prompt 还有用吗？
**追问答**：有用，它降低出错概率、减少重试；但安全不能靠它。prompt 让模型“想对”，AST 让模型“错得无害”。

### Q4.4 你说的“业务口径”是什么？举个例子 ★★

**答**：口径就是“这个指标到底怎么算”。同一个词，不同团队可能定义不同。

比如“销售额”：

- 含不含运费？
- 要不要排除取消/不可用订单？
- 按订单金额算，还是按订单明细的商品金额算？
- 退款要不要扣？

项目里把业务方确认过的口径写进 `metrics.yml`，比如 GMV、复购率、客单价、动销率；模型生成时“照抄表达式”，不要自己发挥。这样同一个问题不同人问，结果一致。

**追问**：口径写错了怎么办？
**追问答**：结果会系统性错，而且 SQL 能跑、看不出来。所以口径要业务方确认、要版本化、要测试；不能靠模型猜。

### Q4.5 “枚举值对齐”是什么？为什么需要 ★★

**答**：库里很多字段存的是代码，不是中文。比如 `customer_state` 存 `SP`，不是“圣保罗”；`order_status` 存 `delivered`，不是“已送达”。

用户说中文，模型可能写 `WHERE customer_state = '圣保罗'`，SQL 能跑，但一行都查不到。所以系统会先从问题里识别实体，再映射到库里的物理字段和值，把“圣保罗 → `customer_state = 'SP'`”作为提示放进 prompt。

**追问**：模型自己想不到吗？
**追问答**：有时能，有时不能；尤其小写/大小写、缩写、中文译名不一致时。枚举对齐是确定性的，能减少这类静默错误。

### Q4.6 16 条失败里 7 条是“输出形状”，具体指什么 ★★

**答**：指 SQL 能跑、结果也对，但**返回的列和标准答案对不上**。常见四种：

1. **id 还是 name**：标准答案要 `level_id`，模型给 `level_name`；
2. **多一列/少一列**：标准答案 3 列，模型 2 列；
3. **行/列转置**：标准答案按“收货州 + 登记州”成对出行，模型做成 same/diff 两列；
4. **增长量还是增长率**：标准答案要“增长了多少”，模型给百分比。

这类错误最麻烦：SQL 有效、结果看起来合理，但评估判错。修法不是再加一句 prompt，而是把“返回哪些列、什么精度、什么聚合”做成显式契约。

### Q4.7 COUNT(*) 和 COUNT(DISTINCT) 怎么选？时间窗口怎么写 ★★

**答**：先确定“数的是什么”：

- 数订单/记录行数：`COUNT(*)`；
- 数“去重后的实体”（比如一个订单有多条评价，数订单）：`COUNT(DISTINCT order_id)`；
- 一对多 join 后直接 `COUNT(*)` 会把行数放大，结果偏大。

时间窗口统一用“左闭右开”：`>= 起点 AND < 终点`。不要用 `BETWEEN`，它会把终点那一天也算进去；按周期分组用 `DATE_TRUNC`，不要用 `to_char` 把时间转成字符串。

**追问**：那 COUNT(DISTINCT) 一定更安全吗？
**追问答**：不一定。它更贵，而且问题问“多少条评价”时，去重反而错。关键是先确定计数对象，再选函数。

### Q4.8 示例提示（few-shot）和 temperature 分别有什么用 ★

**答**：few-shot 是给模型几个“问题 + SQL”的示例，让它照格式写；示例只从开发集取，不能碰评估集，否则等于漏题。项目里最多放 2–3 条，按表重叠和相似度选。

temperature 是采样随机性；我们设 0，让同样输入尽量同样输出。但温度 0 不等于完全确定：模型服务端的批处理、并行、模型版本更新仍会带来波动，所以三次 84/85/86 是正常范围。

## Part 5 · 安全：把模型输出当不可信输入

### Q5.1 为什么用 AST 解析，而不是正则匹配关键字 ★★

**答**：正则有三个洞：注释里出现 `DROP` 会误杀；关键字中间插注释、大小写混写、Unicode 同形字能绕过；拿不到结构信息，判断不了有没有 LIMIT、用了哪张表。

AST 是把 SQL 解析成语法树，“是不是 SELECT”变成一次类型判断，没有歧义；还能拿到表名、函数名、LIMIT。代价是解析器可能不认识某些方言，所以**解析失败必须拒绝**，不能放行。

**追问**：JSqlParser 解析不了怎么办？
**追问答**：解析失败一律拒绝，这是安全组件唯一正确的默认值。宁可误杀，不可放行。

### Q5.2 多语句注入怎么防 ★★

**答**：先检查是不是多条语句，再解析。因为 `SELECT 1; DROP TABLE orders` 会被解析成两条合法语句，如果只校验第一条，第二条就漏了。

实现上先剥掉末尾分号，再用 `parseStatements` 数语句数；大于 1 就拒绝。不能简单数字符串里的分号，因为 `WHERE name = 'a;b'` 里的分号不是语句分隔符。

### Q5.3 表白名单怎么做的？能挡住什么 ★★

**答**：从本次请求的 schema 上下文里取表名，用 AST 取出 SQL 里所有表，逐个比对；不在白名单就拒绝。

它挡两类问题：攻击者引用系统表/其他库表；模型臆造不存在的表。后者能在执行前暴露，省一次数据库往返，也让错误归因更准确。

**追问**：检索漏表导致合法 SQL 被拒怎么办？
**追问答**：先看 `retrievedTables` 和表召回：如果是漏召回，修检索/桥接；如果是模型引用了上下文外的表，拒是对的。不能为了让这题过而放宽白名单。

### Q5.4 列白名单为什么只做“带表前缀的列” ★★

**答**：裸列名的合法来源太多：SELECT 别名、CTE 输出列、派生表列、集合操作两侧同名列；做全了必然误杀正常查询。

带前缀的列（`o.customer_id`）能精确归属到某张表，判定是确定的，所以先做这一半。它挡住的是 `sellers.region_name` 这种“列存在但不在那张表”的真实错误。

**追问**：CTE 里同名别名怎么办？
**追问答**：项目里踩过：外层 `brands bp`、CTE 内 `brand_products bp`，同一个 `bp` 指两张表。修法不是实现完整词法作用域，而是承认边界：只要别名绑定过 CTE/派生表，该别名的列一律不判定；宁可少拦，不可误杀。

### Q5.5 函数黑名单怎么防绕过？为什么 53 条对抗里有 `WITH` 子句和表函数 ★★★

**答**：黑名单里是“只读但能造成副作用”的函数：`pg_read_file`、`pg_sleep`、`pg_terminate_backend`、`dblink`、`set_config`、`nextval` 等。光有名单不够，因为解析出来的函数名可能带 schema 前缀或引号（`pg_catalog.pg_sleep`、`"pg_sleep"`），直接比对永远不相等。

所以先归一化：小写、取最后一个点之后、去首尾引号，再比对；而且必须递归遍历整棵语法树，子查询、CTE 里的函数也要查。

新增的 CTE 数据修改（`WITH x AS (DELETE ... RETURNING *) SELECT * FROM x`）最外层是 SELECT，只判 `instanceof Select` 会放行；`FROM` 表函数也可能藏副作用。所以补了 6 条对抗用例：3 条 DML CTE、3 条 FROM 表函数。

**追问**：为什么用 `getStatement()` 而不是 `getSelect()`？
**追问答**：对 DML CTE 调 `getSelect()` 会抛 `ClassCastException`，内部是裸强转；必须用 `getStatement()` 拿原始语句，再判断类型。

### Q5.6 强制 LIMIT 怎么做？为什么多取一行 ★★

**答**：如果查询可能返回多行且没有 LIMIT，就在语法树上补 `LIMIT maxRows + 1`；执行时最多取 201 行，如果读到第 201 行，说明被截断，丢掉第 201 行并标记 `truncated=true`。

多取一行是为了区分“恰好 200 行”和“还有更多”；只取 200 行永远判断不出截断。单行聚合（无 GROUP BY、全是聚合函数）不补 LIMIT。

**追问**：LIMIT 能防慢查询吗？
**追问答**：不能。LIMIT 只限制返回行数，不限制扫描/计算；`COUNT(*)` 大表仍可能很慢。所以还要超时、EXPLAIN 代价护栏。

### Q5.7 只读账号和超时怎么做的？能挡住什么 ★★

**答**：应用连库用 `text2sql_ro`，只授 SELECT，显式 REVOKE 掉 INSERT/UPDATE/DELETE/TRUNCATE 和 CREATE；连接设置只读、10 秒查询超时、最多 200 行。

它挡住的是**写操作和资源耗尽**：最坏情况是读到不该读的数据，而不是删库。挡不住的是**合法 SELECT 的数据泄露**，那需要行级/列级权限。

**追问**：只读账号能挡住 `pg_read_file` 吗？
**追问答**：不一定。`pg_read_file` 是函数权限，某些版本/角色可能允许；所以还要函数黑名单。只读账号挡的是 DML/DDL，不是所有副作用。

### Q5.8 53 条对抗用例覆盖什么 ★★

**答**：覆盖六类：写操作（INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE）、多语句注入、危险函数（含 schema 前缀、引号标识符绕过）、系统目录探测、列级越界、注释/大小写/CTE/表函数绕过。

53 条不是“写几条看着像攻击的 SQL”，每条对应一个真实绕过或真实错误；新增绕过时先加用例、让测试红，再修代码。测试总数 280。

**追问**：53 条够吗？
**追问答**：不够证明绝对安全，但能守住已知回归。安全测试是“已知攻击集”，不是“所有攻击”；还要靠只读账号、超时、审计兜底。

### Q5.9 AST 被绕过的最坏情况是什么？只读账号够不够 ★★★

**答**：最坏情况是**读到不该读的数据**，而不是删库：写操作被只读账号挡住，资源攻击被 10 秒超时/200 行挡住，但合法的 SELECT 仍可能读到敏感行/列，或者调用有副作用的函数。

只读账号不够：它只防写，不防越权读，也不防“读到数据后发出去”。要继续收敛，需要行级安全（RLS）、列级授权/脱敏视图、函数白名单、审计日志、网络出口限制。

**追问**：为什么不做 RLS？
**追问答**：项目是单租户、单只读账号，RLS 的收益场景不存在；而且会增加 schema/查询计划复杂度。范围外，不是忘了。上线给外部客户前必须补。

## Part 6 · 代价：不是 token，是 SQL 执行代价

### Q6.1 “代价”是 token 消耗吗 ★★

**答**：不是。项目里说的“代价”是**数据库执行这条 SQL 的代价**，不是模型 token。

- **代价**：`EXPLAIN` 里的 `Total Cost`、扫多少行、怎么 Join、是不是笛卡尔积；
- **成本**：调模型花了多少 token/多少钱；
- **延迟**：端到端耗时。

“选表、口径、安全、代价、错误归因”里的代价，指的是执行代价，对应 `EXPLAIN` 预执行护栏；token 我单独叫“模型成本/用量”。

**追问**：为什么容易混？
**追问答**：英文都叫 cost。PostgreSQL 的 `EXPLAIN` 输出 `Total Cost` 是优化器的相对代价单位，不是毫秒也不是钱；模型的 cost 是 token 账单。

### Q6.2 EXPLAIN 是什么？它真的执行 SQL 吗 ★★

**答**：`EXPLAIN` 是让数据库“彩排”一遍：告诉你会用哪个索引、怎么 Join、预估多少行、总代价多少，但**不真正执行**（不带 `ANALYZE` 时）。

我们用它做两件事：看总代价有没有超阈值；递归看执行计划里有没有“无约束的嵌套循环”（笛卡尔积）。它比直接执行安全，但计划是估算，统计信息过期会偏。

**追问**：EXPLAIN 有开销吗？
**追问答**：有，多一次数据库往返和规划开销；所以护栏默认关闭，本地配置才开，阈值也要按库标定。

### Q6.3 笛卡尔积和“索引嵌套循环”怎么区分 ★★★

**答**：笛卡尔积是两张表每行都互相配对，行数爆炸；索引嵌套循环是正常的 Join：外层每行，按内层索引直接找匹配行。

PostgreSQL 会把连接条件下推到内表索引，放在 `Index Cond` 里；这时顶层的 `Nested Loop` 节点**没有 `Join Filter`**。如果只看“顶层有没有 Join Filter”，会把所有索引连接误判成笛卡尔积。

所以判定要递归看子节点：只要有 `Index Cond` / `Recheck Cond`，就说明连接谓词下推了，不判笛卡尔积；同时要求没有 `Hash Cond`、没有单行标量子查询、预估行数大于 1000。

**追问**：这个细节为什么重要？
**追问答**：不递归看 `Index Cond`，正常的多表查询会被护栏误杀，表现为“SQL 没错但被拒绝”。这是护栏最容易犯的错。

### Q6.4 Cost Guard 的判定条件是什么 ★★★

**答**：两个独立条件：

1. **总代价**：`Total Cost > maxAllowedCost`（默认 100000）→ 拒绝；
2. **笛卡尔积**：节点是 `Nested Loop`、自身没有 `Join Filter`、没有 `Hash Cond`、所有子节点递归都没有 `Index Cond`/`Recheck Cond`、没有单行标量子查询、`Plan Rows > 1000` → 拒绝。

拒绝不是直接报错给用户，而是把风险诊断回灌给 Agent，触发一次反思重规划；重试仍失败才返回。

**追问**：阈值 100000 怎么定？
**追问答**：先验值，按本库规模/评估集标定；不是通用阈值。不同库、不同统计信息要重新标定。

### Q6.5 能说“零误杀”吗？护栏默认开吗 ★★

**答**：不能说零误杀。代码和测试只能证明“覆盖的用例里没有误杀”，不能证明所有 SQL；统计信息过期、Merge Join、分区表、方言差异都可能误判。

`rejectCartesianProduct` 默认 true，但 `explainCostGuardEnabled` 默认 **false**——护栏默认不生效，本地配置才打开。线上要先标定阈值、观察误杀率，再开。

**追问**：那默认配置下笛卡尔积不是没拦吗？
**追问答**：是。默认只靠 AST + 只读账号 + 超时；EXPLAIN 护栏是可选增强。线上应该开，但要先标定。

### Q6.6 代价、成本、延迟三者怎么区分 ★★

**答**：三个不同维度：

| 维度 | 回答的问题 | 项目指标 |
|---|---|---|
| 代价 | 这条 SQL 执行起来重不重 | `EXPLAIN Total Cost`、Plan Rows、笛卡尔积 |
| 成本 | 这次问数花了多少 token/多少钱 | prompt/completion token、¥0.221/100 题 |
| 延迟 | 用户等了多久 | P50 1.9s、P95 12–17s |

优化时不能混：降 token 不一定降延迟（模型调用次数可能没变）；降执行代价不一定降成本（模型才是大头）。面试时要把这三个词分开说。

## Part 7 · 结果检查与自纠错

### Q7.1 什么是“静默错误”？为什么它最危险 ★★

**答**：静默错误是“SQL 能跑、结果不报错，但答案是错的”。比如连表条件写偏、过滤条件大小写不匹配、金额列和数量列搞反；数据库不会报错，用户也看不出来。

项目里 84 那轮 16 条失败全是这种：SQL 有效执行率 100%，但结果不对。它比语法错误危险，因为没有信号；所以要有结果检查、评估归因、必要时重试。

### Q7.2 ResultChecker 的 8 条规则是什么 ★★

**答**：8 条人工规则：

1. 有 WHERE 却返回 0 行；
2. 单行聚合结果全是 NULL；
3. 比率列超出 0–100；
4. 金额/数量出现负数；
5. JOIN 没有 ON/USING；
6. 问按月/周/年却没有时间分组；
7. 问金额却只 COUNT 没有 SUM；
8. 问退款金额却 SUM 了退款数量。

它不是“答案检查器”，只是“结果看起来可疑”的熔断器；触发后把原因回灌模型重试一次。

**追问**：这是量纲引擎吗？
**追问答**：不是。没有量纲元数据、没有单位换算、没有 LLM Critic，就是 8 条关键词/统计规则。说“量纲守恒引擎”会被追问穿。

### Q7.3 比率规则把 40000 判成越界，后来怎么修 ★★

**答**：第一版对结果集每个单元格做数值判断：问“各州订单占比”时，结果里有一列 `order_count`（SP 州 4 万单），40000 > 100 被判定“比率越界”，触发重试；而重试策略是“第二次成功就采用第二次”，结果把原本正确的答案覆盖掉了。

修法：先按列名认出“像比率的列”（rate/ratio/pct/percent/占比/比例/率），认不出来就不判；增长率/环比/同比还额外排除（允许负数/超过 100%）。

教训：**误报的代价不是多一次调用，而是正确答案被打挂**；规则要窄，宁可少报。

### Q7.4 自纠错为什么收益是 0 ★★

**答**：因为首答 SQL 有效率已经 96–100%，线上只有“校验拒绝/执行失败/空内容”三种信号，能回灌的错误很少。实测 100 条触发 1 次、救回 0 条。

即使打开结果检查，触发率也很低；收益上界由“结果校验器能发现多少错”决定，而当前校验器只有 8 条关键词规则，很弱。所以自纠错不是没用，是**没有足够信号**；默认关闭。

**追问**：那为什么还保留？
**追问答**：它覆盖执行失败的长尾；保留代码、默认关闭，等有更强校验器或更弱模型时再评估。不能把 84–86 的功劳归给它。

### Q7.5 自纠错提示泄露标准答案，70 条跑到 95.7%，怎么回事 ★★★

**答**：第一版把标准答案的样例行写进了反馈提示，模型等于看到了答案，70 条跑到 95.7%；删掉标签后同配置回落到 72%。这不是模型变强，是答案泄露。

教训：凡是“加了自我反思就大幅提升”的结果，先查提示里有没有混进标签/标准答案。现在反馈只给问题、上一条 SQL、数据库报错、模型自己结果的前 3 行，不给标准答案。

**追问**：那 95.7% 还能用吗？
**追问答**：不能作为模型成绩，只能作为“泄露会让数字虚高”的反面案例；简历/汇报里绝对不能用。

### Q7.6 为什么不做 LLM Critic / 量纲引擎 ★★

**答**：因为要先证明“有没有用”。项目实测自纠错收益 0，说明当时最大瓶颈不是“校验器不够聪明”，而是“没有足够错误信号”；先上 LLM Critic 会多一次模型调用、增加成本/延迟，而且 Critic 本身也会错。

量纲引擎需要字段语义元数据（金额/数量/时间/比率）、单位换算、非负性等；项目只有 8 条字段名关键词规则，没有元数据。要做可以以后做，但不能把没做的说成做了。

### Q7.7 执行准确率为什么比字符串匹配好？标准答案有缺陷怎么办 ★★

**答**：同一个问题有无数种正确写法：列顺序、别名、Join 写法、子查询 vs join 都会变；字符串匹配会把大量正确答案判错。执行准确率是“两条 SQL 都执行，规范化结果集后比较”，更接近事实。

但标准答案也可能有缺陷：T2-037 问“订单数”，标准答案却数客户；T5-007/018 多 join 了不产出列的表；T6-013 的优惠券和订单明细一对多，SUM 会被放大，模型先按订单预聚合反而更对。

**追问**：那为什么不改标准答案？
**追问答**：改了会让 47→52→62→71→84 的历史曲线失去可比性，等于“改标准答案让系统变好看”。正确做法是记录成评估集缺陷，等整体重跑时统一修正。

## Part 8 · 评估：84/85/86 到底怎么来的

### Q8.1 200 道评估题怎么设计 ★★

**答**：六层难度：单表基础 40、单表聚合 40、时间窗口 30、多表 Join（2–3 表）45、深层 Join（4+ 表）20、业务口径 25，共 200。

每题有标准 SQL、标准结果、难度标签、能力标签、备注；标准 SQL 当场执行拿结果，不读快照。200 道按 id 哈希切开发集/评估集各 100，few-shot 只从开发集取，评估集只在验收时跑。

**追问**：200 够吗？
**追问答**：对内部对照够用，对“统计显著”不够；100 条里 1 条就是 1 个百分点，置信区间很宽。所以我说“可复现”，不说“显著提升”。

### Q8.2 执行准确率怎么算 ★★

**答**：不是比 SQL 字符串，而是两条 SQL 都执行：

1. 标准 SQL 执行，拿期望结果；
2. 模型 SQL 执行，拿实际结果；
3. 规范化：数字四舍五入到 4 位、NULL 和空串区分、日期/当天零点统一；
4. 行顺序：只有 `ORDER BY` 和 `LIMIT` 同时出现才保留顺序，否则按多重集比；
5. 列名不参与，但列位置参与；列换序会判错。

一致就是 1，不一致就是 0；84 就是 100 条里 84 条一致。

**追问**：为什么列名不参与？
**追问答**：同一个答案可以起不同别名，列名不承载语义；但列位置承载语义，所以换序会判错。更完善的做法是按语义列名对齐，当前没做。

### Q8.3 为什么不用字符串匹配 / LLM 当裁判 ★★

**答**：字符串匹配会把正确写法判错：别名、列顺序、Join 写法、子查询都会变；LLM 裁判成本高、非确定、可能被提示注入，而且裁判本身也会错。

执行结果比对是当前最接近“事实”的方式；代价是标准答案有缺陷时会把好答案判错。LLM 可以辅助解释失败原因，但计分仍用执行结果。

### Q8.4 开发集/评估集怎么切？hashCode 切分有什么缺陷 ★★

**答**：按 `Math.floorMod(id.hashCode(), 2)` 切成 100/100；few-shot 只从开发集取，评估集只在验收时跑。

缺陷不是“不同 JDK 会变”——`String.hashCode` 的算法在 Java 规范里是固定的，跨 JDK 稳定；真正的问题是：它不是随机分组、可能和 ID 命名/难度相关、没有分层保证、ID 改了切分就变。更稳的做法是显式 `split` 字段或按稳定内容哈希 + 分层抽样。

**追问**：那 84–86 有没有数据泄漏？
**追问答**：有风险。开发期看过全部 200 条，评估集也跑过多组配置；所以只能作内部回归参照，不能宣称无泄漏泛化。要证明泛化，需要另建未见测试集。

### Q8.5 为什么是 84/85/86，而不是一个固定数字 ★★

**答**：100 条样本，单题噪声就有 ±1–2 条；三次分别是 84/85/86，并集 18 条失败，其中 12 条三次都失败，6 条是单次波动（T3-016、T2-037、T5-016、T4-024、T5-007、T6-002）。

4 张表以上的深层题只有 10 条，±1 条就是 10 个百分点。写范围比写最高值诚实，也能解释“为什么不是 90”。

**追问**：那 86 是不是最好成绩？
**追问答**：是单次最高，但不可复现；写 84–86 更可信，面试官对照报告时不会觉得你挑数。

### Q8.6 84 那轮 16 条失败错在哪一层 ★★★

**答**：16 条全是“执行成功但结果不对”，检索类 0 条。下面是内部题号（`T2-015` 就是第 2 类第 15 题），面试时可以说“有一道会员等级题”，不必报编号：

- 输出列/形状 7 条：T2-015、T2-019、T3-012、T4-017、T4-024、T5-003、T5-018；
- 聚合/去重 2 条：T4-013、T5-009；
- 时间/业务口径 2 条：T3-018、T5-016；
- 度量/过滤 1 条：T4-035；
- 精度 1 条：T2-004；
- join 类型 2 条：T5-012、T6-002；
- 标准答案多余 join 1 条：T5-007。

**追问**：为什么 T2 单表聚合只有 80–85%，比多表还低？
**追问答**：T2 的错多是精度/输出列，不是聚合不会写；多表题虽然表多，但输出形状更标准。难度层不等于错误率，要看具体失败类型。

### Q8.7 47%→84–86% 怎么归因？为什么不是自纠错的功劳 ★★★

**答**：这是累计消融，不是单变量；中间换过模型：

| 阶段 | 变化 | 增量 |
|---|---|---:|
| baseline（ernie，全量 schema） | 47% | — |
| + 检索 Top-8（ernie） | 52% | +5 |
| 换 deepseek-flash（检索基线） | 62% | +10（模型变化，不算系统优化） |
| + 业务口径注入 | 71% | +9 |
| + 外键图/实体对齐/护栏 | 77% | +6 |
| + 时序/输出纪律/prompt v8 | 84% | +7 |

同模型下系统优化约 62→84（+22pp），跨模型约 +15pp；不能把 47→84 全算成工程优化。自纠错在评估集触发 1 次、救回 0 条，默认关闭，不在这 37pp 里。

### Q8.8 P95 12–17 秒没达标，成本怎么算 ★★

**答**：P95 目标 <8 秒，三次分别是 12.61、12.06、17.27 秒，都没达标；平均 3–4 秒，P50 约 1.9 秒，尾部被重试和多表 Agent 侦察拉长。

成本只算模型 API：第三次 cache-aware 102 次调用，prompt 199,436 + completion 48,992，缓存命中 89.27%，总成本 ¥0.2209/100 题，单题 ¥0.002209。不含数据库、机器、人工。

**追问**：为什么不报 0 元？
**追问答**：报告金额 0 是单价没配，不是免费；现在按官方空闲价算，才是真成本。

### Q8.9 怎么证明 84–86 不是过拟合？280 项测试都测什么 ★★★

**答**：能做的：开发/评估 100/100 不重叠、few-shot 只从开发取、配置冻结后评估集只验收、三次复跑、消融对照、280 项测试。

不能宣称的：开发期看过全部 200 条，评估集也跑过多组配置；存在测试集反馈影响决策的风险。要证明泛化，需要另建未见测试集、重复实验、记录代码版本和数据 hash。

280 项测试覆盖单元、集成、53 条对抗、编排；测试通过不等于业务正确，只证明“已知回归不被破坏”。

## Part 9 · 缓存、多轮与成本

### Q9.1 为什么缓存 SQL，不缓存结果 ★★

**答**：缓存结果会把过期数据当正确答案返回，而且没有信号能发现：SQL 没问题、格式正常，只是数字是旧的。缓存 SQL 只省模型调用，数据每次现取；SQL 描述“怎么查”，不拥有数据。

命中后仍然走完整校验和执行；如果缓存 SQL 这次跑不通，回退重新生成。缓存的是“生成成本”，不是“执行结果”。

### Q9.2 缓存键为什么必须带配置指纹 ★★

**答**：同一个问题在不同配置下应该得到不同 SQL：换模型、换 prompt、开关检索/列剪枝/few-shot/口径/工具、改 LIMIT/行数，都会改变模型看到的东西或最终 SQL 的形状。

只拿问题文本做键，改完配置旧答案会继续命中，表现成“我改了配置，数字一点没动”。指纹要覆盖所有影响生成结果的开关，项目里是 17 项。

**追问**：漏字段会怎样？
**追问答**：最初漏了 few-shot，打开 few-shot 重跑消融，数字纹丝不动——命中的全是关掉 few-shot 时缓存的 SQL。报告格式正常，只是数字是上一次配置的。

### Q9.3 L1/L2 怎么分工？为什么不用 Redis ★★

**答**：L1 是进程内 LRU（上限 1000 条），热路径零网络；L2 是 PostgreSQL 的 `semantic_cache` 表，跨重启、跨实例共享。

不用 Redis 的理由：项目是单实例，共享缓存的问题此刻不存在；Redis 多一个中间件、一次网络往返、一类新失败模式。缓存不可用时降级成“没有缓存”，不能变成“请求失败”。

**追问**：L1/L2 的坑？
**追问答**：第一版缓存键用 `\u0000` 分隔，PostgreSQL 的 text 列不允许 NUL，落库报 `invalid byte sequence 0x00`；换成 `\u001F`。还有 L2 查询在锁内做网络 I/O，把缓存读写串行化；后来移到锁外。

### Q9.4 缓存收益 −53%/−50% 和 89.27% 是一回事吗 ★★★

**答**：不是，两个不同层面的缓存。

- **应用层 SQL 缓存**：20 题重复 2 遍，50% 重复；命中后省模型调用，平均延迟 1106→521ms（−52.9%），输入 token −50%；这是“重复提问/看板”场景，标准 100 题问题互不重复，命中率是 0。
- **DeepSeek 前缀缓存**：系统提示词在 100 次调用里高度重复，命中 178,036/199,436 输入 token（89.27%）；这是模型厂商的自动缓存，不是我们写的 SQL 缓存。

不要把两个 50% 混着说；也不要说“缓存 0ms 响应”——SQL 还要执行。

### Q9.5 多轮追问怎么改写？为什么不把历史全塞进去 ★★

**答**：把“那 2017 年的呢”改写成完整问题“2017 年销售额最高的 5 个州是哪些”，再走标准链路。优先用 LLM 改写，失败/超时降级规则改写（年份替换、前 N 名、条件切换、剥离语气词）。

不全塞历史的原因：历史里的表名/SQL 会污染当前检索，导致表召回漂移；token 随轮次线性涨；模型可能把上一轮 SQL 当模板。改写后的问题仍要重新生成 SQL，不是改 SQL 字符串。

### Q9.6 Schema 复用 0ms 是怎么回事？会不会复用错 ★★

**答**：上一轮的 `SchemaContext` 缓存在会话里；追问且 `reuse-schema=true` 时，直接取上一轮表上下文，跳过检索，检索耗时 0ms。

但**不是整轮 0ms**：问题变了仍要重新调模型生成 SQL。当前复用判定是粗粒度的：只要判定为追问就复用，没有校验“是否同一业务域”；主题突然切换时可能复用错表，这是已知风险。

**追问**：为什么会复用错？
**追问答**：`canReuseSchema()` 只看 `isFollowUp()`，没有实体/主题一致性校验；用户说“那退款率呢”仍以“那”开头，可能复用上一轮的订单/客户表，漏掉退款表。更稳的做法是加主题校验，或只在时间/排序/LIMIT/同实体时复用。

### Q9.7 会话状态存哪？重启/多实例会怎样 ★★

**答**：内存是 `synchronizedMap + LinkedHashMap` 的 LRU（上限 1000），持有最近 5 轮和上一轮 schema；关闭/30 分钟超时/应用关闭时批量落 PostgreSQL 的会话表。

重启后内存态丢失；已关闭会话只在库里用于列表/审计，**不会自动恢复成对话上下文**；上一轮 schema 也不持久化，恢复后第一轮要重新检索。多实例更直接：两个实例各有各的 LRU，同一个会话打到不同实例就读不到上下文；要做就得把会话挪 Redis/共享库。

## Part 10 · Agent 通用题（面试官不懂 AI 也能听懂）

### Q10.1 Agent、Workflow、RAG 到底怎么区分？你项目算 Agent 吗 ★★★

**答**：用“实习生”打比方：

- **普通大模型**：你问一句，它答一句，不会自己查资料；
- **Workflow**：一条写死的流水线，第一步查表、第二步写 SQL、第三步检查，顺序由代码决定；
- **Agent**：你给它一个目标，它自己决定下一步做什么、要不要调工具、查到什么再继续；
- **RAG**：先查资料再回答，解决“模型不知道”的问题。

我项目的主链路是 **Workflow**：选表→写 SQL→检查→执行，步骤是代码写死的；只有遇到 3 张表以上的复杂问题，才可选地进入 `AgentLoop`，让模型自己决定“先查哪张表、要不要验证连表”。三次 84/85/86 都没有开 Agent，所以它们是 Workflow 的成绩，不是 Agent 的。

**追问**：没有 Agent 也能叫智能问数吗？
**追问答**：能。智能不等于“让模型自由发挥”；选表、连表、校验、执行这些确定性步骤用 Workflow 更稳、更可解释。Agent 只用在“需要环境反馈”的局部。

### Q10.2 一个 Agent 通常包含哪些模块？你项目缺什么 ★★

**答**：六个模块：

1. **感知**：看懂问题、识别实体；
2. **记忆**：记住当前对话和长期偏好；
3. **规划**：把任务拆成步骤；
4. **推理**：决定下一步；
5. **行动/工具**：查数据库、调 API；
6. **反思**：检查结果、纠正错误。

项目里：感知是问题改写/枚举对齐；记忆是最近 5 轮对话 + 摘要；规划是选表和连表的算法；推理是模型生成 SQL；工具是 5 个只读侦察工具；反思是 8 条结果检查 + 一次重试。

缺的是：开放式任务规划、跨会话长期记忆、多 Agent 协作。不是忘了做，是当前 SQL 任务不需要；硬加会多一层复杂度和不确定性。

### Q10.3 ReAct、Plan-and-Execute、Reflection、Multi-Agent 分别是什么？你用哪种 ★★★

**答**：四种工作方式：

- **ReAct**：想一步、做一步、看结果，再想下一步；适合需要边查边改的任务；
- **Plan-and-Execute**：先写完整计划，再按计划执行；适合步骤多、可并行的长任务；
- **Reflection**：先做一版，再审查、重写；适合有明确评价标准的任务；
- **Multi-Agent**：多个角色分工，比如一个查资料、一个写、一个审。

我项目用的是 **窄版 ReAct**（3 张表以上、最多 3 轮工具侦察）+ **窄版 Reflection**（结果可疑时重试一次）；没有全局 Plan，也没有 Multi-Agent。因为 SQL 问数步骤固定，先写计划只会多一次调用，还可能计划错。

**追问**：那为什么还保留 Agent 工具？
**追问答**：为了验证“复杂多表时，模型是不是缺真实数据”；实测评估集上没量出增益，所以默认关闭。保留是为了以后换数据集时能复测，不是为了好看。

### Q10.4 Function Calling 是什么？模型真的执行函数吗 ★★★

**答**：不是。模型只负责“说要调哪个工具、传什么参数”，真正执行的是应用。

流程是：应用先告诉模型“有哪些工具、每个工具要什么参数”；模型输出一段结构化的调用指令（工具名 + 参数）；应用解析、校验、执行；再把结果回传给模型，模型继续回答。

所以模型像“点菜”，应用像“厨房”；模型不会自己进厨房。生产上必须校验工具名、参数类型、业务权限，不能模型说什么就执行什么。

**追问**：参数类型不对怎么办？
**追问答**：先按工具定义校验；能安全转换的转换（比如字符串 “10” 转数字），不能的返回结构化错误让模型重试；不能硬塞进下游。

### Q10.5 你项目的 `[TOOL_CALL]` 和原生 Function Calling 有什么区别 ★★★

**答**：我项目用的是“文本协议”：模型输出 `[TOOL_CALL] 工具名(参数)`，我们用自己的解析器从文本里抠出工具名和参数。原生 Function Calling 是模型直接返回结构化的 `tool_calls`，应用不用解析自然语言。

文本协议的好处是简单、兼容任意模型；坏处是解析脆弱：工具名拼错、参数括号截断、参数里带逗号/括号都可能出错，而且没有 schema 校验。

如果重做，我会优先原生 Function Calling；模型不支持时再降级到文本协议。当前 5 个工具、兼容多家模型，是历史取舍。

### Q10.6 MCP 是什么？解决什么问题 ★★★

**答**：MCP 是“工具接入的通用插座”。没有它时，每个应用要接每个工具，都要写一套适配，N 个应用 × M 个工具 = N×M 套；有了 MCP，应用接协议、工具实现服务端，变成 N+M。

MCP 里有三个角色：Host（你的应用）、Client（应用里负责通信的模块）、Server（工具服务）。Server 暴露工具、资源、提示模板；Client 用一套标准的远程调用格式（JSON-RPC）发现和调用。本地走标准输入输出（stdio），远程走 HTTP + 服务器推送（SSE）。

**追问**：MCP 能解决安全吗？
**追问答**：不能。MCP 只解决“怎么接”，权限、审计、沙箱、AST 校验仍要自己做；工具描述本身也可能被篡改，不能盲信。

### Q10.7 Agent 的记忆怎么设计？你项目做到哪一层 ★★

**答**：分三层：

- **工作记忆**：当前这一步的临时状态；
- **短期记忆**：这次对话的历史；
- **长期记忆**：跨会话的用户偏好/知识，通常放向量库或数据库，按当前问题召回。

项目只有前两层：最近 5 轮对话 + 早期轮次的摘要；会话结束落库，但只用于列表/审计，不在下次请求时召回。所以用户上次说“只看 SP”，新会话不会自动继承。

**追问**：上下文太长怎么办？
**追问答**：三种办法：只留最近几轮（滑动窗口）、把早期对话压成摘要、把历史做成向量按需召回。项目用“窗口 + 正则摘要”，便宜、确定，但会丢自然语言条件，不是无损。

### Q10.8 多 Agent 什么时候值得？你为什么不用 ★★★

**答**：多 Agent 适合“任务能拆、子任务能并行、需要不同专业/权限”的场景，比如一个查法律、一个查财务、一个写报告。代价是通信、状态同步、冲突处理、调试变难。

Text2SQL 是单目标、强顺序、共享上下文：选表→写 SQL→检查→执行，拆成多个 Agent 只会增加协调成本，不会让 SQL 更对。所以项目是单 Agent/单编排器。

如果真要加，我会加一个“SQL 审查 Agent”：它只读，不改 SQL，只按规则给出“阻断/警告/建议”；最多 1–2 轮，不能无限否决；审查和生成用同一个模型会有共同盲点，所以先跑确定性规则，再让模型补充。

### Q10.9 Agent 常见的失败模式有哪些？怎么防 ★★★

**答**：三类最常见：

1. **死循环**：反复调同一个工具、反复改同一条 SQL；防法是最大轮数、重复动作检测、预算上限；
2. **跑题/目标漂移**：越查越远，忘了最初问题；防法是每轮对照原始目标、限制子任务范围；
3. **上下文爆掉**：工具返回太多、历史太长；防法是截断工具结果、摘要历史、设 token 预算。

项目只做了最基础的三条：最多 3 轮、SQL 10 秒超时、会话最多 5 轮；没有动作哈希、没有 token 预算器、没有目标漂移检测。这些是下一阶段要补的。

### Q10.10 Agent 评测和普通问答评测有什么区别？你项目缺什么 ★★

**答**：普通问答只看“最后答案对不对”；Agent 还要看“过程”：

- 任务有没有完成；
- 工具选得对不对、参数对不对；
- 走了几步、花了多少 token/时间；
- 有没有违规操作；
- 失败了能不能恢复。

项目现在只有执行准确率（最后结果集对不对）、SQL 有效率、表召回、P50/P95、token；没有轨迹指标、没有工具调用准确率。所以我能说“结果对不对”，不能说“过程好不好”。

**追问**：怎么补？
**追问答**：先给每次请求加 traceId，记录每一步的工具名、参数摘要、结果状态；再抽 100 条人工标“该用什么工具、该查什么表”，算工具选择准确率和步数效率；成本大约 3–5 小时。

### Q10.11 面试官说“你只是 Workflow，不是 Agent”；项目没做 MCP/A2A，怎么答 ★★★

**答**：先承认，再解释，不要硬装。

> “对，主链路是 Workflow；Agent 只用在 3 张表以上的局部侦察，而且默认关闭。84–86 是 Workflow 的成绩，不是 Agent。我选 Workflow 是因为 SQL 问数步骤固定、错误代价高、需要逐层归因；Agent 的开放式规划在这里收益不明确。”

MCP/A2A 没做也直接说：

> “MCP 是工具接入的通用协议，A2A 是 Agent 之间协作的协议；我项目只有 5 个进程内工具、单 Agent，没有跨应用复用/多 Agent 协作需求，所以没接。硬接只会增加协议、权限、部署复杂度；要做的话，先把工具执行器包成 MCP 服务，再补权限和审计。”

不编“我们内部实现了 MCP”。面试官追问 `tools/list`、JSON-RPC、stdio/SSE 就穿帮；诚实 + 知道什么时候该做，反而加分。

## Part 11 · Java / Spring / PostgreSQL 基础

### Q11.1 项目用了 Java 21 的哪些特性 ★

**答**：主要用了：

- **record**：不可变数据对象，比如接口响应、连接计划；自动生成构造器、getter、equals/hashCode；
- **text block**：多行字符串，比如 prompt 模板、SQL 示例；
- **switch 表达式/模式匹配**：把状态映射成 HTTP 状态码、判断 SQL 类型；
- **`List.getFirst()`**：Java 21 的顺序集合 API，取排名第一的表；
- **`instanceof` 模式匹配**：判断 `Select`/`PlainSelect` 等类型。

虚拟线程没有用：当前瓶颈是模型 I/O 和数据库连接池，不是平台线程数量。

### Q11.2 Spring Boot 自动装配是什么？你为什么关掉 Spring AI 的自动配置 ★★

**答**：Spring Boot 会根据依赖和配置自动创建对象（Bean）。比如引入 Spring AI 的 OpenAI starter，它会自动创建一个聊天模型客户端。

问题在于：没配 Key 时，它会在启动阶段报错，导致“只想跑数据库/校验/评估”的人被卡死。所以我用配置显式关掉自动配置，改成手写装配：有 Key 才建客户端，没 Key 也能启动，只是问数接口返回“未配置”。

**追问**：自动装配和包扫描有什么区别？
**追问答**：包扫描扫的是你自己写的 `@Component/@Service`；自动装配是 starter 提供的、按条件生效的默认对象。来源不同，优先级也不同。

### Q11.3 你怎么接大模型？怎么做到只改配置换厂商 ★★

**答**：用 OpenAI 兼容协议：配 `base-url`、`completions-path`、`model`、`api-key` 四项；DeepSeek、通义、千帆只要兼容这个协议，改配置就能换。

端点是 `base-url + completions-path` 拼起来的，所以不要把 `/v1` 写进 `base-url`，否则会拼成 `/v1/v1/...` 404。判断端点对不对：带假 Key 请求，返回 401 说明路对了，返回 404 说明路径错。

**追问**：没 Key 能启动吗？
**追问答**：能。没 Key 时客户端为空，问数接口返回 503；数据库、校验、评估链路仍可离线跑。这是刻意的“可检查状态”，不是异常。

### Q11.4 依赖注入、AOP、拦截器分别用在哪 ★

**答**：依赖注入用构造器注入：依赖不可变、启动就暴露循环依赖，单测可以直接 new。AOP 在项目里用得少，主要是全局异常处理；探味志项目里用拦截器做登录校验和续期。

三者的区别：过滤器在 Servlet 容器层，拦截器在 Spring MVC 层，AOP 在方法调用层。拦截器能拿到 Controller 方法信息，AOP 适合日志/事务这类横切逻辑。

### Q11.5 项目里哪里用了并发容器/线程池/ThreadLocal ★★

**答**：项目里并发点不多：缓存用 `synchronized + LinkedHashMap` 做 LRU；BYOK 客户端池、会话缓存也用同步包装的 LRU；检索器/关系图用 `volatile` 做惰性缓存；数据库连接池是 Hikari，最大 5 个连接；评估是串行，没有自定义线程池。

ThreadLocal 主要用在探味志的登录上下文：拦截器里 set 用户，请求结束 `finally remove`；线程池复用线程，不 remove 会串用户/内存泄漏。

**追问**：`synchronized` 会不会成为瓶颈？
**追问答**：缓存读写是内存操作，锁竞争很低；真正慢的 L2 数据库查询已经移到锁外。QPS 上来可以换 Caffeine/分段锁。

### Q11.6 大结果集/JVM 内存有什么风险？怎么防 OOM ★★

**答**：最大风险是 `SELECT * FROM geolocation` 这种百万行结果把堆打满。项目三层防：SQL 层补 `LIMIT maxRows+1`；执行层 `setMaxRows(201)`；读完最多保留 200 行，多的一行用来判断截断。

另外 schema 元数据只加载 37 张表，缓存/会话都有 LRU 上限，调用日志默认不记 prompt/回复内容，避免“输入决定内存”。

**追问**：`setMaxRows` 和 SQL LIMIT 有什么区别？
**追问答**：`setMaxRows` 是 JDBC 驱动层限制，数据库可能仍算完再返回；SQL LIMIT 是数据库层限制，能减少计算/传输。项目两者都用。

### Q11.7 为什么编排层不抛异常，而是返回状态 ★★

**答**：因为评估要连续跑 100 条，任何一条抛异常都会中断整轮；而且失败类型本身就是要统计的数据。统一返回状态（成功、被校验拒绝、生成失败、执行失败、未配置、需要澄清），Controller 再映射 HTTP 状态码。

这样日志里不会出现“同一类错误两种形态”，评估报告也能按状态统计。

**追问**：内部未知异常怎么办？
**追问答**：全局异常处理器兜底，返回 500；已知失败都翻译成状态，不吞异常，记录上下文。

### Q11.8 PostgreSQL 和 MySQL 有什么区别？索引/MVCC 怎么讲 ★★

**答**：选 PostgreSQL 的原因：分析型 SQL 更顺手（窗口函数、CTE、`DATE_TRUNC`、`FILTER`）、`EXPLAIN` 的 JSON 格式方便程序分析、只读角色/权限模型清晰。MySQL 也能做，但在“JSON 计划树 + 复杂分析查询”上 PG 更直接。

索引：MySQL InnoDB 主键是聚簇 B+ 树，二级索引叶子存主键；PostgreSQL 是堆表 + B-tree 索引，索引叶子存行指针。联合索引遵循最左前缀；覆盖索引是查询需要的列都在索引里，不用回表。

多版本并发控制（MVCC）：PG 给每行保留版本号（xmin/xmax），更新产生新版本，旧版本由 vacuum 清理；MySQL InnoDB 用 undo log + read view。默认隔离级别 PG 是 Read Committed，MySQL 是 Repeatable Read。

**追问**：为什么 PG 的 COUNT(*) 慢？
**追问答**：MVCC 要判断每行对当前快照是否可见，不能只读一个行数计数器；大表只能扫可见行。近似计数可以走统计信息/物化视图。

## Part 12 · 行为面与开放题

### Q12.1 这个项目最大的失败是什么？你学到什么 ★★

**答**：最大的失败不是某个 bug，是几次“以为有用、实测没用”的误判：

- 第一版 Join 规划：52%→52%，token 反涨 29%，还引入过度 Join；我把它默认关掉；
- 自纠错：首答有效率高，100 条触发 1 次、救回 0 条；我如实写收益 0；
- 答案泄露：把标准答案样例写进反馈，70 条跑到 95.7%；删掉后回落到 72%。

学到三件事：先证伪自己的假设、任何提升都要有对照、别用修改标准答案让系统变好看。

### Q12.2 给你三个月，你优先做什么 ★★

**答**：先修“决定天花板”的两层：4 张表以上的深层题（40–60%）和输出形状（7 条失败）；再做评估集口径统一/标准答案审计；然后建未见测试集证明泛化；最后才考虑向量检索、多方言这些增量。

顺序原则：先修正确性瓶颈，再修评估可信度，最后做新功能。不是先上 Agent、也不是先做性能。

### Q12.3 为什么不用 LangGraph / LangChain4j / AutoGen / CrewAI ★★

**答**：因为链路固定（选表→生成→校验→执行→有限重试）、只有 5 个工具、要求逐层归因。框架会把控制流藏进黑盒，出问题难定位；手写编排约百行，状态可控、日志可读、依赖少。

Java 生态可以用 Spring AI（`@Tool`/MCP）、LangChain4j；但当前链路简单，框架收益小于理解成本。等链路变长、需要人工审批/断点恢复/多 Agent 时再上。

### Q12.4 你最大的优势和短板是什么 ★

**答**：优势是工程闭环和归因：能把一个不确定的模型能力包进检索、校验、评估、成本账本里，能说清每个数字的条件和每个失败的层。

短板是模型侧理论深度不够：embedding、向量检索、模型微调没有真正落地；项目也是单实例，没有多租户、数据权限、真实高并发的考验。这些是下一阶段要补的，不是嘴上说“学习能力强”。

### Q12.5 你有什么问题问我们 ★

**答**：问三类：

1. 团队现在的 AI 应用，最大瓶颈是准确率、延迟还是成本？
2. 这个岗位前 3–6 个月的成功标准是什么？
3. 团队的评估集/线上反馈闭环是怎么做的？

不要第一句问薪资/加班，也不要问官网能查到的信息。问“成功标准”是确认期望，不是挑活。

### Q12.6 用一句话总结这个项目 ★

**答**：**它不是“让模型写 SQL”的 demo，而是一条把模型输出变成可执行、可拦截、可评估、可归因的工程链路；84–86 不是终点，是我能说清每一条错在哪一层的起点。**
