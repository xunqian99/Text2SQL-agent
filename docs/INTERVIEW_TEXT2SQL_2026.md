## Part 0 · 三版项目介绍

### Q0.1 30 秒介绍 ★

**答**：

> 我做了一个 Text2SQL Agent，把中文业务问题翻译成只读 PostgreSQL SQL。它不是一个「生成 SQL 的 demo」，重点在**可评估**：我自建了 200 条六层评测集，三次独立运行执行准确率 **84/85/86**，SQL 有效执行率 100%；16 条失败逐条归因，**没有一条是检索错误**，7 条是输出列形状。工程上是 Java 21 + Spring Boot，词典检索 + Join 拓扑 + AST/只读账号/超时三层护栏，280 项测试、53 条对抗。

**面试官想听**：你有没有「评测驱动」的意识，而不是只会调 API。

### Q0.2 2 分钟介绍 ★★

**答**：

> 项目解决的是「中文问题 → 可执行 SQL」这条链路。难点不在写 SQL，而在四件事：选表、业务口径、Join 拓扑、结果形状。
>
> 链路是：问题进来先做多轮改写/澄清/缓存；然后 Schema 检索，从 37 张表里召回 Top-8，并做连通性修复；再注入 metrics.yml 的业务口径和枚举值对齐；Prompt 里放 schema、指标、枚举、问题，调 DeepSeek 生成 SQL；生成后过 JSqlParser AST 白名单、EXPLAIN 代价护栏、只读账号执行；最后做 8 条启发式结果检查和必要的错误回灌重试。
>
> 评测是执行准确率：gold SQL 和生成 SQL 都执行，ResultNormalizer 规范化后比结果集，不是字符串匹配。三次运行 84/85/86，T1 100%，T5 40–60%。失败里检索 0 条、输出形状 7 条，所以瓶颈在「模型和 gold 的结果约定」，不是「找不到表」。
>
> 我知道它的边界：T5 深层 Join 只有 40–60%，P95 12–17s 没达到 8s，单租户、无 RLS，不做写操作和多方言。

**追问**：为什么不直接说「准确率 86%」？
**追问答**：单次最高值不可复现；三次 84/85/86，12 条稳定失败、6 条波动，写范围比写最高值诚实，也经得起对照报告。

### Q0.3 5 分钟技术深挖版 ★★★

**答**（按「问题 → 设计 → 数字 → 边界」讲）：

1. **问题**：37 张表、201 列、13 条真实外键；中文和物理 schema 之间没有词边界，模型容易选错表、猜错列、写错口径。
2. **检索**：领域词典最大匹配（长词优先、单字权重 0.5）→ 关系扩展（源分数 × 0.4 衰减 × 边强度，取 max）→ 全序排序（分数 → 直接命中 → 表名）→ Top-8 → BFS 最短桥接修复（最多补 2 张）。表全召回 98.00%、平均召回 99.55%、精确率约 28%。
3. **Join**：外键 1.0、词典关联 0.5；以最相关表为根，对每张目标表求加权最短路并取并集，再按「强度 → 相关度 → 表名」做 Prim 式生长，输出 JOIN PLAN。
4. **口径**：metrics.yml 维护 GMV、复购率、客单价等 23 条可注入指标；按关键词 + 依赖表过滤，T6 三次 34/36。
5. **护栏**：AST 只允许单 SELECT、表/列白名单、函数黑名单归一化、CTE 数据修改 / FROM 表函数检查；只读账号 `text2sql_ro`；10s 超时 + 200 行上限；53 条对抗全绿。
6. **评测**：200 条六层，id 哈希切 dev/eval；执行 gold + 生成 SQL，规范化后比结果集；三次 84/85/86；16 条失败全是 SUCCESS，检索 0 条。
7. **成本**：第三次 cache-aware 102 次调用，prompt 199,436 + completion 48,992，cache 命中 89.27%，¥0.221/100 题，单题 ¥0.002209。
8. **边界**：T5 40–60%、P95 12–17s、单租户无 RLS、28 张扩展表是合成数据、eval 有泄漏风险。

### Q0.4 一句话说清「这个项目难在哪」 ★★

**答**：

> 难的不是让模型写出一条能跑的 SQL，而是让它在 37 张表里**选对表、连对路、用对口径、输出对形状**；更难的是一旦错了，你能说清错在哪一层。我的 16 条失败里检索 0 条，7 条是输出列形状——这句话就是这个项目的价值。

### Q0.5 项目边界：什么不做 ★

**答**：

> 不做写操作、多 SQL 方言、模型微调、多租户/RLS；P95 没达到 8s；成本只算 LLM API，不含数据库/机器/人工。这些不是「没做完」，是明确的范围取舍，写在 README 的「已知局限」里。

## Part 1 · 总览与数据流

### Q1.1 一个请求从进来到出结果，经过哪些步骤？ ★★

**面试官想听**：你能不能按数据流讲，而不是按类名堆。

**答**：

1. `AskController` 收 JSON，校验 `question` 长度、`sessionId` 格式，映射 HTTP 状态码。
2. `Text2SqlOrchestrator.ask()`：多轮场景先判断是否追问，做改写/澄清/缓存；再取 Schema。
3. `SchemaProvider`：`FullSchemaProvider`（baseline）或 `HybridSchemaProvider`（检索 + Join 拓扑 + 口径 + 枚举 + 列剪枝 + few-shot）。
4. `LlmSqlGenerator` + `PromptTemplate`：拼 system/user prompt，调 OpenAI 兼容模型，记录 token/延迟/成本。
5. `SqlValidator`：多语句 → AST → 必须 SELECT → 函数黑名单 → 表/列白名单 → 补 `LIMIT maxRows+1`。
6. `QueryPlanAnalyzer`（可选）：EXPLAIN JSON 代价/笛卡尔积护栏。
7. `SqlExecutor`：只读连接、10s 超时、200 行上限，多取 1 行判截断。
8. `ResultChecker` / 自纠错：8 条启发式规则，命中可疑就把错误回灌重试；失败保留首次结果。
9. `AgentResponse`：SQL、列/行、召回表、分阶段耗时、token/成本、会话字段。

**追问**：为什么编排层不放在 Controller？
**追问答**：HTTP 和 `EvalRunner` 两个入口必须共用同一条链路，否则评估测的不是线上行为；Controller 只做协议转换。

### Q1.2 为什么 HTTP 和评估器共用编排层？ ★★

**答**：评估要证明「线上真实行为」，不是另一套复制逻辑。`EvalRunner` 直接调 `orchestrator.ask()`，和 `/api/ask` 走同一条检索、生成、校验、执行、记账链路；差异只在入口和报告聚合。这样报告里的 84/85/86 才能代表线上。

### Q1.3 为什么不用 LangChain / LangGraph，手写 Pipeline？ ★★★

**答**：

- 我需要**精确控制每一阶段的失败分类和耗时**：检索错、生成错、校验拒、执行错、结果口径错，这五类要分开统计；框架黑盒会把它们揉成一个「Agent 失败」。
- 评估要求同一条链路可复现，手写 Pipeline 的输入输出都是显式的，报告 meta 能记录每个开关。
- Spring AI 只用来做 OpenAI 协议适配，编排、重试、缓存、会话都是自己写的；不是「不用框架」，是「不用框架接管控制流」。

**追问**：手写 Pipeline 的代价是什么？
**追问答**：要自己处理状态、重试、超时、并发和可观测性；换来的是可解释和可测试。这个项目里 280 项测试和逐条失败归因，就是这笔交易的收益。

### Q1.4 为什么 application.yml 里大部分优化默认关闭？ ★★

**答**：baseline 必须随时可复现。检索、口径注入、few-shot、缓存、多轮、Agent、自纠错、代价护栏默认都是 `false`；`application-local.yml` 才打开。这样「加了检索提升多少」才是干净的对照，而不是默认值悄悄生效。代价是第一次跑的人容易以为「怎么只有 baseline」——README 写清了要用 local profile。

### Q1.5 37 张表怎么来的？合成数据会不会影响结论？ ★★★

**答**：

- 9 张是真实 Olist 表（orders、order_items、customers、products 等），28 张是扩展表（会员、优惠券、退款、结算、库存、工单等），数据按真实订单反推生成。
- 影响：T5/T6 大量跑在扩展表上，真实库的脏数据、空值、口径冲突覆盖不足；所以 84–86 只能当**内部回归基线**，不能宣称跨库泛化。
- 我没有把扩展表说成「37 张真实业务表」；简历和 README 都写了 9 真实 + 28 扩展。

### Q1.6 你的系统里「Agent」体现在哪？为什么默认不是 Agent？ ★★★

**答**：

- `AgentLoop` + `ToolParser` + `ToolExecutor` 实现了 5 个只读侦察工具（INSPECT_TABLE / INSPECT_COLUMN / SAMPLE_QUERY / CHECK_JOIN / EXPLAIN_QUERY），最多 3 轮，模型用 `[TOOL_CALL]` / `[FINAL_SQL]` 交互。
- 但默认 `tool-use.enabled=false`：主链路是确定性 Pipeline，不是自主 Agent。评估集上 Agent 模式**没有量出增益**，所以 84–86 不算它的功劳；保留它是为了证明「37 表上工具侦察不划算」这个负结果。

**追问**：那你还叫它 Agent？
**追问答**：叫「Agent 编排链路」可以，叫「自主 Agent」不行。我的简历写的是「Agent 问数系统」，但我会主动说明默认是 Pipeline。

### Q1.7 如果 QPS 上来，哪里先崩？ ★★★

**答**：

1. **LLM 调用**：同步阻塞、单次 2–20s，先撞限流/超时；没有队列、限流、熔断。
2. **数据库连接池**：Hikari 只读池 5 个连接，慢查询会占满。
3. **内存**：会话 LRU 1000、缓存 LRU 1000、BYOK 客户端 LRU 32，目前有上限，但单实例。
4. **没有鉴权/租户隔离**：公网部署前必须加。

**追问**：怎么改？
**追问答**：异步化 + 队列削峰、按 token/并发限流、连接池按负载调、加 requestId/trace、把评估和线上隔离。

### Q1.8 如果重做，你先改哪三件？ ★★★

**答**：

1. **输出形状**：把「每个指标返回哪些列、精度、聚合口径」做成 metric registry 的显式字段，而不是靠 18 条 prompt 规则猜——这是 7 条失败的最大类。
2. **T5 桥接表**：把 4+ 表的桥接路径和输出形状单独评测，不要只用整体 84–86 掩盖 40–60%。
3. **可复现/CI**：固定 profile、seed、数据 hash，CI 带真库跑集成测试；现在的 CI 无库会跳过 9 条。

## Part 2 · 评测体系与数字

### Q2.1 执行准确率怎么算？为什么不比 SQL 字符串？ ★★

**答**：把 gold SQL 和生成 SQL 都执行，`ResultNormalizer` 规范化后比较结果集；每题对/错二值。不比字符串，因为同一个问题有无数种正确写法（JOIN/子查询、别名、大小写），字符串匹配会把正确答案判错。也不是 LLM 裁判，裁判本身有偏差。

### Q2.2 ResultNormalizer 有哪几条规则？ ★★

**答**：

1. 数字统一四舍五入到 4 位小数，去掉多余零；禁止科学计数法（`610` 不能变 `6.1E+2`）。
2. NULL 与空字符串区分；JDBC null 归一成 `NULL`。
3. 完整日期和当天零点 timestamp 归一成 `yyyy-MM-dd HH:mm:ss`；`2018-01`、`2018-Q1` 不展开。
4. 行顺序：只有 gold 同时有 `ORDER BY` 和 `LIMIT` 才按有序列表比；否则按多重集比。
5. 列名不参与比较，但列位置参与；不支持自动换序列对齐。

**追问**：为什么列名不比？
**追问答**：业务关心数字和列位置，不关心别名；但列位置参与，因为「多一列/少一列/列换序」都是结果形状错误。

### Q2.3 dev/eval 怎么切？为什么按 id 哈希？ ★★

**答**：200 条按 `Math.floorMod(id.hashCode(), 2)` 切 dev/eval 各 100；few-shot 只从 dev 取。按 id 而不是按行号，是为了排版/顺序调整不改变样本归属；不按难度层切，是因为那样 dev 全是单表题，多表和业务语义没法调参。

**追问**：这能保证无泄漏吗？
**追问答**：不能。开发期看过全量 200 条，eval 也跑过多组配置；只能作内部回归参照，不能宣称无泄漏泛化。

### Q2.4 为什么三次是 84/85/86，而不是一个固定数字？ ★★

**答**：100 条样本，单题噪声就有 ±1–2 题；三次分别是 84/85/86，并集 18 条失败，其中 **12 条三次都失败**，6 条是单次波动（T3-016、T2-037、T5-016、T4-024、T5-007、T6-002）。T5 只有 10 条，±1 题就是 10pp。写范围比写最高值诚实，也能解释「为什么不是 90」。

### Q2.5 16 条失败错在哪一层？检索 0 条说明什么？ ★★★

**答**：以第一次 15 条为例：输出列/形状 7、聚合去重 2、时间/口径 1、度量/过滤 1、精度 1、join 类型 1、gold 多余 join 1、输出格式 1。**检索类 0 条**，说明「选表」已经不是瓶颈；瓶颈在「模型和 gold 的结果约定」——输出列、聚合粒度、时间窗口、精度。这是 prompt 规则和指标注册表该管、但没完全管好的部分。

### Q2.6 12 条稳定失败，举 3 个例子 ★★★

**答**：

- **T2-004**：gold `ROUND(AVG(cnt),4)`，模型 `ROUND(...,2)`；逻辑一样，只差精度。
- **T2-015**：gold 输出 `level_id`，模型输出 `level_name` 并多 join 了 `member_levels`；输出列形状错。
- **T3-018**：gold 用 `orders.order_delivered_customer_date - order_purchase_timestamp`，模型用 `shipments.delivered_at - shipped_at`；「配送时长」口径不同。
- 另外 T4-013 的 `COUNT(*)` vs `COUNT(DISTINCT order_id)`、T5-018 的「成对行」vs「same/diff 两列」也是典型。

### Q2.7 T5 为什么只有 40–60%？ ★★★

**答**：T5 是 4+ 表、桥接表、深层关联，只有 10 条。三次分别 4/5/6 条正确（40/50/60%），±1 题就是 10pp。具体瓶颈：桥接表召回不全、join 路径有歧义、输出形状复杂。它不是「检索崩了」，而是「深层结构和结果约定」没解决；我不会拿单层数字下结论。

### Q2.8 47%→84–86% 是怎么归因的？为什么不是自纠错的功劳？ ★★★

**答**：这是累计消融，不是单变量：

| 阶段 | 变化 | 增量 |
|---|---|---:|
| Phase 1 baseline（全量 schema） | 47% | — |
| + Schema 检索 Top-8 | 52% | +5pp |
| + 业务口径注入 | 71% | +19pp |
| + 外键图/实体对齐/代价护栏 | 77% | +6pp |
| + 时序保全/输出纪律/prompt v8 | 84% | +7pp |

自纠错在评估集触发 1 次、救回 0 条，默认关闭；所以 47→84 不能记在自纠错头上。这个归因是项目里最重要的「不抢功劳」证据。

### Q2.9 gold 有缺陷吗？为什么不改 gold？ ★★★

**答**：有。T2-037 问「订单数超过 5000 的州」，gold 却用 `customers` 的 `COUNT(*)`（数客户，不是订单）；T5-007/018 的 gold 多 join 了不产出列、只起过滤作用的表；T6-013 的优惠券和订单明细一对多，`SUM(discount_amount)` 会被放大，模型先按 order 预聚合反而更对。改 gold 会让 47→52→71→84 这条曲线失去可比性，等于「改标准答案让系统变好看」；我只记录成评估集缺陷。

### Q2.10 评估集有泄漏吗？能宣称泛化吗？ ★★★

**答**：不能。开发期看过全量 200 条，eval 也跑过多组模型/K/配置；切分只保证确定性，不保证统计独立。84–86 是内部回归基线，不是未见测试集成绩。要证明泛化，得另建未见测试集、做重复实验、记录版本和数据 hash。

### Q2.11 dry-run 200/200 说明什么？不能说明什么？ ★★

**答**：说明评估器/校验器/执行器自身没坏：把 gold SQL 当模型输出跑下游，200 条都能通过校验、执行、结果比对。不能说明模型准确率，也不能证明规范化永远正确。dry-run 用全量 schema 校验 trusted gold SQL，并跳过代价护栏；检索召回仍单独报告（200 条中 6 条不完整召回，都是 gold 里的无关 join）。

### Q2.12 面试官说「84% 不高」，你怎么回？ ★★★

**答**：

> 对，84–86% 不是生产级数字。但它在 37 张表、200 条六层题、单模型单轮、合成扩展表的条件下是可解释的：T1 100%、T5 40–60%；16 条失败检索 0 条、输出形状 7 条。真实企业落地我会先做模板路由和口径治理，而不是把 84% 直接上线。更重要的是，我能说清剩下的 16 条错在哪一层——这比一个漂亮的 90% 更有用。

## Part 3 · Schema 检索

### Q3.1 为什么不用 pgvector / tsvector？ ★★★

**答**：实测 PG 的 `to_tsvector('english','统计每个州的订单数量')` 把整串当一个 token，`simple` 也一样；`pg_trgm` 的 `show_trgm('订单数量')` 返回空数组。中文没有空格，PG 内置分词对中文是死的。我没有引入 embedding/pgvector，因为检索的难点不是「相似度」，是「中文词 → 哪张表」的领域映射；词典最大匹配零依赖、可审阅、可增删，先拿一个干净 baseline。以后要加向量，是增量，不是替换。

### Q3.2 词典最大匹配怎么做的？为什么不用 jieba？ ★★★

**答**：把 glossary 里的表别名、列别名、枚举 label 展开成 `MatchTerm`，按词长降序；从左到右扫描问题，在每个位置找最长匹配，命中后跳到词尾，避免「订单明细」同时命中 `order_items` 和 `orders`。单字别名（州/券/仓）权重 ×0.5，兼顾召回和误命中。不用 jieba，是因为通用分词能把「复购率」切成「复购」「率」，但它不知道「复购」对应哪张表；难点是领域映射，不是切词。

### Q3.3 关系扩展的分数怎么算？为什么取 max 不累加？ ★★

**答**：从直接命中的表出发，`delta = 源表分数 × 衰减(0.4) × 边强度`；同一张表可能有多条路径可达，取**最大**分数而不是累加。累加会让「邻居多的表」靠数量堆分数，而我们要的是「最强的那条路径有多可信」。扩展只从分数最高的 3 张表出发，避免一个宽泛问题扩出十几张表。

### Q3.4 连通性修复的 BFS 最短桥怎么做的？ ★★★

**答**：Top-8 选出来后，先在「已选表」内部做 BFS 求连通分量；如果多于 1 个分量，就从 0 号分量做多源 BFS，第一次碰到属于其他分量的已选表，就是最短桥；把路径上的中间表补进来。预算最多 2 张，装不下就整条放弃，保留不连通（模型会报错，错误可见），而不是悄悄把上下文撑爆。它和「把 topK 调大」的区别：只补能消除不连通的那几张，已经连通的一张不补。

### Q3.5 Top-8 怎么定的？为什么不是 5 或 10？ ★★

**答**：评估集里 4 表以上的题只占 20 条，gold SQL 最多用到 6 张表，8 留了余量；dev 上 Top-5 和 Top-8 做过对照：Top-8 多答对 2 题、完整召回多 7 题，代价是平均多约 103 个 prompt token。但我也保留不利证据：早期 eval Top-5 是 54%，高于最终 Top-8 的 52%；单轮差异不能证明 Top-8 更好。

### Q3.6 表全召回 98%、精确率 28%，怎么解释？ ★★★

**答**：这是**召回优先**的取舍：Top-8 先保证「该用的表在里面」，代价是上下文有噪声表。精确率 28% 意味着平均召回 6.85 张里只有约 2 张是 gold 表；噪声靠生成、AST 和执行兜底。我不宣称精确率，因为在这个任务里「漏表」比「多表」更致命：漏了必然错，多了只是浪费 token、可能干扰模型。

**追问**：为什么不把精确率做高？
**追问答**：可以做 rerank/分类器，但需要标注和评估；当前优先级是召回和结果正确，精确率是下一迭代的事。

### Q3.7 列剪枝的保全规则？为什么不能裁主键/外键/指标列？ ★★★

**答**：剪枝只裁「明显无关」的列，以下永远保留：

1. 主键、外键（数据库元数据里的真实主键，不靠列名猜）；
2. `ValueRetriever` 命中的枚举/实体列；
3. 命中指标 expression/filter 引用的列；
4. 问题文本里直接出现的列名/中文别名；
5. 时间语义问题的日期/时间列；
6. 度量措辞问题的数值列；
7. 少于 `minColumns` 时按注释和原顺序补齐。

裁掉主键/外键，join 直接断；裁掉指标列，模型只能猜列名；裁掉枚举列，WHERE 会写中文值。这些都是实测踩过的坑。

### Q3.8 ValueRetriever 枚举对齐怎么做的？ ★★

**答**：从 glossary 的 `enum` 定义和巴西 27 州映射里建倒排索引（别名 → 表/列/物理值），按别名长度降序做包含匹配；命中后注入「问题中的『圣保罗』对应 `customer_state = 'SP'`」这样的提示。它解决的是「模型把州写成『圣保罗』、把状态写成『已取消』」的静默错误——SQL 能跑，但结果恒为 0。

### Q3.9 检索的失败模式？词典没命中怎么办？ ★★

**答**：失败模式有四类：词典没收录（OOV）、单字误命中、桥接表漏召回、精确率低。词典一个词都没命中时，回退全量 schema（37 张表），宁可多给上下文，也不能因为词典没收录就把必要表筛掉；回退率本身是要监控的指标，回退高说明词典覆盖不足。

### Q3.10 如果让你把精确率从 28% 提到 50%，你怎么做？ ★★★

**答**：三步：1）用 gold 表构造正样本、用 Top-8 里的非 gold 表构造硬负样本，训一个轻量 reranker（逻辑回归/GBDT 即可）；2）加表级特征：词典命中类型/权重、与已选表的连通距离、是否被指标依赖、是否在问题里出现英文标识符；3）在 dev 上做消融，确认召回不掉。不会直接上大模型 rerank，成本和延迟不划算。

## Part 4 · Join 拓扑规划

### Q4.1 为什么光有「边列表」不够？ ★★

**答**：边列表只回答「哪两列能连」，不回答「先连谁、后连谁」。多表题里同一组表可能有多条路径都连通，比如 T5-001 的 `orders → customers → members → member_levels` 和 `orders → coupon_usages → members` 在图上都通；只给边，模型眼里两条路径等价，容易选错。生成树给的是「推荐顺序」，边列表给的是「备选关系」，两者都要有。

### Q4.2 Dijkstra 最短路并集 + Prim 生长，具体怎么做？ ★★★

**答**：

1. 以检索分数最高的目标表为根；
2. 对每张其他目标表，在「外键权重 1.0、词典关联 2.0」的图上跑 Dijkstra，取最短路径；
3. 把所有路径的边取并集，得到候选子图；
4. 在候选子图上做 Prim 式生长：每轮从边界挑一条边，优先级是「边强度降序 → 新连表的相关度升序 → 表名」；
5. 输出 `from.col = to.col -- table [FK]/[约定]` 的等式形式，模型可以直接抄进 ON。

### Q4.3 边强度 1.0 / 0.5 的依据？相关度为什么是第二排序键？ ★★★

**答**：外键是数据库强制约束的硬事实，强度 1.0；词典关联是人工核对的软知识，0.5。强度只能区分「硬/软」，不能区分「软知识里哪条更该走」；T5-001 第三轮出现三条 0.5 的候选边，如果按表名字母序，`coupon_usages` 会排在 `members` 前面，主干就变成「经优惠券到会员」——正是错的那条。加上检索相关度做第二键后，`members` 排名更高，主干回到 gold 的路径。

### Q4.4 为什么根选「最相关表」而不是随便选？ ★★

**答**：树是给模型照着写 SQL 的，从事实表（orders、order_items）出发符合 SQL 自然写法；从维表（regions）出发会得到语义别扭的树。检索分数已经排好「哪张表最相关」，直接复用，不再造启发式。

### Q4.5 生成树只覆盖一个连通分量，怎么告诉模型？ ★★★

**答**：`Plan.incomplete()` 会判断「树覆盖的表数 < 上下文表数」，渲染时加一行「注意：还有 N 张表与起点不在同一连通分量，本段未给出连接顺序；它们的关联见上面的 JOINS」。这不是装饰，是防止模型把 JOIN PLAN 当成「全部 join」而漏表；漏表的错误是「SQL 能跑、结果错」，最难查。

### Q4.6 过度 join 怎么防？ ★★★

**答**：三件事：1）只为「核心目标表」规划，核心表不足 2 张就完全不输出 JOIN PLAN，杜绝单表题被强行 join；2）JOINS 列表和 JOIN PLAN 两个开关独立，阶段 3 实测过「给多了」和「规划错了」要能拆开；3）prompt 明确「只连问题需要的表」。过度 join 的代价是行数放大和口径偏移，不是语法错，所以必须单独评测。

### Q4.7 多表 join 放大行数，COUNT(*) 和 COUNT(DISTINCT) 怎么选？ ★★★

**答**：只要 join 后可能一对多，就用 `COUNT(DISTINCT 主键)`；单表、无 join 才用 `COUNT(*)`。T4-013 差评订单按州统计，评价表一单多评，`COUNT(*)` 会重复计数；T4-017 会员等级订单数同理。这不是「写法偏好」，是口径错误——计数口径错了，分组结果整体偏移。

### Q4.8 T5 的瓶颈在 Join 规划还是输出形状？ ★★★

**答**：两者都有，但输出形状更大。T5 的失败里既有桥接表漏召回（T5-007 漏 member_levels、T5-018 漏 order_items），也有输出形状完全不同（T5-018 gold 是成对行，模型是 same/diff 两列）。Join 规划解决「能不能连」，输出形状解决「连完输出什么」；后者是 prompt 和指标注册表该管的，当前没完全管好。

## Part 5 · Prompt 与 SQL 生成

### Q5.1 18 条规则里，哪几条最重要？ ★★

**答**：按失败归因排：

- 规则 8/11：只输出问题要求的列，不多加 id/name/展示列——对应 7 条输出形状失败；
- 规则 10：join 后去重计数用 `COUNT(DISTINCT)`——对应聚合失败；
- 规则 12：比例/精度口径（0–1 还是百分比、ROUND 几位）；
- 规则 13/14：`DATE_TRUNC` 分组、左闭右开时间窗；
- 规则 15：枚举值用物理值（`'SP'` 不是「圣保罗」）；
- 规则 7：metrics 命中就照抄表达式，不自己发挥。

### Q5.2 为什么把问题放在 prompt 最后？ ★★

**答**：长上下文里模型对末尾内容注意力更强；schema、指标、枚举是背景，问题放最后能减少「答非所问」。这是 prompt 工程里少数有稳定收益的经验，不是玄学。

### Q5.3 为什么 temperature=0？ ★★

**答**：Text2SQL 是确定性任务，不是创作；温度 0 让同样输入尽量产生同样输出，评估数字才可复现。代价是模型「认死理」写错时不会换写法，这个代价由自纠错/重试承担。

### Q5.4 为什么不用 Spring AI 自动配置？ ★★★

**答**：`spring-ai-starter-model-openai` 默认 base-url 指向 api.openai.com，没 Key 时启动阶段就抛异常；我需要「没 Key 也能启动」，这样数据库、校验、评估链路能离线自检。所以手工装配 `OpenAiApi` + `OpenAiChatModel`，有 Key 才建客户端，没 Key 置空，调用时抛 `NOT_CONFIGURED`。Spring AI 只做协议适配，编排不交给它。

### Q5.5 模型返回带解释、markdown 围栏，怎么清洗？ ★★

**答**：`SqlExtractor` 三步：取第一个 ```sql 围栏；剥掉 `SQL:`/`SQL：` 前缀；按空行切掉尾部解释，只保留以 SQL 关键字或 `, ) ;` 开头的续行。抽不出 SQL 就抛 `GenerationException(UNPARSEABLE)`，而不是把整段解释当 SQL 送进校验器——那会报 `PARSE_ERROR`，被误归因为「模型写错 SQL」。

### Q5.6 为什么 prompt 要版本号？ ★★

**答**：评估报告要记录 prompt 版本（当前 `p8-semantic-pruning-v8`）。没有版本号，「这次提升来自 prompt 改动还是检索」就永远说不清；消融实验的数字也没有可比性。阶段 2 改的是「上下文里有哪些表」，不是措辞，所以版本号刻意不变。

### Q5.7 规则 12/16 帮倒忙的案例？ ★★★

**答**：

- 规则 12 要求「金额/平均统一 ROUND 2 位」，但 T2-004 的 gold 是 `ROUND(...,4)`；模型严格照规则写 2 位，被判错。
- 规则 16 要求「承运商配送时长用 shipments 的 delivered_at - shipped_at」，但 T3-018 的 gold 是 orders 的「下单到签收」；「配送」一词在两个口径间歧义，规则把模型带偏。

这说明 prompt 规则不能一刀切，数值精度和业务口径应该做成指标注册表的显式字段，而不是 18 条自然语言规则。

### Q5.8 换模型怎么保证可复现？ ★★★

**答**：同一套 200 条评估集、同一 prompt 版本、同一检索/校验配置，只换模型；报告 meta 记录模型、base-url、prompt 版本、检索开关、self-correction。比较的是**执行准确率、失败模式、工具调用序列**，不是文本快照；模型生成有波动，单轮差异不能直接下结论，至少重复两轮。

## Part 6 · 校验与安全

### Q6.1 为什么不能靠 prompt 约束「只读」？ ★★★

**答**：prompt 是概率性约束，模型 99% 遵守，剩下 1% 可能给你 `DROP TABLE orders`；在生产库里 1% 就是灾难。正确心智模型是：**LLM 输出等价于不可信的用户输入**。既然不会把用户输入直接拼进 SQL，也不该把模型输出直接执行。所以 AST 校验的定位不是「提升准确率」，是「让错误无害化」。

### Q6.2 AST 校验的六步？ ★★★

**答**：

1. 多语句检查：先剥尾部分号，`parseStatements` 数量 > 1 就拒；
2. 解析 AST，解析失败一律拒绝（fail-closed）；
3. 必须是 `Select`，挡住 DROP/UPDATE/DELETE/INSERT/ALTER/TRUNCATE；
4. 递归遍历函数黑名单，函数名归一化（小写 → 取最后一个 `.` 之后 → 去首尾双引号）；
5. 表白名单 + 带别名列白名单；再检查 CTE 数据修改 / FROM 表函数；
6. 强制 LIMIT：需要 LIMIT 且没有时，APPEND `maxRows+1` 或 REJECT。

### Q6.3 多语句怎么拦？为什么先剥尾分号？ ★★

**答**：用解析器而不是数分号，因为分号可能出现在字符串字面量里（`WHERE name = 'a;b'`）。解析器会把结尾多一个分号也算成一条语句，所以先循环剥掉尾部分号再 `parseStatements`；`SELECT 1; DROP TABLE orders` 会被解析成两条，直接拒。

### Q6.4 危险函数黑名单怎么防 schema 限定名/引号绕过？ ★★★

**答**：黑名单里是裸名 `pg_sleep`，但 JSqlParser 的 `Function#getName()` 可能返回 `pg_catalog.pg_sleep`、`"pg_sleep"`、`pg_catalog."pg_sleep"`；直接比裸名，加一个前缀或一对引号就能绕过。归一化顺序：小写 → 取最后一个 `.` 之后 → 去掉首尾双引号。这三个洞是实测出来的，不是假设。

### Q6.5 列白名单为什么只查带别名列？ ★★★

**答**：裸列名的合法来源太多：SELECT 别名、GROUP BY 位置、CTE 输出列、派生表列、集合操作两侧同名列；一旦判错，正常查询会被拦下，护栏就从「防护」变成「故障源」。带前缀的列（`o.customer_id`）能精确归属到某张表，判定是确定的，所以先把这一半做扎实。

**追问**：别名作用域问题怎么处理？
**追问答**：T6-016 里外层 `FROM brands bp`、CTE 内 `FROM brand_products bp`，同一别名指两张表；压平后会误杀。修法不是实现完整词法作用域，而是承认边界：只要某个别名被绑定到过 CTE/派生表，该别名的列一律不判定；多个候选表都没有这一列时才报错。少拦几条，换不误杀。

### Q6.6 CTE 数据修改 / FROM 表函数怎么拦？为什么用 getStatement()？ ★★★

**答**：

- `WITH x AS (DELETE FROM orders RETURNING *) SELECT * FROM x` 最外层是 `PlainSelect`，只判 `instanceof Select` 会放行；真正的 DELETE 藏在 `WithItem` 里。对 DML CTE 调 `WithItem.getSelect()` 会抛 `ClassCastException`（内部裸强转 `ParenthesedSelect`），必须用 `WithItem.getStatement()` 拿到原始语句，再判是不是 `ParenthesedSelect`。
- `FROM dblink(...)` / `pg_ls_dir(...)` 走 `FromItemVisitor`，函数黑名单的 `ExpressionVisitor` 覆盖不到；在 `FromItemVisitor` 里遇到 `TableFunction` 直接拒。
- 这两条是 H2/H4，已补 6 条对抗用例（3 条 DML CTE + 3 条 FROM 表函数），`AdversarialSqlTest` 47→53。

### Q6.7 只读账号是第几层？能防什么、不能防什么？ ★★★

**答**：第二层（AST → 只读账号 → 超时/行数）。`text2sql_ro` 只有 SELECT，没有 INSERT/UPDATE/DELETE/TRUNCATE/CREATE；就算 AST 被绕过，数据库也会拒绝写。它**不能**防「合法 SELECT 越权读」：没有 RLS、没有列级权限，单租户；公网部署前必须加鉴权和行级/列级授权。

### Q6.8 LIMIT 为什么补 maxRows+1？ ★★

**答**：执行层要知道「结果是被上限截断的，还是恰好这么多行」。如果补 `maxRows`，数据库最多返回 `maxRows` 行，执行层无论怎么多读一行都读不到，`truncated` 永远是 false，调用方会以为拿全了。补 `maxRows+1`，执行层取到第 201 行就判定截断，再把多出来那行丢掉，对外仍然最多 200 行。

### Q6.9 CHECK_JOIN 为什么强制等值？ON 1=1 怎么防？ ★★★

**答**：`CHECK_JOIN` 的连接条件来自模型输出，等于不可信输入；直接拼进 `ON` 子句会开注入面（任意 SQL 片段、`ON 1=1` 笛卡尔积）。现在强制 `表.列 = 表.列` 的正则，表名必须命中 catalog 且不能相同，列必须真实存在，等值两侧必须分别来自两张表；不满足就拒绝。这样既防注入，也防「自己连自己」。

### Q6.10 提示注入 / 合法 SELECT 越权读，怎么答？ ★★★

**答**：提示注入方面，AST + 只读账号能保证「不能写、不能执行危险函数」，但不能保证「不泄露合法表里的数据」；如果用户诱导模型查薪资表，只要表在白名单里，就是合法 SELECT。当前没有 RLS/列级权限，这是明确边界；公网部署要加鉴权、租户隔离、行级授权、限流。语义错误（SQL 合法但口径不对）不属于安全漏洞，属于准确率问题。

## Part 7 · 执行、结果与自纠错

### Q7.1 SqlExecutor 的三道防线？ ★★

**答**：1）只读事务 `setReadOnly(true)`，PostgreSQL 在协议层拒绝写；2）`setQueryTimeout(10s)` 防慢查询占连接；3）`setMaxRows(maxRows+1)` 防大结果集打爆内存，多取一行判截断。形态合法 ≠ 资源可控，所以超时和行数上限不依赖校验层。

### Q7.2 为什么 setReadOnly + 10s + maxRows？ ★★★

**答**：`setReadOnly` 是数据库层面的兜底，不依赖代码正确性；10s 是防止一条没写好条件的 join 把连接占满几十秒；200 行是评估集最大 gold 结果 73 行，200 有足够余量，同时 200 行 × 若干列的 JSON 只有几十 KB。三者是正交的：权限、时间、空间。

### Q7.3 执行失败怎么分类？ ★★★

**答**：`AgentResponse.Status` 六态：SUCCESS、NOT_CONFIGURED、GENERATION_FAILED、REJECTED、EXECUTION_FAILED、NEEDS_CLARIFICATION。分开的原因：NOT_CONFIGURED 是环境问题，重试没用；GENERATION_FAILED 是模型侧；REJECTED 是护栏拦下；EXECUTION_FAILED 是数据库/方言/超时；NEEDS_CLARIFICATION 是问题没问清。混成一类，评估数字换环境就会漂移。

### Q7.4 ResultChecker 的 8 条规则？ ★★★

**答**：

1. 空结果：有 WHERE 且 0 行，问题又不是「没有/未/零」；
2. 单行聚合全 NULL；
3. 比率越界：只检查列名像 rate/ratio/pct/percent/占比/比例/率的列，排除增长率；
4. 负数指标：金额/GMV/费用/价格/数量/笔数/人数出现负数；
5. JOIN 缺 ON/USING；
6. 时间维度丢失：问题要按月/周/年，SQL 没有 DATE_TRUNC/EXTRACT/GROUP BY；
7. 金额题只用 COUNT 没用 SUM；
8. 退款金额聚合了 refund_qty 而不是 refund_value。

### Q7.5 自纠错什么时候触发？为什么线上不重试「结果不对」？ ★★★

**答**：线上只在 `!success()` 时重试——校验拒绝、执行失败、模型返回空内容，这三类有明确错误信号；「执行成功但结果不对」在线上没有信号（没有 gold），所以不重试。评估器里有 `ERRORS_AND_MISMATCH` 档，是上限实验，不是线上策略。实测 `ERRORS_ONLY` 触发 0 次，因为首答 SQL 有效率已经 96–100%。

### Q7.6 重试失败为什么保留首次结果？ ★★

**答**：把一次糟糕的重试当成最终答案，会让系统比不重试更差；实测出现过「首次能跑通、重试反而执行失败」。所以只有第二次**成功**才采用，否则原样返回第一次结果。重试的 token/延迟仍要合并记账，不能因为失败就不算成本。

### Q7.7 重试的 token/延迟怎么记账？ ★★

**答**：`LlmCallRecord.combine(first, second)` 把两次的 prompt/completion/total token、延迟、成本相加；`AgentResponse.combineAttempts` 把两次 Timings 逐项相加。结果取第二次，账目记两次之和——否则成本被低估一半，报告和账单对不上。

### Q7.8 EXPLAIN 代价护栏怎么防误杀？ ★★★

**答**：`QueryPlanAnalyzer` 用 `EXPLAIN (FORMAT JSON)` 拿 Total Cost 和 Plan Rows；笛卡尔积检测不是「看到 Nested Loop 就杀」，而是要求：没有 Join Filter、没有 Hash Cond、子节点没有 Index Cond、不是单行标量子查询广播、预估行数 > 1000，才判高危。这样避免把「索引嵌套循环」「标量广播」误判成笛卡尔积。护栏默认关，local/评估配置开。

## Part 8 · 缓存、成本与可观测

### Q8.1 为什么缓存 SQL，不缓存结果？ ★★★

**答**：结果集会过期，而且过期了没有信号——业务库更新后，缓存结果仍然“看起来正确”，这是最危险的错误。缓存 SQL 则不同：命中后仍然走完整校验和执行，数据变了结果自然变；SQL 跑不通会回退重新生成。缓存的是“生成成本”，不是“执行结果”。

### Q8.2 L1/L2 怎么设计？key 怎么算？ ★★★

**答**：L1 是进程内 `LinkedHashMap` LRU（上限 1000，accessOrder），纳秒级；L2 是 PostgreSQL 的 `semantic_cache` 表，跨实例、重启不丢。key = 归一化问题（小写、去空白、去末尾标点）+ `\u001F` + 配置指纹。分隔符用 ASCII Unit Separator，因为第一版用 `\u0000` 在 PostgreSQL text 列会报 `invalid byte sequence 0x00`，这个 bug 只在加持久化后暴露。

### Q8.3 配置指纹为什么要编进 17 项？ ★★★

**答**：只要一个开关会改变“模型看到的内容”或“最终 SQL 的形状”，它就必须进指纹，否则改了配置仍命中旧 SQL，表现为“配置改了但数字一点没动”。指纹包含：模型、prompt 版本、retrieval 的 enabled/topK/joinHints/joinList/joinPlan/bridgeRepair/columnPruning、semantic、fewshot、dataProfile、foreignKeys、toolUse、limitMode、maxRows、routing。踩过的坑：最初漏了 few-shot，打开 few-shot 重跑消融，数字纹丝不动。

### Q8.4 缓存命中为什么还要执行 SQL？ ★★★

**答**：缓存的是 SQL，不是结果；不执行就无法知道当前数据下的结果。命中省的是模型调用（输入 token 归零），不是数据库执行。所以延迟降到“数据库执行耗时”，不是 0ms；README 里明确写了这一点。

### Q8.5 缓存收益 −53% / −50% 的条件？ ★★★

**答**：这是“20 题重复 2 遍 = 40 次请求、50% 重复”的负载：缓存开，平均延迟 1106→521ms（−52.9%），输入 token −50.0%，准确率 95.0% vs 92.5%（样本内波动）。标准 100 题 eval 问题互不重复，命中率是 0；所以这个收益只在“高频重复提问/看板”场景成立，不能当普适结论。

### Q8.6 成本怎么算？为什么 ¥0.221 不是 0？ ★★★

**答**：第三次 cache-aware 全量：102 次调用，prompt 199,436 + completion 48,992；官方空闲价 1.0 / 4.0 元每百万，缓存命中 0.02；成本 = miss×1.0 + hit×0.02 + completion×4.0，除以 1e6，得到 **¥0.2209 / 100 题**，单题 **¥0.002209**。前两次没有 cache 字段，按“全部未命中”算上限 ¥0.370 / ¥0.363；报告金额 0 是当时单价没配，不是免费。

### Q8.7 cache hit 89.27% 怎么来的？为什么这么高？ ★★

**答**：DeepSeek 的自动前缀缓存：系统提示词在 100 次调用里高度重复，命中 178,036 / 199,436 输入 token（89.27%），未命中 21,400。命中价只有未命中的 1/50，所以成本比上限低很多。JSONL 现在记录 `cacheHitTokens` / `cacheMissTokens`，成本按分段算；历史两次没有这两个字段，只能算上限。

### Q8.8 共享 API Key 怎么隔离成本？ ★★★

**答**：控制台账单是账号级，无法按项目隔离；所以不看控制台，直接用项目自己的 JSONL：每次调用记 prompt/completion/cache hit/miss，`scripts/report_llm_cost.py` 按时间窗过滤、按官方单价算，结果只含本项目。这是“逐条 token 账本”而不是“账号账单”，也是为什么成本能精确到 ¥0.002209/题。

## Part 9 · 多轮与 Agent

### Q9.1 多轮怎么判断“这是追问”？ ★★

**答**：`QuestionRewriter.isFollowUp()` 三段：1）前缀词（那/那么/然后再/再看/换成/改成/只看/如果/去掉/加上/其中/按照/按/除了/对比）；2）代词（这个/这些/上述）；3）长度 ≤ 20 且带语气词（呢/怎么样/如何）或含“前/top/排序/升序/降序/最高/最低”。命中才改写；不是追问就按新问题走。

### Q9.2 改写用 LLM 还是规则？失败怎么办？ ★★★

**答**：优先 LLM 改写（带上下文），但只接受“非空白且长度 < 300”的结果；否则降级规则改写：年份替换、数量限制（只看前 N/前 N/top N）、条件切换（换成/改成）、语气词剥离拼接。规则是确定性的兜底，保证 LLM 超时/乱答时链路不断。改写那一次调用的 token/延迟也要并入本轮账目。

### Q9.3 上下文压缩怎么做的？会丢信息吗？ ★★

**答**：`maxTurns=5` 滑窗；被滑出的早期轮次交给 `SessionContextCompressor`，用正则从 SQL 里抽 `order_status` 过滤、州过滤、表名、年份，从问题里抽指标关键词，合并成“会话早期历史偏好与约束摘要”，压到 O(1) 量级。会丢信息——它不是语义无损压缩，保留的是关键约束（状态/地区/年份/指标/表），不是完整对话。

### Q9.4 Schema 复用怎么做的？ ★★

**答**：追问且 `reuse-schema=true` 时，直接取 `session.lastSchema()`，跳过检索；`schemaReused=true` 会回传。前提是“追问通常还在同一个业务域”；如果问题切到新域，`isFollowUp` 不命中，不会复用。复用省的是检索时间，不是生成时间。

### Q9.5 Agent 的 5 个工具是什么？为什么默认关？ ★★★

**答**：INSPECT_TABLE（看前 5 行）、INSPECT_COLUMN（看列的高频值）、SAMPLE_QUERY（包一层 LIMIT 5 跑样例）、CHECK_JOIN（测两表连接匹配行数）、EXPLAIN_QUERY（看执行计划/代价）。默认 `tool-use.enabled=false`：评估集上没量出增益，且多轮工具调用会拉高延迟和 token；保留它是为了验证“37 表上工具侦察是否值得”，结论是不值得。

### Q9.6 Agent 模式为什么没量出增益？ ★★★

**答**：三个原因：1）检索已经把 Top-8 选出来了，模型缺的不是“更多信息”，是“输出约定”；2）工具调用的 token/延迟成本高于它修正的错误；3）评估集里需要侦察的题（T5）只有 10 条，样本太小。所以我把它默认关掉，84–86 不算它的功劳；这是一个负结果，不是失败。

### Q9.7 “加州订单”追问“那德州呢”，SQL 怎么变？ ★★

**答**：`isFollowUp` 命中“那”前缀 + 长度短，进入改写；LLM 改写拿到上一轮 SQL 和原问题，输出“德州订单量”，再走完整生成。这里有个坑：改写只改自然语言，不改 SQL——如果直接改 SQL 字符串，`customer_state` 的取值域、时间窗、聚合口径都可能被改错，而且绕过 AST 校验。所以我的选择是“改写问题、重新生成 SQL”，代价是多一次完整生成。

**追问**：那缓存不就失效了？
**追问答**：会。缓存 key 是“归一化问题 + 17 项配置指纹”，改写后的问题和上一轮不同，必然 miss。这是有意的：多轮场景本来就不该指望缓存命中，缓存收益主要来自“同一批题重复跑”（评估场景 20 题 × 2 遍，命中 89.27%）。

### Q9.8 会话状态存哪？进程重启会怎样？ ★★

**答**：内存 `ConcurrentHashMap<sessionId, Session>` 持有最近 5 轮和 `lastSchema`；持久化到 PostgreSQL 的 `conversation_session` / `conversation_turn` 两张表。重启后内存态丢失，但可以从库里按 sessionId 恢复最近 N 轮；`lastSchema` 不持久化，恢复后第一轮会重新检索。

**追问**：多实例部署呢？
**追问答**：现在就坏了——两个实例各有各的内存 Map，同一个 sessionId 打到不同实例就读不到上下文。要做的话得把 session 挪到 Redis，或者用一致性哈希绑会话。这是我写在“上线还缺什么”里的条目之一，不是我不知道。

### Q9.9 为什么不用 LangChain / Spring AI 的 Agent 抽象？ ★★★

**答**：三条理由：1）我要控制每一次 LLM 调用的入参、出参和 token 账目，框架的封装会把这层藏起来，而我的核心资产恰恰是“逐层可归因”；2）我的 Agent 是“5 个只读工具 + 两种标记协议（`[TOOL_CALL]` / `[FINAL_SQL]`）”，用框架反而要写适配层；3）Spring AI 我只用了 `OpenAiChatModel` 这一层，而且是手工装配（`spring.ai.model.chat=none`），因为它自动配置在没 Key 时会让应用起不来。

**追问**：那你不就是“不用框架所以显得原始”？
**追问答**：反了。框架解决的是“快速搭起来”，我解决的是“测得准、说得清”。真要用框架，我会在“工具编排”这一层用，不会在“调用与记账”这一层用。

### Q9.10 多轮 + Agent + 缓存三者叠加，冲突在哪？ ★★★

**答**：三处冲突：1）**缓存 vs 多轮**——缓存 key 含归一化问题，多轮改写后问题变了，命中率必然掉；2）**Agent vs 延迟**——工具侦察是多轮 LLM 往返，P95 已经 12–17s，再叠工具会破 20s；3）**缓存 vs Agent**——Agent 模式下同一问题可能因为侦察结果不同产出不同 SQL，缓存会固化第一次的结果。所以我的默认组合是“多轮开、Agent 关、缓存开”，三个开关独立，不做“全开”的假演示。

## Part 10 · 工程化、测试与部署

### Q10.1 280 项测试怎么分布？53 条对抗是什么？ ★★

**答**：280 = 单元测试 + 集成测试 + 对抗测试；其中 `AdversarialSqlTest` 53 条（47 原有 + 6 新增：3 条 DML CTE、3 条 FROM 表函数），`SqlValidatorTest` 19 条，9 条真库集成测试（无库自动跳过）。测试覆盖检索、Join 规划、列剪枝、结果规范化、会话、缓存、工具、自纠错、评估表召回。

### Q10.2 9 条真库集成测试在 CI 怎么办？ ★★

**答**：CI 没有 PostgreSQL 时，这 9 条自动跳过；本地有库时全跑。所以“CI 绿”不等于“本地 280 全绿”，README 里写清了。更好的做法是 CI 起一个 postgres service，把 9 条也跑起来；当前是取舍，不是遗漏。

### Q10.3 为什么 Mockito 参数固化在 pom？ ★★

**答**：Mockito 5 默认 inline mock maker，需要把 byte-buddy agent 自附加到当前 JVM；JDK 9+ 默认禁止自附加，裸跑 `mvn test` 会报 `Could not initialize plugin: MockMaker`，59 个 Error。把 `-Djdk.attach.allowAttachSelf=true` 写进 surefire 的 `argLine`，让默认路径就是正确路径，不依赖每个人的命令行记忆。

### Q10.4 数据库怎么初始化？只读/读写角色怎么分？ ★★★

**答**：`docker/docker-compose.yml` 起 PostgreSQL 16；`data/schema/01~06` 依次建表、导 Olist、建扩展表、生成扩展数据、建只读角色、建持久化表。业务查询用 `text2sql_ro`（只有 SELECT）；持久化用 `text2sql_rw`（只对 semantic_cache / llm_call_log / conversation_session / conversation_turn 有权限）。两个账号按用途拆，业务账号永远没有写权限。

### Q10.5 为什么 schema 从数据库读，不读 DDL 文件？ ★★

**答**：文件是“意图”，数据库是“事实”；有人手工改过库、或 DDL 执行失败，两者就分叉，模型会基于错误事实生成 SQL，错误以“表不存在”在最后一步才暴露。从 `information_schema` / `pg_catalog` 读，保证模型看到的永远等于它要查的库；代价是启动多几条元数据查询，用 `SchemaCatalog` 缓存。

### Q10.6 如果表结构变了，哪里会坏？ ★★★

**答**：1）`SchemaCatalog` 缓存要重启/刷新；2）glossary 的别名/枚举可能失效，`GlossaryLoader` 启动时校验，列不存在会丢弃；3）评估集 gold SQL 可能跑不通，`goldBroken` 会剔除；4）列剪枝的主键/外键依赖元数据，会跟着变；5）prompt 里的 schema 文本自动更新。所以“改表”不是只改 DDL，要重跑 dry-run 和评估。

### Q10.7 日志/审计/隐私怎么处理？ ★★

**答**：`LlmCallLog` 每次调用写 JSONL（时间、模型、状态、token、延迟、成本），`include-content=false` 默认不写 prompt/response；prompt 含用户原始问题，落盘前要显式打开。数据库 `llm_call_log` 只给 INSERT/SELECT，不给 UPDATE/DELETE，审计记录不可改。会话只存 SQL 和结果摘要，不存全量结果集。

### Q10.8 如果上线，缺什么？ ★★★

**答**：鉴权、租户隔离、RLS/列级权限、限流/配额、异步队列、traceId、告警、成本预算、CI 带真库、灰度/回滚。当前是单租户、单实例、只读账号；安全边界是“防写”，不是“防合法越权读”。这些写在 SECURITY.md 的“已知边界”里。

## Part 11 · 简历与行为面

### Q11.1 为什么简历写 84–86，而不是 84 或 86？ ★★

**答**：三次独立运行 84/85/86；12 条稳定失败、6 条波动。写范围比写最高值诚实，也能解释“为什么不是 90”；面试官对照报告时，不会觉得你挑数。单次最高值不可复现，写它反而给自己挖坑。

### Q11.2 你最大的贡献是什么？ ★★

**答**：不是“写了一个 Agent”，是“把 Text2SQL 的误差拆到了层”：自建 200 条六层评测集、执行准确率、逐条失败归因；证明 16 条失败里检索 0 条、输出形状 7 条，从而把优化重点从“检索”转到“结果约定”。这个判断比多写一个功能值钱。

### Q11.3 最难的一个 bug？ ★★★

**答**：会话持久化“功能整体失效但只写 WARN”。`text2sql_rw` 没有 CREATE 权限，应用运行时建表兜底永远失败，用户结束会话只看到一条 WARN，历史一条没进库；跑了几十轮评估都没发现，因为它只在异常分支执行。修法：DDL 放到 `06_persistence.sql`，应用先 `to_regclass` 探测、缺表给“去跑哪个脚本”的提示，并补真库集成测试。教训：兜底路径也必须被验证。

### Q11.4 你和 AI 的分工？代码是不是你写的？ ★★★

**答**：AI 辅助实现，设计决策和验证是我做的。我能讲清每条链路为什么这么选：为什么不用向量、为什么 Top-8、为什么补 maxRows+1、为什么 CTE 用 getStatement；也能当场改一行代码并解释影响。面试官真正在意的不是“每个字符是不是你敲的”，是“你能不能为设计负责”。

### Q11.5 如果面试官说“这就是 prompt 工程”，你怎么回？ ★★★

**答**：如果只是拼 prompt，确实像。但我的工作在 prompt 之外：37 张表的检索与连通性修复、Join 拓扑、AST/只读/超时三层护栏、执行结果规范化、200 条评测与逐条归因、成本记账。prompt 只是其中一层；84–86 的失败里检索 0 条、输出形状 7 条，说明瓶颈不在“措辞”，在“结果约定和结构”。

### Q11.6 为什么不写“生产级”？ ★★★

**答**：因为不是。没有鉴权、限流、多租户、RLS，P95 没达到 8s，单实例。写“生产级”会在第一个追问就崩；写“可评估、可归因”反而准确，也留出了“上线还缺什么”的讨论空间。

### Q11.7 你的项目有什么失败/负结果？ ★★★

**答**：三个：1）Agent 工具侦察、自纠错、few-shot、Join 提示都做了对照，没增益就默认关；2）T5 深层 Join 只有 40–60%，不回避；3）gold 自身有缺陷（T2-037 数客户不数订单、T5-007/018 无关 join），但不改 gold，因为会让历史曲线失去可比性。敢报负结果，比只报赢的更容易建立信任。

### Q11.8 你接下来会怎么迭代？ ★★★

**答**：优先级：1）输出形状做成指标注册表显式字段（返回列/精度/聚合口径），直接打 7 条最大失败类；2）T5 桥接表和 Join 路径单独评测；3）CI 带真库、固定 profile/数据 hash；4）成本单价接入实际账单；5）多租户/RLS 是产品化才做，不在当前范围。

### Q11.9 为什么做这个项目？ ★

**答**：起点是一个很具体的挫败感：让模型直接写 SQL，它写得出，但你不知道它为什么错、错在哪一层。市面上的 Text2SQL demo 大多只报一个准确率数字，没有失败归因。我想做的不是“又一个 demo”，是“一个能把误差拆开的实验台”——所以第一版先写评测集和归因，再写生成。

**追问**：那你是先有评测还是先有系统？
**追问答**：先有最小生成链路跑通，然后立刻停下来写 200 条评测集和 `ResultNormalizer`。这个顺序很关键：没有规范化，执行准确率根本不可信（同样的结果集，列顺序不同、数值精度不同，字符串比较会全判错）。

### Q11.10 项目做了多久？投入多少？ ★★

**答**：按“有效工作日”算，主体 6–8 周，之后是断断续续的加固（安全缺口、成本核算、文档）。我没有夸大工时的必要——这个项目的体量（64 个主类、11,828 行、280 项测试）本身就是证据，面试官一看代码结构就知道不是三天拼出来的。

**追问**：AI 帮你写了多少？
**追问答**：实现层面大部分是 AI 辅助生成、我逐段审；设计决策、评测口径、失败归因、安全加固是我做的。判断标准很简单：随便挑一个类，我能讲清它为什么存在、换一种写法会坏在哪。

### Q11.11 如果重做一遍，哪里会不一样？ ★★★

**答**：三件事：1）**先写结果约定，再写检索**——7 条失败是“输出形状”问题，如果一开始就把“返回列名/精度/聚合口径”做成显式契约，这 7 条大概率能省掉；2）**评测集一开始就按层标注 + 固定数据快照**——现在 eval 有泄漏风险（dev/eval 用 `hashCode` 切分，但扩展表是合成数据，分布可能偏），重做会把数据 hash 和 profile 固定下来；3）**成本记账从第一天做**——我是后期才补的 `cacheHitTokens`，导致前两次运行的账目只能算上界。

### Q11.12 和别人有分歧怎么办？举个例子。 ★★

**答**：拿“要不要上向量检索”举例。直觉上 37 张表该用 embedding 做 schema 召回，我最后没上，理由是：37 张表的规模下，领域词典 + 关系扩展 + 连通性修复的召回已经够（表全召回率在 84–86 的失败里没有一条是“表没找全”导致的），而向量会引入“不可解释的召回”——错了你没法说清为什么召回这张表。分歧的解法不是说服，是**用评测数据裁决**：我加了对照实验，没增益就不上。

### Q11.13 为什么用 Java 而不是 Python 做 AI 应用？ ★★★

**答**：分两层。**这个项目**：主链路是“HTTP 服务 + 数据库 + 并发 + 可观测”，Java 的工程能力（Spring 的事务/连接池/配置、强类型、成熟的测试栈）比 Python 省事；模型调用只是其中一次 HTTP 请求，不是瓶颈。**这个岗位**：我投的是 Java 后端 / AI 应用开发，Java 是我的主语言，用主语言做项目才能被追问到 JVM、并发、框架源码这一层。

**追问**：那 Python 生态的 LangChain/LlamaIndex 你不用，不落后吗？
**追问答**：不落后，是分工不同。Python 强在“实验快、生态全”，Java 强在“服务稳、可维护”。真做产品，常见形态是 Python 做离线评测/训练，Java 做在线服务。我这个项目刻意选了“在线服务”这一侧，因为它是简历上更稀缺的能力。

### Q11.14 你最大的短板是什么？ ★★

**答**：**没有真实用户和真实流量**。我的 84–86 是在自建 200 条评测集上测的，题目是我自己按业务域分层造的，它证明“系统在已知分布上稳定”，不证明“在陌生用户的脏问题上稳定”。第二个短板是**没做过高并发和线上运维**——P95 12–17s 在评估场景可接受，在交互场景不可接受。

**追问**：那你凭什么让我信你能做线上？
**追问答**：我不主张我现在能做线上。我主张的是：我知道线上需要什么（鉴权、租户、RLS、限流、traceId、告警、灰度），并且已经把“已知边界”写进 `SECURITY.md` 而不是藏起来。能把边界说清的人，补上这些比“以为自己已经生产级”的人快。

## Part 12 · 简历其他内容（Java / Redis / 项目二）

> 这一部分不是 Text2SQL 的主战场，但简历上写了，面试官一定会抽查。

### Q12.1 Java 21 有什么新特性？项目里用了吗？ ★★

**答**：record（`AgentResponse`、`LlmCallRecord`、`SchemaContext` 大量使用）、pattern matching for instanceof（`usage.getNativeUsage() instanceof OpenAiApi.Usage`）、switch expression（状态映射）、text block（SQL/prompt）、虚拟线程（项目未用，因为评估是串行、LLM 调用是阻塞 IO，收益不明显）。不要背全部特性，讲你真正用过的。

### Q12.2 线程池参数怎么设？项目里哪里用了并发？ ★★

**答**：项目主链路是单请求同步，评估串行；并发点主要是 Hikari 连接池（只读 5、持久化 4）、BYOK 客户端 LRU 的同步 Map、LlmCallLog 的锁。线程池参数按“CPU 密集/IO 密集”讲：IO 密集可大于核数，但要有队列和拒绝策略；项目没做高并发，所以不吹线程池调优。

### Q12.3 AQS/CAS 怎么理解？ ★★

**答**：CAS 是“比较并交换”的原子指令，解决无锁更新的原子性；AQS 用 `volatile state` + CLH 队列管理同步状态，ReentrantLock/CountDownLatch 都基于它。项目里没有直接用 AQS，但 `ConcurrentHashMap`、`LinkedHashMap` 的同步包装、Hikari 内部都用并发容器/锁；不要硬编“我用了 AQS”。

### Q12.4 Spring Boot 自动装配原理？ ★★

**答**：`@SpringBootApplication` = `@EnableAutoConfiguration` + `@ComponentScan` + `@Configuration`；`@EnableAutoConfiguration` 通过 `AutoConfigurationImportSelector` 读 `META-INF/spring/...AutoConfiguration.imports`，按 `@ConditionalOnClass/@ConditionalOnMissingBean` 等条件装配。项目里刻意关掉 Spring AI 自动配置（`spring.ai.model.chat=none`），改成手工装配，避免没 Key 启动失败。

### Q12.5 MySQL 索引/最左前缀/覆盖索引？ ★★

**答**：InnoDB 聚簇索引按主键组织数据，二级索引叶子存主键；联合索引 `(a,b,c)` 遵循最左前缀，范围查询会截断后续列；覆盖索引是查询列都在索引里，避免回表。项目主库是 PostgreSQL，但简历写了 MySQL；被问时讲清“原理相通，项目实际用 PG”。

### Q12.6 事务隔离级别/MVCC？ ★★

**答**：MySQL 默认 RR，InnoDB 用 undo log + read view 实现 MVCC，快照读不加锁；当前读（`FOR UPDATE`）加 next-key lock 防幻读。PostgreSQL 默认 Read Committed，用 MVCC + SSI 可串行化。项目里业务查询是只读，不需要事务；持久化写入是单条 INSERT/UPDATE。

### Q12.7 Redis 缓存穿透/击穿/雪崩？ ★★

**答**：穿透=查不存在的数据，用布隆过滤器/空值缓存；击穿=热点 key 过期，用互斥锁/逻辑过期；雪崩=大量 key 同时过期，用随机 TTL/多级缓存/熔断。项目二用了 Redis BitMap/ZSet，Text2SQL 项目用的是进程内 LRU + PG 表，不是 Redis；别混。

### Q12.8 Redis + Lua + Redisson 一人一单怎么实现？ ★★★

**答**：Lua 脚本把“查库存 + 查是否已下单 + 扣库存 + 记录用户”放在一次原子执行里，避免 check-then-act 竞态；Redisson 分布式锁兜底跨 key 操作，注意锁续期（watchdog）和锁失效后的幂等。失败模式：Lua 里不能做耗时操作、集群模式下多 key 要同 slot、锁超时要大于业务执行时间。

### Q12.9 RocketMQ 削峰怎么保证不丢/不重复？ ★★★

**答**：生产端同步发送 + 重试 + 本地消息表；Broker 持久化 + 主从；消费端手动 ACK + 幂等键（订单号）去重。削峰是“把同步下单变成异步处理”，要接受最终一致；不能只说“用了 RocketMQ”，要讲清重复消费和消息丢失的兜底。

### Q12.10 项目二 1000 并发/80%/57% 怎么测的？ ★★★

**答**：这是简历里最容易被追问穿的一条。标准答法要给出：机器配置、JMeter 脚本、基线 RT/TPS、优化前后的对比、瓶颈在哪。如果没有压测报告，就把数字改成“完成 1000 并发压测，定位并优化了 X”，不要报具体百分比；面试官要的是证据链，不是数字。

### Q12.11 HashMap 原理？为什么阈值是 8 转红黑树？ ★★

**答**：数组 + 链表 + 红黑树；`hash = h ^ (h >>> 16)` 让高位参与运算；容量 2 的幂，用 `(n-1) & hash` 代替取模；负载因子 0.75 是“空间 vs 冲突”的经验平衡点；链表长度到 8 且容量 ≥ 64 转红黑树（`O(n)` → `O(log n)`），退化到 6 转回链表（留 2 的缓冲避免反复转换）。

**追问**：为什么容量必须是 2 的幂？
**追问答**：为了让 `(n-1) & hash` 等价于取模，且 `n-1` 的低位全 1，散列更均匀。扩容时元素要么留在原位、要么移动 `oldCap`，不需要重新计算 hash——这是 JDK 8 相对 JDK 7 头插改尾插之外的另一个优化。

### Q12.12 JVM 内存结构与 GC，项目里调过吗？ ★★

**答**：堆（新生代 Eden + 2×Survivor、老年代）、方法区/元空间、虚拟机栈、本地方法栈、程序计数器；对象优先在 Eden 分配，熬过 `MaxTenuringThreshold` 进老年代。GC 分 Minor/Full，收集器有 Serial/Parallel/CMS/G1/ZGC。**项目里没调过 GC**——单实例、低 QPS、堆压力小，`-Xmx` 用的是默认值。硬讲调优参数是给自己挖坑。

**追问**：那你怎么排查 OOM？
**追问答**：`-XX:+HeapDumpOnOutOfMemoryError` 拿 dump，MAT 看 dominator tree 找最大持有链。这个项目最可能 OOM 的点是“全量结果集入内存”——所以我加了 200 行上限和 `maxRows+1` 探测，从源头掐掉。

### Q12.13 synchronized 和 ReentrantLock 的区别？ ★★

**答**：`synchronized` 是 JVM 层面（monitor 指令），自动释放、非公平、不可中断、不支持超时；`ReentrantLock` 是 AQS 实现，可公平/非公平、可 `tryLock(timeout)`、可中断、可多条件队列，但必须 `finally` 释放。JDK 6 之后 `synchronized` 有偏向锁/轻量级锁优化，简单场景性能不差。

**追问**：项目里用了吗？
**追问答**：用了 `synchronized`，在 `LlmCallLog` 写 JSONL 那一段——文件追加不是线程安全的，且这里是低频写（每次 LLM 调用一次），不值得上锁对象。`ReentrantLock` 没用，因为没有“需要超时或中断”的场景。

### Q12.14 Spring 事务在什么情况下会失效？ ★★★

**答**：五类：1）**自调用**——同类内部 `this.method()` 不走代理；2）**方法非 public**（默认代理模式下）；3）**异常被吞**——`catch` 了没抛，或抛的是受检异常而 `rollbackFor` 没配；4）**类没被 Spring 管理**——自己 `new` 出来的对象；5）**多数据源/多线程**——事务绑定在 ThreadLocal 上，子线程拿不到。

**追问**：你这个项目有事务吗？
**追问答**：业务查询是只读，不需要事务；持久化是单条 INSERT/UPDATE，也不需要。所以我没有“用了事务”可以吹——但我知道上面五类失效，因为这是 Java 后端必考项，不是项目专属。

### Q12.15 项目二的架构讲一下？ ★★

**答**：按“接入层 → 业务层 → 存储层”讲，别背名词：Nginx 负载 → Spring Boot 应用 → MySQL 存订单/商品、Redis 存库存和一人一单标记、RocketMQ 做下单削峰。关键链路是“秒杀下单”：先 Redis 预扣库存 + Lua 原子判重，成功才发 MQ，消费端落库并做幂等。

**追问**：为什么库存放 Redis 不放 MySQL？
**追问答**：因为秒杀场景下 MySQL 行锁会把并发打回串行，QPS 上不去。Redis 单线程 + Lua 保证原子性，能扛住瞬时流量；MySQL 只做最终的持久化和对账。代价是要处理“Redis 扣了但落库失败”的不一致——用 MQ 重试 + 定时对账兜底。

### Q12.16 项目二最难的点是什么？ ★★★

**答**：**一致性**，不是性能。秒杀链路里有三个状态：Redis 库存、MQ 消息、MySQL 订单，任意一步失败都会不一致。我的处理是：Redis 扣减成功才发消息（本地消息表保证不丢）、消费端用订单号做幂等键（保证不重）、定时任务扫“Redis 已扣但 MySQL 无单”做补偿。

**追问**：那 1000 并发/80%/57% 是怎么来的？
**追问答**：这里我要说实话——如果没有压测报告，我不该报具体百分比。正确说法是“做过 1000 并发压测，定位到瓶颈在 X，优化后 QPS 提升明显”。数字要有 JMeter 脚本、机器配置、前后对比支撑，否则第一个追问就崩。

### Q12.17 怎么防超卖？ ★★★

**答**：三层：1）**Redis 预扣**——Lua 脚本里 `if stock > 0 then decr`，判断和扣减原子；2）**数据库兜底**——`update stock set num = num - 1 where id = ? and num > 0`，靠 `num > 0` 条件 + 行锁保证不会扣成负数，影响行数为 0 就回滚 Redis；3）**幂等**——一人一单用 `setnx` 或 ZSet 去重，防同一用户重复下单。

**追问**：Lua 里为什么不能做耗时操作？
**追问答**：Redis 是单线程执行命令的，Lua 脚本执行期间会阻塞其他所有请求。脚本里做 `keys *` 或者循环几万次，直接把整个 Redis 拖死。所以我的脚本只有几条 O(1) 命令。

### Q12.18 接口幂等怎么做？ ★★

**答**：常见四种：1）**唯一索引**——最可靠，靠数据库兜底；2）**token 机制**——先取 token，提交时删 token，删成功才处理；3）**状态机**——只允许 `待支付 → 已支付`，重复请求状态不匹配就拒；4）**分布式锁 + 业务号**——`setnx(orderNo)` 短期锁。秒杀场景我用的是 1 + 3 组合，锁只用来削峰不去重。

## Part 13 · 设计题与开放追问

> 这一部分没有标准答案，考的是“你能不能把已有经验迁移到新约束上”。答法统一是：先问清约束 → 说方案 → 说代价 → 说怎么验证。

### Q13.1 如果表从 37 张变成 1000 张，哪里先崩？ ★★★

**答**：先崩的不是模型，是**检索**。现在 Top-8 靠领域词典 + 关系扩展，37 张表时词典能覆盖大部分业务词；1000 张表时词典维护不动、同义词爆炸、Top-8 里塞不下真正需要的表。方案是分两级：先用 embedding/BM25 把 1000 张粗筛到 50 张（召回优先），再用现在的词典 + 连通性修复做精排到 8 张（精度优先）。代价是多一次召回、多一层不可解释性。

**追问**：那你怎么验证 1000 张表下没退化？
**追问答**：造“干扰表”——保留 200 条 gold，另外灌 800 张语义相近但不该被选中的表，看表全召回率和执行准确率的差值。差值小说明抗干扰，差值大说明粗筛把对的表筛掉了。

### Q13.2 要支持 MySQL，改哪里？ ★★★

**答**：四处：1）**方言层**——标识符引用（`"col"` → `` `col` ``）、`LIMIT/OFFSET`、日期函数（`date_trunc` → `DATE_FORMAT`）、`EXPLAIN` 格式（PG 是 JSON，MySQL 是表格）；2）**元数据层**——`information_schema` 查询要按方言分支，主键读 `KEY_COLUMN_USAGE`；3）**AST 层**——JSqlParser 本身方言无关，但函数黑名单要按方言扩；4）**schema 文本**——DDL 渲染要换类型名。所以我会抽一个 `SqlDialect` 接口，而不是到处 `if (isPg)`。

### Q13.3 用户说“这个数不对”，你怎么排查？ ★★★

**答**：按链路倒着查，四步：1）**看 SQL**——`AgentResponse` 里带 `generatedSql` 和 `retrievedTables`，先确认它查的是不是该查的表；2）**看口径**——`metrics.yml` 里这个指标的定义（分子分母、去重口径、时间窗），大概率是口径理解错而不是 SQL 语法错；3）**跑 gold**——同一问题跑人工 gold SQL，两边结果比对，差异就是归因点；4）**看数据**——如果是扩展表，可能是合成数据本身的问题。这四步能覆盖我 16 条失败里的全部类型。

### Q13.4 怎么让用户“信任”这个 SQL？ ★★★

**答**：三件事：1）**把 SQL 给用户看**——不是藏在后端，而是展示出来，让懂业务的人能核对；2）**把口径写出来**——“订单量 = 去重 order_id 计数，不含 canceled”，比 SQL 本身更能建立信任；3）**把不确定性标出来**——检索到的表、是否复用 schema、是否走了改写，都回传。可解释性不是“解释模型怎么想的”，是“让用户能自己验证”。

### Q13.5 准确率从 85 做到 95，你的路线？ ★★★

**答**：不看总数，看失败结构。现在 16 条失败里输出形状 7 条、深层 Join 4–6 条、gold 缺陷 3 条。所以路线是：1）**输出形状契约化**（7 条里能救 5 条左右，+2.5pt）；2）**T5 桥接表专项**（补中间表识别，+1.5pt）；3）**gold 修正**（3 条，但会破坏历史可比性，要另开一套 eval v2）。剩下的长尾（歧义问题、数据本身脏）不建议硬刚，边际收益低。**我不会承诺 95**，因为 200 条样本的置信区间本身就有 ±2.5pt。

### Q13.6 怎么防 prompt 注入？ ★★

**答**：分三层：1）**输入侧**——用户问题只作为“数据”拼进 user message，不拼进 system；schema 文本做白名单渲染，不让库里的注释/表名注入指令；2）**输出侧**——AST 校验是硬闸，注入成功让模型写 `DROP TABLE` 也会被拦（H2/H4 就是这么补的）；3）**权限侧**——只读账号兜底，即使前两层都破，也写不了库。**核心观点**：prompt 注入在 Text2SQL 里的危害被 AST + 只读账号这两层削掉了大半，真正危险的是“合法越权读”（读别的租户的数据），那个要靠 RLS，我现在没有。

### Q13.7 怎么评估“多轮”的效果？ ★★★

**答**：单轮 eval 测不出来，得单独造集：每条样本是“首轮问题 + N 轮追问 + 最终期望 SQL”，评分看“最终轮执行准确率”和“追问轮次”。我现在的 200 条是单轮的，多轮只有手工验证——这是缺口，我在“接下来怎么迭代”里没把它排进前三，因为多轮不是当前主战场。

### Q13.8 LLM 服务挂了，怎么降级？ ★★

**答**：四层：1）**重试**——只对超时/5xx 重试，指数退避，最多 2 次；2）**改写降级**——多轮改写 LLM 失败就退规则改写（已实现）；3）**生成降级**——生成失败直接返回明确错误，**不返回半成品 SQL**，因为错的 SQL 比没有 SQL 更危险；4）**缓存兜底**——命中缓存的问题不依赖 LLM。注意“降级到模板 SQL”这种方案我不做，模板在 37 张表上覆盖不了，会产出看似成功实则错误的答案。

### Q13.9 如果要做“生成图表”，怎么加？ ★★★

**答**：不加在生成侧，加在**结果侧**。理由：让模型同时输出 SQL 和图表配置，会显著拉低 SQL 准确率（多任务互相干扰）。更好的做法是 SQL 执行完之后，拿“结果集的列类型 + 指标元数据”做规则推断：单行单列 → 指标卡；一维 + 一维数值 → 柱/折线；两维 + 数值 → 分组柱或热力。模型只在规则推不出来时兜底。这样图表错了不影响 SQL 对。

### Q13.10 现场白板：画一下主链路。 ★★

**答**：`问题 → QuestionRewriter（是否追问）→ SchemaRetriever（词典匹配 + 关系扩展 + 连通性修复，Top-8）→ JoinPlanner（Dijkstra 最短路 + Prim 生长）→ ColumnPruner（7 条保全规则）→ PromptBuilder（schema + 指标 + few-shot）→ LLM → SqlValidator（AST 白名单 + 函数黑名单）→ QueryExecutor（只读账号 + 10s + 200 行）→ ResultNormalizer → 返回`。旁路两条：`SqlCache`（L1 LRU + L2 PG）在检索前查、`LlmCallRecord` 在每次 LLM 调用后记账。**画的时候一定要标出“哪一步失败会导致什么错误类型”**，这是加分项。
