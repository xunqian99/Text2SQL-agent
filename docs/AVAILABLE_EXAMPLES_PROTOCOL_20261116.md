# 参考示例表依赖可用性：阶段3开发筛选协议

## 单一变量与范围

前序[离线诊断](LATENCY_FEASIBILITY_20261116.md)发现dev100中59题选中的few-shot示例引用了当前Schema之外的表。本次只比较原 `overlap-v1` 选择策略和候选 `available-tables-v1`，后者先要求示例实际SQL表依赖全部可用，再沿用原排序。

配置入口 `agent.fewshot.require-available-tables` 默认false；仅候选开启。`scripts/run_eval.ps1 -RequireAvailableExampleTables` 显式传true，不传时显式false。两种SchemaProvider均传递该配置。生产默认、系统Prompt、Schema检索/列剪枝/Join、指标定义、题目、Gold、示例文本和评分规则均不在本实验中修改。叶子表裁剪不接入本实验。

## 输入、次数和冻结

原始题库200道，dev100/eval100不变；另100道AI候选题不参与，不新增题目。先运行原200题Gold自检，必须200/200、模型调用0。随后同100道dev题两种配置各一次，合计**100道不同问题、200次真实请求**，不是新题200道，更不是600道。

顺序：Gold → overlap → available-tables；各独立JVM。先提交实现、运行器、审计器和本协议，运行前后检查提交和受保护文件SHA-256；私有配置只记录哈希，不记录密钥。禁止覆盖已有输出目录。默认先跑可能影响供应商缓存和时间漂移，本轮只有开发筛选效力。

## 机制、身份、数学与边界

`ExampleLoader`沿用已有JSqlParser解析示例SQL真实表名；示例内容仍来自原 `fewshot/examples.yml`。设示例依赖集合为E、当前上下文可用表集合为C，候选准入条件是 **E非空且E⊆C**，比较表名忽略大小写。匹配当前问题的同题示例仍排除。

准入后沿用原比较器：共同表数 `|E∩C|` 降序 → Jaccard `|E∩C|/|E∪C|` 降序 → 示例ID字母序。没有重设权重，也不靠排序把缺表风险“降权”；不合格示例根本不能进入Top-K。上限2，符合条件只有1条就给1条，没有就给0条，不补不合格示例，不自动扩大Schema。

依赖解析失败、无表表达式SELECT 1和空依赖均保守排除；CTE别名不当真实表，其内部依赖和嵌套子查询依赖仍必须可用。空上下文不选有表依赖的示例。配置只约束**表存在**，不保证示例所用列在剪枝后都出现，也不保证示例与当前业务问题口径一致。跨表示例可能提供有用结构，过滤可能损失泛化帮助，必须用真实对照检验，不能仅凭59→0宣布优化成功。

`ExampleSelector.policyVersion()`标识选择策略；缓存键带启用状态、示例上限和策略版本，避免切换后复用另一策略的SQL。默认策略缓存键也新增版本后缀，会产生一次保守失配；这不是生产模型输入变化。评测配置新增 `fewshotRequireAvailableTables/fewshotSelectionPolicy`；JSONL新增对应configured字段。配置标记不证明实际选中了哪些示例，实际消息身份另由 `promptSha256` 及事前配对记录验证。

配对探针保留每条示例的ID、questionSha256、sqlSha256、解析表集合和missingTables；不把不同出身压成一个分数。两种实际Provider输出剔除examples后必须逐字节一致，系统消息相同。100组事前捕获再重复300次同进程比较，必须无漂移；全量Schema路径另检查2次。原策略的100条消息还必须匹配前序当前口径下的冻结记录，保证新增开关默认关闭时没有顺带改Prompt。

## 固定条件

deepseek-flash、temperature0、maxTokens8192、`reasoning_effort=provider-default`（省略供应商参数）、显式四步指令保留。Top8、列剪枝、Join提示/规划、语义指标、示例上限2固定。澄清、生产纠错和结果检查开启；请求总预算15秒、最多2次模型调用、重试剩余时间门槛2秒、SDK最多1次；缓存、升级路由、工具循环、多轮会话和评测器外层纠错关闭。

指标定义使用已提交的会员订单占比修复，原先历史实验不能冒充同期默认组。本轮两组指标资源指纹必须相同。配置价格沿用每千Token：输入未命中0.001元、命中0.00002元、输出0.004元，仅为估价，非供应商账单。

## 预先固定的筛选门槛

保持完整100题分母，澄清、超时、拒绝和失败都不剔除。记录每组P50/平均/P95/最大墙钟、正确数、SQL成功数、难度/表数分层、逐题得失、调用/重试/恢复/退化、截断、Token、缓存命中/未命中及未知用量。P95取第95顺位墙钟，含重试。

候选进入正式三轮确认必须同时满足：

1. 正确数相对同期默认下降≤2/100。
2. P95相对同期默认下降≥10%；绝对P95是否<8秒另外列出。
3. 新增截断请求≤1/100。
4. 完整100题配置估价≤0.30元，未知usage必须0；未知不是免费，完整费用门槛标为未确认。
5. 请求最多2次模型调用、墙钟≤16秒工程界限，取消提交拒绝0。
6. 题意/Gold SQL/Gold结果、非实验配置、实际首答与对应事前消息配对及逐调用账目审计全部通过。

任一失败不推广；不补跑直到挑出一次成功、不改题或Gold挽救候选、不事后放宽门槛。正式阶段3仍需按另行冻结的原eval三轮协议确认平均P95<8秒、准确率相对冻结基线退步≤2pp及完整成本等原门槛。本轮不能宣布阶段3或整体项目通过。

## 可验收路径与技术答辩

验收顺序：Java全量测试与实际消息配对 → 两种命令Preview → 离线审计测试 → 提交冻结 → 运行专用脚本 → 原始报告/JSONL/指纹审计 → 归档结果与最终决策。

```powershell
& scripts/run_eval.ps1 -Preview
& scripts/run_eval.ps1 -Preview -RequireAvailableExampleTables
& scripts/run_available_examples_screen.ps1 -OutputDir reports/available-examples-screen-20261116
python scripts/summarize_available_examples.py reports/available-examples-screen-20261116
```

例如当前Schema只有orders/customers，原策略可能优先选“orders JOIN customers JOIN members”的示例，因为共同表数2胜过只用orders的1；候选先因members不可用排除它，再选可用示例。示例进入PromptTemplate用户消息，模型生成SQL后仍走原只读护栏和数据库执行，结果与冻结Gold比较，不直接拼接或执行示例SQL。

为什么不用“缺表示例降权”？只要为了凑满2条继续补齐，风险仍可能重新进入；准入过滤使不变量清楚。为什么不把缺表补进Schema？这会同时改变检索、Join规划与Token，不是当前单因素实验，也可能扩大噪声。面试回答必须同时承认过滤可能移除有帮助的跨表示例，实验结果比直觉更重要。

无需用户新增服务或凭据；沿用当前本地只读库和已配置Key，运行脚本不打印密钥。用户需能说明依赖从SQL解析而来、过滤发生在Top-K之前、空候选为什么不凑数，以及每次实际调用的Token和费用。

冻结前验证：Java全量526/526，失败/错误/跳过均0；Python离线审计96/96，其中新增12项使用明确标注的临时合成协议夹具，不是真实模型结果。100组实际消息预检查、300次重复比较与两种Provider检查通过，原策略100/100与前序消息一致；缺表示例题数59→0，4题候选示例为空。两种Preview仅该开关不同。真实模型准确率、P95和费用仍待本协议执行，不能由这些离线数字推导。
