# DeepSeek空闲时段评测约束

2026-11-17用户最新要求：按阶段继续；阶段3 P95暂缓；不得在DeepSeek官方高峰收费时段使用用户API跑评测。旧的“14点整段停工、18点恢复”改为费用边界：高峰仍可进行本地代码、测试与文档，真实模型验收只在空闲时段进行。

## 官方规则与保守边界

已于2026-11-17核对[官方中文价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)和[英文价格页](https://api-docs.deepseek.com/quick_start/pricing/)。北京时间周一到周五（中国法定节假日除外）09:00–12:00、14:00–18:00为高峰；其余时段、周末和法定节假日全天为空闲。空闲价为高峰的一半。不是历史的每日00:30–08:30优惠规则。

本项目暂不维护未经核实的节假日白名单：周中节假日也按普通工作日保守拒绝，因此可能少用优惠时间，不会据此放行高峰。时区固定Asia/Shanghai，与电脑显示时区无关。官方规则可能变化，后续付费评测前仍需重新核对页面。

默认在距高峰开始两分钟内拒绝新请求，即工作日08:58–12:00、13:58–18:00暂停准入。单次网络超时更长时，余量取`max(120秒, timeoutSeconds+10秒)`；与高峰边界恰好相接也拒绝。该余量是本地准入保护，不证明供应商的完成时间或实际账单时间一定处于空闲区间。在途请求的取消也不等于供应商未计费。

## 机制与数据流

以星期二15:00输入“2018年订单数”为例：编排完成检索后进入`LlmSqlGenerator.invoke`，识别真实OpenAiChatModel客户端和DeepSeek目标，使用注入的Clock获取绝对时间并转换到北京时间。当前处于高峰，立即抛出`OFF_PEAK_REQUIRED`，不预留金额、不增加模型调用记录。编排不因这个错误触发自纠错，响应保留明确的未发送提示；当前响应状态沿用GENERATION_FAILED，不新增页面流程。

18:00后同一个问题通过时间判定，先预留金额，再登记调用，进入Spring AI请求工厂；`BudgetHttpRequestFactory`在创建网络请求和真正execute前各检查一次。首次生成、纠错、改写、工具消息和BYOK都经过这条共同链路，SDK仍限制为一次尝试。即使请求在13:55创建、14:00才发送，第二次检查也会拒绝，底层execute不会被调用。

身份依据不混用：`appliesTo`用解析后的URI主机匹配deepseek.com及其子域；远程代理还可通过配置的deepseek模型名识别。localhost、127.0.0.1、::1的模拟模型可继续离线回归；相似字符串主机不按官方域名识别。未知名称的第三方代理无法凭域名证明是DeepSeek，本轮不会改用此类代理绕过限制。纯Mockito模型替身不具备真实传输，生成入口检查只对真实OpenAiChatModel生效；请求工厂仍独立保护官方目标。

判定是区间相交，无评分、权重或Top-K：将`[当前时间, 当前时间+停止余量]`与当天/跨日工作日高峰比较，交集非空即拒绝。`Decision`保留policy、checkedAt、beijingTime、allowed、reason、nextAllowedAt、guardSeconds；PEAK_HOURS与PEAK_BOUNDARY_RESERVE区分当前高峰和预防跨界。13:58拒绝后的最早接续时间为18:00，而非14:00。

`EvalRunner`在真实批评测起跑前检查，dry-run不受影响；`DemoHttpAcceptanceProbe`在真实HTTP验收起跑及每条问数前检查。新冻结协议记录时区、规则版本、来源和120秒余量，每条调用方Decision另存window-checks。应用内部的多次模型请求由共同入口和传输门禁再保护，不能仅依赖调用方一次检查。若中途跨界，保留部分报告，不改分母、不覆盖重放，不生成完整20条通过结论。

极端边界：如果费用预留后长时间停顿，最终传输检查仍会阻断；直接的未发送拒绝会撤销金额预留。若预算已登记调用或框架包装了异常，现有用量证据可能保守保留为未知，不得将其当真实供应商收费，也不得据此宣称完整成本。没有建立供应商侧的强制时段封锁，不能阻止用户另用其他客户端或旧进程调用API。接续验收必须使用本轮已编译的新进程。

## 设计取舍与面试答辩

没有只用定时任务起跑：单轮可跨过高峰边界，纠错和改写也会额外花钱。没有自动排队睡到优惠时段：这会占用请求/会话资源，且可能在恢复时偷偷重放；本地明确拒绝，由已冻结协议接续。没有引入节假日服务或新依赖，采用可解释的保守日历，代价是部分法定节假日无法使用。

问：为什么定时18:00启动还要每次检查？答：定时器只触发任务；实际发送可能延迟，且一条问数可有多次模型调用。最终网络边界必须再检查，不能把调度时间当作计费时间。

问：两分钟余量能保证账单都按空闲价吗？答：不能。它约束本地准入并降低跨界风险，供应商处理完成和取消后的计费不受本地控制。报告仍逐次记Token与未知用量，不承诺供应商账单硬上限。

用户无需重新提供Key。需要掌握的是：时间检查在模型发送前、费用预留在其后；本轮无付费调用；OFF_PEAK_REQUIRED归因于费用策略，不是表/列/Join/业务口径错误。
